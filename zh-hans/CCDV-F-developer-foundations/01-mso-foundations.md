# MSO 基础
## 模型选择与优化基本功

> **免责声明：** 为精读而写的原创备考笔记。依据**公开** Anthropic 文档中关于选模型、effort、上下文窗口、定价概念，以及缓存／批量成本杠杆的内容——模型 ID 与价格会变；记住*决策准则*，考前再核对当前模型卡。

**主要对应：** 模型选择与优化（**16.8%**）。
**也喂给：** 应用与集成（当题干是「为成本／延迟挑 API 路径」时）。

**怎么读：** 先学会三轴取舍（能力 × 延迟 × 成本），再练习在一个硬限制之下逼出唯一最佳答案。大多数 MSO 题是限制谜题，不是「哪个模型最聪明」。

---

## 1. 概览

MSO（模型选择与优化）是把工作**路由到正确智能预算**的技能。在 Claude 上，这份预算通过下列方式表达：

1. **模型家族／层级**（前沿对中阶对快速／便宜）。
2. **Effort／思考设置**（*同一个*模型要多认真）。
3. **上下文与输出上限**（窗口大小、最大输出 token）。
4. **服务路径**（交互式 Messages 对流式对 Message Batches 对已缓存前缀）。
5. **运营旋钮**（钉定版本、别名对完整 ID、区域／云端主机）。

公开文档把模型选择框成平衡**能力、速度与成本**。近期的 Opus／Sonnet 等级模型多了一个 **effort** 参数，能在*同一个*模型里用智能换延迟／成本——常常是比跳层级更好的第一个杠杆。

**考试姿态：** 优先选能通过评测质量闸门的**最小且足够**的模型／effort。当题干强调成本或 p95 延迟时，过度购买智能是常见的错误答案。

## 2. 关键地图（闪卡）

| 概念 | 一句意思 | 考试触发词 |
| --- | --- | --- |
| 模型层级 | 能力类别（前沿／均衡／快速） | 「complex refactor」、「classify at scale」、「chat UI」 |
| Effort | 单一模型内部的测试时运算 | 「same model, better answers」、「lower latency same model」 |
| 上下文窗口 | 提示词＋历史能塞进多少 | 「long repo」、「1M context」、「truncate」 |
| 提示词缓存 | 重用前缀，让重复调用更便宜／更快 | 「stable system+tools」、「multi-turn agent」 |
| Message Batches | 异步大批量，有折扣 | 「overnight eval」、「latency tolerant」 |
| 流式 | 逐 token 的用户体验／提前取消 | 「TTR」、「user-facing chat」 |
| 钉定 | 冻结模型字符串以求可重现 | 「prod regression」、「version drift」 |
| 别名 | 指向「最新 sonnet／opus／…」的会移动指针 | 「always newest」、「dev sandbox」 |

## 3. 深入笔记

### 3.1 三轴决策框架

每一个正式环境选择都坐在一个三角形上：

```text
 能力
 /\
 / \
 / \
 / ? \
 /________\
 成本 延迟
```

- 当失败很贵时，往**能力**移动（安全审查、跑数小时的 agent、困难的写程序）。
- 当人类在等首个 token 或完整答案时，往**延迟**移动（客服聊天、编辑器行内建议）。
- 当量主导时，往**成本**移动（分类、抽取、夜间批量）。

**考试经验法则：** 找出题干硬限制的是哪一个顶角，然后删去忽略它的选项。

### 3.2 模型家族心智模型（即使名称会变仍然稳定）

公开选模型指引（2026）大致依工作负载形态组织：

| 工作负载形态 | 优先（概念上） | 为什么 |
| --- | --- | --- |
| 数小时 agent、深度推理、大型重构、视觉很重的企业工作 | 前沿 Opus 等级（例如公开文档里的 Claude Opus 5 家族） | 最高自主性与推理空间 |
| 每日写程序、数据分析、内容、扎实的 agentic 工具使用 | Sonnet 等级 | 大多数应用最好的默认平衡 |
| 高 QPS 例行分类、简单转换、便宜循环 | Haiku 等级 | 速度与单位经济 |
| 最长／最难的前沿 agent 执行（有提供时） | Fable 等级（坐在 Opus 之上的模型家族；Claude Code 的 `best` 别名会交互式解析到顶层） | 明确给最难的长时间任务 |

**不要背营销口号。** 要背**适配**：

- **工具很重的写程序 agent** → 中阶到前沿＋适当 effort。
- **对黄金 schema 做结构化抽取** → 常常是中阶＋严格 schema／工具；只有评测失败才升级。
- **面对用户的低延迟助手** → 更快层级，或同一层级配更低 effort；加流式。

### 3.3 Effort 作为模型内部旋钮

公开文档把近期 Opus／Sonnet 模型上的 **effort** 描述成用智能换延迟与成本。默认常常是 **high**；更高设置（例如有提供时的 `xhigh`、`max`）帮助吃重的 agentic／写程序工作；更低设置帮助例行任务。

**运营模式：**

1. 钉定一个模型。
2. 从该模型**文档记载的默认**开始。
3. 只有当评测显示系统性推理不足时，才提高 effort。
4. 当 p95 延迟／成本预算破掉、而质量仍然通过时，降低 effort。

**考试陷阱：** 题干说「为了缓存稳定／合约而保持同一个模型 ID」时仍去换模型——答案通常是**改 effort**，不是改模型。

**缓存备注：** 改变思考设置会让**消息层级**的缓存断点失效；工具／系统前缀那一段仍然可缓存。预热与正式流量之间对齐 effort／思考仍是安全运营规则——对不齐的预热，会让你的消息层级条目没被读到。

### 3.4 上下文窗口与输出上限

把上下文当**预算**，不要当垃圾场：

| 压力 | 症状 | MSO 响应 |
| --- | --- | --- |
| 历史太长 | 截断、指示遗失 | 压缩摘要；把持久规则移出聊天 |
| 工具 schema 巨大 | 浪费前缀 token | 工具搜索／延迟加载；更少工具 |
| 每回合都送大型文档 | 成本爆炸 | 缓存稳定文档；检索切片 |
| 需要长输出 | JSON 做到一半被截断 | 提高 `max_tokens`；结构化流式；任务切块 |

公开材料强调大窗口（包括部分模型上的 **1M** 等级窗口）以及前沿模型上的高最大输出。考试在乎的是：你**知道何时**该请求大窗口别名（长会话／大型存储库），何时检索加缓存比把所有东西塞进去更便宜。

### 3.5 仍然算「MSO」的成本杠杆

MSO 不只是「挑 Opus 还是 Sonnet」。有成本意识的答案常常组合：

1. **更小模型**（若质量撑得住）。
2. **更低 effort**（若质量撑得住）。
3. **提示词缓存**（稳定前缀：系统、工具、参考文档）。
4. **Message Batches**（延迟可以等时；公开文档：异步大批量、相对同步有折扣；缓存可叠加，但命中是尽力而为）。
5. **更短输出**（要求简洁；用 schema 约束）。
6. **避免改写已缓存前缀**（打乱工具顺序、系统提示词里的时间戳、会话中途换模型）。

**批量对即时决策树：**

```text
是否有用户正在等这个回应（数秒内）？
 是 → 同步 Messages（若用户体验需要提早拿到 token，就加串流）
 否 → 是否有大量独立请求、且 SLA 可容忍数小时？
 是 → Message Batches（＋共用的 cache_control，若有提供则偏好较长 TTL）
 否 → 同步加缓存；考虑队列＋工作者
```

值得记住的公开批量限制：没有流式结果路径、没有仅限同步的速度模式、不能在批量里面用 `max_tokens: 0` 预热、有状态的对话串参数通常不适用。

### 3.6 延迟杠杆

| 杠杆 | 效果 | 副作用 |
| --- | --- | --- |
| 更快的模型层级 | 更低 TTFT／总时间 | 可能掉质量 |
| 更低 effort | 更快 | 可能掉质量 |
| 流式 | 更好的*感知*延迟 | 总运算大致不变 |
| 提示词缓存命中 | 更快预填 | 需要稳定前缀 |
| 更小提示词 | 更快 | 可能需要更好的检索 |
| 并行工具调用（有支持时） | 墙钟时间胜利 | 更多并行复杂度 |

**考试细微处：** 流式修的是**用户体验的等待**，不是单位成本。如果题干讲的是**账单**，单靠流式很少是答案。

### 3.7 质量杠杆（表现不足时）

除非题干禁止，否则按这个顺序升级：

1. 修好**提示词／上下文**（缺的限制、坏的例子、吵杂的工具）。
2. 加上**工具／模型上下文协议（MCP）**，让模型能抓事实依据。
3. 提高 **effort**。
4. 升级**模型层级**。
5. 改**架构**（多步骤 agent、验证模型、人工闸门）。

直接跳到最大模型是常见的干扰选项。

### 3.8 版本钉定对上别名

| 作法 | 何时用 | 风险 |
| --- | --- | --- |
| 完整带日期／明确模型 ID | 正式环境、评测、合规 | 你必须规划升级 |
| 别名（`sonnet`、`opus`、`haiku`、`best`、…） | 开发、「永远最新」的沙箱 | 安静的行为漂移 |
| Claude Code 别名（`opusplan`、`sonnet[1m]` 等） | 会话的工作流程偏好 | 为了 CI 可重现性仍应钉定 |

**正式环境检查清单：** 在设置里钉定模型字符串；记进评测报告；舰队升级前先做金丝雀；若依赖提示词缓存，绝不要在对话中途改模型。

### 3.9 路由模式（架构碰上 MSO）

**A. 静态路由：** 产品界面用一个模型。操作简单，优化有限。

**B. 分层路由：** 分类器或规则把容易的流量送到 Haiku 等级，困难的送到 Sonnet／Opus 等级。

**C. 级联／升级：** 先试便宜路径；信心低或 schema 验证失败时，在昂贵路径上重试。

**D. 双模型验证：** 中阶上的生成器；同一层或更高层的评论／验证模型，用于高风险输出。

题干提到「90% 琐碎工单、10% 新奇事故」时，几乎总是要**分层或级联**，不是「全部走前沿」。

### 3.10 云端托管仍然贴着 MSO

公开 Academy 主题包括 Bedrock 与 Vertex／Agent Platform。会出现在情境题里的选择差异：

- **模型 ID 格式**依主机而异（Anthropic API 名称对 Bedrock 推理配置文件 ARN 对 Vertex 版本名称）。
- **功能落差／对等** — 确认该主机上的工具、缓存、批量与 beta 可用性。
- **数据驻留／IAM** — 即使另一个区域有更新的 SKU，也可能被迫待在某个区域。

若题干的硬限制是**数据驻留**，正确的模型选择是「已核准的区域 SKU」，不是全球最新的 ID。

### 3.11 迷你情境演练

**情境 A — 客服聊天机器人，p95 < 2s，中等质量。**
优先快速／中阶层级、较低到默认 effort、流式、缓存系统＋工具前缀。避免前沿＋max effort。

**情境 B — 过夜评测 5 万则提示词。**
Message Batches；相同的 `cache_control` 区块；若有提供则用较长缓存 TTL；除非评测需要前沿，否则用中阶。

**情境 C — 自主、跑数小时的写程序 agent。**
前沿或强 Sonnet／Opus 等级配提高的 effort；视需要用大上下文；缓存工具；执行中途不要抖动换模型。

**情境 D — 「在系统提示词加上时间戳」之后成本暴增。**
缓存破坏。修好前缀稳定；不要先跳到更便宜的模型。

### 3.12 证明 MSO 决策的指标

一起追踪，否则你会优化错的轴：

| 指标 | 在问 |
| --- | --- |
| 任务成功／评分量规分数 | 质量有撑住吗？ |
| 每次成功任务成本 | 不是每次原始调用的成本 |
| p50／p95 延迟 | 人类在等的路径 |
| 缓存命中率 | 前缀工程健康度 |
| 升级率 | 路由有校准吗？ |
| 安全事故率 | 更便宜的路径有跳过过滤器吗？ |

## 4. 决策树与表格

### 4.1 主选择树

```text
起点：若我们选错，最先坏掉的是什幺？
│
├─ 安全／法务／高爆炸半径的失败
│ → 更高能力＋强护栏；需要时加上人工关卡
│
├─ 有人在等（互动式）
│ → 偏好更快层级或更低 effort；串流；缓存前缀
│ → 只有在质量评测失败时才升级模型
│
├─ 大批量／离线
│ → 批量＋共用缓存；用评测样本把模型调到刚好
│
└─ 长时间 agentic 写程序
 → 有能力的模型＋足够 effort；稳定工具；钉定版本
```

### 4.2 Effort 对上换模型

| 观察 | 第一个动作 | 避免 |
| --- | --- | --- |
| 同一个模型，多步骤计划很弱 | 提高 effort | 只是随机把提示词拉长 |
| 同一对话串做模型 A／B 测试后缓存未命中 | 不要在对话串中途换 | 「第 12 回合就试 Opus」 |
| 简单任务太贵 | 降低 effort 或更小模型 | 什么都留在前沿 |
| 困难的 5% 出现质量断崖 | 把困难的 5% 往上路由 | 升级 100% 流量 |

### 4.3 成本堆栈（小心组合）

| 堆栈元素 | 典型收益 | 需要 |
| --- | --- | --- |
| 更小模型 | 大 | 评测对等 |
| 更低 effort | 中 | 评测对等 |
| 提示词缓存读取 | 在 agent 上很大 | 稳定、有序的前缀 |
| 批量折扣 | 在大批量上很大 | 能容忍延迟 |
| 更短输出 | 中 | 清楚指示／schema |

## 5. 考试陷阱

1. 题干强调成本或延迟时，仍**挑最聪明的模型**。
2. 把**流式当省钱手段**（它不是）。
3. 把 **Batches 用在聊天 UI**（延迟类别错了）。
4. 依赖缓存时，仍在**对话中途改工具或模型**。
5. 把**易变量据**（时间戳、每用户机密）放进已缓存的系统前缀。
6. 正式环境用**别名**却没有钉定＋金丝雀故事。
7. **忽略主机／区域限制**（Bedrock／Vertex 数据驻留）。
8. 优化**每 token 成本**而不是**每次成功任务成本**。
9. 用**提高 max_tokens** 去「修」坏结构——应优先用 schema 与切块。
10. 把 **effort 与模型层级当成同一个旋钮**——它们是分层的。

## 6. 自测问答（20）

**Q1.** 产品需要 FAQ 聊天达到亚秒级感知回复。中阶层级模型的质量已经「够好」。最佳的第一个优化是什么？
**A1.** 保留中阶层级模型，启用**流式**，确保稳定系统／工具前缀的提示词**缓存**命中，若质量评测仍通过则考虑**更低 effort**。不要跳到前沿。

**Q2.** 你必须在明天早上前为 20 万份文档评分；没有用户在等。最佳 API 模式？
**A2.** **Message Batches**，可选择搭配共用已缓存上下文，以及有提供时用较长缓存 TTL。

**Q3.** 部署后缓存命中率崩掉。差异比较显示工具定义每次请求都随机排序。根因？
**A3.** **前缀不匹配**——非确定性的工具顺序会破坏提示词缓存。把工具确定性地串行化。

**Q4.** 评测显示模型在困难写程序任务上规划不足；采购要求模型 ID 必须固定。杠杆？
**A4.** 提高 **effort**（并改善提示词／工具）。若限制禁止，不要改模型。

**Q5.** 为什么在对话串中途从 Sonnet 换到 Opus，对 agent 会话的伤害会超过原始价格？
**A5.** 缓存是**以模型为范围**的；切换会让已缓存前缀失效，并可能让行为不稳。

**Q6.** 尽管 QPS 很高，何时 Haiku 等级仍是*错误*答案？
**A6.** 当题干需要深度多步骤自主性、细致政策判断，或评测显示小模型撑不住的高答错代价推理时。

**Q7.** CI 里的别名 `sonnet` 在一次安静升级后开始失败。如何预防？
**A7.** 在 CI／正式环境**钉定**明确模型 ID；只在可接受漂移的地方用别名。

**Q8.** 批量工作有 `cache_control` 但缓存命中仍低。可能漏了什么？
**A8.** 各项目前缀不完全相同、缓存 TTL 对异步处理太短，或期待保证命中（文档：批量里是**尽力而为**）。

**Q9.** 批量处理需要流式吗？
**A9.** 不需要——批量结果是以已完成结果／文件取回，不是即时 token 流式。

**Q10.** 有 1M 上下文选项。每个应用都该启用吗？
**A10.** 不该——只在会话／存储库真正需要时用；否则检索加缓存常常更便宜、更清楚。

**Q11.** 级联路由：什么信号该触发升级？
**A11.** 验证失败、低自我信心分数、政策风险标志，或评分量规失败——不是「随机 10%」。

**Q12.** 每次调用成本下降了，但用户抱怨上升。缺了哪个指标？
**A12.** **任务成功／每次成功任务成本**（也可能是安全事故）。

**Q13.** 用 `max_tokens: 0` 预热——目的？
**A13.** 填入提示词缓存但不产出答案（同步路径）；依公开批量限制，批量里面不可用。

**Q14.** 预热与正式流量的思考／effort 不同。症状？
**A14.** 在一种思考设置下写入的消息层级缓存条目，对不上正式流量（工具／系统前缀仍可能命中）→ 看起来像「缓存坏了」的部分未命中。对齐设置。

**Q15.** 只走 Bedrock 的客户被锁在某个区域。最新 Anthropic API 模型那边没列出。正确动作？
**A15.** 选符合政策的**已核准区域**模型／配置文件；规划对等测试——不要违反政策去发明跨区域调用。

**Q16.** 「让它更便宜」题干；agent 每回合用 40 个工具。强的 MSO 动作？
**A16.** 保持工具清单稳定，但用**延迟加载／工具搜索**模式，让完整 schema 不必总是展开——再加上缓存稳定的 stub 前缀。

**Q17.** 双模型验证模式——何时合理？
**A17.** 高风险输出（法律／医疗摘要、正式环境迁移），且验证成本 < 答错代价时。

**Q18.** p95 延迟很差；缓存命中率 5%。第一个调查？
**A18.** 前缀稳定（系统／工具排序、易变系统文本），不是立刻「用更大实例去买同一个错误」。

**Q19.** 为什么提高 effort 可能让成本增加超出预期？
**A19.** 更多 token／工具循环／思考——账单随测试时运算上升，不只是价目表价格。

**Q20.** 把这一章对应到考试配分比重。
**A20.** **模型选择与优化 16.8%** 的核心，再加上其实是成本／延迟路由题的集成题。

## 9. 扩展深挖 — 生产环境 MSO playbook

### 9.1 写一份 MSO 政策文档（资深工程师真正会发布的东西）

一个「在 PR 里临时挑模型」的团队，会在集成风格情境题里失败。编码一份简短的 **MSO 政策**：

1. 交互式产品界面的**默认模型**。
2. 脱机评分的**批量模型**。
3. 工具循环写程序／运维 agent 的 **agent 模型**。
4. 失败／高严重程度的**升级模型**。
5. 各接口的 **effort 默认**。
6. **钉定规则**（正式环境用完整 ID；别名只允许在个人沙箱）。
7. **评测关卡** — 没有黄金标准集差异报告，就不改舰队模型。
8. **缓存合约** — 有序工具、冻结系统区段、前缀变更的负责人。

考试喜欢听起来像**治理**、不是氛围的答案：「更新钉定设置＋金丝雀＋评测报告」，不是「在聊天 UI 里换成 Opus」。

### 9.2 不必背价目表的 token 经济

你不需要精确的美元图表。你需要**相对**推理：

- 公开 Anthropic 定价页上，输出 token 通常比输入 token 贵——所以**冗长**会伤。
- 缓存**写入**比缓存**读取**贵（概念上：付钱填入，重用时省下）。
- 批量折扣适用于合格的大批量工作；它们不会神奇修好膨胀的提示词。
- 工具结果会再进入上下文——话多的工具是隐藏的成本放大器。

**实用考试启发式：** 若两个选项都「能用」，选那个能减少**重复的未缓存预填**或**不必要输出**的，不是那个只在系统提示词里换形容词的。

### 9.3 长上下文策略矩阵

| 策略 | 最适合 | 失败模式 |
| --- | --- | --- |
| 把完整文档塞进提示词 | 很小、稳定的参考 | 成本＋分心 |
| 提示词缓存稳定语料 | 许多请求共用文档 | 一改就破坏 |
| RAG／检索切片 | 大型、会变的语料 | 切块差 → 答错 |
| 摘要记忆 | 跨越多日的长 agent | 摘要漂移 |
| 1M 等级窗口 | 真正巨大的单一会话 | 成本；仍不是塞垃圾上下文的借口 |

**教学重点：** 更大窗口不能替代**上下文工程**。考试上的公开提示与上下文主题，把「什么该进上下文」当成贴着 MSO 的一等技能。

### 9.4 Agent 循环成本控制

Agentic 会话会把回合数乘上去。成本驱动因子：

1. **工具 schema 大小 × 回合数**（这就是延迟加载／工具搜索重要的原因）。
2. **每回合重读大型文件**却没有缓存策略。
3. **无界循环**，没有步骤预算或停止条件。
4. 每个微步骤都用**过高 effort**（分类、再计划、再编辑——不是每一步都需要 max effort）。

**模式：** 用有能力的模型做**计划**回合；只有在你接受复杂度时，才考虑用更便宜模型做**狭窄机械**回合——许多团队为了缓存稳定而维持一个模型。除非题干明确要求路由，考试常常偏好**一个稳定模型＋effort／提示词纪律**，而不是聪明的多模型抖动。

### 9.5 当评测与直觉不一致

假设在线用户「喜欢」更聪明的模型，但脱机评分量规分数持平、成本却 +40%。CCDV-F 风格的判断：

- 优先采对齐业务结果的标注集上的**可测量**质量。
- 分段评测（易／难）。也许只有困难区段值得前沿。
- 分开看**安全**指标——一个会泄漏 PII 的有趣模型，不是升级。

### 9.6 迁移 playbook（模型升级）

```text
1. 冻结黄金评测集＋正式流量的影子样本
2. 在金丝雀设定中钉定候选模型
3. 比较：成功率、延迟、每次成功成本、安全旗标、缓存命中率
4. 若 effort 默认不同，先调 effort，再怪模型
5. 备妥回滚 ID 后再向前推行
6. 更新 runbook 与 CLAUDE.md／服务设定文档
```

错误答案模式：「周五全域改别名。」

### 9.9 反模式画廊

1. **什么都用神模型** — 摧毁毛利；掩盖糟糕提示。

3. **把缓存当成可选** — 对 agent 把缓存当可有可无。
4. **无评测替换** — 经典正式环境停机启动包。
5. **延迟剧场** — 微调 TTFT，同时 agent 做 30 次不必要的工具调用。

### 9.13 再五题问答

**Q21.** 为什么 `opusplan` 风格别名会出现在 Claude Code，却不该出现在你的后端 API 服务？
**A21.** 它编码的是**会话工作流程**（用一个模型计划、用另一个执行）。后端服务通常需要明确钉定的 ID 与刻意的路由逻辑，而不是交互式别名。

**Q22.** 你的同步路径用自动缓存；预热用了带顶层自动缓存的占位用户消息。命中失败。为什么？
**A22.** 自动缓存可能以**最后一个**区块（那个占位）为键。预热应在共用系统／工具前缀上用**明确**断点，对齐正式流量。

**Q23.** 降低 `max_tokens` 一定降低成本吗？
**A23.** 它上限了**潜在**输出成本并防止失控，但若模型仍吐到接近上限，质量可能受害；搭配「要简洁」与 schema。它不降低输入／缓存成本。

**Q24.** 利益相关者要求用「最强模型」做分类器，Haiku 等级已经有 99.5%。回应？
**A24.** 留在 Haiku 等级；把力气花在那 0.5% 错误的数据／规则上，或只对那些案例级联——MSO 是限制之下的足够性。

**Q25.** 说出两个 Bedrock 与 Anthropic API 功能对等对 MSO 重要的理由。
**A25.** （1）某个缓存／批量／工具功能可能不可用，因而改变最佳设计；（2）模型 SKU 名称不同，所以钉定与 runbook 必须依主机而定。

## 11. 主要学习深化 — 给应用与集成题干的 MSO

应用与集成占 CCDV-F 的 **33.1%**。那些题很多是*打扮成 API 设计的 MSO 决策*：要钉定哪个模型字符串、要不要流式、要不要批量、如何让缓存保持热、如何避免设置漂移。这一节训练那个重叠，让第 01 章成为主要学习来源，不是快速浏览。

### 11.1 模型身份机制（考试稳定概念）

公开 Anthropic 模型文档强调：

| 想法 | 对建造者的意思 | 考试触发 |
| --- | --- | --- |
| 钉定快照 ID | 你可以重现的特定模型发行 | 「prod regression」、「no surprise upgrades」 |
| 便利别名（旧模式） | 可能解析到带日期 ID 的指针 | 「always latest」、「sandbox only」 |
| 较新世代的不带日期 ID | 仍是**钉定快照**，不是常青会移动目标 | 不要假设不带日期＝自动升级 |
| 主机特定 SKU | Bedrock／Vertex／Foundry ID 与 Claude API 不同 | 多云客户；数据驻留 |
| Models API 内省 | 查询 `max_input_tokens`、`max_tokens`、能力 | 不必写死的能力闸控 |

**主要学习规则：** 正式环境在设置里钉定明确模型识别码。别名与「最新」营销名称属于实验室与交互式 Claude Code 会话，除非你刻意接受漂移。

### 11.2 Effort、自适应思考与扩展思考（概念地图）

近期公开文档区分：

1. **Effort**（`output_config.effort`／相关接口）——旋钮控制模型有多认真；API 默认是 **high**，而 Claude Code 默认是 **xhigh**（写程序／agentic 工作的甜蜜点）。
2. **自适应思考** — 模型自己决定何时思考（较新的 Opus／Sonnet／Fable 线）。
3. **扩展思考**（`thinking.type: "enabled"`） — 部分模型上仍存在的较旧／明确思考控制（例如公开比较表里的 Haiku 4.5）。

**决策纪律：**

```text
要在同一个模型 ID 上得到更好的答案？
 → 先提高 effort／放宽思考预算
要在同样的质量门槛下降低延迟／成本？
 → 降低 effort；若评测仍然通过，再考虑更小的层级
需要不同的能力类别（视觉等边缘能力、自主性、最便宜的高 QPS）？
 → 改模型层级——并把它当成一场迁移（钉定、缓存、评测）
```

**缓存耦合：** 思考设置变更会让**消息层级**缓存断点失效（工具／系统前缀仍可缓存）。让预热与正式思考／effort 对齐，缓存每一层才真的会被读到。

### 11.3 服务路径矩阵（集成 × MSO）

| 路径 | 人类在等？ | 成本姿态 | 流式？ | 典型用途 |
| --- | --- | --- | --- | --- |
| 同步 Messages | 是／近即时 | 完整同步费率 | 可选 | 聊天、agent、在线工具 |
| 同步＋流式 | 是 — 用户体验在乎 TTFT | 同一运算类别 | 是 | 面对用户的助手 |
| 同步＋提示词缓存 | 是，重复前缀 | 预热后更便宜 | 可选 | 有稳定系统＋工具的 agent、应用 |
| Message Batches | 否（数小时可以） | 折扣异步 | 否 | 评测、分类、大批量生成 |
| 批量＋缓存 | 否 | 折扣可以**叠加**；命中尽力而为 | 否 | 共用前缀的夜间工作 |

**当成判断记住、不是 trivia 的公开批量限制：**

- 批量结果生成时不能流式。
- 批量里的缓存命中是**尽力而为**（并行异步工作者）。
- 用 `max_tokens: 0` 预热是**同步**模式——不要预期在批量里面。
- 部分模型经 beta header 支持延伸批量最大输出（核对现行文档）；考试上不要发明 header——要知道同步与批量上限可以不同。

### 11.4 提示词缓存作为 MSO 杠杆（深度）

缓存不会缩小上下文；它折扣**重复的前缀 token**，且命中时常常改善 TTFT。

**前缀顺序（概念上）：** tools → system → messages，直到 `cache_control` 断点。

**TTL 主题（公开）：**

- 默认短暂生命期常被讨论成约 **5 分钟**，读取时刷新。
- 较长 TTL（例如 **1 小时**）在命中间隔很长时可用，但有额外成本。
- 生命期从写入／读取的那次请求起算——长流式响应会消耗 TTL 墙钟。

**什么会让缓存失效或未命中（学习清单）：**

- 已缓存前缀字节的任何变更（系统文本、工具 JSON 顺序／名称、插入的时间戳）。
- 对话串中途改模型 ID。
- 思考／effort 设置与你写入的条目不匹配（让消息层级断点失效；工具／系统前缀不受影响）。
- 自动缓存以预热占位用户回合为键（预热应在共用系统／工具上用**明确**断点）。
- 把工具集重排当成「模式切换」。

**MSO 考试句：** 若题干说成本在「我们为调试在系统提示词加上时间戳」之后暴增，修正是从已缓存前缀拿掉易变字段——不是买更便宜的模型。

### 11.5 上下文窗口策略作为优化

公开模型卡显示现行 Opus／Sonnet／Fable 线有 **1M** 等级窗口，部分快速模型窗口较小。考试在乎*策略*：

| 情况 | 优先 |
| --- | --- |
| 带大型存储库的数小时 agent | 大窗口模型＋压缩＋检索；不要每回合倾倒整个 monorepo |
| 稳定政策＋文档 | 缓存它们；检索易变切片 |
| 50+ 工具 | 工具搜索／延迟加载＋缓存 stub 清单 |
| 便宜高 QPS 抽取 | 更小／更快模型＋严格 schema；大窗口若你填满它才是浪费钱 |

**规则：** 更大窗口是允许你多拿一些——不是要求你多送一些。

### 11.6 以 MSO＋集成出现的路由架构

1. **静态路由：** 产品界面一个钉定模型。
2. **级联：** Haiku／Sonnet 尝试 → 低信心／验证器失败时升级到 Opus。
3. **分段路由：** 依租户层级、地区或风险类别用不同模型。
4. **计划／执行拆分：** 更强模型计划；更快模型执行工具调用（Claude Code 别名交互式编码这个；服务要明确实现）。
5. **脱机／在线拆分：** 分析用 Batches；用户体验用同步。

**陷阱：** 没有预算的级联会变成意外的到处都是 Opus。永远上限升级次数并记录原因。

### 11.7 考试出题者喜欢的成本会计

用**单位经济**想，不是发票截图：

```text
success_adjusted_cost = (input + output + cache_write + cache_read + tool_overhead) / successful_task
```

- 缓存**写入**比基础输入贵；它们在命中时回本。
- 批量折扣适用于合格 token；与缓存叠加被允许，但命中是概率性的。
- Agent 循环把回合数乘上去——「便宜」模型用 3× 回合，可能输给 1× 回合的更强模型。
- 输出 token 常常比输入贵——schema 与「要简洁」是 MSO 控制。

### 11.8 钉定、弃用与迁移

公开文档维持弃用／迁移指引。主要学习习惯：

1. 在环境／设置里钉定模型 ID，不要散落在源代码文件。
2. 为每个主机维持一份**兼容性矩阵**（API 对 Bedrock 对 Vertex 功能标志）。
3. 迁移顺序：黄金评测 → 影子流量 → 金丝雀钉定 → 完整切换上线 → 删除旧钉定。
4. 没有二分调试计划时，绝不要在同一次发布中同时改模型、提示词与工具。

### 11.9 集成×MSO 情境演练（原创）

**情境 A — 客服聊天，p95 TTFT SLA。**
流式；优先 Sonnet 或 Haiku 等级；质量撑得住就用中／低 effort；缓存稳定系统＋工具；**不要**批量。

**情境 B — 夜间对 200 万张工单做已屏蔽 PII 的分类。**
Message Batches；最小足够模型；在指示＋标签分类法上共用 `cache_control`；接受尽力而为的缓存命中；不要流式。

**情境 C — 写程序 agent 碰上不稳定的困难错误。**
钉定 Opus 等级；跳到更稀有顶层模型之前先提高 effort；为缓存保持工具 schema 稳定；压缩历史；用测试（工具）验证，不是氛围。

**情境 D — 多云企业，欧盟数据驻留。**
MSO 包括推理跑在**哪里**。即使全球路由更快，也要选满足政策的区域端点；确认该主机上的功能对等（缓存／批量／工具）。

**情境 E — 「有帮助」的重构后缓存未命中风暴。**
对请求前缀做差异比较；找工具重排、动态日期、插入系统文本的实验标志，或 SDK 升级后的 effort 默认变更。

| --- | --- |

| p50／p95 TTFT 与总延迟 | 用户体验／SLA |

### 11.11 额外问答（Q26–Q35）

**Q26.** 产品经理为了「一致性」想用同一个模型做聊天与过夜评测。MSO 反驳是什么？
**A26.** *质量门槛*的一致性可以用共用评分量规与重叠评测；服务路径不同。聊天需要同步／流式；过夜应批量。若质量需要，你仍可在两条路径钉定同一个模型 ID——但不要强迫一种服务模式。

**Q27.** 何时选 1 小时缓存 TTL 而不是默认短 TTL？
**A27.** 当共用前缀的请求间隔长过短 TTL（尖峰流量、仅营业时间的工具），且额外写入／存储成本胜过重复完整预填未命中时。

**Q28.** 你的 Bedrock 部署缺少你在 Claude API 用过的 beta 工具功能。正确回应？
**A28.** 依该主机的功能矩阵重新设计（或把那一切片跑在支持它的主机上）。不要假设 SKU 名称对等就代表功能对等。

**Q29.** 流式更便宜吗？
**A29.** 本质上不是。它改善感知延迟并允许取消；产生的输出仍按 token 计费。

**Q30.** SDK 升级后 effort 默认变了、成本上升。第一个检查？
**A30.** 在设置里明确把 effort 设回先前已验证的值；重跑评测；确认缓存命中率（不匹配也可能让缓存未命中）。

**Q31.** 大上下文窗口但 Haiku 等级模型——何时仍是错的？
**A31.** 当任务需要评测显示 Haiku 失败的前沿推理／自主性时——窗口大小不能替代能力层级。

**Q32.** Agent 循环烧预算时，第一个 MSO 动作是什么？
**A32.** 加上停止条件、工具预算与进度检查；然后才考虑能用更少回合完成的更强模型。

**Q33.** 为什么在 Claude Code 与后端服务钉定方式不同？
**A33.** Code 会话可能用工作流程别名与用户 `/model` 切换；后端需要为 SLO、缓存与审计做确定性钉定。

**Q34.** 缓存写入加价对命中节省——何时第一天就该缓存？
**A34.** 当同一个前缀会被很快重用时（agent、多轮应用、共用工具 schema）。一次性独特提示词可能回不了本。

**Q35.** 说出三个会改变你选哪个模型的集成功能。
**A35.** 需要流式用户体验；需要批量成本结构；需要只在某些模型线上稳定的工具／MCP 功能——再加上主机／区域限制。

## 12. LLM 基础入门（考试蓝图技能 5.2%）

*2026-08-23 添加——官方 LLM 基础陈述测验「token、上下文窗口、采样、非确定性、下一个 token 生成……以及基本提示技术（zero-shot、single-shot、multi-shot）」。这份入门补上那个缺口。*

### 12.1 模型实际上怎么生成

- **Token** 是一切的单位：模型读写 token（子词块——英文平均大约一个字的 3/4），计费、上下文窗口与 `max_tokens` 都用它们计数。代码、JSON 与非英文文本的分词效率低于普通英文叙述文字。
- **下一个 token 生成：** 模型一次产出一个 token，每个选择都以整个可见上下文（提示词＋目前已生成的一切）为条件。没有在 token 之外的前瞻「计划」；长结构化输出会在结尾失败，因为每一步都会复合。
- **采样与非确定性：** 每一步模型对可能的下一个 token 有概率分布，并从中*采样*——这就是为什么两次相同请求可以产出不同答案。历史上，`temperature`／`top_p`／`top_k` 塑造那个分布。**现况：** 在 Opus 4.7+、Opus 5、Sonnet 5 与 Fable 等级模型上，这些采样参数已**移除**（带它们的请求会被拒绝）；它们只留在较旧模型上（4.6 世代、Haiku 4.5）。
- **确定性陷阱：** `temperature: 0` 从不保证字节完全相同的输出，而且在现行模型上这个旋钮根本不存在。若题干需要可重复结构，正确杠杆是 **schema／结构化输出、验证器，以及 few-shot 锚点**——不是采样设置。

### 12.2 样本数术语（精确定义这些）

| 术语 | 意思 | 何时用 |
| --- | --- | --- |
| **Zero-shot（零样本）** | 只有指示；没有做过的例子 | 任务对模型来说常见／容易；让提示词短且可缓存 |
| **Single-shot（单样本／one-shot）** | 恰好一个做过的例子 | 格式不寻常但一致；一个例子便宜地锚定形状 |
| **Multi-shot（few-shot，少样本）** | 数个做过的例子 | 边界案例、标签边界或内部风格重要；挑多样、高信号的例子（边界案例 > 快乐路径） |

**MSO 角度：** 例子活在提示词里，所以每一枪都在每次调用上花 token——把例子区块**稳定**放在已缓存前缀里，并修剪不再赚回 token 的例子。

### 12.3 自测问答（Q36–Q40）

**Q36.** 为什么两次相同的 API 调用会回不同措辞？
**A36.** 输出是从下一个 token 概率分布**采样**的——非确定性是固有的，不是错误。

**Q37.** 同事在现行 Opus 等级模型上设 `temperature: 0`「为了确定性 JSON」。两个问题？
**A37.** 采样参数在现行模型上已移除（请求会出错），而且即使历史上 temp 0 也不保证相同输出。用 schema＋验证。

**Q38.** 分类提示词只在模糊边界案例失败。不是升级模型的 zero-shot 修正？
**A38.** 改走 **multi-shot**：加上几个正好坐在令人困惑边界上的例子。

**Q39.** 为什么 2,000 字英文提示词可能比 500 行 JSON 花更少 token？
**A39.** 分词效率不同——叙述文字比稠密结构化文本更能压进 token。

**Q40.** 高流量已缓存端点的 few-shot 例子该放哪？
**A40.** 放在稳定的已缓存前缀（与系统／工具一起），请求之间不变——编辑一个例子会破坏缓存。

## 13. 快速模式（考试蓝图具名的模型选项——要知道它存在以及何时用）

*2026-08-23 添加。官方 LLM 基础陈述把 **快速模式** 与扩展思考、自适应思考、effort 并列；本包先前省略了它。下列事实缓存于 2026-08——研究预览功能，考前请核对当前文档。*

**它是什么：** **同一个模型**以最高约 2.5× 的输出 token／秒运行，采**溢价定价**（例如 Opus 5 fast 大约是标准 Opus 5 每 MTok 费率的 2×）。它是同一智能上的*速度／价格*交易——不是更小模型，不是质量变更。

**机制（概念上）：** 只在 **Claude Opus 5 与 Opus 4.8** 上作为研究预览提供。请求按调用选择加入：beta messages 端点＋快速模式 beta 标志＋顶层 `speed: "fast"` 参数；响应用量会回报实际服务的速度。快速模式有**自己的速率限制**，与标准流量分开。

**它不可用的地方（高信号考试事实）：**

- 不在 Bedrock／Vertex／Foundry——只在 Claude API（以及托管 agent 会话）。
- 不能与 **Batch API** 并用（批量是能容忍延迟的路径；快速模式是延迟关键的路径）。
- 不能与优先容量层级并用。

**运营判断：**

```text
有人在等、且输出长度主导延迟、且预算允许溢价？
 是 → 快速模式候选（同一模型，约 2.5× 输出速度、约 2× 价格）
 否 → 先用更便宜的杠杆：串流（感知延迟）、缓存命中（TTFT）、
 更低 effort、更快层级
遇到快速模式 429：依指示的延迟重试，或退回标准速度——
 并记住切换速度会让提示词缓存条目失效。
```

**何时它胜过降层级：** 任务需要前沿质量（降级会让评测失败），但用户感觉得到生成时间——例如长代码审查或即时流式给等待中专家的草稿文档。

### 13.1 自测问答（Q41–Q45）

**Q41.** 快速模式对上换成 Haiku 等级——核心差异是什么？
**A41.** 快速模式在更高输出速度与更高价格下保持**同一个模型的质量**；换层级是用质量换速度／成本。

**Q42.** 你能用快速模式跑过夜 20 万文档批量来「更快做完」吗？
**A42.** 不能——快速模式不能与 Batch API 并用，而且批量工作本质上能容忍延迟；它是错的杠杆。

**Q43.** 只走 Bedrock 的企业要求快速模式。回应？
**A43.** 那边没有（Claude API 研究预览，只限 Opus 5／Opus 4.8）——改在他们的主机上提供流式、缓存、effort 调校或层级选择。

**Q44.** 快速模式请求开始回 429，而标准 Opus 流量没事。为什么可能？
**A44.** 快速模式有**自己分开的速率限制**；等指示的延迟后重试，或降回标准速度（接受速度切换造成的缓存失效）。

**Q45.** 题干说「降低账单」——快速模式会是答案吗？
**A45.** 不会。快速模式为速度提高单位价格。成本题干要更小模型、更低 effort、缓存、批量、更短输出。
