## 概览

模型上下文协议（MCP）是一套开放标准，用来把 AI 主机（Claude Desktop、集成开发环境（IDE）、自定义 agent）连到外部工具与数据，**不必**为每一种应用程序×服务组合亲手写一份独一无二的 JSON 工具 schema。入门课程公开的学习目标强调：架构（把工具定义／执行移到专门服务器）；与传输层无关的消息传递；端到端请求流程；用 Python SDK 打造服务器（装饰器对上手写 JSON schema）；文档风格工具；MCP Inspector；**资源**（直接型＋模板型）；客户端读取资源与 MIME 类型；**提示**作为可重用工作流程；在工具／资源／提示之间做选择；以及自动完成、上下文注入等集成模式。

**公开模块形状：** 导论 → 动手做 MCP 服务器 → 连接 MCP 客户端。

**公开点名的先修：** 基础 Python、async/await、API 素养。

**这份笔记与 API 课程的关系：** Building with the Claude API 教的是*单一*应用程序内部的 Messages／工具循环。MCP 教的是许多应用程序如何通过共同协议，共享同一组外部能力。考试时，若看到「跨主机重用」或「Inspector」，就想到 MCP。

## 关键概念（速查表）

| 概念 | 一句话 |
|---------|-----------|
| **主机（Host）** | 用户看到的 AI 应用程序（编排客户端、UI、模型调用） |
| **客户端（Client）** | 主机内的连接器；与单一 MCP 服务器**一对一** |
| **服务器（Server）** | 暴露工具、资源与／或提示的进程／服务 |
| **工具（Tools）** | 模型控制的动作（允许副作用；类似函数调用） |
| **资源（Resources）** | 应用程序控制、大致只读、以统一资源标识符（URI）寻址的数据 |
| **提示（Prompts）** | 用户控制、预先打造的指示模板 |
| **传输层（Transport）** | JSON-RPC 消息如何移动（本机常见 **STDIO**；远程为 Streamable HTTP／SSE） |
| **数据层（Data layer）** | JSON-RPC 方法、生命周期、原语、通知 |
| **Inspector** | 浏览器辅助工具，用来列出／调用工具并帮服务器调试 |
| **能力协商** | initialize 握手，双方声明各自支持什么 |

**心智模型：** 主机问模型该做什么 → 模型可能选一个工具 → 客户端调用 MCP 服务器 → 服务器与真实系统交谈 → 结果回流进模型上下文。

## 分主题深入笔记

### 1. MCP 为什么存在

没有 MCP，每个 AI 应用程序都要为 GitHub、Slack、数据库、文件系统等重复写集成代码。有了 MCP：

- **N 台服务器**（每台对应一个系统或能力领域）＋ **M 个主机／客户端**，胜过 **M×N** 个定制适配器。
- 服务器拥有后端的身份验证、输入验证，以及领域逻辑。
- 主机专心做用户体验、政策与模型编排。

考试用语要记住：MCP 把工具定义与执行的负担，从你那个单体应用服务器**转移**到**专门的 MCP 服务器**。

**比喻：** USB 标准对上各家专有线材。主机讲 MCP；服务器讲 MCP；后端留在服务器适配层后面。

**MCP 不是什么**

- 不是 Claude Messages API 的替代品（主机仍然调用模型）。
- 本身不是数据库，也不是向量嵌入（embedding）存储。
- 不保证安全——范围定得太松的服务器仍然危险。
- 不是「只给 Anthropic 用」；它是开放协议，许多主机都能实现。

### 2. 架构：主机、客户端、服务器

```
User ↔ Host (LLM app) ↔ Client₁ ↔ Server₁ (e.g. docs)
 ↔ Client₂ ↔ Server₂ (e.g. calendar)
```

- **主机职责：** 生成／管理客户端；把提示／资源呈现给用户；决定哪些上下文送到模型；强制执行用户同意与安全政策；运行或调用大型语言模型（LLM）。
- **客户端职责：** 能力协商／会话生命周期；把主机需求翻译成 MCP 请求；把一台服务器与另一台隔开。
- **服务器职责：** 声明并实现原语；保持聚焦（单一领域比较容易保护与测试）。

**一对一规则：** 每个客户端恰好只跟一台服务器说话。使用三台服务器的主机，就跑三个客户端。这种隔离是考试最爱。

**本机对上远程服务器**

| | 本机（常为 STDIO） | 远程（常为 Streamable HTTP） |
|--|---------------------|--------------------------------|
| 进程 | 主机启动子进程 | 独立服务 |
| 典型扇出 | 每个进程一个客户端 | 许多客户端连到同一服务 |
| 验证故事 | 操作系统用户权限 | HTTP 验证／OAuth／token |
| 失败模式 | 宕机杀掉那一台服务器 | 网络分区、版本偏差 |

安全边界提醒：被攻陷或权限过大的服务器很危险——最小权限原则、清楚的 roots／路径，以及敏感工具要用户核准，即使在「本机」STDIO 设置里也成立。

### 3. 分层：数据层对上传输层

官方架构把 MCP 分成：

1. **数据层** — JSON-RPC 2.0 消息语义：生命周期、工具／资源／提示、通知，以及客户端功能如采样／询问请求（elicitation）（进阶）。
2. **传输层** — 字节如何移动：STDIO 对上 Streamable HTTP（可选 SSE）、讯框处理，以及传输层验证。

入门考试标准：你要能解释**同一套** JSON-RPC 方法可以跑在不同传输层上。进阶课程才深入讲生产环境的 HTTP 扩展。

### 4. 消息流程（请求 → Claude → 工具 → 回来）

典型的一轮：

1. 用户在主机里问一个问题。
2. 主机组装上下文（对话记录、选定的资源、选定的提示模板）。
3. 主机调用 Claude，带上从 MCP 服务器发现的可用工具定义。
4. Claude 回传一个工具调用（名称＋参数）。
5. 主机／客户端向对的服务器送出 MCP `tools/call`。
6. 服务器执行（读文件、编辑文档、查询 API）并回传结构化结果。
7. 主机把工具结果附加进对话，再次调用 Claude。
8. Claude 产出用户看得到的答案（或更多工具调用）。

要分清**请求／结果**成对（RPC 调用）与**通知**（单向事件）。更深的消息分类出现在 Advanced Topics 课程。

**原创时序图（文本）**

```text
User → Host: "Summarize Q3 plan doc"
Host → Client(docs): resources/read docs://q3-plan
Client → Server: resources/read
Server → Client: text/markdown body
Host → Claude: messages + tool defs + injected resource
Claude → Host: tool_use edit_section(...)
Host → Client: tools/call edit_section
Server → Client: ok
Host → Claude: tool_result
Claude → Host: final summary for user
```

### 5. 生命周期（入门深度）

MCP 会话不是「先乱射方法」。概念上的生命周期：

1. **连接**传输层（启动 STDIO 进程或打开 HTTP 会话）。
2. **Initialize** — 交换协议版本、`clientInfo`／`serverInfo`，以及能力。
3. **initialized 通知** — 客户端声明自己准备好了。
4. **操作** — `tools/list`、`tools/call`、`resources/list`、`resources/read`、`prompts/list`、`prompts/get` 等。
5. **关闭** — 关闭流／终止子进程；不要泄漏子进程。

**能力协商的直觉**

- 服务器可以声明支持工具、资源、提示，以及清单会不会变（`listChanged`）。
- 客户端可以声明支持服务器稍后可能请求的功能（采样、询问请求——进阶）。
- 调用不支持的方法是协议上的异味——先探索。

考试提示：若被问「`tools/list` 之前发生什么？」回答 **initialize／协商**，不是「立刻调用工具」。

### 6. 打造 MCP 服务器（Python SDK 心态）

入门课程重点：用 SDK，这样你就**不必**亲手写巨型 JSON schema。

- 装饰器／类型提示／`Field` 描述会变成模型看到的工具元数据。
- 好的描述会大幅改善工具选择——把它们当成提示工程。
- 公开大纲的范例领域：**文档管理**——读取与编辑文档的工具。
- 工具要窄：`read_document(id)` 与 `update_section(id, section, text)` 胜过含糊的 `do_anything(payload)`。

**原创装饰器风格草图（示意，不是 SDK 转储）**

```python
# Conceptual only — verify current SDK APIs before coding
@server.tool()
def read_document(doc_id: str) -> str:
 """Return the full text of a document by id. Use when the user asks what's inside a doc."""
...

@server.tool()
def update_section(doc_id: str, section: str, text: str) -> str:
 """Replace one named section. Prefer this over rewriting the entire document."""
...
```

**描述写作检查清单**

- 工具做什么，一句话。
- 什么时候用／什么时候不用。
- 单位、id 格式、副作用。
- 模型该预期的失败模式。

**Inspector：** 跑起服务器，在浏览器打开 MCP Inspector，列出工具、发起调用、检查载荷，之后再接完整主机。这是考试题「如何为服务器调试」的绝佳答案。

### 7. 资源：直接型对上模板型

**资源**暴露以读取为导向的数据，由*应用程序*（不是模型自己）决定要抓取并注入。

- **直接资源：** 静态 URI，例如 `docs://index` 或 `config://app-settings`。
- **模板资源：** 带参数的 URI 模板，例如 `docs://{doc_id}`——由客户端填入参数。

客户端读取检查清单：

- 用 URI 请求资源。
- 处理 **MIME 类型**（例如 `application/json` 对上 `text/plain`），才能正确解析。
- 刻意把内容注入模型上下文（整份文档对上摘录）。

**何时用资源、何时用工具？** 若主要是「为上下文抓取数据」、没有有意义的副作用 → 资源。若改变状态或执行动作 → 工具。

**URI 设计提示**

- 每个服务器领域用清楚的 scheme（`docs://`、`db://`、`config://`）。
- id 保持 URL 安全；把模板参数写成文档。
- 注入提示时，优先用不可变快照，以便可审计性。

**MIME 处理范例**

| MIME | 客户端行为 |
|------|-----------------|
| `text/plain` | 当文本注入；或许截断 |
| `text/markdown` | 同样处理，可能的话保留标题 |
| `application/json` | 解析；或许美化打印选定字段 |
| `image/png` | 主机可路由到具备视觉能力的消息区块 |

考试陷阱：忽略 MIME，永远 `json.loads`——二进位或纯文本会炸掉。

### 8. 提示作为 MCP 原语

**提示**是可重用、高质量的指示模板，用于常见工作流程（课程公开提到的例子包括文档格式化）。

- **用户控制：** 通常从菜单挑选（「把选取内容格式化成 RFC 风格备忘录」），而不是由模型默默发明。
- 可以参数化字段（标题、语气、受众）。
- 帮团队跨主机共享最佳实务指示。

**原创提示模板草图**

```text
Name: format_as_adr
Args: title, status, context
Body:
 Write an Architecture Decision Record titled {title}.
 Status: {status}.
 Context: {context}.
 Use sections: Context, Decision, Consequences.
```

主机用户体验：用户挑提示 → 填入参数 → 主机展开 → 送给模型（可选择附上相关资源）。

### 9. 在工具、资源、提示之间做选择

| 原语 | 谁主导？ | 典型用途 | 有副作用？ |
|-----------|-------------|-------------|---------------|
| 工具 | 模型 | 搜索、编辑、送出、运算 | 常常有 |
| 资源 | 应用程序／主机逻辑 | 把文件、设置、数据集加载上下文 | 通常没有 |
| 提示 | 用户 | 用审过的指示启动已知工作流程 | 没有（只有指示） |

考试陷阱：什么都叫「工具」。评分者要看的是上面那个控制平面区分。

**分类操练（背下来）**

- 「把 README 加载上下文」 → **资源**
- 「创建 GitHub issue」 → **工具**
- 「套用 ADR 模板」 → **提示**
- 「搜索文档然后编辑」 → **工具**（已知 URI 时或许加上资源）
- 「展示公司风格指南」 → **资源**或**提示**，取决于它是原始数据还是工作流程模板

### 10. 传输层（入门程度）

MCP 在消息层是**与传输层无关**的（JSON-RPC 风格消息）。常见选项：

- **STDIO：** 客户端把服务器当子进程启动；通过 stdin／stdout 沟通。适合本机桌面／IDE 集成。一般调用之前需要正确的**初始化握手**（细节在 Advanced Topics 讲得更多）。
- **HTTP + SSE／Streamable HTTP：** 给远程／连网服务器；服务器可以推送事件；想想会话、验证与扩展的取舍。现代文档强调 **Streamable HTTP**（客户端对服务器发 HTTP POST，可选 SSE 做流式），且通常建议用 OAuth 处理 token。

入门考试标准：说出传输层名称，并说明何时选本机 STDIO、何时选远程 HTTP。双连接 SSE 细节与无状态水平扩展留给进阶课程。

**传输层选择备忘（原创）**

当服务器必须碰本机文件系统或开发者笔记本电脑的密钥库，而且主机能管理子进程时，用 STDIO。当全公司多个主机要共享一个受管集成（需要真正的验证、审计日志与集中更新）时，用 Streamable HTTP。

### 11. 实务集成模式

- **上下文注入：** 主机读取资源 → 把相关文本附到模型请求上。
- **自动完成／探索：** 列出工具、资源与提示，让 UI 能建议动作。
- **生命周期：** 连接 → initialize／协商 → 操作 → 干净关闭（不要泄漏子进程）。
- **组合：** 一个主机、多台服务器（文档＋issue 追踪器＋数据库），各自待在自己的客户端后面。
- **通知：** 若服务器声明 list-changed 能力，它可以通知客户端刷新 `tools/list`（以及类似清单）——主机应更新模型可用的工具。
- **错误浮现：** 工具失败应变成模型看得到的结构化错误，而不是主机默默崩溃。

### 12. 客户端功能（指引——进阶）

入门只要有意识（深度在 Advanced Topics）：

- **采样（Sampling）：** 服务器请主机／客户端跑一次 LLM 补全（不绑定特定模型的服务器）。
- **询问请求（Elicitation）：** 服务器请主机搜集用户输入／确认。
- **日志／进度：** 服务器为长时间工作发出日志或进度。

入门小考不要对这些过度宣称——知道它们存在，并知道是哪一边暴露它们。

### 13. 安全考量（入门必过）

1. **用户同意：** 主机应核准敏感的工具调用，尤其是第一次使用。
2. **最小权限原则：** 文件系统服务器拿到的是目录根，不是整个 `$HOME` 磁盘，能收窄就收窄。
3. **密钥处理：** 服务器应使用操作系统钥匙串／环境变量／密钥管理器——不要把 token 写死在工具响应里。
4. **混淆代理人：** 一份恶意文档可能试图胁迫模型去调用 `delete_repo`——仍然需要政策闸口。
5. **供应链：** 把第三方 MCP 服务器当成安装软件；审查权限。
6. **传输层验证：** 远程服务器需要真正的身份验证；STDIO 继承用户的操作系统权限——默认仍然不安全。
7. **审计：** 记录工具名称、脱敏后的参数、操作者、时间戳。

### 14. 端到端文档管理心智实验

呼应课程的公开项目主题，但不抄实验原文：

1. 服务器暴露 `list_docs`、`read_document`、`update_section` 工具。
2. 服务器暴露 `docs://{doc_id}` 模板资源与 `docs://index` 直接资源。
3. 服务器暴露一个 `format_document` 提示。
4. 在接入 Claude 之前，先用 Inspector 调用 `read_document`。
5. 主机列出提示做成「格式化」菜单；选定后展开提示，可选择注入资源。
6. 当用户要求编辑时，模型仍然可以把 `update_section` 当工具调用。

这一个领域就操练了**全部三种原语**。

### 15. MCP 对上普通的 Messages 工具定义

| 关注点 | Messages 里普通的工具 JSON | MCP |
|---------|------------------------------|-----|
| 探索 | 写死在应用程序里 | 来自服务器的 `*/list` |
| 重用 | 拷贝 schema | 跨主机共享服务器 |
| 资源／提示 | 自己做 | 一等原语 |
| 运维 | 进程内函数 | 本机进程或远程服务 |
| 何时最好 | 一个应用程序、少数工具 | 生态系统／许多主机 |

桥接洞察：主机常常在底层把 MCP 工具 schema **翻译**成模型供应商的工具格式。MCP 没有拿掉 Claude 的工具循环——它标准化的是外层集成。

### 16. JSON-RPC 心智模型（轻量）

入门考试知道这些就够：

- **请求：** 有 `id`、`method`、`params` → 期待同 `id` 的**结果**或**错误**。
- **通知：** 有 `method`（或许有 params）但**没有 `id`** → 没有响应。
- 方法长得像 `initialize`、`tools/list`、`tools/call`、`resources/read`、`prompts/get`。
- 未知方法／坏 params → 结构化 JSON-RPC 错误，不是 HTTP HTML 页面（即使在 HTTP 传输层上，载荷仍然是 RPC 形状）。

### 17. 常见失败模式与调试

| 症状 | 可能原因 | 修复方法方向 |
|---------|--------------|---------------|
| 主机显示没有工具 | 初始化失败／能力缺失／没调用 list | 在 Inspector 检查 initialize ＋ `tools/list` |
| 工具调用类似 404／未知工具 | 服务器变更后清单过期 | 处理 list_changed；刷新 |
| MIME 解析错误 | 把文本资源当 JSON | 依 MIME 分支 |
| STDIO 服务器卡住 | 握手未完成／stdout 被日志污染 | 协议走 stdout；日志走 stderr |
| 远程 401 | 缺 bearer／OAuth | 修好传输层验证 |
| 模型从不调用你的工具 | 描述太弱／重叠工具太多 | 改写描述；精简集合 |
| 子进程僵尸 | 主机没有收尾生命周期 | 退出时拆除客户端 |

### 18. 主机实现检查清单（「好」长什么样子）

当你打造或审查一台讲 MCP 的主机，评分者（以及生产环境审查者）要看的不只是「连过一次」。

1. **配置面：** 用户可以添加／移除服务器（STDIO 用 command＋args；HTTP 用 URL＋验证）。
2. **同意使用体验：** 第一次使用工具时提示；区分只读与会改动状态的工具。
3. **统一注册表：** 合并所有客户端的工具，并用命名空间处理碰撞（`docs.read` 对上 `db.read`）。
4. **模型翻译：** 把 MCP 工具 schema 对应成你的 LLM API 所期待的供应商工具格式。
5. **结果卫生：** 截断巨大的工具输出；保留足够细节让模型能继续。
6. **取消：** 用户可以中止长时间的工具调用；在支持时，客户端取消进行中的 RPC。
7. **可观测性：** 每台服务器的延迟、错误率，以及注入了哪些提示／资源。
8. **优雅降级：** 一台服务器挂了，其他服务器继续运作。

### 19. 服务器设计模式（文档领域与之外）

**模式 A — 薄适配层**
MCP 服务器包住既有 REST API。工具 ≈ 端点。资源 ≈ 可以安全注入的 GET。

**模式 B — 领域门面**
较少、较聪明的工具（`search_and_summarize_locally`）把后端混乱藏起来。对模型较容易；较难让描述保持诚实。

**模式 C — 读写分离**
把读取暴露成资源；写入暴露成需要确认的工具。干净地对应控制平面三原语。

**模式 D — 提示包**
服务器主要交付提示＋少数资源（风格指南）。适合团队标准化工作流程，又不把写入权交给模型。

**反模式 — 大杂烩**
一台服务器任意执行 shell 命令、读取所有文件、还能发送邮件。违反最小权限原则，也吓到主机的权限 UI。

### 20. 对应 Claude Academy 模块 → 今晚的练习动作

| 公开模块 | 今晚练习什么 |
|---------------|--------------------------|
| 导论 | 画架构；背三原语 |
| 动手做服务器 | 做 2–3 个工具；打开 Inspector |
| 连接客户端 | 读资源＋MIME 分支；列出提示；注入上下文 |

呼应 Building with the Claude API：MCP 回传工具输出之后，你仍然要做 Messages 的 `tool_result` 续接——MCP 没有抹掉那个循环。

### 21. 走完的故事：自动完成＋上下文注入

**自动完成：** 主机在闲置时调用 `prompts/list` 与 `tools/list`。UI 显示「格式化成 ADR」、「搜索文档」、「创建 issue」。用户挑「格式化成 ADR」→ 主机带参数调用 `prompts/get` → 把展开的文本放进编辑器。

**上下文注入：** 用户用 @ 提及一份文档。主机解析 `docs://{id}` 资源、检查 MIME、把截断后的正文注入下一则用户消息（放在标了标签的 `<doc>` 分隔符里），并且*另外*在用户要求编辑时，继续提供写入工具。

考试洞察：自动完成是**探索 UX**；注入是**上下文组装**。两者都是主机职责，即使数据来自服务器。

### 22. 版本与兼容性心态

- 协议版本出现在 initialize；不兼容的版本应快速失败。
- 服务器与主机独立升级——能力标志的存在，是为了让可选功能不要硬性破坏。
- 考试时：优先回答「协商能力并优雅降级」，不要发明一个永远不变的版本号。

## 自我检核问答

**Q1. MCP 的三个角色是什么？**
**A：** 主机（LLM 应用程序）、客户端（一对一连接器）、服务器（暴露原语）。

**Q2. 谁通常决定调用一个工具？**
**A：** 模型（加上主机的政策闸口）；工具是模型控制的动作。

**Q3. 谁通常选取提示模板？**
**A：** 用户（用户控制的原语），通常通过 UI。

**Q4. 直接资源对上模板资源？**
**A：** 直接 = 固定 URI；模板 = 带参数的 URI 模式，由客户端填入。

**Q5. 为什么用 Python SDK 装饰器？**
**A：** 从类型／Field 描述推导工具 schema，而不是亲手维护原始 JSON schema。

**Q6. MCP Inspector 是做什么的？**
**A：** 浏览器测试／调试服务器工具／资源，再接到完整主机集成。

**Q7. 说出两种传输层，并各给一个使用情境。**
**A：** STDIO 给本机子进程服务器；Streamable HTTP（或 HTTP／SSE 家族）给远程服务器。

**Q8. 这门入门课之后下一步去哪里？**
**A：** [MCP Advanced Topics](https://academy.claude.com/courses/model-context-protocol-advanced-topics)，学采样、进度／roots，以及生产环境传输层／扩展细节。

**Q9. MCP 在数学上减少了什么问题？**
**A：** 把 M×N 定制集成，收敛成 M 个主机＋N 台专门服务器。

**Q10. MCP 的两层是什么？**
**A：** 数据层（JSON-RPC 语义／原语）与传输层（STDIO／HTTP）。

**Q11. 一般的 tools/list 调用之前必须发生什么？**
**A：** 传输层连接＋initialize 能力协商（＋ initialized 信号）。

**Q12. GitHub MCP 服务器的后端 API 密钥由谁拥有？**
**A：** 通常是服务器（或其密钥存储）——不是每个主机都把 token 写死。

**Q13. 客户端该如何响应 tools/list_changed？**
**A：** 刷新工具清单，并更新模型可以调用的东西。

**Q14. 资源还是工具：「为上下文抓取 schema」？**
**A：** 资源（以读取为导向、应用程序控制的注入）。

**Q15. 资源还是工具：「插入一列」？**
**A：** 工具（副作用／动作）。

**Q16. 为什么 STDIO 服务器要保持 stdout 干净？**
**A：** 协议消息走 stdio——日志噪音会破坏讯框处理；日志改走 stderr。

**Q17. 什么是上下文注入？**
**A：** 主机读取资源（或其他数据），并刻意把它们附到模型请求里。

**Q18. MCP UI 里的自动完成／探索是什么？**
**A：** 列出工具／资源／提示，让用户／主机不必写死就能挑选能力。

**Q19. MCP 有取代 Claude 的 tool_result 循环吗？**
**A：** 没有。主机仍然要把工具结果喂回模型对话。

**Q20. 说出一个客户端暴露的进阶原语。**
**A：** 采样、询问请求，或日志（入门：只要有意识）。

**Q21. 好的工具粒度规则是什么？**
**A：** 窄而可组合、schema 清楚的工具，胜过一个巨型工具。

**Q22. 为什么 Field 描述重要？**
**A：** 它们变成模型面对参数的指引——工具的提示工程。

**Q23. 「本机 = 安全」的安全错误是什么？**
**A：** STDIO 服务器以用户权限执行，仍然可以外泄或删除数据。

**Q24. 提示如何帮助团队？**
**A：** 跨主机共享审过的指示模板，而不是每个用户自己重发明措辞。

**Q25. 经典的 MIME 相关错误是什么？**
**A：** 把 text/plain 资源当 JSON 解析（或完全忽略内容类型）。

**Q26. 凭记忆画：4 台服务器要几个客户端？**
**A：** 四个客户端（一对一），由一个主机管理。

**Q27. 这里的「与传输层无关」是什么意思？**
**A：** 同一套数据层方法可以跑在不同传输层上。

**Q28. 通知缺少请求所具备的什么？**
**A：** 一个 `id`／预期的响应。

**Q29. 什么时候普通内嵌工具比 MCP 更好？**
**A：** 单一应用程序原型、少数稳定函数、没有重用需求。

**Q30. 新服务器行为异常时，你第一个用的工具是什么？**
**A：** MCP Inspector（列出／调用／检查载荷），再接到完整主机集成。

1. **凭记忆草图：** 主机／客户端／服务器，接上两台服务器；标出哪一跳是一对一。
2. **原语分类：** 给一份清单，如「加载 README」、「创建 issue」、「套用 ADR 模板」，把每一项标成资源、工具或提示。

10. **桥接操练：** 用四句话解释 MCP 的 `tools/call` 如何在主机内部变成 Claude 的 `tool_use`／`tool_result` 来回。

## S1. MCP 工具的结构化错误响应（任务 2.2）

**`isError` 标志**是 MCP 把工具失败传达回 agent 的机制，而且是*包在一次成功的协议响应里*：`tools/call` 结果带着 `isError: true`，错误细节放在 `content`，这样**模型**才能读到失败并推理如何恢复。（协议层的 JSON-RPC 错误是给格式错误的调用；*工具领域*的失败则以一般结果加上 `isError: true` 发送。）

**为什么泛用错误会失败：** 一律回 `"Operation failed"`，agent 就没有依据在重试、替代做法、上报，或问用户之间做选择。对永久错误浪费重试、对可恢复错误却放弃，都源自非结构化错误。

**考试使用的错误分类法（背这四类）：**

| 类别 | 例子 | 可重试？ | Agent 的正确动作 |
| --- | --- | --- | --- |
| **暂时性（Transient）** | 超时、服务不可用 | 是 | 重试（带退避） |
| **验证（Validation）** | 输入格式错误、坏的 ID 格式 | 否（原样） | 先修正输入，再重试 |
| **业务（Business）** | 政策违反（退款上限） | **否** | 向用户解释／替代工作流程 |
| **权限（Permission）** | 调用者缺少访问权 | 否 | 上报／改走不同凭证路径 |

**结构化错误元数据模式：** 回传 `errorCategory`（`transient`／`validation`／`permission`／business）、一个 **`isRetryable` 布尔值**，以及一份**人类可读的描述**。对业务规则违反，把可重试设成 **false**，并附上 agent 可以转述的**对客户友善说明**（「超过 500 美元的退款需要主管核准」）——agent 接着沟通，而不是猛打重试。

**多 agent 链接（领域 5.3）：** 子代理在本地恢复**暂时性**失败；只有无法解决的错误才传到协调者，并带上尝试过什么与部分结果。而且要保持**访问失败 ≠ 有效的空结果**：空结果集是*成功的*查询、零条匹配，永远不要 `isError: true`。

## S2. Claude Code 里的 MCP 服务器：范围与设置（任务 2.4）

**两个范围，一个考试区分：**

| 文件 | 范围 | 共享？ | 用于 |
| --- | --- | --- | --- |
| **`.mcp.json`**（项目根目录） | 项目 | 是——提交进版本控制；每个队友 clone／pull 就拿到 | 共享的团队工具（团队的 Jira／GitHub／数据库服务器） |
| **`~/.claude.json`** | 用户 | 否——只在个人机器上 | 你在试用的个人／实验服务器 |

**`.mcp.json` 里的环境变量展开**——例如 env／标头值里的 `${GITHUB_TOKEN}`——让团队可以提交服务器*配置*，同时每位成员从自己的**环境提供凭证**。考试框架：如何共享配置**又不提交密钥**？→ 项目范围 `.mcp.json` 里的环境变量展开。

**探索模型：** 来自**所有已配置 MCP 服务器的工具，在连接当下被发现，并同时对 agent 可用**——项目服务器与个人服务器共存于同一个会话（官方准备练习 2 就是要你核实这一点）。

**MCP 资源作为内容目录：** 把 issue 摘要、文档层级或数据库 schema 暴露成**资源**，让 agent *看见有哪些数据存在*，而不必把轮次烧在探索性工具调用上。目录 = 资源；动作 = 工具（与上方第 7–9 节的三原语一致）。

**另外两项 2.4 技能：**

- **与内置工具的描述竞争：** 若你的 MCP 工具描述很薄，agent 可能偏好内置工具（如 Grep）而不是你那个更有能力的服务器工具。修复方法是**丰富 MCP 工具描述**，写出它的能力与输出——描述质量驱动采用，不只是在相似工具之间做选择。
- **社区对上自定义服务器：** 标准集成（例如 Jira）优先用既有的社区 MCP 服务器；把自定义服务器留给团队专属工作流程。（部署／托管 MCP 服务器基础设施对考试**明确超出范围**。）

## S3. 内置工具：选择标准（任务 2.5）

考试点名的 agent 端工具箱——知道每个工具的*选择标准*：

| 工具 | 何时选用…… | 典型例子 |
| --- | --- | --- |
| **Grep** | 在文件**内容**里搜索模式 | 找出函数的所有调用者；定位错误消息；找 import 语句 |
| **Glob** | 依模式匹配文件**路径／名称** | `**/*.test.tsx`——依命名惯例找所有测试文件 |
| **Read** | 加载文件全文 | 跟着 Grep 找到的 import 走 |
| **Write** | 写入完整文件 | 当 Edit 无法锚定时，与 Read 搭配 |
| **Edit** | **通过唯一文本匹配做针对性修改** | 替换一个函数本体 |
| **Bash** | 执行命令（测试、构建、git） | 执行测试套件 |

**Edit 失败模式（会考）：** Edit 要求锚点文本**唯一**符合。当它因非唯一匹配而失败时，回退是**Read 全文，再 Write 修改后的版本**——不是用更长的锚点反复尝试 Edit。

**渐进式探索模式（会考）：** **渐进地**创建对代码库的理解——先 Grep 进入点，再 Read 跟着 import 走并追踪流程——而不是一开始就把所有文件读完（上下文膨胀；见领域 5.4）。跨包装器模块追踪用法：先找出所有导出名称，再在代码库里搜索每个名称。

## S4. 补充问答

**SQ1.** MCP 工具如何告诉 agent 它失败了？
**A.** 工具结果上的 `isError: true`，细节放在 content——领域失败以可读结果发送，不是协议错误，这样模型才能推理如何恢复。

**SQ2.** 说出四种错误类别，以及哪一种可重试。
**A.** 暂时性（可重试）、验证（先修正输入）、业务（不可重试——向用户解释）、权限（不可重试——上报／凭证）。

**SQ3.** 哪三个字段让错误响应成为「结构化」？
**A.** `errorCategory`、`isRetryable` 布尔值、人类可读描述（业务违反再加对客户友善的说明）。

**SQ4.** 为什么一律 `"Operation failed"` 的响应会伤害 agent？
**A.** 它们拿掉恢复决策的依据——导致对永久错误浪费重试、对可恢复错误却放弃。

**SQ5.** 共享的团队 MCP 服务器放哪里？个人实验呢？
**A.** 项目范围 `.mcp.json`（纳入版本控制）；用户范围 `~/.claude.json`。

**SQ6.** 如何提交 MCP 配置而不提交 token？
**A.** `.mcp.json` 里的环境变量展开（例如 `${GITHUB_TOKEN}`）——每位成员经由自己的环境提供凭证。

**SQ7.** 来自多台服务器的 MCP 工具何时可用？
**A.** 在连接当下被发现；所有已配置服务器的工具同时可用。

**SQ8.** Agent 一直做探索性调用，想知道有哪些数据。MCP 修复方法？
**A.** 把内容目录（issue 摘要、文档层级、schema）暴露成**资源**。

**SQ9.** Agent 偏好内置 Grep，而不是你那个更有能力的 MCP 搜索工具。修复方法？
**A.** 丰富 MCP 工具的描述，写出能力与输出——描述驱动采用。

**SQ10.** Grep 对上 Glob，一句话？
**A.** Grep 在文件*内容*里搜索模式；Glob 匹配文件*路径／名称*。

**SQ11.** Edit 一直因非唯一匹配而失败。回退？
**A.** Read 全文，再 Write 修改后的版本。

**SQ12.** 创建对大型代码库理解的正确方式？
**A.** 渐进地：Grep 进入点 → Read 跟着 import／追踪流程——不是一开始全读。

**SQ13.** 子代理的搜索超时一次，重试后成功。协调者收到什么？
**A.** 什么都没有——暂时性失败在本地恢复；只有无法解决的错误才往上传（带尝试与部分结果）。

**SQ14.** 空搜索结果：`isError: true` 还是不要？
**A.** 不要——有效的空结果是成功查询、零条匹配；把它标成错误会破坏重试逻辑。
