## 关键概念（速查表）

| 概念 | 记住 |
|------|----------|
| Messages API | 对话回合，角色为 `user`／`assistant`；messages 里**没有** `system` 角色 — 用顶层 `system` |
| 验证 | API 密钥经环境变量／密钥存放处；送出必填版本标头；绝不提交密钥 |
| `max_tokens` | 生成 token 的必填上限；截断 vs 完整答案 |
| Temperature | 较高 → 较多样；较低 → 较确定性；与评测配对 |
| 流式 | 服务器推送事件（SSE）事件流；组装增量；工具的 `input_json_delta` 需特别处理 |
| 停止原因 | `end_turn`、`max_tokens`、`tool_use`、`stop_sequence`、`pause_turn`、`refusal` — 各需不同下一步 |
| 工具 | 模型发出 `tool_use`；你的应用执行工具；下一回合回传 `tool_result` |
| 平行工具 | 一个助理回合可有多个 `tool_use` 区块；依每个 id 回传一个结果 |
| 结构化输出 | 受 schema 约束的 JSON（及／或严格工具），用于可靠管线 |
| RAG | 检索相关切块 → 注入上下文 → 带引用来源／锚定生成 |
| 提示词缓存 | 缓存稳定前缀（工具 → 系统 → 消息）以降低延迟／成本 |
| 批量 | 异步 Message Batches，用于大型脱机工作；相对同步通常有折扣 |
| Agent | 工作流程 vs 自由型 agent；平行／串接／路由模式 |
| MCP | 跨主机标准化工具／资源／提示（见配套 MCP 笔记） |

> **时效注记（2026-08）：** (1) *Temperature* — 采样旋钮（`temperature`／`top_p`／`top_k`）在**现行前沿模型上已移除**（Opus 4.7+、Opus 5、Sonnet 5、Fable 5 会回 400）；在 4.6 及更旧模型上仍有效。确定性建议改靠 schema／结构化输出。(2) *System 角色* — 「`messages` 里没有 `system` 角色」仍是基础考试答案，但最新 Opus／Fable 层级模型确实接受附加到 `messages` 的**对话中途** `{"role": "system"}` 消息（对缓存友好的操作者信道）；`messages[0]` 仍然不能是这种消息。

## 依主题的深入笔记

### 1. 用 API 访问 Claude

#### 身份验证与设置

- 在 Anthropic Console 创建 API 密钥；存在环境变量或密钥管理器（`ANTHROPIC_API_KEY`），绝不放进版本控制或客户端应用。
- 可能时用官方 SDK（Python／TypeScript）：它们处理标头、重试与流式辅助。
- HTTP 客户端必须送出 API 密钥与 API 版本标头（常见为 `anthropic-version`）。把版本标头当成契约的一部分：错误／缺失会大声失败。
- 典型请求字段：`model`、`max_tokens`、`messages`，可选 `system`、`temperature`、`tools`、`stream`、`tool_choice`、缓存控制、思考设置等。
- 依能力对上成本／延迟选模型。对认证准备：知道*为什么*分类或路由会挑更快／更便宜的模型，困难推理或工具编排会挑更强的模型。
- **服务器端 vs 客户端密钥：** 浏览器应用绝对不能持有长效 API 密钥。把对 Claude 的调用放在你的后端后面。

**原创范例 — 最小心智请求形状**

```text
POST /v1/messages
Headers: x-api-key, anthropic-version, content-type: application/json
Body: {
 model: "<current-model-id>",
 max_tokens: 1024,
 system: "You are a careful support triage bot. Reply in JSON.",
 messages: [
 { role: "user", content: "Order #4421 never arrived." }
 ]
}
```

#### 模型与选择启发式

| 工作负载 | 优先选 | 为什么 |
|----------|--------|-----|
| 意图路由／便宜分类 | 较小／较快的模型 | 量大、歧义低 |
| 困难推理、长工具链 | 更强的模型 | 工具犯错较少、规划较好 |
| 批量脱机标注 | 够强 + Batches API | 成本 + 吞吐量 |
| 交互式 UI 聊天 | 中／强 + 流式 | 感知延迟 + 质量 |

考试陷阱：「永远用最大的模型。」正确答案是依任务**调整规模**，并用评测衡量。

#### 消息与多回合上下文

- 每则消息有 `role` 与 `content`（字符串或内容区块）。
- 用户／助理回合交替。你的应用拥有历史：修剪、摘要或丢掉旧回合，以待在上下文限制内。
- 内容可以是多模态：文本加上影像或 API 支持的文档输入。
- 陷阱：把「系统」消息塞进 `messages` 并把角色设成 `system` — Messages API 期望的是顶层 `system` 参数。*（时效注记：最新 Opus／Fable 层级模型接受附加到 `messages` 的对话中途系统消息；考试层级规则——系统指示放顶层 `system`——仍然成立。）*
- 工具之后继续时，附加完整助理回合（含 `tool_use` 区块），以及一则放 `tool_result` 区块的用户回合。不要发明假的助理文本来代替工具结果。

**历史卫生模式**

1. **滑动窗口：** 保留最近 N 个回合；丢掉更旧的用户／助理配对。
2. **摘要并替换：** 定期把早期回合换成精简摘要消息。
3. **钉住关键事实：** 把持久政策放进 `system`；把会话事实放进短的钉住用户／助理前言。
4. **只要仍需可审计性，就绝不默默改写工具逐字稿**——即使为模型做了摘要，也把原始工具日志存在脱机处。

#### 系统提示词

- 系统文本设置角色、规则、输出格式、安全边界与工具使用政策。
- 使用提示词缓存时让系统提示词保持稳定；把易变的用户数据放进用户消息。
- 宁可给明确指示（「永远回传符合 schema X 的 JSON」）也不要模糊感觉（「请帮帮忙」）。
- 用标过名的区段组织长系统提示词（XML 风格标签是常见模式）：`<role>`、`<rules>`、`<output_format>`、`<examples>`。
- 工具政策也属于这里：何时调用工具、何时问用户、何时拒绝。

#### Temperature、max_tokens 与输出控制

- Temperature（及相关采样旋钮）在创意与一致性之间取舍 — **在它们仍然存在的模型上**。现行前沿模型（Opus 4.7+、Opus 5、Sonnet 5、Fable 5）已**移除** `temperature`／`top_p`／`top_k`（送出会回 400）；在 4.6 及更旧模型上仍有效。
- 对评分、萃取与工具参数生成，优先把 **schema／结构化输出**当主要一致性杠杆（较低 temperature 只在支持它的旧模型上再用）。
- 务必用心设置 `max_tokens`：太低会在 JSON 中途截断；太高且你不需要长答案时会浪费预算。
- `max_tokens` 是**上限**，不是目标。模型常较早以 `end_turn` 停止。
- 自定义 `stop_sequences` 可在哨兵字符串上停下生成；此时 `stop_reason` 变成 `stop_sequence`。少用——结构化工作通常 schema 胜过脆弱的停止字符串。

#### 流式（服务器推送事件，简称 SSE）

- 设 `stream: true` 以在模型生成时接收服务器推送事件。
- 典型事件流：`message_start` →（`content_block_start` → 增量 → `content_block_stop`）* → `message_delta` → `message_stop`（加上适用的 `ping`／`error` 事件）。
- 对 UX：立刻渲染文本增量；把工具 JSON 缓冲到区块完成（或小心遵循细粒度工具流式规则）。
- 考试提示：流式**不改变**最终语义结果；它改变交付方式以及你如何组装消息。
- 工具流式细节：`tool_use` 区块常以空的 `input: {}` 开始；参数以 `input_json_delta`／`partial_json` 片段到达。把片段串接起来，然后在 `content_block_stop` 之后解析。
- 思考流式（若启用）可能在思考区块关闭前发出 `thinking_delta` 与 `signature_delta`——把签名当完整性元数据，不是给用户看的叙述文字。
- SDK 通常提供辅助（`text_stream`、`get_final_message`／`finalMessage`），除非你在建裸 HTTP 客户端，否则不必手解 SSE。
- 优雅处理未知事件类型（版本可能添加事件）。

#### 停止原因（必记表）

| `stop_reason` | 意义 | 典型下一步 |
|---------------|---------|---------------------|
| `end_turn` | 自然完成 | 显示／使用回复 |
| `max_tokens` | 撞上你的输出上限 | 提高 `max_tokens` 或继续生成 |
| `tool_use` | 模型要客户端工具 | 执行工具；送出 `tool_result` |
| `stop_sequence` | 撞上你的自订停止字符串 | 处理哨兵；可能继续 |
| `pause_turn` | 服务器端循环暂停（例如长服务器工具／思考） | 依文档继续回合（常重送助理内容） |
| `refusal` | 政策拒绝 | 安全浮出；不要用同一提示盲目重试 |

考试陷阱：把每个未完成答案都当模型失败。先查 `stop_reason` 与 `usage`。

#### 结构化输出

- 用受 schema 约束的 JSON，让下游代码不必靠脆弱正则表达式解析。
- 严格工具 schema 同样减少无效工具参数。
- 把结构化输出与评测结合：断言形状*以及*语义正确。
- 可用时优先用官方结构化输出／JSON schema 功能，而不是只靠「请用 JSON 回复」。
- 若 schema 在正式环境失败：记录原始文本，关键路径解析失败即关闭，只有安全时才回退到修复提示。

#### 错误、重试与速率限制

- 预期 HTTP 类失败：验证（401）、错误请求（400）、找不到（404）、速率限制（429）、过载／容量（例如 529 类）、5xx。
- 遇到 429：有 `retry-after` 就遵守；用指数退避 + 抖动；多租户时隔离每租户预算。
- 区分**请求速率** vs **token 速率**限制（每分钟请求数（RPM） vs 每分钟输入／输出 token）。「小型」聊天应用仍可能用巨大 RAG 上下文炸掉每分钟输入 token（ITPM）。
- 幂等心态：重试不得让副作用双重计费——让工具执行幂等，或依 tool_use id 去重。
- 流式错误可能在流式中途以 SSE `error` 事件到达；你的客户端必须干净中止，并决定是否恢复。

#### Message Batches（异步规模）

- Message Batches API 异步提交许多 Messages 风格请求——适合脱机评测集、大量分类、隔夜富化。
- 同样 token 通常比同步 Messages 便宜；结果稍后获取（不是即时聊天 UX）。
- 每笔需要 `custom_id`，才能把结果接回来源列。
- 仍受批量特定速率／队列限制；未及时处理的请求可能过期（文档提到长外层窗口，例如约 24h 处理边界——考试前核对现行数字）。
- 功能对等范围广（工具、视觉、缓存常支持），但在批量内用 `max_tokens: 0` **预热缓存**并不合适，因为短暂缓存可能在后续跑之前就过期。
- 设计模式：交互用户走同步路径；回填与评测扫描走批量路径。

### 2. 提示工程与评测

**考试会出现的技巧**

- **清楚指令：** 说要做什么、不要做什么，以及输出契约。
- **XML／标签区段：** 把指示、上下文、范例与用户输入分开，让模型能把注意力放在对的区块。
- **Few-shot（少样本）范例：** 展示符合期望风格与边界案例的输入→输出配对。
- **思维链（适当时）：** 对困难问题要求有推理步骤；对结构化萃取，优先用 schema 而不是开放漫谈。
- **角色提示：** 把专业与限制放进 `system`。
- **分隔符卫生：** 绝不把不可信的用户文本在没有清楚边界的情况下接到指示旁边——降低指示注入风险。

**原创迷你模式（仅供研读）**

```text
system:
 <role>You extract invoice fields.</role>
 <rules>If a field is missing, use null. Never invent tax IDs.</rules>
 <output>JSON object with keys vendor, total, currency, due_date.</output>

user:
 <document>
... raw OCR text...
 </document>
```

**评测心态**

- 正式环境不要「用眼睛看」提示词。建一小份案例数据集（快乐路径、边界、对抗性）。
- 自动化评分：精确比对、评分量规分数，或带固定评分量规的模型当裁判。
- 迭代：一次只改一个提示变量；追踪回归。
- 产生合成测试案例，再人工抽查真实性。
- 把**提示回归**与**模型版本**回归分开——评测执行钉住 model id。
- 质量之外也追踪成本与延迟；质量提升 2% 却让 token 变成三倍，可能是产品损失。

**评测循环（记住）**

1. 把任务成功准则写下来。
2. 收集 30–200 笔已标注案例（从小开始）。
3. 冻结评分者（脚本或评分量规）。
4. 跑基准线 → 改一件事 → 比较。
5. 只有质量↑且成本／延迟可接受才晋升。

### 3. 用 Claude 做工具使用

**核心循环**

1. 送出用户消息 + 工具定义（`name`、`description`、JSON `input_schema`）。
2. 模型可能回传一个或多个 `tool_use` 区块（id、name、input）。
3. 你的应用执行工具（并强制授权！）。
4. 附加绑到每个 `tool_use` id 的 `tool_result` 区块；继续对话直到模型用纯文本回答（或再调用更多工具）。

**设计提示**

- 描述是提示词的一部分：精确说明何时调用工具、每个字段是什么意思。
- 宁可要许多小型、可组合的工具，也不要一个参数含糊的巨型工具。
- 处理平行／批量工具调用：安全执行（幂等、超时、部分失败）。
- 内置／服务器工具（例如网页搜索、代码执行、依产品接口而异的电脑操作变体）与客户端执行的工具不同：知道哪一边跑代码。
- `tool_choice` 可以轻推或强制工具使用（`auto`／`any`／指定工具／none——在现行文档确认确切枚举）。
- 对严格参数有效性，有提供时启用 schema 严格工具模式。

**平行工具检查清单**

- 一则助理消息可含多个 `tool_use` 区块。
- 在下一则用户消息为每个 id 回传**一个** `tool_result`（可以是同一则用户消息的内容数组）。
- 失败：仍回传带错误负载的结果，让模型能恢复——不要省略 id。
- 并行：只平行化可以安全一起跑的工具（没有冲突写入）。

**客户端工具 vs 服务器工具**

| 种类 | 谁执行？ | 你的工作 |
|------|---------------|----------|
| 客户端工具 | 你的应用／MCP 服务器／后端 | 跑函数；送出 `tool_result` |
| 服务器工具 | Anthropic 基础设施 | 常在流式中以服务器工具使用 + 结果区块出现；你仍可能需要在 `pause_turn` 上继续 |

**常见失败**

- 忘了为每个 `tool_use` id 回传结果。
- 执行用户无权跑的工具。
- 上下文紧时把巨大原始工具转储不加摘要就喂回去。
- 把幻觉出来的工具名称当真实——对照你的注册表验证。
- 在 `content_block_stop` 之前解析中途的部分 JSON。
- 没有最大迭代／预算护栏的无限工具循环。

**原创范例 — 天气工具往返（概念）**

```text
Assistant content:
 [tool_use id=toolu_1 name=get_weather input={location:"Singapore"}]

Your next user content:
 [tool_result tool_use_id=toolu_1 content="31°C, thunderstorms"]

Then model produces end_turn text for the user.
```

### 4. RAG 与 agentic 搜索

**为什么要 RAG：** 上下文窗口有限；私有语料会变；你要带来源的锚定答案。

**管线积木**

- **切块：** 依大小／结构（标题、段落）切文档；重叠有助连续性。
- **矢量嵌入 + 矢量搜索：** 模糊查询的语义相似度。
- **BM25／词汇搜索：** 对精确词、ID、罕见 token 很强。
- **混合检索：** 结合词汇 + 稠密；常再加**重排序**。
- **上下文化检索：** 用文档层上下文丰富切块，让检索较少歧义。
- **多索引：** 依语料或模态分开索引；路由查询。

**注入模式**

```text
system: Answer ONLY using <sources>. If missing, say you don't know.
user:
 <question>...</question>
 <sources>
 [1]...chunk...
 [2]...chunk...
 </sources>
```

**Agentic 搜索模式**

- 不是一次检索→回答，而是让模型（或规划器）发出后续搜索、精炼查询，证据够了再停。
- 永远保留引用轨迹：哪些切块 ID 支撑哪些主张。
- 为循环设预算：最大搜索次数、最大 token、最大墙钟时间。

**评测拆分（考试常考）**

| 层 | 指标构想 |
|-------|----------------|
| 检索 | Recall@k、MRR、引用命中率 |
| 生成 | 忠实度、答案正确性、格式有效性 |
| 系统 | 延迟 p95、每次查询成本、工具错误率 |

**陷阱**

- 切块太大（噪声）或太小（意义流失）。
- 检索到相关文本，却埋在弱提示下（「若有帮助请用上下文」）。
- 不把检索命中率与生成质量分开评测。
- 在 CMS 更新文档却忘了重新索引。
- 让模型引用未检索到的来源（幻觉引用来源）。

### 5. Claude 延伸功能

- **扩展思考／推理模式：** 对困难多步骤问题有用；理解成本／延迟取舍，以及依 API 接口，思考内容可能与最终答案可分离。
- **影像与 PDF：** 以内容区块传入；要求结构化萃取；留意大型文档的 token／成本意涵。
- **视觉输入：** 常见来源类型含 base64、URL 或 Files API 参照；媒体类型通常含 jpeg／png／gif／webp——确认现行限制。
- **文档／PDF：** 重复分析时优先经 Files API 上传一次并以 id 参照；页数限制与 token 成本对考试「规模下什么会坏？」很重要。
- **引用来源：** 可用时，优先能把引文锚到来源跨度的功能，以做出可信 UX。
- **提示词缓存：** 标记稳定前缀；衡量缓存命中率；不要把每请求机密或唯一 ID 放进会破坏重用的缓存前缀。

#### 提示词缓存 — 操作细节

- 要记住的可缓存前缀顺序：**工具 → 系统 → 消息**（以及到缓存断点为止的纳入内容区块）。
- 把 `cache_control` 放在你期望重用的**最后一个共享区块**——不要放在会让缓存键变差的唯一占位用户消息上。
- 监控用量字段，例如缓存创建 vs 缓存读取 token（回应里名称如 `cache_creation_input_tokens`／`cache_read_input_tokens`）。
- TTL／短暂行为：知道缓存条目会过期；高翻搅前缀会在重复写入上浪费钱。
- 某些形式存在预热（含用 `max_tokens: 0` 填缓存的模式）——只有后续流量很快会命中时才用。

#### 文件、视觉与文档 — 设计检查清单

1. 质量允许时，上传前先缩放／压缩巨大影像。
2. 宁可要文件 id，也不要反复运送百万字节的 base64 负载。
3. 对 PDF：版面简单时抽文本；版面重要时走文档／视觉路径。
4. 建审计轨迹时要求结构化字段 + 页码参照。
5. 屏幕截图进日志或提示词之前先屏蔽机密。

### 6. MCP（课程模块 — 高阶）

这门 API 课也涵盖建 MCP 服务器／客户端，让工具与资源可跨主机重用。要深入，读专用 MCP 笔记（`04-introduction-to-mcp.md`）。考试相关对应：

- 主机应用 ↔ MCP 客户端 ↔ MCP 服务器。
- 原语：**工具**（动作）、**资源**（只读数据）、**提示**（可重用指示模板）。
- 许多应用需要同一套集成时优先用 MCP；一次性原型优先用内嵌工具。
- 生命周期：初始化／协商能力 → 列出原语 → 调用工具／读资源 → 干净关闭。
- 安全：用户同意、最小权限，以及清楚边界，即使工具经 MCP 到达而不是写死的 JSON schema，仍然适用。

### 7. Anthropic 应用：Claude Code 与 Computer Use

- **Claude Code：** 终端／IDE 里的 agentic 编程助理；加速存储库任务；常集成 MCP 做项目工具。
- **Computer Use：** 模型驱动的 UI 自动化（屏幕截图 + 动作）；强大且有风险 — 沙箱、最小权限、敏感步骤要人类核准。
- 认证框架：知道*用例*与*安全边界*，不是产品营销文案。
- 对应到 API 知识：Computer Use 是工具使用 + 视觉的极端形式；Claude Code 是带权限、hooks 与 MCP connectors 的 agent 主机。

### 8. Agent 与工作流程

**工作流程 vs agent**

- **工作流程：** 你定义图（步骤、分支）；模型填节点。确定性控制，较易测试。
- **Agent：** 模型用工具决定下一步，直到停止条件。弹性，较难评测。

**核心模式**

- **平行化：** 把独立子任务扇出；合并结果。
- **串接：** 步骤 N 的输出成为 N+1 的输入（萃取 → 转换 → 验证）。
- **路由：** 分类意图，再送到专门提示／模型／工具路径。
- **调试：** 记录每次工具调用、中间状态、token 用量；加超时与最大迭代上限，防止失控循环。

**对照表**

| 模式 | 控制 | 最适合 | 失败模式 |
|---------|---------|----------|--------------|
| 串接 | 高 | 像提取、转换、加载（ETL）的 LLM 步骤 | 没有验证器时错误串联 |
| 平行 | 中 | Map-reduce 风格任务 | 合并冲突／不一致 schema |
| 路由 | 高 | 多领域助理 | 误路由 → 错的专家 |
| 自由 agent | 低 | 开放式研究 | 循环、支出暴增、审计困难 |

**正式环境护栏（考试写这些）**

1. 最大工具迭代／最大墙钟。
2. 每工具授权与允许清单。
3. 不可逆动作要人类核准。
4. 结构化日志（request id、tool id、token、stop_reason）。
5. 失败工具副作用的死信队列。
6. 启用新工具前先有评测套件。

**原创路由草图**

```text
User message
 → cheap classifier (billing | technical | cancel)
 → billing prompt + CRM tools
 → technical prompt + docs RAG
 → cancel workflow (deterministic steps + confirmation)
```

### 9. 端到端请求解剖（研读图）

分层想，考试情境才不会糊成一团：

1. **传输／验证层** — HTTPS、API 密钥、版本标头、可选 beta header。
2. **采样层** — model id、temperature、`max_tokens`、停止序列、思考设置。
3. **上下文层** — `system`、先前 `messages`、检索到的 RAG 切块、影像／文件。
4. **能力层** — `tools`／MCP 发现的工具、`tool_choice`、结构化输出 schema。
5. **交付层** — `stream` 开／关；客户端事件组装；超时。
6. **控制平面层** — 你的重试、速率限制预算、agent 迭代上限、授权。

若有东西失败，先定位层。客户端解析错误不是「模型质量」问题；没有结果的 `tool_use` 不是 temperature 问题。

### 10. 值得记住的多回合对话模式

**A. 纯对话**
用户 → 助理（`end_turn`）→ 用户 → …

**B. 工具中断的回合**
用户 → 助理（`tool_use`）→ 用户（`tool_result`）→ 助理（`end_turn` 或更多工具）

**C. 平行工具**
用户 → 助理（`tool_use` A + `tool_use` B）→ 用户（`tool_result` A + `tool_result` B）→ …

**D. RAG 增强回合**
检索器（用户查询）→ 用户（问题 + 来源）→ 助理锚定答案

**E. 路由工作流程**
分类器 → 分支特定的系统／工具集 → 专门答案

**F. 批量脱机**
把 N 笔独立 Messages 参数入队列 → 依 `custom_id` 轮询／获取结果

原创练习提示：给一份错误报告（「助理问了天气却从未回答」），对到模式 B，再问哪一跳坏了（模型没调用工具／应用没执行／应用没回传结果／第二次模型调用缺失）。

### 11. 提示词缓存实作范例（概念）

假设每张客服工单共享：

- 同一套 3 个工具（CRM 查询、退款计算器、政策搜索），
- 同一份 2,000 token 的政策系统提示词，
- 但工单本文唯一。

**好：** 缓存工具 + 系统（也许再加一份静态政策资源）。只把工单文本放在中断点之后、会变的用户消息里。

**差：** 把 `Ticket #{{id}}` 放进被缓存的系统字符串——每张工单写一个新前缀。

**衡量习惯：** 记录缓存写入 token vs 缓存读取 token。功能「有用缓存」但读取接近零，是表演。

**失效直觉：** 改工具 schema、系统文本、思考／effort 设置，或中断点位置，可能错过先前的缓存条目。想命中的请求之间，让被缓存的字节保持字节稳定。

### 12. 结构化输出与工具 — 选契约

| 需求 | 优先选 | 注记 |
|------|--------|-------|
| 最终答案必须是可解析 JSON | 结构化输出／JSON schema 模式 | 最适合给客户的 API 回复 |
| 模型必须调用你的函数 | 工具 + input_schema（+ 有则严格） | 最适合副作用 |
| 两者都要 | 动作用工具 + 结构化最终文本／schema | 常见 agent 模式 |
| 只要软格式 | 提示指示 | 脆弱；只用于原型 |

考试陷阱：「工具只用于副作用，从不用于 JSON。」历史上，工具*也被*用来强制 JSON 形状；现代结构化输出功能对最终答案可能更干净——两种故事都要知道，并查现行文档。

### 13. 速率限制、错误与韧性 playbook（操作手册）

**为失败分类**

| 信号 | 可能类别 | 第一回应 |
|--------|--------------|----------------|
| 401／403 | 验证／权限 | 修密钥／范围；不要盲目重试 |
| 400 | 请求形状／参数 | 修负载；记录主体（已屏蔽） |
| 404 | 路径错／缺资源 | 修端点或文件 id |
| 429 | 速率限制 | 退避；卸载；减少 token |
| 5xx／过载 | 容量 | 带抖动重试；政策允许则回退模型 |
| SSE `error` 事件 | 流式中途失败 | 干净中止 UI；可选恢复策略 |

**韧性模式**

- 每租户 token bucket。
- 交互流量与批量流量分开队列。
- 错误率暴增时用断路器。
- 非关键路径回退到较小模型。
- 工具触发的退款／邮件周围用幂等键。

### 14. RAG 正式环境检查清单（超越快乐路径）

1. **语料治理：** 谁能加文档？个人识别信息（PII）清洗？
2. **切块策略有记录：** 大小、重叠、切分器版本——才能重现索引。
3. **矢量嵌入模型版本钉住。**
4. **混合权重**在已标注查询集上调，不是靠感觉。
5. 提示前**把 top-n 重排序**。
6. **提示强制引用来源**只能来自提供的 id。
7. **检索为空时拒绝。**
8. **时效：** 发布时重新索引；相关时向用户显示文档更新时间。
9. **投毒觉察：** 不可信的用户上传文档可能指示模型——沙箱并标记它们。
10. **成本护栏：** 上限检索 token；不要倾倒整本手册。

### 15. Agent 调试情境（考试风格）

**情境 1 — 支出暴增。** 日志显示每回合 40 次工具调用。修复方法：最大迭代、工具允许清单、昂贵工具要求先计划再行动。

**情境 2 — 不稳定的 JSON。** 对象中途 `stop_reason=max_tokens`。修复方法：提高上限、缩小 schema，或继续；写入数据库前验证。

**情境 3 — 选错工具。** 描述重叠（「search」vs「search_users」）。修复方法：改名、收窄描述、加「何时不要用」注记、减少工具数量。

**情境 4 — 锚定落空。** 答案听起来自信却没有来源。修复方法：检索评测；加强「只用来源」系统规则；可用则加引用来源功能。

**情境 5 — 缓存从不命中。** 中断点在唯一用户回合上。修复方法：把中断点移到共享系统／工具。

### 16. API 建造者的安全与合规注记

- 把提示词 + 工具结果当**数据存放处**：它们可能含机密；清洗日志。
- 把**模型信任**与**工具信任**分开：即使模型要求 `delete_all_users`，你的授权层也必须拒绝。
- 经检索文档或网络工具结果的提示注入是真的——不可逆动作优先用允许清单工具与确认。
- 对 Computer Use／浏览器工具：专用 VM、没有正式环境凭证、要求时录制会话供审计。
- 数据保留：知道你的组织是否要求零数据保留选项或区域处理（云端课程另讲 Bedrock／Vertex 落地）。

## 考试提示

1. **Messages vs Completions 心智模型：** Claude 的公开 API 路径以 Messages 为中心；系统在顶层。
2. **工具循环完整性：** 每个 `tool_use` 需要对应的 `tool_result`（或刻意中止策略）。
3. **流式组装：** 文本增量 vs 工具的部分 JSON — 除非你知道它完整，否则不要在流式中途 `json.loads`。
4. **评测胜过感觉：** 预期会考数据集、评分者，以及改提示时的回归。
5. **RAG 是两套系统：** 检索质量与生成质量失败方式不同 — 分开诊断。
6. **缓存与成本：** 知道缓存*什么*（稳定前缀）以及*为什么*（延迟 + 支出）。
7. **安全：** 密钥、工具授权、computer-use 沙箱，以及日志里的 PII，对「这个设计哪里不对？」都是公平考题。
8. **MCP 指引：** 若题目提到跨主机标准化可重用工具，想到 MCP — 不是临时复制 schema。
9. **重试前永远先读 `stop_reason`。**
10. **Batches ≠ 流式聊天。** 产品形态不同。
11. **平行工具：** 对 id，不要只对名称。
12. **速率限制：** 退避 + 抖动；把 RPM 与 token 预算分开。

## 考试陷阱（常见错答）

| 陷阱 | 为什么错 | 较好答案 |
|------|----------------|---------------|
| 把 `role: "system"` 放进 `messages` | Messages API 形状错误 | 顶层 `system` |
| 假设流式改变答案质量 | 交付 ≠ 采样语义 | 同一请求参数 → 同一最终内容意图 |
| 丢掉失败的工具 id | 模型永远等／出错 | 为该 id 回传错误 `tool_result` |
| 把唯一用户问题当前缀缓存 | 毁掉命中率 | 缓存工具／系统／静态文档 |
| 一个巨型工具 `do_anything` | 参数含糊、授权困难 | 小型工具、清楚 schema |
| RAG 只量最终答案准确度 | 掩盖检索失败 | 分开量检索与生成 |
| 没有最大 agent 迭代 | 成本／失控风险 | 硬上限 + 紧急停止开关 |
| 把 API 密钥放进移动应用 | 密钥遭窃 | 后端代理 |

*（第 1 列时效注记：最新 Opus／Fable 层级模型现在接受对话中途 `{"role": "system"}` 消息 — 但「顶层 `system`」仍是基础考试对系统指示该住哪的正确答案。）*

## 自我检核问答

**Q1. 系统指示在 Messages API 放哪里？** 
**A：** 顶层 `system` 参数 — 不是角色为 `system` 的消息。

**Q2. Claude 回传 `tool_use` 区块后，你的应用必须做什么？** 
**A：** 执行已授权工具，然后用对应的 `tool_result` 内容区块（依 tool use id）继续对话。

**Q3. 举一个要流式回复的理由。** 
**A：** 较低的感知延迟／渐进 UI 更新；最终组装的消息应与非流式语义相符。

**Q4. 为什么 RAG 要把 BM25 与矢量嵌入结合？** 
**A：** 词汇搜索抓住精确 token／ID；稠密搜索抓住语义改写；混合 + 重排序常胜过单独任一方。

**Q5. 用一句话说明提示评测工作流程？** 
**A：** 固定测试案例 + 自动评分，让提示变更可衡量、回归可被抓住。

**Q6. 何时确定性工作流程比开放式 agent 更好？** 
**A：** 当步骤已知、合规／可审计性重要，或你需要可靠的服务水平协议（SLA）与更便宜的调试。

**Q7. 提示词缓存前缀该放什么？** 
**A：** 跨请求重用的稳定内容（长系统提示词、工具定义、静态文档）— 不是会毁掉命中率的每用户唯一负载。

**Q8. MCP 与这门 API 课有何关系？** 
**A：** 它标准化主机如何发现并调用外部工具／资源／提示，而不是每个应用重新发明 schema。

**Q9. `stop_reason: "max_tokens"` 意味着什么？** 
**A：** 输出撞上你的上限；提高 `max_tokens` 或继续生成——不要把截断的 JSON 当完整。

**Q10. `input_json_delta` 做什么用？** 
**A：** 流式部分 JSON 片段，在内容区块停止后组装成工具的 `input` 对象。

**Q11. 客户端工具 vs 服务器工具——谁跑代码？** 
**A：** 客户端工具在你的环境跑；服务器工具在 Anthropic 那边跑（你的应用仍可能需要继续回合）。

**Q12. 为什么需要 `max_tokens`？** 
**A：** 它限制生成成本／长度；模型可能较早停，但你永远设天花板。

**Q13. 点名两个速率限制维度。** 
**A：** 每分钟请求与每分钟 token（输入／输出）；429 需要退避。

**Q14. 何时会用 Message Batches？** 
**A：** 大型异步工作（评测、回填），不需要交互延迟，且折扣定价有帮助。

**Q15. 如何处理平行 `tool_use` id？** 
**A：** 执行每个已授权工具，并在后续用户回合为每个 id 回传一个 `tool_result`。

**Q16. 萃取用的安全 temperature 默认是什么？** 
**A：** 在旧模型（4.6 及更早）：低 temperature 加上 schema。现行前沿模型已移除采样参数 — schema／结构化输出**就是**确定性杠杆。

**Q17. 视觉影像应如何提供？** 
**A：** 作为影像内容区块，经支持来源（例如 base64、URL 或 Files API id）——不是假装的文本路径。

**Q18. 上下文化检索想修什么？** 
**A：** 缺文档层上下文的歧义切块，会伤害矢量嵌入匹配质量。

**Q19. 为什么评测要钉住 model id？** 
**A：** 这样提示变更才不会跟默默的模型升级混在一起。

# CCAR-F 领域 4 缺口卡（2026-08-23 添加）

> 精简补充，对准**考试指南任务 4.3／4.4／4.6** 的细节，上文只轻触。对照官方任务陈述的原创综合整理。

## G1. 对抗捏造的 schema 设计（任务 4.3）

- **可空／可选字段防止捏造：** 若来源文档可能缺某个字段，**必填** schema 字段会强迫模型捏造一个值来满足 schema。改成**可选／可空**，模型才能回传 null — 这是考试对「模型捏造值」的标准修复方法。
- **可扩充枚举：** 对歧义案例加 `"unclear"`，对枚举外类别加 `"other"` **外加一个细节字符串字段** — 封闭枚举会强迫误分类。
- **经 tool_use 的严格 schema 只消除*语法*错误** — 从不消除*语义*错误（明细加总对不上所称总额、正确值放错字段）。语义检查是验证层工作（G2）。
- 来源格式会变时，在严格输出 schema 旁边把**格式规范化规则放进提示词**。

## G2. 验证、重试与反馈循环（任务 4.4）

- **带反馈错误重试：** 验证失败时，后续请求包含**原始文档、失败的萃取，以及具体验证错误** — 模型对具名错误自我修正，远胜于光说「再试一次」。
- **重试的限制（会考）：** 重试修**格式／结构**错误；当信息**不在来源里**（或住在你没提供的文档里）时无效。烧掉重试前先诊断你有*哪一类*失败。
- **自我修正流：** 同时萃取 `calculated_total` 与 `stated_total` 以标记差异；对不一致来源数据加 `conflict_detected` 布尔值。
- **`detected_pattern` 字段：** 为每个发现标上触发它的程序构建／模式，让被驳回的发现能系统分析误报模式（喂进 4.1 精确率循环）。

## G3. 多实例与多遍次审查（任务 4.6）

- **自我审查限制：** 产生代码的模型**保留其推理上下文**，不太可能在同一会话质疑自己的决定。「仔细审查你的工作」指示或扩展思考，都不能替代独立性。
- **独立审查实例：** 第二个**没有产生者推理上下文**的 Claude 实例，能抓住自我审查漏掉的细微问题（与文件 05 补充篇的持续集成（CI）会话隔离点成对）。
- **多遍次审查：** 把大型审查拆成**逐文件本地遍次 + 跨文件集成遍次** — 造成单遍次审查不一致的是注意力稀释，不是上下文大小（见 08 §6）。
- **校准后路由：** 让审查者在每个发现旁自我报告**信心**以启用审查路由 — 然后在信任那些分数前先校准（见 09 §5）。

## G4. 缺口卡问答

**GQ1.** 模型填了一个文档没有的发票字段。Schema 修复方法？
**A.** 把该字段改成可选／可空 — 必填字段强迫捏造。

**GQ2.** 严格 tool-use schema 消除哪些错误，什么会留下来？
**A.** JSON 语法错误被消除；语义错误（加总错误、放错字段的值）留下来，需要验证逻辑。

**GQ3.** 描述带反馈错误重试。
**A.** 后续请求 = 原始文档 + 失败的萃取 + 具体验证错误，引导针对性自我修正。

**GQ4.** 何时重试永远修不好萃取？
**A.** 当所需信息不在提供的来源里 — 那是数据问题，不是格式问题。

**GQ5.** 为什么独立实例比「彻底审查你自己的代码」更好？
**A.** 产生者保留其推理上下文，不会质疑自己的决定；独立性拿掉那种偏见。

**GQ6.** 审查发现里 `detected_pattern` 字段的用途？
**A.** 让你能系统分析哪些构建触发被驳回的发现 — 这是削减误报类别的原料。

**Q20. 什么是路由工作流程？** 
**A：** 分类请求，再送到专门提示／模型／工具路径。

**Q21. Agent 回合该记录什么？** 
**A：** 消息 id、stop_reason、工具名称／id／输入（已屏蔽）、结果状态、token 用量、延迟。

**Q22. 要记住的缓存前缀顺序？** 
**A：** 工具，然后系统，然后消息——直到缓存断点。

**Q23. `pause_turn` 在发什么信号？** 
**A：** 长时间服务器端回合暂停；依文档继续，而不是当硬失败。

**Q24. 为什么工具描述是「提示工程」？** 
**A：** 模型用它们决定*何时*与*如何*调用工具——含糊描述造成错误调用。

**Q25. 把巨大 SQL 倾倒当 tool_result 有什么问题？** 
**A：** 上下文膨胀与分心；摘要或分页结果，原始数据留在服务器端。

**Q26. 拒绝与空答案有何不同？** 
**A：** `stop_reason: "refusal"` 表示政策拒绝——用安全 UX 处理，不要对同一内容无限重试。

**Q27. 举一个 Computer Use 安全控制。** 
**A：** 沙箱／最小权限／敏感 UI 动作要人类核准。

**Q28. 串接与平行化有何差异？** 
**A：** 串接是串行依赖；平行化把独立工作扇出再合并。

**Q29. 为什么把检索指标与答案指标分开？** 
**A：** 糟糕答案可能是好文笔盖在坏切块上——或好切块配弱提示；修复方法不同。

**Q30. 工具使用「卡住」时的第一个调试步骤是什么？** 
**A：** 检查每个 `tool_use` id 是否收到 `tool_result`，并检查 `stop_reason`／迭代上限。

## 快速实验检查清单（练习时不要复制课程实验）

把这当私人操练清单，同时研读官方文档／SDK：

1. **Hello Messages：** 单次用户消息 → 打印助理文本；然后加第二则用户回合，并保留先前助理消息。
2. **系统消融：** 同一用户问题配三份不同系统提示词；记下语气与限制遵守。
3. **流式组装：** 串接文本增量；可能时断言与同一 seed／设置的非流式输出相等。
4. **工具往返：** 假天气工具；验证 `tool_result` 上 id 吻合；若模型发出两个工具，强制平行双调用。
5. **结构化解析：** `{ "sentiment": enum, "confidence": number }` 的 schema；解析丢例外就让构建失败。
6. **迷你 RAG：** 三个 markdown 档 → 切块 → 矢量嵌入或 BM25 → 带「sources:」行回答。
7. **缓存健全性：** 把长静态系统提示词放在缓存控制后面；比较请求 1 vs 请求 2 的延迟。
8. **Agent 预算：** 最多 5 次工具迭代；循环时回「budget exceeded」而不是卡住。
9. **停止原因操练：** 故意把 `max_tokens` 设很小，确认你检测到截断。
10. **批量模拟运行设计：** 草拟 100 列分类列，带 `custom_id` 与结果接回器（即使不调用 API）。
11. **429 模拟器：** 写一个带指数退避 + 抖动与最大重试上限的重试辅助。
12. **视觉萃取：** 一张屏幕截图／收据影像 → 结构化 JSON 字段；确认你没有写死假光学字符识别（OCR）。

这些操练强化考试机制；它们不能取代 Anthropic 的计分测验。
