## 概览

考试的领域 1 测试你能否设计并推理 **agentic（自主代理式）循环**（任务 1.1）、**协调者–子代理（subagent）编排**（1.2）、**子代理生成与上下文传递**（1.3）、**工作流程强制执行与交接**（1.4）、**Agent SDK hooks**（钩子机制）（1.5）、**任务拆解**（1.6），以及 **会话状态、恢复与分叉**（1.7）。题目是情境形的：生产环境日志呈现一个失败模式，你要挑出架构上相称的修复方法。

**总体心智模型：** 一个 agent = 模型 + 工具 + 循环。*模型* 根据上下文决定下一个要调用的工具（模型驱动的决策）；*循环* 是笨拙的管线，负责执行工具并把结果喂回去；*hooks*（钩子机制）是包在这层管线外面的确定性政策层；*子代理*（subagent）是协调者为聚焦工作而生成的额外隔离循环。

## 深入笔记

### 1. Agentic 循环（任务 1.1）

每个循环都实现的生命周期：

1. 把请求（messages + tools）送给 Claude。
2. 检查 **`stop_reason`**：`"tool_use"` → Claude 想要执行工具；`"end_turn"` → Claude 完成了。
3. 执行被请求的工具。
4. 把助理消息 **以及** `tool_result` 区块附加到对话历史。
5. 把更新后的历史送回去；重复直到 `end_turn`。

```text
loop:
 response = call_claude(history, tools)
 history.append(response)
 if response.stop_reason == "tool_use":
 results = execute(response.tool_calls)
 history.append(user_message(tool_results=results))
 continue
 if response.stop_reason == "end_turn":
 break # final answer is in response content
```

**为什么附加工具结果很重要：** 模型在请求之间是无状态的。只有当某个工具的输出出现在它*下一次收到的对话*中，它才能对那个输出进行推理。丢弃或截断一个 `tool_result`，会静默改变模型「知道」的东西。

**模型驱动对预先设置：** 考试区分 agent（Claude 根据累积上下文推理下一个要调用的工具）与由你写死的决策树或固定工具序列。Agent 在高度模糊的输入上表现出色（退货、账务争议），这类路径无法事先枚举；固定管线在路径已知时表现出色（见任务 1.6）。

**循环终止反模式（考试指南点名这些——要背起来）：**

| 反模式 | 为什么失败 | 正确信号 |
| --- | --- | --- |
| 解析自然语言信号（「我完成了！」）来决定终止 | 脆弱的字符串匹配；模型表达完成的方式千变万化 | `stop_reason == "end_turn"` |
| 把任意的迭代次数上限当成**主要**停止机制 | 切断合理的长任务；掩盖真正的 bug | stop_reason；上限只保留为*安全后备闸* |
| 检查助理消息是否包含文本，作为完成指标 | 助理回合可以同时包含文本*与* tool_use 区块 | stop_reason，绝不是内容形状 |

### 2. 协调者–子代理编排（任务 1.2）

**中枢辐射式：** 一个协调者 agent 掌管任务拆解、委派、结果汇总与错误处理。子代理之间绝不直接对话——**所有子代理间的通信都经由协调者路由**。为什么：可观测性（只有一个地方记录日志）、一致的错误处理（只有一套复原政策）、受控的信息流（没有未经审查的交叉通话）。

**上下文隔离（考试重点）：** 子代理**不会**自动继承协调者的对话历史，多次调用之间也不共享记忆。每个被生成的子代理都以全新的上下文开始，只包含它自己的系统提示词，加上协调者传入的提示词字符串。如果综合子代理需要网页搜索的发现，协调者必须**把那些发现放进综合子代理的提示词里**——没有任何东西会隐性流动。

**协调者的工作清单：**

- 分析查询并**动态选择**要调用哪些子代理——不是总是跑完整管线。一个简单的查询不该惊动四个专家。
- **跨子代理划分范围**，把重复降到最低（为每个 agent 指派不同的子主题或来源类型）。
- **汇总**结果，并评估综合输出有没有缺口。
- **迭代式精炼循环：** 若综合输出有覆盖缺口，就用*有针对性的*查询重新委派给搜索／分析子代理，然后重新调用综合；重复直到覆盖范围足够。

**领域 1 的招牌失败——过窄的拆解**（官方样例题 Q7）：关于「创意产业」的研究报告只涵盖视觉艺术，因为协调者把主题拆解成数字艺术／平面设计／摄影。每个子代理都正确执行了它的任务；**根本原因是它们被指派的内容**。考试反射：当子代理日志看起来干净、但覆盖范围很差时，怪协调者的拆解，不要怪下游的 agent。

**协调者提示词设计：** 指定**研究目标和质量标准**（「涵盖每一个主要的创意产业部门；每个主张都附引用来源」），而不是一步一步的程序指令。目标形的提示词让子代理能够适应；程序形的提示词在第一个意料之外的情况就崩坏。

### 3. 生成、AgentDefinition 与上下文传递（任务 1.3）

**Task 工具**是协调者用来生成子代理的机制，而且协调者的 **`allowedTools` 必须包含 `"Task"`**，否则它根本无法委派——经典的考试干扰选项，就是委派失败的根本原因是少了 Task 条目。*（现行文档注记：Claude Code 在 v2.1.63 把此工具改名为 `Agent`；考试指南与附录仍使用 `Task`——用指南的术语作答，并知道这次改名存在。）*

**AgentDefinition** 设置每种子代理类型（已对照现行 SDK 文档查证——`query()` 的 `agents` 选项把名称对应到定义）：

| 字段 | 用途 |
| --- | --- |
| `description` | 协调者什么时候该用这个子代理——Claude 靠这个把任务配对到 agent |
| `prompt` | 子代理的**系统提示词**：角色、专长、限制 |
| `tools` | 工具限制清单——综合 agent 拿不到网页工具；审查者只拿只读的 `["Read", "Grep", "Glob"]` |
| `model` | 选用的逐子代理模型覆盖（例如用较便宜的模型做大量阅读） |

**考试指南列出的明确上下文传递技巧：**

- 把**先前 agent 的完整发现直接放进子代理的提示词**（例如把搜索结果和文档分析传进综合提示词）。
- 使用**把内容与元数据分开的结构化数据格式**（主张文本对来源 URL／文档名称／页码），做出处归属能在交接之后存活——这个概念在领域 5.6 会再次出现。
- **平行生成：** 在**协调者的单一回应中发出多个 Task 工具调用**，而不是每回合一个。每回合一个会把本可同时进行的工作串行化；单一回应模式是文档记载的平行化方式（官方备考练习 4 测量的就是延迟收益）。

**基于分叉的探索**在概念上属于这里（细节见第 7 节）：分叉一个会话，从共享的分析基线出发，探索分歧的做法。

### 4. 多步骤工作流程：强制执行与交接（任务 1.4）

**程序化强制执行对提示词引导——领域 1 被考得最多的区别**（官方样例题 Q1）：

> 12% 的案例在执行 `process_refund` 之前跳过了 `get_customer`。修复方法？**一个程序化前置条件，在前置条件完成之前挡住下游的调用。** 提示词措辞和 few-shot（少样本）范例是概率性的——它们降低失败率，但永远降不到零。当错误有财务或合规后果时（「金融操作前的身份验证」），只有确定性的闸口可以接受。

强制执行阶梯（最弱 → 最强）：系统提示词指令 → few-shot 范例 → **代码中的 hook／前置条件闸口**。考试奖励的是选择*相称*的那一阶：审查提示词的精准度问题，给标准和 few-shot（领域 4）；合规关键的顺序，给代码。

**多重事项的请求：** 把一则包含几个不同事项的消息拆解成项目，逐一调查（彼此独立的就平行进行，并共享共同上下文，例如已验证的客户 ID），然后综合成**一个统一的解决方案**——不要回答了事项 1，却静默丢掉事项 3。

**人工升级用的结构化交接协议：** 接收升级案件的真人客服，通常**看不到对话逐字稿**。一份合规的交接摘要要携带：客户 ID、关注的事项、**到目前为止的根因分析**、涉及的金额／订单编号、已经尝试过什么，以及**建议的行动**。什么结构化载荷都没有就升级给真人，会逼那个人从零开始重新调查——这是反模式，情境题干会惩罚它。

### 5. Agent SDK hooks（任务 1.5）

Hooks 是 SDK 在固定生命周期点触发的回调；它们是**确定性保证层**，相较于提示词指令的**概率性遵从**——与文件 `05` 的 Claude Code 一节同一条建议式对强制式轴线，现在搬进了 SDK。

考试点名的两种 hook 模式：

1. **PostToolUse——在模型看到结果之前做转换。** 不同的模型上下文协议（MCP）后端回传异质格式：一个工具输出 Unix epoch 时间戳，另一个输出 ISO 8601，第三个输出数字状态码。PostToolUse hook **在 agent 处理工具结果之前，把它们规范化成单一标准格式**，模型就不必在推理途中同时应付三种日期格式。*（现行 SDK 机制，已查证：hooks 通过 `hooks` 选项注册，以事件名称为键，附带匹配器；PostToolUse 回调可以替换工具输出——`updatedToolOutput`——或附加 `additionalContext`。）*
2. **工具调用拦截——对外发调用强制执行合规规则。** 在*执行之前*拦截调用；若它违反政策（退款 > 500 美元），**挡住它并转到替代工作流程**（人工升级）。*（现行 SDK 机制，已查证：PreToolUse 回调回传 `permissionDecision: "deny"`，并附上模型看得到的 `permissionDecisionReason`；或用 `updatedInput` 改写参数；当多个 hooks 触发时，deny 永远胜出。）*

**何时用 hooks、何时用提示词：** 需要**保证**遵从的业务规则 → hooks。风格、语气、软性偏好 → 提示词。若题目说「永远不准」、「合规」、「监管」，或点名一个美元门槛——答案就是 hook 或闸口，不是在系统提示词里写一句更好的话。

### 6. 任务拆解策略（任务 1.6）

两个家族：

| 策略 | 形状 | 何时使用 |
| --- | --- | --- |
| **提示链**（固定的顺序管线） | 预先定义的步骤 1 → 步骤 2 → 步骤 3 | 可预测的多面向工作：步骤事先已知 |
| **动态自适应拆解** | 计划从中间发现中浮现 | 开放式调查：下一步要做什么，取决于你发现了什么 |

**提示链范例（同时是官方样例题 Q12／领域 4.6）：** 一份涵盖 14 个文件的 pull request（PR）用单一回合审查，产出深度不一致、结论互相矛盾——**注意力稀释**。修复方法：**逐文件的局部分析遍次**，加上**独立的跨文件集成遍次**。拆分是拆解类的答案，不是加大上下文窗口类的答案（Q12 的选项 C 之所以错，正是因为更大的窗口修不好注意力稀释）。

**自适应范例：** 「为一个遗留代码库加上全面的测试」——你无法事先枚举步骤。先**绘制结构图**，识别**高影响区域**，创建一份**会随着依赖被发现而调整的优先级计划**。这份计划是活的工件，随着发现到来而重新生成。

**怎么选：** 问「我能不能在开始之前写出完整的步骤清单？」能 → 用提示链。不能 → 用自适应。混合式很常见：外层是自适应计划，内层是链式的遍次。

### 7. 会话状态、恢复与分叉（任务 1.7）

- **`--resume <session-name-or-id>`** 延续一个特定的先前对话，连同完整上下文（读过的文件、做过的分析、下过的决策）。已查证的现行 CLI：`--resume` 接受会话 **ID 或名称**（或显示一个选择器）；`--continue` 抓取目前目录中最近的会话。在 SDK 中，于 query 选项传入 `resume=<session_id>`（Python）／`resume: sessionId`（TypeScript）。
- **`fork_session`** 从共享的分析基线创建一个**独立分支**：分叉会拷贝原会话的历史，并得到自己的会话 ID；**原会话保持不变**。用它探索分歧的做法——例如从一次昂贵的代码库分析出发，比较两种测试策略或两种重构设计，每种做法一个分叉。已查证的 SDK 拼写：`fork_session=True`（Python）／`forkSession: true`（TypeScript），*与* `resume` 一起传入。
- **代码变动之后的恢复：** 被恢复的会话，其工具结果描述的是文件*当时*的样子。**告诉 agent 哪些文件变了**，让它专门重新分析那些文件，而不是信任过期的读取——有针对性的重新分析，胜过全面重新探索。
- **恢复对上带摘要重开：** 若先前上下文*大致仍有效* → 恢复（便宜，而且保留细微差异）。若先前工具结果*大幅过期* → **开新会话，并注入一份仍然有效结论的结构化摘要**。一个带着干净、当前事实的新会话，比一个拖着已被推翻的文件读取、而模型仍可能信任的恢复会话，更可靠。

## 决策树

**「agent 没做 X」的分流排查：**

```text
它是否跳过了必要步骤（合规／顺序）？
 → 程序化前置条件，或 PreToolUse 式拦截 hook（1.4／1.5）
它是否在相似工具之间选错了工具？
 → 先修工具描述（领域 2.1），再补 few-shot
它是否产出不完整的覆盖，而子代理日志很干净？
 → 协调者的拆解太窄（1.2）
它是否完全没有委派？
 → 协调者的 allowedTools 里有没有 "Task"？（1.3）
它是否过早终止或无限循环？
 → 检查 stop_reason 处理；移除自然语言解析／文本存在检查（1.1）
```

**会话延续：**

```text
先前上下文仍然有效？
 是 → --resume（加一则列出任何变动文件的说明）
 大致有效，想试两个方向 → 恢复 + 每个方向一个 fork_session
 否（工具结果过期） → 新会话 + 注入的结构化摘要
```

## 考试陷阱

| 陷阱 | 修复方法 |
| --- | --- |
| 对合规关键的顺序 bug「加强系统提示词」 | 程序化前置条件／hook——提示词是概率性的 |
| 以为子代理看得到协调者的对话 | 它们只看到自己的系统提示词 + 生成时传入的提示词 |
| 把覆盖缺口怪到下游 agent 头上 | 先查协调者的拆解（样例题 Q7） |
| 把平行子代理分散在多个回合生成 | 在单一回应中发出多个 Task 调用 |
| 把迭代次数上限当主要循环终止器 | stop_reason `end_turn`；上限只当后备闸 |
| 只带一个「需要真人」标志就升级给真人 | 结构化交接：ID、根因、金额、建议行动 |
| 在大量代码变动之后恢复会话，却不说明 | 点名变动的文件，或带着摘要重开 |
| 以为分叉会改变原会话 | 不会——分叉把历史拷贝到一个新的会话 ID |
| 用 hooks 处理语气／风格偏好 | Hooks 给保证；提示词给偏好 |
| 因为上下文窗口装得下，就做一个巨大的审查回合 | 注意力稀释——拆成逐文件遍次 + 集成遍次 |

## 自我检查问答

**Q1.** 当 `stop_reason` 是 ___ 时循环应继续，是 ___ 时应终止。
**A.** `"tool_use"`；`"end_turn"`。

**Q2.** 为什么工具结果必须在下一个请求之前附加到历史？
**A.** 模型在每个请求上是无状态的——它只能纳入出现在所收到对话中的结果。

**Q3.** 说出考试指南列出的三个循环终止反模式。
**A.** 解析自然语言完成信号；把任意迭代次数上限当主要停止机制；检查助理文本内容作为完成指标。

**Q4.** Agent 对预先设置管线——决定性差异是什么？
**A.** 模型驱动的决策：agent 根据上下文推理下一个工具；管线遵循写死的序列。

**Q5.** 中枢辐射式里，谁跟谁说话？
**A.** 所有子代理通信都经由协调者路由——为了可观测性、一致的错误处理，以及受控的信息流。

**Q6.** 研究报告只涵盖主题的一小块；每个子代理的日志看起来都正确。根本原因？
**A.** 协调者的任务拆解太窄——子代理的指派没有涵盖主题（样例题 Q7 模式）。

**Q7.** 协调者要生成子代理，`allowedTools` 必须满足什么条件？
**A.** 必须包含 `"Task"`（生成子代理的工具；目前 Claude Code 已改名为 `Agent`——考试使用 Task）。

**Q8.** 刚生成的子代理以什么上下文开始？
**A.** 它自己的系统提示词（AgentDefinition `prompt`）加上协调者传入的提示词字符串——没有父代历史，也没有共享记忆。

**Q9.** 综合 agent 需要搜索 agent 的发现。它怎么拿到？
**A.** 协调者把完整发现直接放进综合 agent 的提示词，最好是把内容与来源元数据分开的结构化数据。

**Q10.** 如何平行执行三个子代理？
**A.** 协调者在单一回应中发出三个 Task 工具调用。

**Q11.** AgentDefinition：说出两个必填字段，以及各自做什么。
**A.** `description`（告诉协调者什么时候用这种 agent 类型）和 `prompt`（子代理的系统提示词）；`tools` 和 `model` 是选用的限制／覆盖。

**Q12.** 12% 的退款跳过身份验证。最好的修复方法？
**A.** 一个程序化前置条件，在 `get_customer` 回传已验证 ID 之前挡住 `process_refund`——确定性的，不像提示词／few-shot 修复方法（样例题 Q1）。

**Q13.** 结构化人工升级交接该包含什么？
**A.** 客户 ID、关注的事项、根因分析、金额／订单编号、已尝试的事项、建议行动——真人没有逐字稿访问权。

**Q14.** 三个 MCP 工具分别以 epoch、ISO 8601 和字符串回传日期。在哪里规范化？
**A.** 一个 PostToolUse hook，在模型处理之前把工具结果转换成单一标准格式。

**Q15.** 超过 500 美元的退款永远不准自动执行。用什么机制？
**A.** 工具调用拦截（PreToolUse 式）hook，挡住调用并转到人工升级——hooks 给确定性保证；提示词是概率性的。

**Q16.** 提示链对自适应拆解——一句话规则？
**A.** 步骤能事先枚举 → 用提示链；计划取决于发现 → 用自适应。

**Q17.** 大型多文件审查产出互相矛盾、不一致的结论。怎么重组？
**A.** 逐文件的局部分析遍次，加上独立的跨文件集成遍次（注意力稀释修复方法；样例题 Q12）。

**Q18.** 「为遗留代码库加上全面的测试」——前三个动作？
**A.** 绘制结构图、识别高影响区域、创建一份随依赖浮现而调整的优先级计划。

**Q19.** fork_session——分叉与原会话共享什么、改变什么？
**A.** 它以原会话历史的副本开始，使用新的会话 ID；原会话不受影响。

**Q20.** 什么时候新会话加摘要胜过 `--resume`？
**A.** 当先前工具结果过期时（代码大幅变动）——注入有效结论的摘要，胜过含有已被推翻读取的恢复上下文。

**Q21.** 你在编辑两个文件之后恢复一个调查会话。你的第一则消息该包含什么？
**A.** 哪些文件变了，让 agent 专门重新分析那些文件，而不是信任过期读取或重新探索一切。

**Q22.** 协调者提示词该指定 ___，而不是 ___。
**A.** 研究目标和质量标准；一步一步的程序指令（适应力）。

**Q23.** 迭代次数上限什么时候可以合理地存在于循环中？
**A.** 作为防止失控的安全后备闸——绝不作为主要终止机制。

**Q24.** 协调者把每个查询都路由到全部四个子代理，连琐碎的也一样。评论？
**A.** 协调者应该按查询复杂度动态选择子代理——全管线路由浪费延迟／成本，还增加失败面。

**Q25.** 迭代式精炼循环——描述它。
**A.** 协调者评估综合输出的缺口 → 把有针对性的查询重新委派给搜索／分析 agent → 重新调用综合 → 重复直到覆盖范围足够。

## 词汇表

| 术语 | 含义 |
| --- | --- |
| Agentic 循环 | 送出请求 → 检查 stop_reason → 执行工具 → 附加结果 → 重复 |
| stop_reason | 驱动循环控制的 API 字段：`tool_use` 继续，`end_turn` 停止 |
| 协调者 | 掌管拆解、委派、汇总与错误处理的中枢 agent |
| 中枢辐射式 | 所有子代理通信都经过协调者的拓扑 |
| Task 工具 | 生成子代理的工具（目前 Claude Code 已改名为 Agent） |
| allowedTools | 自动核准所列工具的 SDK 选项；要委派就必须包含 Task |
| AgentDefinition | 逐子代理的设置：description、prompt、tools、model |
| 上下文隔离 | 子代理从全新状态开始；只有生成提示词把上下文带进去 |
| 程序化前置条件 | 一个代码闸口，在前置条件完成之前挡住下游工具 |
| PostToolUse hook | 在模型看到工具结果之前，将其转换／规范化的回调 |
| 工具调用拦截 | 执行前的 hook，挡住或改写违反政策的调用 |
| 提示链 | 由聚焦遍次组成的固定顺序管线 |
| 自适应拆解 | 从中间发现生成并修订的计划 |
| 注意力稀释 | 一个遍次涵盖太多文件／面向时发生的质量劣化 |
| --resume | 以完整上下文延续具名或有 ID 的会话，CLI／SDK 皆有的选项 |
| fork_session | 把会话历史分叉到一个新的、独立的会话 ID |
| 结构化交接 | 人工升级载荷：ID、根因、金额、尝试过的事项、建议 |
