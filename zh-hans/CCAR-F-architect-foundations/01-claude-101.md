# Claude 101 — 备考笔记

> **免责声明：** 这些是原创备考笔记 — **非** Anthropic 官方材料。课程大纲来源：https://academy.claude.com/courses/claude-101。功能细节已对照公开的 Anthropic Help Center 文章核对；产品 UI 与方案闸门可能变动——考试前请再核对。

## 概览

Claude 101 是 Anthropic 把 Claude 带进日常工作的入门路径。公开课程页面描述为 **13 堂课与 1 次测验**（约 2.5 小时），结束时会拿到完成徽章。它面向任何有 Claude 账号的人（Free 到 Enterprise）。少数功能（例如 Cowork 与 Enterprise Search）需要付费或 Team／Enterprise 方案才能动手试；概念对考试仍然重要。

**读完这份材料之后，你应该能做这些事**

- 解释 Claude 是什么，并进行一场有用的第一轮对话
- 写出更清楚的提示词，在结果不如预期时迭代，并把提示连到 AI 流畅度的 4D
- 在桌面应用程序的三种「工作形态」之间做选择：逐轮 Chat、交办工作（Cowork），以及打造软件（Code）
- 用 Projects、Artifacts 与 Skills 组织上下文与可重复的工作
- 用 Connectors、Enterprise Search 与 Research 扩大触及范围
- 把 Claude 对应到常见角色，并认识相邻产品（Claude Code、Claude Tag、Claude Design、Claude for Microsoft 365、Claude in Chrome）

**典型模块路线（对齐公开大纲）**

1. 认识 Claude — 它是什么；第一场对话
2. 拿到更好的结果 — 提示；Chat／Cowork／Code
3. 组织工作与知识 — Projects、Artifacts、Skills
4. 扩大触及范围 — Connectors、Enterprise Search、Research
5. 集成起来 — 角色用例；其他与 Claude 共事的方式

这些笔记以原创语言重写概念，供阅读与 Claude 认证备考。它们**不是**课程逐字稿。请把这里的原创备考措辞当完整版使用；不要把它当成 Academy 课文。

**如何把本档当主要研读来源**

1. 先把关键概念地图扫一遍
2. 按顺序读深入笔记（功能彼此堆叠）
3. 反复操练决策树／对照表，直到能不假思索挑对工具
4. 走一遍常见考试陷阱
5. 不偷看先做自我检核，再对答案
6. 考前一晚用快速复习清单
7. 搭配 `02-ai-fluency.md` — Claude 101 应用框架；流畅度解释框架

## 关键概念地图

| 概念 | 一句话意义 | 流畅度链接 |
|------|------------------|--------------|
| 提示词模式 | 给角色／舞台、任务与规则（上下文、格式、限制） | 描述（Description） |
| 迭代 | 第一份输出是草稿；用具体回馈精修 | 描述–明辨循环 |
| Chat | 在对话中逐轮协作 | 增强（Augmentation）默认 |
| Cowork | 交办涉及文件／应用程序的多步骤工作（受方案闸门限制） | 偏向自主代理的自动化 |
| Code | 打造软件的工作形态 | 实作的自主代理 |
| Projects | 带有知识 + 指示、跨对话持续的工作区 | 常驻的描述（Description） |
| Artifacts | 侧边面板里的独立输出（文档、代码、应用程序） | 看得见的交付物 |
| Skills | Claude 可执行的可重复使用*操作程序* | 程序面的描述（Process Description） |
| Connectors | 连到网络服务或本机桌面工具 | 平台触及范围 |
| Enterprise Search | 公司知识检索（Team／Enterprise） | 内部锚定 |
| Research | 超越单次对话猜测的、更广的多来源调查 | 多步骤搜索自主代理 |
| 4D 流畅度 | 委派（Delegation）、描述（Description）、明辨（Discernment）、尽责（Diligence） | 整套实践 |
| 检索增强生成（RAG，项目） | 知识变大时检索相关切块 | 容量但不超载 |
| 渐进式揭露（skills） | 需要时才加载相关 skill 片段 | 上下文卫生 |

**记忆挂钩：** *形态 → 上下文 → 交付物 → 程序 → 触及范围*

- 形态 = Chat／Cowork／Code
- 上下文 = Projects（+ 指示）
- 交付物 = Artifacts
- 程序 = Skills
- 触及范围 = Connectors／Enterprise Search／Research

## 依主题的深入笔记

### 1. Claude 是什么（以及不是什么）

Claude 是 Anthropic 的 AI 助理，用于写作、分析、编程协助、研究与协作解题。把它当**有能力的协作者**，不是神谕。它依训练中的模式，加上你放进当前对话与已连接上下文的内容，预测有帮助的回复。

**考试风格要点：** 语气上的自信 ≠ 正确。高风险事实需要独立验证、引用来源，或网络锚定。

**实务提示：** 每个新领域开头先写一份短「合约」：目标、受众、限制，以及「完成」长什么样子。这会在你追逐巧妙措辞之前先把描述（Description）设好（见 AI 流畅度）。

**陷阱：** 丢一句模糊请求（「写点 Q3 相关的东西」）然后怪模型。模糊进 → 空泛出。

**原创实作范例 — 第一份合约**

差：「帮忙做入职。」

较好：「你在协助一位新任 CS 经理入职。交付一份第 1 周用的 1 页检查清单。受众：讨厌空话的经理。必须包含：权限申请、伙伴会议、第一次工单跟班。避免：励志语录。若有任何歧义，起草前先问我 3 个澄清问题。」

**若考试问 X，想到 Y**

- X：「为什么 Claude 捏造了一个统计数字？」→ Y：LLM 生成流畅的续写；没有锚定／工具时可能捏造。要验证。
- X：「Claude 语气自信时是否永远正确？」→ Y：否。语气 ≠ 真相。需要明辨。

### 2. 有效的第一轮对话

强的第一则消息通常包含：

1. **你是谁／角色**（或 Claude 应扮演谁）
2. **你需要什么**（具体交付物）
3. **上下文**（受众、利害、先前决策）
4. **格式与限制**（长度、结构、语气、必须包含／必须避免）

公开课文常把简单模式写成 **角色 + 任务 + 上下文 + 格式**，或舞台、任务与规则的三部分框架。记住*精神*，不要背品牌口号：**定向 → 指定 → 约束**。

**自我检核习惯：** 送出前问自己「一个聪明的新进员工只靠这则消息能否成功？」若不能，补上下文。

**反模式**

| 反模式 | 为什么失败 | 修复方法 |
|--------------|--------------|--------|
| 单词请求 | 没有交付物 | 点名产物 |
| 隐藏限制 | 语气／长度错了 | 写出必须避免 |
| 整串邮件串全丢进去 | 噪声 > 信号 | 摘要利害 + 只贴关键摘录 |
| 「扮成专家」但没有任务 | 角色表演 | 角色 + 具体输出 |
| 从不迭代 | 卡在草稿 1 | 精准回馈 |

**原创实作范例 — 改写邮件**

提示词骨架：

```text
角色：你是帮我改客户信件的编辑。
任务：把下面的草稿改写成一封语气平静的道歉信。
上下文：客户已经等了 6 天；我们没达成 SLA；退款已核准。
格式：120–150 字；主旨列 + 本文；不要法律术语腔；以一个明确的下一步收尾。
规则：不要责怪客户；不要捏造政策；凡无法从我的草稿核对的主张都要标记出来。
[贴上草稿]
```

### 3. 拿到更好的结果：常见修复方法

输出不如预期时，先诊断失败模式：

| 症状 | 可能原因 | 修复方法 |
|---------|--------------|-----|
| 太空泛 | 上下文太薄 | 补受众、限制、历史 |
| 长度错了 | 期望没说清楚 | 设字数／段落上限 |
| 结构错了 | 没展示格式 | 给骨架或范例 |
| 语气错了 | 默认「有帮助的专业人士」 | 点名语气；贴一份样本 |
| 听起来合理但错了 | 幻觉风险 | 验证；要求来源／信心；用搜索／Research |
| 过度附和 | 过度迎合（sycophancy） | 要求批评／对立观点 |
| 对话串一团乱 | 转折太多 | 用清理过的提示词开新对话 |

**迭代心态**

- 把草稿 1 当起点
- 回馈要**精准**（「删第 1 段；让行动号召（CTA）具体」），不要只说「写好一点」
- 若对话串纠缠，**开一场干净对话**并用更清楚的提示词

**轻量评测（明辨的实务）**

对重复性工作：

1. 收集 5–10 份你已经信任的过去好范例
2. 写出能重现它们的提示词
3. 把 Claude 的输出跟你的黄金范例比较
4. 记下缺口；把缺的规则烘进提示词、Projects 或 Skills
5. 然后才把工作流程用在新数据上

这与「委派尽责循环」同一思路：先在已知答案上测试，再信任新答案。

**原创实作范例 — 每周指标短文的评测**

- 黄金标准集：你已发布的最近 4 篇周五写作
- 输入：同一份原始 CSV + 同一套项目指示
- 评分：事实吻合、长度、图表标注、没有捏造驱动因素
- 发现的缺口：Claude 在没有数据时捏造「季节性」→ 加规则「只宣称数字或我笔记里出现的驱动因素」
- 把规则烘进项目指示；再测一次；然后上线使用

**若考试问 X，想到 Y**

- X：「输出很空泛」→ Y：描述（Description）薄弱／缺受众
- X：「不靠更好的『提示魔法』怎么改进？」→ Y：迭代 + 评测 + Projects／Skills

### 4. 三种工作形态（桌面应用程序）

公开目标强调三种协作模式：

1. **逐轮（Chat）** — 来回起草、问答、在对话中分析。适合你每一步都要紧密控制时。
2. **交办工作（Cowork）** — 较长的会话，Claude 较自主地操作文件与应用程序。适合多步骤运营任务。通常受方案闸门限制（付费方案）。会话可以整理文件、综合整理研究、跑调度任务，并使用为 Cowork 范围化的 projects。
3. **打造软件（Code／Claude Code）** — 以实作为导向的工作：存储库、agent、编程工作流程。

**考试提示：** 对齐*任务形态*，不是闪亮模式。探索式头脑风暴 → Chat。「清理这个发票文件夹并摘要」→ Cowork 式交办。「在存储库交一个功能」→ Code。

**陷阱：** 对仍需要逐轮判断的任务使用 agentic 交办（敏感客户邮件、法律措辞）。

**决策树 — 选形态**

```text
主要目标是逐句写作／判断语气吗？
 是 → Chat
 否 ↓
主要目标是可以放手让它跑的多步骤文件／应用程序操作吗？
 是 → Cowork（若方案允许）
 否 ↓
主要目标是储存库里的软件／coding agent 工作流程吗？
 是 → Code
 否 → 默认用 Chat，任务变大再升级
```

**对照 — Chat vs Cowork vs Code**

| 维度 | Chat | Cowork | Code |
|-----------|------|--------|------|
| 每步控制 | 最高 | 中等（先计划再跑） | 中–高，靠引导 |
| 最适合 | 草稿、问答、判断 | 跨文件／应用程序的运营 | 实作 |
| 自主程度 | 低 | 较高 | 在存储库里较高 |
| 方案闸门 | 访问最广 | 常需付费 | 独立的编程界面 |
| 误用风险 | 浪费时间 | 无人看管的副作用 | 糟糕的提交／范围蔓延 |
| 尽责焦点 | 审查文本 | 审查动作 + 文件 | 审查差异比较 + 测试 |

**反模式**

- 为改写一段话启动 Cowork
- 用 Code 模式「想策略」却没有存储库
- 在不可逆动作上让 Cowork 无人看管、没有检查点

### 5. Projects — 知识中枢

**Projects** 是专用工作区，带有：

- 自己的对话记录
- **项目知识**（上传后 Claude 可重复使用的文档）
- **项目指示**（语气、专业、常驻规则）
- 可选的团队分享同一份共享上下文（Team／Enterprise）

公开 Help Center 框架：Projects 广泛可用（含 Free，Free 有较小的项目数量上限）。付费方案上，大型知识库可转入 **RAG 模式**——Claude 检索相关切块，而不是把一切塞进窗口，扩大容量同时维持质量。

**何时用 Projects：** 你有稳定领域（产品文档、品牌声音、客户简报），许多对话都应共享。

**不要跟 Skills 搞混：** Projects 存放 Claude 应*知道什么*；Skills 编码*如何*跑一套程序。Help Center 对比：Projects = 该工作区加载的静态背景知识；Skills = 动态启用、可跨 Claude 运作的专门程序。

**原创实作范例 — 「Acme Support」Project**

- 知识：FAQ PDF、严重程度矩阵、退款政策、语气范例
- 指示：「绝不捏造政策。引用政策标题。法律主张升级给人类。语气：平静、白话。」
- Project 内的对话：工单改写、宏草稿、每周主题摘要
- Project 外：**不要**期望同样的政策锚定

**反模式**

- 一个巨型 Project 塞进每个客户（上下文渗漏）
- 上传你不会放进共享云端硬盘的机密
- 没有指示，然后怪「Claude 忘了我们的声音」
- 把项目知识当成永远完整「在脑里」，而 RAG 可能选择性检索——问尖锐问题；引用文件

**若考试问 X，想到 Y**

- X：「如何跨对话重用品牌声音？」→ Y：项目知识 + 指示
- X：「知识变很大——概念上会发生什么？」→ Y：检索相关切块（RAG 风格），尤其在付费方案

### 6. Artifacts — 独立输出

**Artifacts** 出现在对话旁边的专用面板。与其把长 HTML／代码／文档区块埋在对话串里，Claude 会渲染一份你可以预览、复制、下载或迭代的东西。

当内容重要、自成一体、可编辑／可重用，且之后可能被引用时，Claude 倾向创建 artifact（通常比短对话回复更长／更有结构）。

常见类型（概念上）：

- 文档（markdown／文本报告、计划、帖子）
- 可直接复制的代码片段
- 交互式／视觉作品（简单应用、图表、计算器、SVG／图解、React 组件）

**提示**

- 若卡在对话里，明确要求：「把这个做成 artifact」
- 调试时在预览与底层代码之间切换
- 用 Artifacts 做可分享的交付物；把对话留给协商与批评
- 版本选择器有助探索方向而不丢掉先前工作
- 发布／分享与高级行为（AI 驱动的 artifacts、artifacts 内的模型上下文协议（MCP）、持久存储）依方案与设置而定——知道它们存在；考试细节请核对在线文档
- 现代 artifact 工作流程常需要代码执行／文件创建能力

**原创实作范例**

要求把「定价比较计算器」做成 artifact → 在面板里迭代 UI → 稳定后下载或分享。把协商（「要不要含年缴折扣？」）留在对话里。

**反模式**

- 把 200 行代码的 HTML 应用只留在对话气泡里
- 每次重贴整个文件来编辑，而不是针对 artifact
- 发布前不检查存储是个人还是共享（隐私）

### 7. Skills — 程序性机器

**Skills** 是可重复使用的指示集（常是指示、脚本与资源的文件夹），用于多步骤工作流程：品牌流程、PDF 包装、通话准备仪式、博客管线等等。它们靠**渐进式揭露**提升一致性——Claude 加载相关部分，而不是把每个 skill 都倒进上下文。

高阶需认得的类型：

- Anthropic 维护的 skills（例如更强的文档创建流程）
- 你撰写的自定义 skills（Markdown 指示；可选脚本）
- 组织部署的 skills（Team／Enterprise）
- 目录里的合作伙伴 skills（常搭配 MCP connectors）

**Projects vs Skills（考试常考）**

| | Projects | Skills |
|--|----------|--------|
| 用途 | 存放知识 | 定义程序 |
| 最适合 | 长期上下文、团队参考 | 可重复的方法论 |
| 持续性 | 该项目内跨对话 | 当 skill 被调用／相关时 |
| 隐喻 | 图书馆 + 家规 | playbook（操作手册）／标准作业程序（SOP） |
| 加载 | 该工作区的背景 | 动态／按需 |

它们很适合搭配：一套「客户通话准备」Skill 可以从 Project 的知识库拉取文件。

**Skills vs Connectors／MCP（短）**

- Connectors／MCP = 对工具与数据的*访问*
- Skills = *如何*为一套工作流程使用那些工具
- 两者并用：MCP 开门；Skills 教舞步

**Skills vs 自定义指示**

- 自定义指示 = 广泛、永远打开的偏好
- Skills = 任务特定、相关时才加载

**陷阱：** 把一次性 trivia 编成 Skill，或把巨型 SOP 塞进没有程序的 Project。

**原创实作范例 — 「每周状态」Skill**

程序步骤：从笔记抽出主题 → 依风险分组 → 起草列表 → 请人类确认阻碍 → 格式化给 Slack。只有这套仪式每周重复时才附加。

**若考试问 X，想到 Y**

- X：「跨对话每次同一套程序」→ Y：Skill
- X：「工作区里每次同一批文档与声音」→ Y：Project
- X：「需要即时 Asana 数据」→ Y：Connector／MCP（+ 工作流程用的 Skill）

### 8. Connectors — 扩大触及范围

**Connectors** 把 Claude 连到外部工具。

- **网页连接器** — 云端应用（Drive、Notion、Slack、Asana、Gmail 等），常经 MCP 风格集成
- **桌面扩充功能** — 经桌面应用程序操作本机文件与原生应用

设置模式：在目录找到 → 连接 → 验证身份 → 授予最小权限 → 用「你看得到 X 吗？」测试。

**尽责角度：** 只安装可信的 connectors；权限可撤销；把已连接数据当成隐私审查的范围。

**反模式**

- 「以防万一」全部连上
- 没有核准关卡就请 Claude 对外发邮件
- 假设 connector 访问 = 无限的全组织可见性（验证与范围很重要）

### 9. Enterprise Search 与 Research

- **Enterprise Search** — 触及公司知识（通常是 Team／Enterprise）。常呈现为专用的组织知识工作区（例如「Ask Your Org」风格的 project），带引导式 connectors 与针对搜索优化的行为。适合答案住在内部文档、而非公开网络时。针对相对快速、带引用来源的内部检索做优化。
- **Research** — 单次对话猜测不够时，跨来源的多步骤、agentic 调查；适合文献式或竞品扫描并做锚定。通常是付费方案；必须能用网页搜索。可用网络 + 已连接的内部上下文；产出带可核对引用来源的详尽答案；可能较快耗尽用量上限。

**对照（考试常考）**

| | Enterprise Search | Research | 对话中的一般网页搜索 |
|--|-------------------|----------|-----------------------------|
| 主要工作 | 快速找内部知识 | 深度多步骤综合 | 快速外部事实 |
| 典型来源 | 已连接的公司工具 | 网络 + 集成，多步骤 | 网络 |
| 深度 | 针对性检索 | 广调查 | 轻 |
| 方案注记 | Team／Enterprise | 付费方案常见 | 依设置而定 |

**考试提示：** 时效或来源锚定重要时用 Research／Search；仍要套用明辨——来源可能不完整或互相冲突。

**原创实作范例**

- 「我们的带薪休假政策在哪？」→ Enterprise Search／内部 connectors
- 「比较三家竞争对手定价页，并摘要自上季以来的变更」→ Research
- 「今年新加坡大奖赛几点？」→ 对话中的网页搜索可能就够

**若考试问 X，想到 Y**

- X：「内部 Slack + Drive 的答案」→ Y：Enterprise Search／connectors
- X：「几分钟内做出带引用来源的多角度报告」→ Y：Research
- X：「一个快速公开事实」→ Y：网页搜索，不是完整 Research

## 常见考试陷阱

1. **Projects = Skills** — 错。知识／工作区 vs 程序。
2. **Artifacts 只是漂亮的对话** — 错。侧边面板的独立交付物。
3. **更多自主 = 更少监督** — 错。Cowork／Code／Research 需要*更多*明辨与尽责。
4. **自信语气 = 已验证事实** — 错。
5. **Free 方案能做每个动手示范** — 错。Cowork／Enterprise Search／部分 Research 行为受方案闸门限制；定义仍可考。
6. **Connectors 取代 Skills** — 错。访问 ≠ 程序。
7. **Enterprise Search = Research** — 错。快速内部检索 vs 深度多步骤调查。
8. **自订指示 = Skills** — 错。永远打开的广泛偏好 vs 任务特定、加载的程序。
9. **RAG 表示 Claude 每次完整读完每个文件** — 误导。知识很大时，检索只拉相关切块。
10. **所有客户共用一个 Project 没问题** — 有风险。上下文渗漏；敏感事项宜分开。
11. **「写好一点」是好回馈** — 弱。要精准。
12. **发布 artifact 没有隐私面向** — 错。共享存储／组织分享规则很重要。
13. **流畅度只是提示把戏** — 错。4D 协作技能（见课程 02）。
14. **Claude 起草了你就可以跳过人类问责** — 错。工作产物由你拥有。

## 扩充自我检核（问答）

**Q1.** 同事说 Projects 与 Skills 一样，因为两者都「给 Claude 上下文」。你如何纠正？

**A1.** Projects 主要在工作区内跨对话保存可重用的*知识与常驻指示*。Skills 编码*可重复程序*，相关时被叫用或加载。知识 vs 程序；两者互补。

**Q2.** 你需要一页客户道歉信，且必须控制每一句。哪种桌面「工作形态」最合适，为什么？

**A2.** Chat（逐轮）。高判断与语气控制偏好对话式迭代，而不是长交办。

**Q3.** Claude 的市场统计看起来精致，但你无法核对。该怎么做？

**A3.** 当成可能是错的；独立验证；要求来源／信心；为当前事实启用网络／Research 锚定。

**Q4.** 举一个描述（Description）薄弱的症状与一个修复方法。

**A4.** 例如：空泛输出 → 补受众、限制与格式范例。

**Q5.** 每周指标写作的轻量评测是什么？

**A5.** 拿上个月已知良好的写作，用同一批原始输入提示 Claude，跟你的原文比较，再把缺的规则烘进提示词／Project／Skill，然后才用在新数据上。

**Q6.** 项目知识变很大时，什么概念转变有助容量？

**A6.** 从把所有文件加载上下文，转为只检索相关切块（RAG 风格），让答案保持锚定又不溢出窗口（付费方案特别强调）。

**Q7.** 网页连接器 vs 桌面扩充功能——关键差异？

**A7.** 网页连接器连云端服务；桌面扩充功能经桌面应用程序在本机跑，用于文件／原生应用。

**Q8.** 「我对最终报告负责，被问时会揭露 AI 协助」对应哪一个流畅度 D？

**A8.** 尽责（Diligence）（责任、透明度、合乎伦理的使用）。

**Q9.** 何时应偏好 Research 而不是单次网页搜索答案？

**A9.** 当你需要多步骤、多来源综合，带系统性探索与引用来源——而不只是一个快速事实。

**Q10.** Enterprise Search 与一般 Project 有何不同？

**A10.** Enterprise Search 专门做组织知识检索（常自动部署、针对搜索优化、有引导式 connectors）。一般 Projects 是通用工作区，带用户可自定义的指示与知识。

**Q11.** 举一个误用 Cowork 的例子。

**A11.** 交办仍需句级人类判断的敏感法律信函、却没有紧密检查点——或在没有审查的情况下跑不可逆文件操作。

**Q12.** Skills vs MCP connectors，各一句。

**A12.** Skills 教*如何*执行一套工作流程；MCP／connectors 提供对外部工具与数据的*访问*。

**Q13.** 项目指示 vs 项目知识该放什么？

**A13.** 指示 = 常驻规则／语气／角色行为。知识 = Claude 应取用的参考文件与事实。

**Q14.** 举三种常见 artifact 内容类型。

**A14.** 任选三个：文档、代码片段、HTML 页、SVG／图解、交互组件／计算器。

**Q15.** 为什么开新对话，而不是继续一团乱的对话串？

**A15.** 纠缠的上下文造成漂移；目标澄清过的干净提示词，往往胜过没完没了的补丁。

**Q16.** 把 Artifacts 对应到一个流畅度概念。

**A16.** 它们让描述（Description）的*产物*看得见、可编辑——支持对具体交付物的明辨。

**Q17.** Free 方案考试陷阱：即使你点不到每个功能，哪些概念仍然重要？

**A17.** Cowork、Enterprise Search、Research 等的定义与适配任务的推理，仍是公平考题。

**Q18.** Skills 的渐进式揭露是什么？

**A18.** Claude 只加载与任务相关的 skill 信息，降低上下文超载。

**Q19.** 你需要 Claude 每周五遵循同一套 PDF 包装步骤。Project 或 Skill——主要选择？

**A19.** Skill（程序）。品牌资产可选择放在 Project。

**Q20.** 「AI 写的，所以我不负责。」哪个 D 失败了？

**A20.** 尽责（Diligence）——人类仍对 AI 协助的工作负责。

**Q21.** 选工具：从已连接的 Slack + Drive 摘要主题，回答「定价我们决定了什么？」

**A21.** Enterprise Search／组织知识 connectors（内部）。若还需要深度外部竞品综合，再用 Research。

**Q22.** 什么回馈比「写好一点」更好？

**A22.** 精准指示：删什么、加什么、语气目标、长度、必须保留的事实。

**Q23.** 为什么把客户事项分到不同 Projects？

**A23.** 降低上下文渗漏；把记录、文件与指示隔开，兼顾准确与机密。

**Q24.** Code vs Chat，用于「解释这份堆栈追踪并提出修补」，而你不在存储库 agent 工作流程里时？

**A24.** Chat 可以分析并提出建议；当你要在实际存储库做 agentic 实作时再切到 Code。

**Q25.** 如何在一套工作流程里组合 Project + Skill + Artifact？

**A25.** 例如：Project 保存产品文档；Skill 跑「发行说明仪式」；Artifact 是你预览并分享的最终 markdown 说明。
