# Claude Code 实战 — 主要备考笔记

> **免责声明：** 这些是用于 Claude 认证准备的**原创**备考笔记。它们对齐 [Claude Code in Action](https://academy.claude.com/courses/claude-code-in-action) 的**公开**课程大纲（仅目标与模块主题）。它们**不是** Claude Academy 课堂内容转储、逐字稿或幻灯片原文。完成官方课程仍是小考的真相来源。请在现行 Claude Code 文档核对 CLI 标志与 UI 标签——名称会演进。

**适合对象：** 已经在用 Claude Code 处理单次提示、想要更长、更少监督、全团队适用工作流程的开发者。

**先修（课程）：** 用 Claude Code 做一次性任务；基本 Git 与命令行。

**如何使用这些笔记：** 一次读一个大节，然后不回头翻页、直接回答自我检核。把表格当闪卡。阶梯 **掌舵 → 设置 → 自动化 → 验证／分享** 是大多数情境题的主干。

---

## 1. 课程地图（公开目标）

公开页面把内容框成四个成果群组（约 9 堂课、1 次小考）：

1. **掌舵工作** — 计划模式、定向压缩、倒回、亲手操作对上自主的目标／循环执行、安全的平行化。
2. **设置 Claude** — 精简的 `CLAUDE.md`、Skills、权限模式、给不能跳过的规则用的 hooks。
3. **把重复工作自动化** — Anthropic 基础设施上的例行调度、你管线里的无头模式、PR／GitHub Action 接线。
4. **验证与分享** — 按照你监督得多少，等比例地验证无人监督的执行；用真正的测试把关；把受信任的设置打包成 Plugin。

**心智模型：** Claude Code 是一个带工具的 agentic 编码循环（文件编辑、bash、搜索等）。考试里你的任务不是「写更长的提示词」，而是针对工作的风险**选对控制面**。

| 层 | 它回答的问题 | 强项 |
| --- | --- | --- |
| 掌舵 | *这个会话*该做什么？ | 暂时性控制 |
| 设置 | Claude *永远*该知道／被允许什么？ | 持久 |
| 自动化 | 这件事如何不用我打字就能跑？ | 运维 |
| 验证／Plugins | 我们如何信任并重用这个设置？ | 保证＋可携性 |

记住：很多考试型题目问的是哪一层**建议**、哪一层**强制执行**。

## 2. 掌舵长时间的会话

### 2.1 计划模式

对于不简单的修改，从**计划模式**开始。Claude 可以读取存储库、执行探索性命令，但在你核准计划之前，它**不应该修改源代码**。在这些时候用它：

- 代码库你不熟悉
- 修改触及很多文件或模块
- 你需要先做架构决策再写程序
- 爆炸半径包含迁移、身份验证、计费或部署脚本

在 CLI 里循环切换模式（常见是 **Shift+Tab**）。学的是每个模式的*意图*，而不是任何单一 UI 字符串——标签会改；从「只读探索」到「自动核准编辑」再到「略过提示」的光谱不会改。

**考试框架：** 计划模式是一个*掌舵*选择，不是永久的项目设置。核准计划之后，你通常切换到一个在你信任的权限下允许实现的模式。

### 2.2 压缩

长时间的会话会填满上下文窗口。Claude Code 会**压缩**较旧的轮次（在很多设置里你也可以手动触发压缩，例如 `/compact`）。摘要会丢掉细节。

**压缩后存活得很差的东西：** 一次性的聊天规则（「永远用 pytest」）、暂时性的命名决定、你仍需要当反例的失败实验路径。

**应该靠设计存活的东西：**

- 持久惯例 → **`CLAUDE.md`**／`.claude/rules/`
- 按需程序 → **Skills**
- 硬性停止 → **hooks**／封锁规则

当你*定向*压缩（保留 X、丢掉 Y）时，优先保留：已核准的计划、未决的决策、限制、失败测试的名称。丢掉：冗长的工具转储、已放弃的钻牛角尖路线、重复的文件清单。

**考试陷阱：** 「压缩弄丢了我们的编码标准」→ 根本原因是标准只活在聊天里，没有活在 CLAUDE.md。

### 2.3 倒回

当会话漂移，**倒回**到之前一个干净的点，而不是在被污染的上下文上叠加互相矛盾的修正。然后重新陈述**一个**清楚的目标。

倒回对上压缩：

| 动作 | 最适合何时 | 误用的风险 |
| --- | --- | --- |
| 倒回 | 错误路线／互相矛盾的指示 | 倒得太远会丢掉后来有用的工作 |
| 压缩 | 上下文已满但方向仍然正确 | 丢掉细节；若聊天很乱，可能强化糟糕的摘要 |

**模式：** 漂移 → 倒回 → 单一目标 →（可选）再次进入计划模式 → 实现。

### 2.4 亲手操作对上自主

| 风格 | 何时用 | 控制 |
| --- | --- | --- |
| 亲手掌舵 | 新颖／高爆炸半径 | 你核准编辑并盯着每一轮 |
| 目标＋循环／自主 | 受信任、范围明确的任务 | Hooks、测试、更严格的权限模式 |
| 平行 agent | 彼此独立的子任务 | **Git worktree**（或各自独立的签出） |

**考试小抄：** 平行 agent 共用一个有未提交修改的工作树，是错误模式；用 worktree 隔离才是安全答案。

### 2.5 掌舵对上自主的决策树

```text
任务是新颖的或高爆炸半径吗？
 是 → 亲手操作 + 计划模式；核准计划之后才用 default/manual 或 accept-edits
 否 → 该进程是否重复且已验证过？
 是 → Skill + hooks；考虑例行调度
 否 → 仍是互动式；过程中把学到的东西写进 CLAUDE.md

需要你笔电上的密钥、私有网络或自订管线吗？
 是 → 在你自己的 CI／agent 主机上跑无头模式
 否 → Anthropic 基础设施上的例行调度可能就够

CI 里每次执行的结果必须完全相同吗？
 是 → 裸／确定性的无头旗标 + 钉定的权限
 否 → 互动式或 auto 模式搭配验证即可

多个 agent 有帮助吗？
 是 → 拆成独立工作；用 worktree 隔离
 否 → 单一 agent、清楚的目标

工作阶段走偏了吗？
 → 先倒回；然后才重新提示
```

## 3. 配置面（建议式对强制式）

| 表面 | 性质 | 强度 |
| --- | --- | --- |
| 聊天提示词 | 暂时 | 建议式 |
| `CLAUDE.md`／规则 | 永远开着的项目上下文 | 建议式但持久 |
| Skills | 按需程序 | 加载时建议式 |
| 权限规则／模式 | 工具允许／询问／封锁 | **由 Claude Code 强制执行** |
| Hooks | 生命周期脚本 | **被强制执行的保证** |

**核心区别：** 在 `CLAUDE.md` 里写「永远不要编辑 `.env`」是客气的请求。一条**封锁**规则，或挡住 `.env` 的 **PreToolUse hook**，才是保证。指示塑造意图；规则与 hooks 改变什么被允许。

### 3.1 精简的 CLAUDE.md

保持短到 Claude 真的会遵守。公开指引与好的考试答案收敛到：

- 项目目的、技术栈、目录结构（几则短句）
- 重要的命令（测试、lint、构建）
- 关于密钥、迁移、force-push 的硬性可做／不可做
- 指向 Skills／文档的指引，供冗长程序使用——**不要**贴进一本小说

把每一类内容放到对的表面上：

| 内容类型 | 表面 |
| --- | --- |
| 永远为真的事实与惯例 | CLAUDE.md |
| 按路径限定范围的惯例 | `.claude/rules/`（功能可用时） |
| 多步骤／偶发的工作流程 | Skills |
| 必须在事件执行的保证 | Hooks |
| 工具允许／封锁 | 权限规则 |

`/init`（或其等价物）扫描存储库并生成 CLAUDE.md 初稿；再用 Claude 单靠代码发现不了的东西去精炼。

**反模式：** 一份 2,000 行的 CLAUDE.md，拷贝了 README、wiki 和每一份编码标准 PDF。Claude 会打折扣地遵守它；考试奖励*精简*的记忆。

**CLAUDE.md 维护循环：** 在一次痛苦的会话之后，问：「有什么东西不应该需要从零重新发现？」把那个事实提升进 CLAUDE.md。如果它是一个程序，就改为提升成 Skill。

### 3.2 Skills

**Skills** 打包重复的程序（从一个执行真正检查的验证 Skill 开始）。概念上，典型 Skill 内容包括：

- 什么时候套用
- 步骤／命令
- 成功标准
- 可选的、给调用那一轮的 allowed-tools 授权（仍受限于基线权限）

Skills **按需**加载（被调用，或在相关时被自动选用）。这就是它们胜过把每个程序都塞进 CLAUDE.md 的原因。

**考试对比：**

- CLAUDE.md = 永远在上下文里 → 保持短小
- Skill = 需要时加载 → 细节没关系
- Hook = 不管 Claude 的「意见」都会执行 → 不可妥协的事项用它

团队的好第一批 Skills：「跑验证套件」、「带检查清单创建 PR」、「安全地迁移数据库」、「安全审查接触点」。

### 3.3 Plugins

**Plugins** 打包 CLAUDE.md 片段＋Skills＋hooks＋相关配置（有时还有 MCP／子代理），让全团队安装同一份受信任的设置。Plugins 谈的是**可携性**，不是新的模型能力。

何时分享：设置已验证、hooks 用真正的测试把关、权限是最小权限原则，而且上手成本从「读一份 wiki」降到「安装 Plugin」。

Plugin 卫生检查清单：

1. 把必要的环境变量与密钥注入点写成文档
2. 测试跑不了时失败即关闭
3. 帮 Skills 加上命名空间，让多个 Plugin 可以共存
4. 帮 Plugin 加上版本；破坏性变更需要变更记录
5. 团队 Plugin 永远不要默认略过权限

## 4. 权限模式（让模式配合风险）

模式在允许／询问／封锁规则之前设置基线。名称会演进；认识光谱：

| 模式（概念） | 行为 | 典型工作 |
| --- | --- | --- |
| 默认／手动 | 第一次使用工具时提示 | 交互式结伴 |
| Accept edits | 自动接受常见工作区编辑 | 受信任的本地功能开发 |
| Plan | 探索；计划核准前不改源代码 | 先设计再实现 |
| Auto（分类器） | 核准例行动作；挡住有风险的 | 带护栏的更快交互 |
| Don't ask | 严格；除非预先允许通常拒绝 | 受控的非交互执行 |
| Bypass／don't ask 的危险变体 | 略过大多数提示 | **仅限**隔离的 CI／沙箱 |

**评估顺序（心智模型）：** 封锁 → 询问 → 允许；先命中者胜。封锁胜过允许。一个以阻挡决定结束的 PreToolUse hook，仍然可以拦下调用，即使允许规则或 bypass 模式本来会放行——在许多设计里，hooks 是最后一道硬闸口。

**权限决策树：**

```text
互动式结伴／正在熟悉程序码库？
 → Default/manual 或 plan
核准计划之后的受信任本地功能？
 → Accept edits（或带分类器的 auto）
CI／无头搭配钉定的允许清单？
 → Don't ask + 明确允许 + hooks
抛弃式容器、没有密钥、文件系统用完即丢？
 → Bypass 也许可以接受
笔电上有生产凭证？
 → 永远不要 bypass；最小权限 + 拒绝规则
```

**考试陷阱：**

- 在持有生产凭证的笔记本电脑上，把 bypass 型模式当默认 → 错
- 以为 CLAUDE.md 会覆盖权限封锁 → 错
- 对一个受信任、规格已明确的单行改名使用计划模式 → 过于缓慢但不「不安全」；通常 accept-edits 或 auto 就行
- 以为 auto 模式可以取代 `.env` 的封锁规则 → 错；分类器是概率性的，封锁是绝对的

管理员可以在团队设置里停用 bypass——要知道组织政策可以移除这个逃生口。

## 5. Hooks：不可跳过的控制

Hooks 在固定的生命周期点触发。值得背起来的例子（确切事件名称可能演进——学的是*职责*）：

| 生命周期职责 | 范例用途 |
| --- | --- |
| 会话开始 | 注入环境事实、存储库分支警告 |
| 工具使用前 | 挡住 `.env`、对 `rm -rf` 强制询问、拒绝生产部署 |
| 权限请求 | 在非交互执行中自动决定 |
| 压缩前 | 把关键限制重新注入摘要 |
| 停止／一轮结束后 | 跑 linter；测试见红就立即中止（fail closed） |
| 文件／规则加载 | 审计什么进入了上下文 |

模式：

1. 封锁受保护路径（`.env`、生产配置、私钥）
2. 用**真正的**测试执行器为一轮把关（红了就失败即关闭）
3. 对敏感 Bash 强制提示，即使 Bash 大致上被允许
4. 压缩之后重新注入关键上下文
5. 以权限决定 JSON／结束码回传允许、拒绝或询问

**Hooks 强制执行；提示词只是建议。**

**非交互提醒：** 在无头 `-p` 执行里，交互式权限提示可能根本不存在。依赖 PreToolUse hooks 与预先声明的允许／封锁规则——不要假设会有人类去按「允许」。

**给考试的 hook 设计提示：**

- 安全检查优先失败即关闭（测试执行器不存在 = 拒绝）
- 保持 hooks 快速；慢的 hooks 会让交互使用受挫，然后被停用
- 记录拒绝时要带足够审计用的细节，但不要把密钥倒进日志
- 不要把不可逆的破坏性能力，只放在软性询问后面

## 6. 自动化光谱

一旦任务受信任，就不要再亲手启动：

1. **例行调度（Routines）** — 在 Anthropic 管理的基础设施上调度提示词（运维最少）。
2. **无头模式（Headless）** — `-p`／`--print`：一次性、没有 TUI；stdin／stdout 给管线与持续集成（CI）。
3. **精简／确定性标志** — 当 CI 需要可重复、低变异的执行时优先使用。
4. **Agent SDK** — 把 Claude Code 嵌进你的 TypeScript／Python 产品。
5. **PR／GitHub Action 接线** — 受管的审查模式；把 Claude 接进 pull request 循环。

**决策规则：** 从例行调度开始；当工作需要*你的*环境或周围脚本逻辑时，降到无头模式；当 agent *就是*产品的一部分时，用 Agent SDK。

```text
需要 Anthropic 托管的调度、自订环境很少？
 → 例行调度（Routine）
需要本机密钥、Docker、私有套件、自订脚本？
 → 在你的 runner 上跑无头模式
需要 agent 嵌进产品 UX？
 → Agent SDK
需要 PR 评论／检查？
 → GitHub Action／受管审查集成
```

没有等比例验证的自动化是不完整的——这句话本身就是考试答案。

**值得记住的无头细节：**

- 非交互意味着权限循环里没有人
- 经由 stdin 或参数送入提示词；捕获 stdout 当日志
- 搭配明确的权限允许清单与 PreToolUse hooks
- 当 CI 不稳定失败代价很高时，优先用确定性设置

## 7. 验证无人监督的工作

**你盯得越少，验证得越多。**

| 无人监督程度 | 最低验证 |
| --- | --- |
| 交互式结伴 | 抽查差异比较 |
| Accept-edits 本地执行 | `git diff`＋冒烟测试 |
| Auto 模式长会话 | 差异审查＋针对性测试＋hook 闸口 |
| 无头／调度／bypass | 强制自动化测试、危险工具的封锁规则、高风险路径的人工审查 |

永远不要相信 Claude「测试通过了」的宣称——在 hook 或 CI 步骤里执行执行器。

**验证 Skill 模式：** 把「跑单元＋lint＋类型检查；打印摘要；失败时非零结束」打包成 Skill，并且把同一组命令接到无人值守执行的 Stop／PreToolUse 闸口。

**依风险分级的审查：**

- 低：格式、注释、文档 → 自动化检查可能就够
- 中：应用逻辑 → 测试＋扫一眼差异
- 高：身份验证、付款、迁移、IAM → 不论 CI 是不是绿的，都强制人工审查

## 8. 实务端到端工作流程（认证检查清单）

1. 初始化／扫描存储库（`/init` 或其等价物）。
2. 在要求功能之前，喂入相关文件／指向子系统。
3. 计划（不写代码）然后核准然后实现。
4. 当质量重要时，优先用有测试意识的循环。
5. 把持久规则编码进 CLAUDE.md；程序进 Skills；硬性停止进 hooks。
6. 依工作风险选择权限模式。
7. 只有验证稳固之后才自动化；经由 Plugin 分享。
8. 若漂移：倒回，然后一个目标，然后继续。
9. 发布 Plugin 之前：用一次故意变红的测试证明 hooks 会失败即关闭。

**会话卫生习惯：**

- 每一段自主工作只有一个目标
- 大型自主执行之前先 commit 或 stash，让倒回或 git restore 容易
- 使用 worktree 时把分支取清楚的名字
- 压缩之后，用一句话重述目前计划

## 9. 反模式（高报酬考试识别）

| 反模式 | 为什么失败 | 优先改用 |
| --- | --- | --- |
| 安全只活在聊天或 CLAUDE.md | 建议式；压力下被忽略 | 封锁加上 PreToolUse hook |
| 笔记本电脑上 bypass 加上生产凭证 | 巨大爆炸半径 | 沙箱 CI 加上最小权限原则 |
| 测试还不存在就自动化 | 大规模无人监督垃圾 | 先写闸口 |
| 两个 agent、一条脏分支 | 合并混乱或丢掉工作 | Worktree |
| 相信模型宣称测试通过 | 幻觉出来的验证 | Hook 执行执行器 |
| CLAUDE.md 里的小说 | 稀释；打折扣遵守 | Skills 加上精简 CLAUDE.md |
| 矛盾之后用压缩代替倒回 | 糟糕摘要把混乱锁死 | 倒回 |
| 永远待在计划模式 | 永远无法发布 | 核准计划然后进入实现模式 |
| 默认 bypass 的 Plugin | 散播不安全默认 | 最小权限默认 |
| 忽略 Stop-hook 失败 | 把坏掉的代码漂绿 | 失败即阻断（fail closed） |

## 10. 比较：控制面深挖

把 Claude Code 配置想成分层防御：

```text
[Chat instructions] advisory, ephemeral
 |
[CLAUDE.md / rules] advisory, durable
 |
[Skills] advisory, on-demand depth
 |
[Permission modes/rules] enforced allow/ask/deny
 |
[Hooks] enforced lifecycle guarantees
 |
[CI / human review] external verification
```

考试喜欢这种情境：学生选了比需要更高的层（例如，需要封锁规则时却往 CLAUDE.md 加一本小说），或比需要更低的层（希望单靠聊天挡住 force-push）。

**走完的情境 A — 密钥文件保护**

- 错：在聊天里请它不要碰密钥文件
- 较好：CLAUDE.md 注记，单靠它仍不够
- 对：对密钥环境文件的编辑／写入设封锁规则，加上挡住那些路径的 PreToolUse hook

**走完的情境 B — 每周依赖套件升级**

- 错：每周一手动重新提示，笔记本电脑上用 bypass
- 对：已验证的 Skill 加上例行调度或无头 CI 工作，加上测试，加上给人类合并的 PR

**走完的情境 C — 不熟悉的付款重构**

- 错：auto 模式隔夜跑
- 对：计划模式、设计审查、范围收紧的 accept-edits、测试、付款路径的人工审查

## 11. 考试提示

- 把情境对应到掌舵／设置／自动化／验证。
- 每次都识别建议式对强制式控制。
- 不熟悉或多文件工作优先用计划模式。
- 平行 agent 优先用 worktree。
- 优先用例行调度，直到你真正需要无头模式或 SDK。
- 没有 CLAUDE.md 的压缩会弄丢惯例——那个失败模式可考。
- 没有隔离的 bypass 是错误的安全答案。
- Hooks 即使在模式宽松时也能挡住——要知道那个顺序故事。
- Plugins 打包信任；它们不取代验证。
- 没有 hooks 的无头模式，对无人值守安全来说是不完整的答案。

## 12. 自我检核问答（附答案）

**Q1.** CLAUDE.md 说永远不要提交密钥，但一个密钥环境文件还是被加入暂存区。什么挡得住它？
**A.** 封锁权限规则与／或 PreToolUse hook——不是那句 markdown 句子本身。

**Q2.** 什么时候计划模式是正确的默认？
**A.** 在大型或不清楚的编辑之前：探索并提案，核准前不改源代码。

**Q3.** 多次失败尝试之后会话混乱了。下一步？
**A.** 倒回（或小心压缩），然后一个清楚的目标——避免互相矛盾的叠加指示。

**Q4.** 每周一同一个提示词。第一个自动化选择？
**A.** 例行调度；若需要本机环境或自定义管线再降到无头模式。

**Q5.** 为什么用 CLAUDE.md 而不是只靠聊天？
**A.** 聊天会被压缩掉；CLAUDE.md 是持久的项目指示面。

**Q6.** 两个 agent 在同一条分支——更安全的模式？
**A.** 用 git worktree／各自独立的签出隔离。

**Q7.** 无头 `-p` 提供什么？
**A.** 非交互、可脚本化的执行，给管线与管道串联。

**Q8.** 完全无人值守的执行要多少验证？
**A.** 最大：测试闸口、危险工具的封锁规则，以及与零人类盯着成比例的审查政策。

**Q9.** 一份 20 步的发布检查清单，用 Skill 还是 CLAUDE.md？
**A.** Skill（按需程序）；让 CLAUDE.md 保持精简，加一个指引。

**Q10.** 在开发者机器上做受信任的本地功能开发，accept-edits 对上 bypass？
**A.** Accept-edits（或带分类器的 auto）。Bypass 属于隔离沙箱／CI，不是笔记本电脑默认。

**Q11.** PreCompact hook 常常该做什么？
**A.** 重新注入关键限制，让压缩摘要不要丢掉不可妥协的事项。

**Q12.** Plugin 对上 Skill？
**A.** Skill = 一个打包的程序／知识单元。Plugin = 可安装的 Skills、hooks、设置组合包（可携层）。
**Q13.** Auto 模式仍然做了危险的事。你的下一步加固？
**A.** 为那类动作加上明确的封锁规则与／或 PreToolUse hook——不可妥协的事项不要单靠分类器。

**Q14.** 什么时候选 Agent SDK 而不是无头 CLI？
**A.** 当编码 agent 嵌在你的产品 TypeScript／Python 应用程序里，而不只是从 shell 管线调用。

**Q15.** GitHub Action 在每个 PR 上跑 Claude。必须先有什么？
**A.** 等比例验证：真正的测试、范围收紧的权限，以及高风险路径的审查——没有闸口的自动化是不完整的。

**Q16.** 允许与封锁都符合同一个工具路径时，评估顺序？
**A.** 封锁胜出（先命中心智模型：封锁在允许之前）。

**Q17.** 为什么 bypass 模式里 hooks 仍然重要？
**A.** PreToolUse hooks 可以不管权限模式就拒绝——它们强制执行用户无法靠翻模式跳过的政策。

**Q18.** 平行 agent 编辑同一个文件——正确吗？
**A.** 不正确。拆成独立工作；隔离工作树；刻意合并。

**Q19.** `/init` 之后，CLAUDE.md 又大又泛。你怎么做？
**A.** 修剪成永远为真的事实；把程序移到 Skills；只加入无法从代码发现的惯例。

**Q20.** 无人值守工作需要私有套件仓库凭证。例行调度还是无头？
**A.** 无头（或你的 CI），密钥与网络住在那里——不是单靠云端例行调度，除非那份基础设施有那些密钥。

**Q21.** 打造团队 Claude Code 成熟度的阶梯顺序是什么？
**A.** 掌舵，然后设置，然后自动化，然后验证／分享。

**Q22.** 抽查差异对调度的隔夜重构够吗？
**A.** 不够——要求自动化测试加上 hooks，加上高风险差异的人工审查。

**Q23.** 不可逆的「永远不准」规则属于哪里？
**A.** 权限封锁规则与 hooks——不是只在 CLAUDE.md。

**Q24.** 定向压缩应优先保留什么？
**A.** 已核准的计划、未决的决策、限制，以及失败测试——丢掉嘈杂的失败实验转储。

**Q25.** 若 CI 已经跑测试，为什么验证 Skill 仍然有价值？
**A.** 本地交互循环更早抓到失败；同一组命令也应把关无人值守的 Stop／PreToolUse hooks，以保持一致。

## 14. 词汇表

- **计划模式** — 研究／提案，核准前不改源代码。
- **压缩** — 摘要较旧上下文以腾出窗口空间。
- **定向压缩** — 引导摘要必须保留／丢掉什么。
- **倒回** — 漂移之后恢复较早的会话状态。
- **CLAUDE.md** — 每个会话加载的持久项目记忆。
- **规则（Rules）** — 模块化／按路径限定范围的指示文件（使用时）。
- **Skill** — 按需打包的程序或领域知识。
- **Hook** — 被强制执行的生命周期脚本（允许／拒绝／询问／副作用）。
- **权限模式** — 工具核准行为的基线。
- **允许／询问／封锁规则** — 明确的工具权限政策。
- **例行调度（Routine）** — Anthropic 基础设施上受管的调度执行。
- **无头模式（Headless）** — 给管线用的 print／一次性 CLI（`-p`）。
- **Agent SDK** — 把 Claude Code 循环嵌进你的应用程序。
- **Plugin** — 可分享的 Claude Code 设置组合包。
- **Worktree** — 隔离平行 agent 用的独立 Git 工作树。
- **验证闸口** — 失败即关闭的真正测试／lint 命令。
- **建议式对强制式** — 提示词／CLAUDE.md 建议；权限／hooks 强制执行。
- **目标与循环** — 自主风格：清楚目标，迭代直到检查通过。
- **分类器 auto 模式** — 由模型协助核准例行动作，并挡住风险。
- **失败即关闭** — 若安全检查跑不了，视为失败／拒绝。

## 15. 额外深度：子代理、MCP 与团队推行

### 子代理（概念）

Claude Code 可以为隔离工作生成专门的子代理（explore、plan 或自定义）。隔离避免把主会话撑大。考试：当子任务不需要完整对话时用子代理；把危险工具约束住；记住非交互模式里的背景子代理无法显示交互提示——由 hooks 与封锁决定。

### Claude Code 里的 MCP

MCP 服务器扩展编码 agent 可用的工具／资源／提示。把 MCP 工具当成任何其他工具：权限规则与 hooks 仍然适用。不要因为 MCP 服务器「只是配置」就假设它安全——它可以暴露强大的副作用。

### 团队推行顺序（实务）

1. 一个存储库试点：精简 CLAUDE.md＋验证 Skill＋封锁密钥
2. 为受保护路径与测试闸口加上 PreToolUse hooks
3. 标准化交互对上 CI 的权限默认
4. 打包成 Plugin；安装到第二个存储库
5. 为一件无聊的每周任务加上例行调度／无头
6. 衡量：较少嘈杂的权限提示、较少事故、更快的 PR 检查
7. 然后才扩大自主程度（auto 模式、更多例行调度）

### 真正重要的指标（不是虚荣）

- 从 issue → 绿的 PR 的时间
- 挡下真正错误的 hook 拒绝率
- 验证闸口的不稳定失败率
- 新工程师带着 Plugin 的上手时间
- 涉及无人监督编辑的事故

### 读书节奏

第 1 天：第 1–5 节（掌舵＋设置）。闪卡建议式对强制式。
第 2 天：第 6–10 节（自动化＋验证＋反模式）。大声走决策树。
第 3 天：全部问答闭书，然后检查清单。只重读漏掉的项目。

- 会话需要倒回时，「压缩」
- 需要 worktree 时，「两个 agent 共用一条分支」
- CI／hooks 必须执行执行器时，「Claude 说测试通过了」

# CCAR-F 领域 3 机制补充（2026-08-23 添加）

> **范围：** **CCAR-F 考试指南领域 3（Claude Code 设置与工作流程，20%）** 会考、而上方课程笔记只概念涵盖的具体设置机制——任务陈述 3.1（CLAUDE.md 层级）、3.2（commands 与 Skills）、3.3（路径特定规则）、3.4（计划模式／Explore）、3.6（CI／CD 标志）。以下所有文件路径与 frontmatter 键已对照现行 Claude Code 文档核实（2026-08）；原创综述，易变细节已加保留说明。

## S1. CLAUDE.md 层级、@import 与 /memory（任务 3.1）

**考试点名的三层：**

| 层级 | 位置 | 共享？ |
| --- | --- | --- |
| **用户** | `~/.claude/CLAUDE.md` | 否——个人，套用到你所有项目，**不在**版本控制里 |
| **项目** | `./CLAUDE.md`（根目录）或 `./.claude/CLAUDE.md` | 是——经由版本控制，全团队 |
| **目录** | 子目录里的 `CLAUDE.md` | 是——当 Claude 处理该目录里的文件时**按需**加载 |

文件**拼接**（较广范围先、较靠近工作的后读）；它们不会互相覆盖。*（现行文档在用户之上加了一层受管／组织政策层——全组织、无法排除——以及给个人单项目注记用、被 gitignore 的 `CLAUDE.local.md`；知道它们存在。）*

**考试喜欢的诊断情境：** 新队友的 Claude 忽略「团队的」指示 → 那些指示活在某人**用户层**的 `~/.claude/CLAUDE.md`，而不是**项目层**配置，所以版本控制从来没把它们送出去。

**`@import` 语法：** 从 CLAUDE.md 用 `@path/to/file` 参照外部文件——被导入的文件在启动时展开进上下文。用它让 CLAUDE.md 保持模块化，例如每个套件的 CLAUDE.md 只导入与它相关的标准文件。*（细节已核实：相对路径相对*导入文件*解析；导入递归最多 **四跳**（依现行官方文档，2026-08-23 核实）；把路径包在反引号里可以*提及*而不导入。）*

**`/memory`** 列出跨范围的记忆文件（CLAUDE.md 与伙伴文件），并让你打开／编辑它们——用它**核实加载了哪些记忆文件，并诊断跨会话的不一致行为**。*（现行文档：`/context` 另外确认这一轮实际加载了什么。）*

## S2. 自定义 slash command 与 Skills（任务 3.2）

**Commands — 范围规则（官方样例题 Q4 就卡在这）：**

| 位置 | 范围 |
| --- | --- |
| 存储库里的 **`.claude/commands/`** | 项目——**纳入版本控制，clone／pull 后自动对每位开发者可用** |
| **`~/.claude/commands/`** | 用户——个人，不共享 |

一个 markdown 文件 `.claude/commands/review.md` 定义 `/review`。团队标准工作流程 → 项目范围；个人助手 → 用户范围。*（现行文档注：自定义 commands 已并入 Skills——`.claude/commands/deploy.md` 与 `.claude/skills/deploy/SKILL.md` 都会创建 `/deploy`；既有 commands 继续可用。考试面对「团队共享的 /review command」的答案，仍然是项目存储库里的 `.claude/commands/`。）*

**Skills** 住在 `.claude/skills/<name>/SKILL.md`（项目）或 `~/.claude/skills/`（个人）。考试点名、且已核实现行的 frontmatter 键：

| Frontmatter 键 | 它做什么 |
| --- | --- |
| **`context: fork`** | 在**隔离的子代理上下文**里跑 Skill，避免冗长的 Skill 输出（代码库分析、头脑风暴）**污染主对话** |
| **`allowed-tools`** | Claude 在 Skill **调用那一轮**可以**不经权限提示**使用的工具——限缩到 Skill 需要的（例如只写文件，以防止破坏性动作） |
| **`argument-hint`** | 自动完成提示，显示预期参数（例如 `[issue-number]`），当开发者调用 Skill 却没带它们时 |

**不影响团队的个人变体：** 在 `~/.claude/skills/` 下用**不同名称**创建你自己的版本，让团队的项目 Skill 保持原样。

**Skills 对上 CLAUDE.md（考试的分界线）：** Skills = **为任务特定工作流程按需调用**（内容只在使用时加载）；CLAUDE.md = **永远加载的通用标准**。一段已经变成*程序*、还在长大的 CLAUDE.md 区块，应搬到 Skill。

## S3. 路径特定规则 — `.claude/rules/`（任务 3.3）

规则文件是 **`.claude/rules/`** 里的 markdown，带 **YAML frontmatter，其 `paths:` 字段放 glob 模式**：

```markdown
---
paths:
 - "src/api/**/*"
 - "**/*.test.tsx"
---
# API + test conventions
- All endpoints validate input
- Tests use the team fixture factory
```

- 规则**只在 Claude 处理符合其 glob 的文件时加载**——不相干的惯例待在上下文外面，节省 token（*没有* `paths` 的规则每个会话都加载，像 CLAUDE.md）。
- **当惯例跨目录时，glob 胜过目录层 CLAUDE.md**（官方样例题 Q6）：测试文件散落在整棵树的源代码旁边，所以 `**/*.test.tsx` 全部抓得到——每个目录一份 CLAUDE.md 做不到，根目录 CLAUDE.md 加标题靠推理，Skills 需要被调用。带 glob 的规则才是确定性、自动的答案。
- 指南自己的练习例子：`paths: ["terraform/**/*"]`，让 Terraform 惯例只在编辑 Terraform 时加载。

## S4. 计划模式、直接执行，与 Explore 子代理（任务 3.4）

具名决策规则（上方第 2.1 节涵盖工作流程；考试要的是*标准*原文）：

- **计划模式** — 复杂任务：大规模变更、**多种有效做法**、架构决策、多文件修改（单体→微服务；45 个文件的函数库迁移）。在**承诺变更之前**安全探索与设计，避免昂贵的返工（样例题 Q5 的正确 A）。
- **直接执行** — 简单、范围明确的变更：带清楚堆栈追踪的单文件错误修正；加上一个验证条件。
- **组合它们：** 调查用计划模式，计划好的实现改用直接执行。
- **Explore 子代理**隔离**冗长的探索输出**并回传摘要，在多阶段工作中**保住主对话上下文**——当题目描述代码库探索期间上下文耗尽时，点它的名。（连到领域 5.4 子代理委派。）

## S4b. 迭代式精炼技巧（任务 3.5）

- 当自然语言对转换的描述被不一致地解读时，**具体的输入／输出例子胜过叙述文字**——提供 **2–3 对例子**，展示输入与预期输出。
- **测试驱动迭代：** 先写测试套件（预期行为、边界情况、性能），然后通过**分享测试失败**来引导渐进改善；带例子输入／预期输出的具体失败案例，能修好边界处理（例如迁移脚本里的空值）。
- **访谈模式：** 在不熟悉的领域，让 Claude **先问你问题**，把你还没预料到的考量（缓存失效策略、失败模式）浮出来，*然后*才实现。
- **互相影响对上独立问题：** 会**互相影响**的修正 → 一则详细消息一次处理全部；**独立**问题 → 循序迭代没问题。

## S5. CI／CD 集成标志（任务 3.6）

| 机制 | 考试事实 |
| --- | --- |
| **`-p`／`--print`** | 以**非交互**方式跑 Claude Code：处理提示词、写到 stdout、结束——当管线工作「卡住等交互输入」时的修复方法（样例题 Q10；像 `CLAUDE_HEADLESS=true` 或 `--batch` 这类干扰选项是**不存在的功能**） |
| **`--output-format json`** | print 模式的机器可解析输出（`text`、`json`、`stream-json`） |
| **`--json-schema`** | print 模式标志，产出**通过验证、符合你 schema 的 JSON**——结构化发现结果，准备好自动贴成 PR 评论 |
| **CI 里的 CLAUDE.md** | 给 CI 调用的 Claude 项目上下文的机制：测试标准、测试夹具惯例、审查准则——更好的测试生成、较少低价值案例 |
| **会话上下文隔离** | **生成**代码的那个会话，较不擅长**审查**它（它保留自己的推理上下文，不会质疑自己的决策）——把审查当**独立实例**跑（连到领域 4.6 多实例审查） |
| **重审不重复** | 新 commit 之后重跑时，把**先前的审查发现结果**放进上下文；指示 Claude 只回报新的或仍未处理的问题 |
| **生成测试不重复** | 把**既有测试文件**放进上下文，让生成的测试跳过已经涵盖的情境 |

## S6. 补充问答

**SQ1.** *（＝官方样例题 Q4）* 一个 `/review` command 必须在 clone／pull 时到达每位开发者。文件放哪里？
**A.** 项目存储库里的 `.claude/commands/`——纳入版本控制的项目范围。`~/.claude/commands/` 是个人的；CLAUDE.md 放指示，不是 command 定义；带 commands 数组的 `.claude/config.json` 不存在。

**SQ2.** *（＝官方样例题 Q6）* React、API 与数据库惯例不同；测试文件到处紧挨着源代码，且共享一套惯例。最可维护的机制？
**A.** `.claude/rules/` 文件加上 YAML frontmatter glob 模式（`**/*.test.tsx`）——有条件、自动、与位置无关。根目录 CLAUDE.md 标题靠推理；每个目录一份 CLAUDE.md 跨不了整棵树；Skills 需要被调用。

**SQ3.** 新队友拿不到「团队的」指示。可能原因？
**A.** 指示活在用户层 `~/.claude/CLAUDE.md`（不经版本控制共享），而不是项目层 `CLAUDE.md`／`.claude/`。

**SQ4.** 如何让每个套件的 CLAUDE.md 保持模块化？
**A.** `@import` 语法（`@docs/standards.md`）——每个套件的 CLAUDE.md 只导入相关标准文件。

**SQ5.** 哪个命令核实加载了哪些记忆文件？
**A.** `/memory`（`/context` 确认这一轮加载了什么）。

**SQ6.** 一个代码库分析 Skill 用输出淹没主对话。Frontmatter 修复方法？
**A.** `context: fork`——在隔离的子代理上下文里跑 Skill。

**SQ7.** 把 Skill 限缩成只写文件以防止破坏性动作——哪个键？
**A.** SKILL.md frontmatter 里的 `allowed-tools`（为调用那一轮授予范围收紧、免提示的工具使用）。

**SQ8.** 开发者调用 `/deploy` 却没带必要参数。哪个键提示他们？
**A.** `argument-hint`（例如 `[environment] [version]`）。

**SQ9.** 你想要团队 Skill 的个人变体，又不影响队友。
**A.** 在 `~/.claude/skills/` 下用**不同名称**创建它。

**SQ10.** Skill 还是 CLAUDE.md：20 步发布程序对上「我们用 2 空格缩进」？
**A.** 程序 → Skill（按需）；通用标准 → CLAUDE.md（永远加载）。

**SQ11.** 有 `paths:` 范围的规则何时加载？
**A.** 只在 Claude 处理符合 glob 的文件时；没有 `paths` 的规则每个会话都加载。

**SQ12.** 单体→微服务重构：计划模式还是直接？
**A.** 计划模式——大规模、多种有效做法、架构决策（样例题 Q5）。带堆栈追踪的单文件错误修正 → 直接执行。

**SQ13.** 多阶段任务在探索期间耗尽上下文。具名解法？
**A.** Explore 子代理——冗长探索被隔离，摘要被回传。

**SQ14.** CI 工作卡住：「Claude Code 正在等交互输入。」修复方法？
**A.** `claude -p "..."` — `-p`／`--print` 标志就是文档化的非交互模式（样例题 Q10；`CLAUDE_HEADLESS`／`--batch` 不存在）。

**SQ15.** 来自 CI、结构化、机器可张贴的审查发现结果——哪些标志？
**A.** `--output-format json` 搭配 `--json-schema`（print 模式）。

**SQ16.** 为什么写代码的那个会话不该审查它？
**A.** 会话上下文隔离：它保留生成时的推理，不会质疑自己的决策——用独立审查实例。

**SQ17.** 新 commit 之后重跑审查，重复评论刷屏。修复方法？
**A.** 把先前发现结果放进上下文，并指示：只回报新的或仍未处理的问题。

**SQ18.** 生成的测试重复既有覆盖。修复方法？
**A.** 把既有测试文件放进上下文，让生成避开已涵盖的情境。
