# 上下文管理与可靠性 — 领域 5（15%）

> **免责声明：** 原创备考读书综整，对齐 **官方 CCAR-F 考试指南 v1.0（2026 年 7 月）** 任务陈述 5.1–5.6 与公开的 Anthropic 文档。

> **为何有这份文件：** 领域 5 贯穿 **六个考试情境题中的四个**（客户支持、Claude Code 会话、多 agent 研究、结构化提取）。它测的是判断层：什么该留在上下文里、什么时候该升级、错误如何在 agent 之间传播，以及人类如何对模型输出保持校准。

## 概览

六条任务陈述：**5.1** 在长交互中保存关键信息；**5.2** 升级与模糊情境的解决；**5.3** 多 agent 系统中的错误传播；**5.4** 大型代码库探索中的上下文；**5.5** 人类审核工作流程与信心校准；**5.6** 多来源综合中的出处可追溯性与不确定性。

**总体心智模型：** 上下文是一个有损的、对位置敏感的、有限的缓冲区。这里的可靠性工程意味着 (a) 决定*什么绝对不能有损*（案件事实、出处可追溯性、错误细节），并把它们移到自由流动的历史之外的**结构化分层**；(b) 永远不要只靠单一的非结构化信号（模型信心、情绪、整体准确率）来做路由决策。

## 深入笔记

### 1. 在长交互中保存关键信息（任务 5.1）

**渐进式摘要的风险：** 每一次摘要，都容易把**数值、百分比、日期，以及客户明说的期望**浓缩成模糊的叙述文字（「讨论过部分退款」丢掉了「星期五之前 $127.50」）。精确的交易事实，正是摘要最先摧毁的东西。

**修复方法——持久化的「案件事实」区块：** 把交易事实（金额、日期、订单编号、状态）提取出来，放进一个结构化区块，**附在每一个提示词里，放在摘要化历史之外**。摘要可以继续有损，因为事实层是无损的。对于有多个问题的会话，把结构化的问题数据（订单 ID、金额、每个问题各自的状态）保存为独立的上下文分层。

**中段遗失：** 模型能可靠处理长输入的**开头和结尾**，但可能漏掉**中段**的发现。缓解方法：把**关键发现摘要放在汇总输入的开头**；用**明确的节标题**组织细节；不要把决定性的限制条件埋在一个 100K token 提示词的 60% 位置。

**工具结果膨胀：** 工具结果累积的 token 和它的相关性不成比例——一次订单查询会回传 40 多个字段，但只有 5 个重要。**在冗长的工具输出进入上下文之前，先修剪到回传相关的字段。** 在多 agent 系统中，把这件事往上游推：下游消费者上下文有限时，子代理应回传**结构化数据（关键事实、引用来源、相关性分数），而不是冗长的内容和推理链**，并附上元数据（日期、来源位置、方法论上下文）以支持准确综合。

**对话连贯性的基本功：** 后续的 API 请求要传完整的对话历史——API 是无状态的；「agent 忘记了上一轮」通常代表客户端没有重新发送它。

### 2. 升级与模糊情境的解决（任务 5.2）

**正当的升级触发条件（考试指南的清单）：**

1. 客户**明确要求真人**——**立即**升级，不要先尝试调查。（若问题简单，你可以认同挫折并*提出*修复方案，但对方重申就升级。）
2. **政策例外或缺口**——政策对这个特定请求含糊或没有规定（要求和竞争对手比价，但政策只涵盖自家网站的价格调整）。注意：这讲的是*政策涵盖范围*，不是案件难度。
3. **无法取得有意义的进展。**

**不可靠的升级信号（考试会当错误答案来考）：**

- **自我报告的信心分数**——校准很差；agent 恰恰在困难案件上自信满满地答错（官方样例题 Q3 的错误选项 B）。
- **情绪分析**——挫折感和案件复杂度没有相关（Q3 的错误选项 D）。
- 升级校准很差时，相称的第一步修复方法是**明确的升级标准，加上系统提示词里示范「升级还是解决」的 few-shot（少样本）范例**（Q3 的正确选项 A）——在创建任何分类器基础设施之前先做这件事。

**模糊情境的解决：** 当查询回传**多个匹配的客户**，指示 agent **要求额外的识别信息**——绝不要用启发法挑选（「大概是最新的那个账户」）。

### 3. 多 agent 系统中的错误传播（任务 5.3）

**结构化错误上下文**让协调者能做出聪明的恢复决策。失败时，子代理回传：**失败类型、尝试过的查询、任何部分结果，以及潜在的替代方案**（官方样例题 Q8 的正确选项 A）。

**两个反模式（考试指南都点名了）：**

- **静默压制**——回传标记为成功的空结果，隐藏了失败，并有让不完整的输出被当成完整呈现的风险。
- **单一失败就终止整个工作流程**——杀死了原本可能成功的恢复策略（用修改过的查询重试、切换到替代来源、带着部分结果继续前进）。

**访问失败对有效的空结果：** 超时（「连不上来源」→ 需要重试决策）与查询成功但没有匹配（一个真正的答案）有根本的不同。错误报告必须区分两者，否则协调者会对空结果重试，并且默默接受中断。

**本地恢复优先：** 子代理自己处理 **transient**（暂时性）失败（用退避重试）；它们只传递本地**无法解决**的错误，并附上尝试过什么以及部分结果。笼统的状态（「搜索不可用」）隐藏了恢复所需的上下文。

**涵盖范围注记：** 当综合在有缺口的情况下继续进行，输出必须**注记哪些发现有充分支持，以及哪些主题领域因为来源不可用而有缺口**——降级的覆盖范围必须可见，不能静默。

### 4. 大型代码库探索中的上下文（任务 5.4）

**劣化症状：** 在拉长的会话中，模型开始给出**不一致的答案**，并引用「典型模式」，而不是它**先前发现的特定类别**——退回一般知识就是信号，代表已发现的事实已被稀释或逐出。

**对策（四个都是考试列出的技能）：**

1. **暂存文件**——agent 维护一个记录关键发现的文件，并**在后续问题中参考它**，让知识跨越上下文边界持续存在。文件是无损的；上下文不是。
2. **子代理委派**——把冗长的调查交给子代理（「找出所有测试文件」、「追踪退款流程的依赖关系」）；探索输出留在子代理的上下文里，主 agent 保持高层协调干净。
3. **阶段摘要**——在启动下一阶段的子代理之前，先摘要这一个探索阶段的关键发现，并**把那份摘要注入它们的初始上下文**。
4. **`/compact`**——在拉长的会话中，当上下文被冗长的探索输出填满时，用来压缩上下文（在 Claude Code 里搭配定向压缩——见文件 `05`）。

**用 manifest 做宕机恢复：** 结构化状态持久化 = 每个 agent **把自己的状态导出到一个已知位置**；恢复时，协调者**加载 manifest 并把它注入 agent 的提示词**。一次宕机付出的代价，只是一个阶段的尾巴，不是整次执行。（同一个「文件胜过上下文」原则，套用到全系统恢复。）

### 5. 人类审核工作流程与信心校准（任务 5.5）

**整体指标会掩盖分段失败：** 「97% 整体准确率」可能藏着某一种文档类型或某一个字段只有 60% 准确率。**在自动化高信心提取之前，要按文档类型、按字段分段验证准确率。**

**分层随机采样：** 即使模型标记为高信心的提取，每个分层也要**持续做随机采样**（文档类型 × 字段），以测量真实的错误率，并捕捉**新出现的错误模式**。没有这个采样，漂移在事故发生前是看不见的。

**校准过的字段层级信心：** 让模型输出**每个字段的信心分数**，然后**用已标记验证集校准审核门槛**——原始的自我报告信心不可信（与 5.2 同一课）；对照标签校准，才让信心可以用于路由。

**路由规则：** 低信心的提取以及**模糊或互相矛盾的来源文档**交给人工审核，把有限的审核人力优先放在错误概率真正最高的地方。

### 6. 多来源综合中的出处可追溯性与不确定性（任务 5.6）

**出处归属会死在摘要里：** 当发现被压缩而没有保存**主张与来源对应**，最终报告就说不出哪个来源支持哪个主张。修复方法：子代理输出**结构化的主张与来源对应（主张、来源 URL／文档名称、相关摘录）**，下游 agent **在综合过程中保存并合并**——出处可追溯性是一份数据契约，不是一种写作习惯。

**可信来源的统计数字互相冲突：** **用来源归因注记这个冲突**——绝不要任意挑一个数字，也绝不要取平均。文档分析完成时，**要把冲突的数值都放进去，并明确注记**，让协调者在综合之前决定如何调和。

**时间元数据：** 要求**结构化输出带上发布／搜集日期**，这样一个 2024 年的数字和一个 2026 年的数字读起来是一条时间序列，而不是矛盾。

**报告结构：** 用明确的小节把**已确立的发现和有争议的发现**分开，保留原始来源的表述方式以及方法论上下文。依内容类型适当呈现——**财务数据用表格、新闻用叙述文字、技术发现用结构化清单**——不要把所有东西压平成一致的叙述文字。

## 决策树

**「这份信息该住在哪里？」**

```text
精确的交易事实（金额、日期、ID）？
 → 每一个提示词的案件事实区块，放在摘要化历史之外
之后还需要的、已发现的代码库／系统事实？
 → 暂存文件（按需重新读取）
冗长的原始工具输出？
 → 在进入上下文之前修剪到相关字段
跨阶段／跨宕机的状态？
 → 结构化状态导出 + 协调者加载的 manifest
跨来源的「谁说了什么」？
 → 在每次交接中都保存下来的主张与来源对应
```

**「升级还是解决？」**

```text
客户明确要求真人 → 现在就升级（不要先调查）
政策对这个请求没有规定／含糊 → 升级（政策缺口）
无法取得有意义的进展 → 用结构化交接升级（文件 08 第 4 节）
只是复杂，但在政策内而且有进展 → 继续解决
多个身份匹配 → 要求更多识别信息，绝不要猜
```

**「一个子代理失败了——什么该向上流动？」**

```text
暂时性？ → 先本地重试；恢复了就什么都不上传
不可恢复？ → 失败类型 + 尝试过的查询 + 部分结果 + 替代方案
空结果集？ → 以零匹配的成功报告（不是错误）
综合无论如何都要继续？ → 输出里附上覆盖缺口注记
```

## 考试陷阱

| 陷阱 | 修复方法 |
| --- | --- |
| 为了省 token 把所有东西都摘要 | 数字／日期／ID 先进入无损的案件事实层 |
| 关键限制被埋在提示词中段 | 开头／结尾的位置安排 + 节标题（中段遗失） |
| 完整的 40 字段工具载荷留在历史里 | 在上游修剪到相关字段 |
| 根据情绪或自我信心路由升级 | 明确标准 + few-shot；在信任信心之前先对照标签校准 |
| 客户要求真人时，却先调查 | 立即升级 |
| 把「搜索不可用」当错误消息 | 结构化错误上下文（类型、尝试、部分结果、替代方案） |
| 把空结果当失败（或把失败当空的成功） | 区分访问失败和有效的空结果 |
| 一个子代理超时杀死整次执行 | 本地恢复，然后是部分结果上传 + 涵盖范围注记 |
| 相信「97% 准确率」就拿去自动化 | 按文档类型 × 字段分段；对高信心分层做分层采样 |
| 在冲突的来源统计数字之间取平均或挑一个 | 把两个数值都连同来源注记；让协调者调和 |
| 发现里的日期被丢掉 | 结构化输出必须带发布／搜集日期 |
| 会话引用「典型模式」而不是已发现的类别 | 上下文劣化 → 暂存文件 + 子代理委派 + /compact |

## 自我检查问答

**Q1.** 渐进式摘要最先摧毁哪类信息？
**A.** 精确的数字、百分比、日期、订单编号，以及客户明说的期望——被浓缩成模糊的叙述文字。

**Q2.** 定义案件事实模式。
**A.** 把交易事实提取出来，放进一个结构化区块，附在每一个提示词里、放在摘要化历史之外——有损摘要底下的无损层。

**Q3.** 什么是中段遗失？有哪两个缓解方法？
**A.** 模型能可靠处理长输入的开头和结尾，但会漏掉中段的内容；把关键发现摘要放最前面，并使用明确的节标题。

**Q4.** 一次订单查询回传 40 多个字段，只有 5 个相关。你要做什么？什么时候做？
**A.** 在结果进入上下文*之前*，修剪到回传相关的字段。

**Q5.** 下游上下文很紧时，上游子代理该回传什么？
**A.** 结构化数据——关键事实、引用来源、相关性分数，加上日期／来源元数据——不是冗长的内容和推理链。

**Q6.** 三个正当的升级触发条件？
**A.** 客户明确要求真人；政策例外／缺口；无法取得有意义的进展。

**Q7.** 客户为一个小事就能修好的问题要求真人。顺序？
**A.** 立即照办；最多认同一次、提出修复方案一次，对方重申就升级——绝不要违背他的请求先调查。

**Q8.** 为什么情绪和自我报告信心是差的升级路由器？
**A.** 两者都和案件复杂度没有相关；信心未经校准——agent 在困难案件上自信满满地答错（样例题 Q3）。

**Q9.** 工具为「John Smith」回传三个客户。正确行为？
**A.** 要求额外的识别信息；绝不要用启发法挑选。

**Q10.** 一个搜索子代理超时。协调者需要什么才能聪明恢复？
**A.** 结构化错误上下文：失败类型、尝试过的查询、部分结果、替代方案（样例题 Q8）。

**Q11.** 说出两个错误处理反模式，以及各自的危害。
**A.** 静默压制（失败被包装成空的成功 → 不完整的输出看起来像完整）以及单一失败就终止整个工作流程（杀死可行的恢复）。

**Q12.** 访问失败对有效的空结果——为什么要区分？
**A.** 一个需要重试决策，另一个是真正的答案；混淆两者会造成错误的重试，以及被默默接受的中断。

**Q13.** 错误什么时候离开子代理？
**A.** 只有在本地恢复（例如对暂时性失败重试）失败之后——上传时附上尝试过什么以及部分结果。

**Q14.** 综合在一个来源中断的情况下完成。报告必须包含什么？
**A.** 涵盖范围注记：哪些发现有充分支持，哪些主题领域因来源不可用而有缺口。

**Q15.** 长时间探索会话的上下文已经劣化，症状是什么？
**A.** 答案不一致，并且诉诸「典型模式」，而不是先前发现的特定类别。

**Q16.** 大型代码库上下文管理的四个对策？
**A.** 暂存文件；把冗长调查交给子代理委派；注入下一阶段上下文的阶段摘要；/compact。

**Q17.** 为多 agent 执行设计宕机恢复。
**A.** 每个 agent 把结构化状态导出到已知位置；恢复时，协调者加载 manifest 并注入 agent 的提示词。

**Q18.** 为什么 97% 整体准确率不足以自动化？
**A.** 整体指标掩盖分段失败——在减少人工审核之前，准确率必须按文档类型、按字段验证。

**Q19.** 分层随机采样在审核工作流程中的角色？
**A.** 对高信心提取按分层持续测量错误率，捕捉新出现的错误模式和漂移。

**Q20.** 模型信心如何变得可用于审核路由？
**A.** 模型输出字段层级分数；门槛对照已标记验证集校准——原始的自我报告不被信任。

**Q21.** 两个可信来源给出不同的市场规模。怎么处理？
**A.** 两个都放进去，附来源归因注记；协调者决定如何调和——绝不任意挑选，也绝不取平均。

**Q22.** 为什么结构化输出要求发布日期？
**A.** 让时间差异读起来是随时间的变化，而不是矛盾。

**Q23.** 什么让出处归属在多 agent 综合中存活？
**A.** 结构化的主张与来源对应（主张、来源、摘录），每个下游 agent 都保存并合并。

**Q24.** 综合报告该如何对待有争议的发现？
**A.** 已确立与有争议的发现分开成明确的小节，保留原始来源的表述和方法论上下文。

**Q25.** 一份报告包含财务数据、新闻和技术发现——格式？
**A.** 分别是表格、叙述文字和结构化清单——依内容类型呈现，不要压平。

## 词汇表

| 术语 | 含义 |
| --- | --- |
| 案件事实区块 | 结构化、无损的事实层，附在每一个提示词里、放在历史之外 |
| 渐进式摘要 | 对历史反复压缩；最先摧毁精确数值 |
| 中段遗失 | 位置效应：长输入的中段会被漏掉 |
| 工具结果修剪 | 在载荷进入上下文之前，缩减到相关字段 |
| 升级触发条件 | 真人请求、政策缺口，或没有进展——不是情绪／信心 |
| 政策缺口 | 政策没有规定或规定含糊的请求 → 升级 |
| 结构化错误上下文 | 失败类型 + 尝试过的查询 + 部分结果 + 替代方案 |
| 静默压制 | 失败被报告为空的成功——反模式 |
| 本地恢复 | 子代理在上传之前，先重试暂时性失败 |
| 涵盖范围注记 | 在综合输出中标出有充分支持的领域和有缺口的领域 |
| 暂存文件 | agent 维护的发现文件，跨越上下文限制持续存在 |
| Manifest | 协调者加载的结构化状态导出，让宕机后可以恢复 |
| 分层采样 | 按文档类型／字段分层做随机质量保证采样，包括高信心分层 |
| 校准 | 用已标记的集合，把模型信心对应到真实错误率 |
| 主张与来源对应 | 结构化的主张 + 来源 + 摘录，在综合过程中被保存 |
| 时间注记 | 附在发现上的发布／搜集日期 |
