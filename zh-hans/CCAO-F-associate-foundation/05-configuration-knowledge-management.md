## 概览

设置 Claude，让反复出现的工作保持一致。官方考试蓝图动词：**设置（configure）** 带指示与知识来源的 Claude Projects；**管理（manage）** 上传的知识与连接器（考试指南点名 Google Drive 与 Gmail）；**创建（create）** 有效的系统层级指示；并随时间 **告知、维护并更新（inform, maintain, and update）** 设置、知识来源与指示。这是「让它对团队可靠」的领域——而且自从 Memory 推出之后，也是「管理 Claude 记得什么」的领域。

## 深入笔记

### 1. 经得起团队考验的 Project 设置

清单：用途；负责人；敏感度标签；指示；知识集；分享权限；模型默认指引；评测笔记。已查证的方案事实（support.claude.com，2026 年 8 月）：Projects 存在于 **所有方案；Free 上限为五个 Project**；**通过检索增强生成（RAG）的增强知识仅付费方案提供，并将容量扩大至约 10 倍**，于知识接近上下文上限时启动；**分享属 Team/Enterprise**，分「可查看」（只读）与「可编辑」（可修改知识／指示），可逐一、批量或全组织授予。

### 2. 指示工程

好的指示会指明：角色；默认受众；输出 schema；引用规则；升级规则（「若不在知识中，回答 **Not found**」）；冲突优先级（法务 > 品牌）；以文件名指向文件。坏的指示会把公司故事从头讲一遍、自相矛盾，或把关键规则埋起来。保持 **简短、稳定、有优先级**——指示会与任务 token 竞争；厚重的政策应放在知识文件中。

用三个黄金任务与三个对抗性任务测试指示（要求知识以外的答案，看「Not found」是否触发）。当失败成群出现时再更新。**Styles／偏好设置 vs 项目指示：** 全域个人口味 vs 工作区规则——Style 无法承载 Project 的法务限制。**Skills vs 指示：** 程序 vs 常态规则；不要把整份 Skill 贴进指示。

### 3. 知识卫生 playbook

- **命名：** `Policy-Refunds-v4-2026-06.pdf` 胜过 `finalFINAL.pdf`。把版本日期放进文件名；用文件名指名要文件。
- **策划：** 新版本落地当天即移除被取代的文档——过期文件是无声的在线缺陷（对文件为真、对世界为假）。不要保留重复或冲突的版本；检索混淆是自找的。
- **结构：** 把不相关领域（法务／人力资源／营销）拆到不同 Projects；保留一份清单备注，列出每份文档及其用途。
- **质量：** 优先使用可萃取文本的文件；光学字符识别（OCR）乱码扫描件会污染检索。
- **RAG 行为：** 知识量大时，预期为搜索式检索——提问要收窄并指名文件。

### 4. Connectors：上传对比连接，以及最小权限原则

上传＝你必须自行刷新的冻结快照；连接器＝带验证与权限复杂性的即时数据。要有意识地选择：每周变动的活文档 → 连接器；稳定的正式政策 → 有版本纪律的策划上传。

治理基础（深入内容属领域 06）：最小权限原则——分析用途优先 **只读**；写入权限范围是治理决策，需搭配人工关卡。Team/Enterprise 模式：**管理员启用，每位用户各自验证**。把 Project 预期使用的连接器写成文档，这样「Claude 看不到 Drive」才会被诊断为验证问题，而非模型故障。**自订连接器（远程模型上下文协议，简称 MCP）各方案皆有；Free 限一个自订连接器**（2026 年 8 月查证）。

### 5. Memory — 设置 Claude 记得什么（本节为添加；考试指南点名此主题）

事实已对照 support.claude.com 查证（2026 年 8 月——此功能会演变；考试前请重新查证）：

- **是什么：** Claude 从你的对话创建 **Memory 条目**——专业背景、角色、偏好、进行中的工作——组织成分类，并套用到后续对话。这取代了「对话是短暂的；对话串之间没有任何东西留存」的旧心智模型。
- **可用性：** 记忆产生在 **Free、Pro、Max**（较新体验）以及 **Enterprise**（旧版 24 小时综合体验）；**对话搜索**（Claude 检索你过去的对话）为 **Pro 以上**。Team 方案 **没有组织层级的记忆控制**——成员各自管理。
- **Project 范围：** 每个 Project 有 **自己独立的记忆** 与摘要，让客户工作、机密对话串与一般对话彼此分开。这就是「防止上下文渗漏」的设置答案。
- **控制项（本领域核心）：** Settings → Memory：**查看**条目、**编辑**、**删除个别条目**，或 **全部重置**；Memory 与搜索 **各自独立开关**；引用来源会显示被记住的事实来自哪一段对话。
- **无痕对话：** 幽灵图标，所有方案皆有，位于 Projects 之外；排除于历史记录、记忆与搜索之外。（Enterprise 会因安全理由将无痕对话保留最短期间，并纳入数据导出——治理细节。）
- **可携性：** Memory 包含在数据导出中；实验性导入／导出可在助理之间搬移记忆。

**管理心法：** Memory 是 *个人上下文层*，不是知识库。像对待知识一样策划它：定期查看条目；删除错误或过期者（一条坏的 Memory 条目，是你带进每一段对话的设置漂移）；敏感事项请关闭记忆或使用无痕对话；承重的团队真相放在 **项目知识**——有负责人的策划文件，胜过按用户推测出来的记忆。当 Claude「记错了」，修复方法是编辑／删除该条目，不是换更大的模型（通往领域 07 的桥）。

### 6. 维护、生命周期与所有权

每个共享 Project 都需要一位指名负责人，对更新问责；没有负责人，设置漂移必然发生。节奏：每月查看指示；政策变动时刷新知识（替换文件＋公告＋在指示中更新版本注记）；共享 Project 在知识中保留变更记录；封存死去的 Projects——在 Free 上，五个 Project 的上限会逼你这么做。带队友上手：分享 Project、解释指示、展示评测清单、确认连接器验证、监督第一个任务。

### 7. 看起来像模型缺陷的失败模式

Claude「无视政策」→ 知识中仍躺着已被取代的 PDF。「混用品牌」→ 两份风格指南没有优先规则。「忘了我们的项目上下文」→ 用户依赖个人 Memory 而非项目知识，或 Memory 条目被删除／范围属于另一个 Project。「看不到 Drive」→ 连接器未验证。「记错了关于我的事」→ 过期 Memory 条目；编辑或删除它。先修设置，再升级模型。

### 8. 迷你案例（设置审计）

**案例 1 — 神秘的品牌语气。** 营销的共享 Project 在正式文案与活泼文案之间摇摆。审计发现 `Brand-Voice-2025.pdf` 与 `Voice-Refresh-2026.docx` 同时躺在知识里，没有优先规则，也没有负责人。修复方法：删掉 2025 年的文件，在指示中加上「语气依 `Voice-Refresh-2026.docx`」，指定一位负责人，并开始一份变更记录。一次审计，每位用户都修好了。

**案例 2 — 顾问的渗漏风险。** 一位独立顾问从一般对话服务两家互相竞争的客户，担心上下文会泄漏。修复方法：每个客户一个 Project（记忆以项目为范围；知识分开），一般 Memory 只放个人偏好，定期查看 Memory 条目，探索性、利益冲突敏感的问题用无痕对话。

**案例 3 — 腐烂的星期五报告 Project。** 3 月建好，4 月被称赞，到 8 月就错了：政策第 5 版已发布，但第 3 版还在知识里；建造者离职了；没有人拥有它。经典的漂移。修复方法：指定负责人、替换文件、在指示中加版本注记，并把每月查看排进行事历。预防比那份揭露问题的坏报告便宜。

**案例 4 — 上手出了差错。** 一位新分析师拿到 Project 访问权，但他第一批输出完全没有引用 Drive 的东西。审计：连接器已由管理员启用，但分析师从未验证；而且他用的是个人账号，不是工作区。修复方法：一个工作区席位、一次逐人验证的导引，以及对照评测清单监督第一个任务。

### 9. 多选题模式库

学会删去这些反复出现的错误选项：「把整份政策贴进指示」（膨胀——那是知识的工作）；「保留旧文件以供参考」（被取代＝删除或清楚封存）；「Memory 会让团队对齐」（按用户，不是共享的）；「给每个人编辑权，这样就没有人被挡住」（权限失败）；文档是活的却「每周重新上传而不连接」（或其镜像：「什么都连接」，包括稳定的政策）。正确组合是把一个 **存放位置** 选择（指示 vs 知识 vs Skill vs 连接器 vs Memory）配上一个 **生命周期** 选择（负责人、版本注记、节奏、封存）。

## 决策树

| 情境 | 行动 |
|---|---|
| 反复出现的团队上下文 | Project（指示＋知识＋负责人） |
| 厚重的参考数据 | 知识文件，命名并标版本——不放指示 |
| 即时、频繁变动的文档 | 连接器（只读，除非写入受到治理） |
| 政策已更新 | 替换文件＋公告＋版本注记 |
| 跨对话的个人偏好 | Memory——在 Settings 中查看／编辑条目 |
| 机密的一次性对话 | 无痕对话（排除于记忆／历史／搜索之外） |
| 上下文绝不能互相渗漏 | 分开的 Projects（记忆以项目为范围） |
| Free 接近五个 Project 上限 | 封存或合并 |
| 记错的事实 | 编辑／删除该 Memory 条目 |
| 共享 Project 行为异常 | 先检查负责人、重复文件、过期，再怪模型 |

## 考试陷阱

1. 把所有东西塞进指示（小说长度，还自相矛盾）
2. 从不更新知识；把被取代的 PDF 留在原地
3. 把个人 Memory 当团队的知识库
4. 以为记忆跨越 Project 边界（它是以项目为范围的）
5. 给纯分析工作的连接器默认写入权限范围
6. 忽略分享权限（对受限制的知识开全组织编辑）
7. 重复冲突的文件造成检索混淆
8. 共享 Project 没有负责人（漂移必然发生）
9. 期待 Styles 承担 Project 的法务合规工作
10. 忘记无痕对话是为敏感的一次性对话而存在的

## 练习问答（18）— 情境题干附答案与理由

**Q1.** 一个团队需要常态的语气规则，加上一份 40 页的政策 PDF，套用到每周的工作。设置是什么？
**A：** 一个 Project：简短的语气规则放进指示；PDF 放进知识，以版本与日期命名；指示用文件名指向它。

**Q2.** 一位 Free 方案顾问在接第 6 个客户时撞上项目上限。选项是什么？
**A：** 封存或合并一个不活跃的 Project，或升级——Free 上限为五个（2026 年 8 月查证；请在 support.claude.com 重新查证目前上限）。

**Q3.** 选出两项知识卫生做法。
**A：** 文件名放版本日期；立即移除被取代的文档。（重复文件与 `finalFINAL` 命名是反模式。）

**Q4.** Claude 引用的是上一季的退款窗口。第 4 版政策昨天发布了。根本原因与修复方法？
**A：** 过期知识——用第 4 版替换第 3 版，公告变更，并在指示中更新版本注记。对文件为真、对世界为假，是维护失败。

**Q5.** Project 的 RAG 什么时候重要，谁有？
**A：** 付费方案，当知识接近上下文上限时——检索将容量扩大至约 10 倍；用清楚的命名与收窄的提问帮它一把。

**Q6.** 一位用户预期新对话自动知道昨天的项目决策。正确的设置答案是什么？
**A：** 把决策放进项目知识（团队真相）——Memory 也许会回想起一些上下文（按用户、依方案而定、以项目为范围），但它不是承重事实的可靠或共享存储。

**Q7.** 纯分析的 Drive 工作流程：哪种连接器范围？
**A：** 只读／最小权限原则。写入权限范围需要治理核准与人工关卡。

**Q8.** Claude 一直把一位经理关联到他几个月前离开的项目。修复方法？
**A：** Settings → Memory：编辑或删除该过期条目。Memory 是用户策划的设置，不是命运。

**Q9.** 共享 Project 上「可查看」与「可编辑」差在哪？
**A：** 查看＝以只读方式使用 Project；编辑＝可修改知识与指示。编辑权要窄授；分享是一种治理控制。

**Q10.** 丰富的多步骤程序该放哪里：指示还是 Skill？
**A：** Skill——程序在相关时才加载；指示承载简短的常态规则。在指示里拷贝一份 Skill 会让上下文膨胀。

**Q11.** 两份冲突的风格指南住在同一个 Project 的知识里。症状与修复方法？
**A：** 检索混淆造成的品牌输出不一致——移除其中一份，或在指示中加一条明确的优先规则。

**Q12.** 一位高阶主管要做敏感的董事会准备，要求在记忆或历史中零痕迹。建议？
**A：** 无痕对话（所有方案皆有，位于 Projects 之外）——排除于历史记录、记忆与搜索之外。若是反复出现的董事会工作，一个分享收紧的专用 Project，胜过反复用无痕对话。

**Q13.** Enterprise Search 对一个团队信誓旦旦说已连接的来源，什么都没回传。检查什么？
**A：** 管理员是否真的启用了连接器；提问的用户是否已验证；来源是否在范围内。先查设置，再怪模型。

**Q14.** 谁维护共享 Project，什么产物能证明？
**A：** 一位指名负责人；知识里的一份变更记录备注，记录文件替换与指示版本。

**Q15.** 一位 Free 方案用户想要三个自订 MCP 连接器。现实是什么？
**A：** 自订连接器在 Free 上存在，但限一个；多个自订连接器需要付费方案（2026 年 8 月查证）。

**Q16.** 个人 Styles vs 项目指示——什么时候 Styles 是错的答案？
**A：** 只要规则是工作区真相（法务限制、团队 schema）：Styles 是个人口味，不管辖共享 Project。

**Q17.** 选出两个「记忆以项目为范围对设置很重要」的理由。
**A：** 客户上下文无法在 Projects 之间渗漏；敏感的项目讨论留在一般对话记忆之外。（这也是为什么「每个客户待在自己的 Project」是常态设计规则。）

**Q18.** 在带队友上手一个已设置的 Project 时，哪两个步骤能防止第一周的混乱？
**A：** 确认他们的连接器验证，以及对照评测清单监督第一个任务。

## 快速复习检查清单（考前）

- [ ] Project 设置：用途、负责人、敏感度、指示、知识、分享
- [ ] 指示：简短、有优先级、冲突规则、「Not found」升级规则、文件指引
- [ ] 知识：有版本的命名、没有重复、替换被取代的文件、清单备注
- [ ] 上传 vs 连接器；最小权限原则；管理员启用＋用户验证
- [ ] Free 上限：五个 Project、一个自订连接器；RAG 付费约 10 倍
- [ ] Memory：方案、以项目为范围、查看／编辑／删除／重置、独立开关
- [ ] 无痕对话：所有方案皆有，没有历史／记忆／搜索
- [ ] 维护节奏＋变更记录＋指名负责人；封存死去的 Projects

## 词汇表

| 术语 | 含义 |
|---|---|
| **项目指示** | 范围限定在工作区的常态行为规则 |
| **项目知识** | 策划过的参考文件；团队的真相来源 |
| **RAG（Projects）** | 付费检索，在接近上下文上限时扩大知识容量 |
| **连接器（Connector）** | 即时集成（例如 Drive、Gmail）；管理员启用、用户验证 |
| **最小权限原则** | 完成工作所需的最小范围；默认只读 |
| **Memory** | 按用户、以项目为范围的被记住上下文；在 Settings 中策划 |
| **Memory 条目** | 一则可编辑、可删除的被记住事实，附对话引用 |
| **无痕对话** | 排除于历史、记忆与搜索之外的对话 |
| **知识卫生** | 命名、版本、去重与修剪的纪律 |
| **设置漂移** | 指示／知识／记忆慢慢偏离现实 |
