## 概览

配分第二重的领域。设计 Claude 如何融入真实工作。官方蓝图动词：**运用** Claude 分析需求与使用案例；**善用** Claude 做研究、规划与流程优化；**使用** Claude 支持解决方案设计、开发与迭代；把 Claude **集成** 进现有工作流程以增强或重新设计它们；向利益相关者 **沟通** Claude 的价值 **与限制**。非开发者解决方案指的是 Projects、Skills、Artifacts、Connectors、Research、代码执行与审核关卡 — 不是 API 架构。

## 深入笔记

### 1. 需求与使用案例分析优先

碰工具之前先引导挖掘：触发事件、输入、输出、用户、频率、延迟需求、敏感度等级、下游系统、完成的定义、错误预算。若利益相关者答不出来，Claude 可以帮忙访谈与勾勒 — 但由人类确认。过早碰工具是经典失败。

把使用案例分类：**generate、transform、retrieve、decide、act。** decide／act 需要更强关卡（决策通常留在人类手上）。generate／transform 仍需要与风险相称的明辨。盘点目前工作流程的步骤，标出 Claude 在哪里起草、检索、转换、运算，或者（很少见地）做决定。

### 2. 解决方案模式目录

- **模式 A — 知识中枢（Knowledge Hub）：** 存放政策／范例／指示的 Project；团队编辑权限；默认 Sonnet；评估检查清单放在指示里。
- **模式 B — 从局面到决策（Landscape to Decision）：** 附引用来源的 Research → 领域 03 主张对照表 → 决策备忘录 Artifact。
- **模式 C — 收件台（Intake Desk）：** Connector 读取信箱／表单 → Claude 起草工单字段 → 人类确认 → 系统更新。写入前的人工关卡就是重点。
- **模式 D — playbook 型 Skill（Playbook Skill）：** Skill 把程序编码下来（例如事故通报更新）；Project 存放严重程度定义。
- **模式 E — 组织大脑（Org Brain）：** Enterprise Search 回答「我们当初决定了什么」，并附带指回 Slack／Drive 的引用。
- **模式 F — 数据到交付物（Data-to-Deliverable）：** 上传数据 → 代码执行计算（总计、趋势、图表）→ 产生 Excel／PDF／幻灯片交付物 → 人类对照来源核对数字。当工作流程的核心是 *运算或文件产出*、不是文本时用它。（代码执行与文件产生所有方案都有 — 已于 2026 年 8 月对照 support.claude.com 查证。）

组合模式；很少有单一功能就是完整解决方案。考试答案里，经过思考的组合胜过单一功能万灵丹。

### 3. 增强 vs 重新设计

**增强：** 保留流程，把 Claude 安插到起草／检索／运算步骤。变革管理成本低；受监管或高风险流程的默认（外加审计轨迹）。
**重新设计：** 移除那些 AI＋ connectors 让它们变得多余的步骤。报酬更高，但需要变革管理、训练与明确所有权。

决策逻辑：高度人工浪费＋低风险＋有意愿的负责人 → 重新设计候选。受监管、对外或不可逆的流程 → 先增强并加人工关卡；用试点证据去赢得重新设计。永远不要为面向客户的发送设计「全自动驾驶」— 起草＋人类发送才是考试正确的形状。

### 4. 研究、规划与流程优化

规划期间用 Research 做外部局面（依领域 03 验证后才让它影响决策）；用 Projects 持久保存计划上下文；用代码执行量化（「哪个步骤吃掉工时？」）。优化目标跟着衡量走，不是感觉：先装上起草耗时、修改轮次、错误类型，再用最便宜的杠杆重新设计最差的步骤。

### 5. 利益相关者沟通（价值以及限制 — 蓝图讲得很明白）

一页摘要：问题、提议的工作流程图、人工关卡、数据流、指标、风险、请求。展示时用真实混乱的输入，不是打磨过的玩具；展示一次 *被抓到的* 幻觉，比一次完美运行更能创建信任。永远包含：幻觉风险与审核标准作业程序（SOP）；数据边界（什么可以／不可以进入哪个方案／功能 — 领域 06）；Claude 不该拥有什么（最终决策、受监管判断）；成功指标与回滚。

异议处理：「它会取代我们」→ 增强指标与工时重新配置到更高价值工作。「它会产生幻觉」→ 展示评估 SOP 与审核后的错误率。「数据会离开我们的系统」→ 方案控管、connector 授权范围、组织政策。没有限制的吹捧在这个领域不及格；没有试点计划的末日论也一样。

### 6. 衡量与迭代

追踪：节省的时间、到交付为止的修改轮次、错误类型（事实性、完整性、语气、政策）、采用度、用量上限消耗。用错误分类法更新指示／知识／Skills — 不要用来责怪用户。试点一个团队；指标过关后再扩大。解决方案是产品：帮它们编版本、记变更记录、指定负责人。

集成失败模式：知识过时、负责人不清楚、死线压力下关卡被绕过、采用被忽略（「我们盖好了，没人来」）。为真实组织设计，不是为幻灯片上的组织设计。

### 7. 迷你案例（套用完整循环）

**案例 1 — 每周高层摘要。** 对内沟通每个星期五花四小时，从 Slack、Drive 文档与两个仪表板汇编摘要。设计：connectors 读取来源；一个 Project 存放摘要模板、语气范例与收录标准；Claude 在星期五早上起草；对内沟通主管验证主张（领域 03）后送出。指标：准备时间、送出后更正。连续四周干净之后成为重新设计候选：拿掉手动仪表板截图步骤，改成导出数据给代码执行画图。

**案例 2 — RFP 工厂。** 业务每季从一个没人更新的 wiki 回答 20 份建议邀请书（RFP）。解决方案：放在项目知识里、经过整理的答案库（由业务运营拥有、编版本）；一个 Skill 把答案组装程序编码下来；RFP 问题的萃取 schema；提交前的人工审核关卡，因为答案是合约承诺。被拒绝的反模式：「自动填写并提交」— 对外承诺保留人工关卡。

**案例 3 — 客服分流。** 目标：缩短首次回应时间。Connector 读取队列；Claude 分类严重程度，并引用政策 Project 起草回应；人员审核后送出；Sev-1 直接路由给人类，附一份 Claude 起草的上下文简报。高影响工单的严重程度 *判定* 留在人类手上；起草与上下文汇整，才是 Claude 安全加速的地方。

**案例 4 — 董事会资料包分析。** 财务长（CFO）想从每月导出得到趋势评论。数据到交付物：代码执行计算趋势并做出图表＋ PDF 附录；主计长对照来源核验算出来的数字；Opus／Sonnet *只根据算出来的数字* 起草评论；人类拥有叙事。组合：代码执行（数学）＋ Project（语气、定义）＋人工关卡（受监管受众）。

每个案例演练同一个循环：需求 → 使用案例类别 → 模式组合 → 关卡 → 指标 → 迭代。

### 8. 多选题模式库

常见应排除的错误配对：「为省时间自动化发送」＋「永远全部手动」（关卡失败＋反委派）；「向利益相关者承诺零错误」＋「开头就讲所有可能出错的事」（吹捧＋末日 — 两者都漏掉 SOP 加指标这个中间地带）；「立即全组织推行」＋「无限期试点、没有扩大标准」（没有证据＋没有决策规则）；「设计自订 API 微服务」（走错轨道）。正确组合把一个 **组合** 选择（Project＋ connector＋关卡；Research＋验证；代码执行＋审核）配上一个 **沟通或衡量** 选择（揭露限制、定义指标、指定负责人）。

## 决策树

| 情境 | 动作 |
|---|---|
| 流程里有不可逆的对外动作 | 执行前设人工关卡 — 不容商量 |
| 带共享上下文的反复工作 | Project（程序丰富则加 Skill） |
| 多来源公开探索 | Research（经验证）— 内部：Enterprise Search |
| 工作流程核心是运算／文件输出 | 代码执行模式 F |
| 利益相关者需要交互工具 | Artifact |
| 需求不清楚 | 先做探索访谈＋流程盘点 |
| 受监管／高风险流程 | 用关卡＋审计轨迹增强；有证据才重新设计 |
| 成功未定义 | 动手之前先定义指标 |
| 试点成功 | 逐步扩大；持续衡量；指定负责人 |

## 考试陷阱

1. 面向客户发送采用全自动驾驶（没有人工关卡）
2. 利益相关者沟通漏掉限制那一半
3. 把 Claude 卖成零错误；或因恐惧而拒绝试点
4. 重新设计时忽略变革管理与训练
5. 在产品轨考试上给 API／微服务架构答案
6. 没有成功指标或回滚计划
7. 需要组合时却端出单一功能万灵丹
8. 没有需求或流程盘点就工具优先设计
9. 优化没人衡量过的步骤
10. 忘记采用：没有负责人的解决方案会腐烂

## 练习问答（18）— 情境题干附答案与理由

**Q1.** 一位主管说「把 Claude 放进我们的开票流程」，没有进一步细节。第一步？
**A：** 需求与使用案例分析 — 在选功能之前先盘点流程、输入／输出、敏感度与完成的定义。需求之前就碰工具是陷阱。

**Q2.** 设计一个搭配 Claude 的客户支持邮件工作流程。考试正确的形状？
**A：** Claude 从 Project 政策知识起草 → 人类审核后送出。面向客户的发送保留人工关卡。

**Q3.** 选两项每周竞争简报解决方案的组件。
**A：** 一个存放简报模板／指示的 Project；Research（附引用验证）做局面扫描。

**Q4.** 你的推行幻灯片只列好处。要通过这个领域的门槛，必须加上什么？
**A：** 限制：幻觉风险＋审核 SOP、数据边界、什么留在人类手上、指标与回滚。沟通限制是蓝图明白写出的。

**Q5.** 财务想从导出的逗号分隔值（CSV）做每月差异分析，以 Excel 交付。哪个模式？
**A：** 数据到交付物：代码执行计算差异并产生电子表格；流通前由人类对照来源核对数字。

**Q6.** 什么时候重新设计胜过增强？
**A：** 高度人工浪费、低风险、有意愿的负责人，以及试点证据 — 移除 AI 让它们变得多余的步骤。受监管流程从带审计轨迹的增强开始。

**Q7.** 哪一对指标最能证明工作流程价值？
**A：** 交付草稿耗时加上审核后错误率。没有质量的速度（或反过来）只是半个论据。

**Q8.** 运营想要一个同事能点击走完的共享交互 SOP 检查器。用哪个功能？
**A：** Artifact — 独立交互式交付物；观看者消耗自己的额度；内容仍须先验证。

**Q9.** 试点输出反复出现语气失误，以及两处可追溯到过期政策 PDF 的事实错误。迭代？
**A：** 更新知识文件（过时）并把语气范例加进指示／Skill — 修正造成每种失误类型的系统。

**Q10.** 高阶主管问「这会取代团队吗？」最佳回应框架？
**A：** 重新框成增强：展示 Claude 吸收哪些步骤、保留哪些人类判断、指标，以及发布的工时去哪里。

**Q11.** 选两项解决方案提案中必须向利益相关者揭露的风险。
**A：** 幻觉／错误风险及其缓解；数据敏感度边界与处理规则。

**Q12.** 团队想跳过试点、全组织推行「才能走得快」。为什么这是错误选项？
**A：** 没有错误分类法、没有采用证据、没有回滚；试点在指示／知识仍生疏时把失败局部化。

**Q13.** 进线邮件应该变成客户关系管理（CRM）工单。关卡在哪里？
**A：** Claude 从 connector 读取的邮件起草工单字段；写入 CRM 之前由人类确认。读可以宽；写要设关卡。

**Q14.** 「上季我们与供应商 X 谈成什么？」一直在 chat 里走进死胡同。解决方案？
**A：** 在已连接的 Slack／Drive 上用 Enterprise Search — 组织内部附引用查询，不是 Research，也不是更大模型。

**Q15.** 一套反复出现的 RFP 回应程序（12 步骤、严格顺序）每周都被重新解释。解决方案组件？
**A：** 一个把程序编码下来的 Skill，样板／来源材料放在项目知识。

**Q16.** 你如何做一场能创建耐久信任的展示？
**A：** 真实混乱的输入，展示评测步骤，并展示一次被抓到的错误及其修复方法 — 证明的是安全网，不只是魔术。

**Q17.** 推行后，用量很高但修改轮次加倍。诊断路径？
**A：** 切分错误分类法：哪些失误类型增加、哪些工作流程步骤产出它们；针对那些步骤收紧指示／知识。衡量 → 锁定目标 → 最便宜的杠杆。

**Q18.** 选两项提议解决方案相对于其风险程度过度自动化的迹象。
**A：** 不可逆的对外动作在没有人类确认下执行；受监管判断（人力资源／法务／财务）被直接委派给 Claude 的输出。

## 词汇表

| 词 | 意义 |
|---|---|
| **使用案例类别** | generate、transform、retrieve、decide、act — 关卡随最后两类放大 |
| **增强** | 把 Claude 安插进现有流程的起草／检索／运算步骤 |
| **重新设计** | 移除那些 AI＋ connectors 让它们变得多余的流程步骤 |
| **人工关卡** | 不可逆／对外动作前必须有的人类确认 |
| **试点** | 有边界的推行，在放大之前产出错误分类法 |
| **错误分类法** | 事实性／完整性／语气／政策失误分类，用来驱动修复方法 |
| **成功指标** | 预先定义的衡量（起草耗时、审核后错误率、采用度） |
| **变革管理** | 让重新设计站得住的训练、所有权与沟通 |
