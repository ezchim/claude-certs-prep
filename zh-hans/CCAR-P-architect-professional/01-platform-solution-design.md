## 概览

CCAR-P 要你用**生产环境架构师**的方式思考，而不是只会修修补补提示词的人。在情境题里，你会：

1. 把杂乱的商务问题翻成 **Claude 驱动的解决方案形状**（输入 → 处理 → 输出 → 回馈）。
2. 在**工作流程**、**增强型 LLM**、**agentic（自主代理式）**与**多 agent** 模式之间做选择，并把取舍讲清楚。
3. 选择**模型层级**（能力 vs 延迟 vs 成本 vs 上下文）并为选择辩护。
4. 把**提示词与上下文**工程做好，让系统在 token、安全与重用限制下仍然可靠。
5. 把设计选择连到**商务价值支柱** —— 用官方指南的措辞：效率、转型、**生产力**、成本，以及性能服务水准协议（SLA）。

本档深挖平台能力与解决方案设计。集成机制（模型上下文协议（MCP）接线、检索增强生成（RAG）管线、评测框架）见档 `02`；治理见 `03`；利益相关者／生命周期／赋能见 `04`。

## A 部分 —— 架构师要懂的 Claude 模型

### A1. 如何看待模型阶梯

公开文档描述一个 **Claude 模型家族**，速度／智力／成本定位不同。精确的 ID 与价格会随时间变动；对 CCAR-P 来说，要背的是**决策逻辑**，不是一张冻结的价目表：

| 决策因素 | 何时优先较高能力层级… | 何时优先较快／较便宜层级… |
| --- | --- | --- |
| 任务复杂度 | 多步骤规划、困难编码、含糊需求、高利害判断 | 分类、萃取、路由、短重写 |
| 延迟 SLA | 脱机批量、异步工作、人类审过的草稿 | 交互式用户体验（UX）、高每秒查询数（QPS）守门者 |
| 上下文大小 | 大型程序库、长文档、长达数小时的 agent 追踪 | 短轮次、负载小的工具密集循环 |
| 成本包络 | 低量／高价值（合约、架构审查） | 高量／边际价值低 |
| 错误成本 | 答错很贵或不安全 | 答错很容易抓到／重试 |

**架构师规则：** 默认用**能在你的评测集上跨过质量门槛的最小模型**。只有评测证明有缺口时，才往上提升能力。当延迟／成本预算失败、但质量仍然站得住时，就往下。

### A2. 设计里会出现的能力旋钮

架构师必须放对位置的公开平台功能：

- **上下文窗口：** 目前前沿 Claude 模型通常标榜**大**窗口（数十万到支持的模型／平台上约 **~1M tokens**）。请求里的一切都算：系统提示词、消息、工具定义、图像／文档、工具结果，以及（若使用）思考 token。缓存改变的是**价格**，不是 token 是否占用窗口。
- **最大输出：** 同步 Messages API vs 批量（Batch；批量可能通过文档记载的 beta header 支持延伸输出——请核实现行文档）。
- **思考／自适应思考／effort（思考力度）：** 困难问题用更深的推理；用 **effort 等级**（`output_config.effort`）控制成本／延迟。自适应思考已取代固定思考预算 —— `budget_tokens` 在 4.6 世代已弃用，在现行模型上已移除（会以错误拒绝）。变更思考设置会使消息层级的提示词缓存断点失效（工具／系统前缀仍可缓存）——设计时要顾缓存稳定。
- **视觉／多模态：** 产品需要截图、图表或扫描文档时，使用图像输入。
- **部署接口：** Claude API、Amazon Bedrock、Vertex AI、Microsoft Foundry、AWS 上的 Claude Platform——各自有 ID 命名与数据驻留细微差异。架构师依企业采购、区域与合规来选——不是只凭品牌偏好。**完整的 CSP／交付路径治理决策对照表在档 `02` 第 D5 部分**（限制排除、ZDR 主题、模型 ID 陷阱、问答）。

### A3. 模型选择决策树

```
START: Define task + quality bar + p95 latency + monthly volume
 │
 ├─ Need long-running agentic coding / complex enterprise judgment?
 │ └─ YES → Start with high-capability model; measure cost on realistic traces
 │
 ├─ Need interactive speed + “good enough” intelligence?
 │ └─ YES → Mid-tier (Sonnet-class); escalate hard cases via router
 │
 ├─ High QPS classify/extract/route?
 │ └─ YES → Fast tier (Haiku-class); sample escalate to mid/high on low confidence
 │
 └─ Mixed workload?
 └─ YES → Explicit router (rules or small model) + per-route SLOs
```

**考试陷阱：** 在确定性的、类似提取、转换、加载（ETL）的管线每一步都选 Opus／Fable 级。优先用**工作流程＋较小模型**，并加验证闸门。

### A4. 多模型架构

常见的生产形状：

1. **路由器 → 专精者：** 便宜的分类器选择萃取 vs 推理 vs 拒绝。 
2. **草稿 → 评论：** 中阶模型起草；更强模型或评分量规评论者审查。 
3. **影子评测：** 新模型平行跑；切换上线前脱机比较。 
4. **后备：** 主路径逾时 → 降级模型或缓存答案＋人类队列。

记录每一跳**为什么**存在（质量、成本、安全）。没有理由的跳会在审查失败，也会在考试要你给最简可行设计的情境题里失败。

## B 部分 —— 提示工程与行为控制

### B1. 系统提示词是架构，不是诗

把系统提示词当成**政策＋接口契约**：

| 区段 | 目的 | 内容示例（示意） |
| --- | --- | --- |
| 角色与范围 | 框住工作 | 「你是货运报价的采购助理。你不谈判合约。」 |
| 工具政策 | 何时调用什么 | 「建议之前先调用 `get_policy`。永远不要发明政策条款。」 |
| 输出契约 | schema／格式 | JSON schema、引用来源要求、严重程度枚举 |
| 安全／拒绝 | 局部护栏 | 禁止动作；升级用语 |
| 质量门槛 | 如何处理不确定性 | 「若信心低，提出澄清问题或回传 `needs_review`。」 |
| 风格 | 受众 | 高阶简报 vs 工程师调试 |

**优先：** 明确限制＋结构化输出。 
**避免：** 含糊的「要有帮助、要彻底」却没有成功准则。

### B2. 架构师应能正确点名的提示技术

| 技术 | 何时使用 | 失效模式 |
| --- | --- | --- |
| zero-shot（零样本） | 任务清楚、基础能力强 | 含糊格式会漂移 |
| few-shot（少样本） | 格式、语气、边缘个案处理 | 坏范例变成法律；token 膨胀 |
| 思维链／结构化推理 | 多步骤逻辑（有平台思考功能时优先用） | 把链泄漏到面向用户的信道；成本 |
| 提示词内拆解 | 单次调用必须涵盖子技能 | 对审计而言仍弱于真正的工作流程闸门 |
| 强制工具（`tool_choice`） | 必须发生检索或动作 | 可选工具存在时过度强制 |
| 宪法式／原则提示 | 局部安全／风格叠加 | 未经审查时与组织政策冲突 |

### B3. 输出契约与机器消费者

若下游系统要解析 Claude 的输出，设计时**机器优先**：

- 优先用 **JSON／类型 schema**，副作用前先验证。 
- 把**面向用户的叙述文字**与**机器字段**分开。 
- 状态用明确枚举（`ok`、`needs_review`、`refused`）。 
- 用代码验证；永远不要「希望」模型有遵守。

### B4. Skills 与模块化提示词重用（公开产品概念）

公开 Claude 产品文档把 **Skills**（以及相关的模块化指示包）描述为可重用的专精指示／资源，让团队不必把巨型指示团块贴进每一次请求。CCAR-P 的架构师要点：

- 把**稳定**的专长放进模块化可重用单位。 
- 把**请求特有**的数据留在用户／工具信道。 
- 像代码一样为 Skills 做版本管理；当 Skills 可能拉取外部内容时，审查提示注入面。

## C 部分 —— 上下文工程

### C5. 什么算进窗口

送出去的一切都算。架构师必须编列预算：

1. 系统／Skills／静态政策 
2. 工具定义（大型 MCP 工具目录可能占主导） 
3. 对话记录 
4. 检索到的切块／文件 
5. 工具结果 
6. 思考 token（若启用）

公开的 **token 计数 API** 可在送出前估算——在设计审查里用它评估最坏情况提示词。

### C6. 渐进式探索 vs 巨型上下文

| 策略 | 想法 | 最适合 | 风险 |
| --- | --- | --- | --- |
| 巨型上下文 | 把「一切可能相关的」塞进提示词 | 小语料、强烈需要全域一致性 | 噪音、成本、中段遗失、缓存抖动 |
| 渐进式探索 | 先精简；用检索／工具拉需要的 | 大语料、工具生态、agent | 检索遗漏 → 答案不完整 |
| 混合 | 缓存核心政策＋动态检索 | 多数企业应用 | 两条路径的复杂度 |

**考试偏好：** 语料或工具集很大时，优先**渐进式探索**（RAG／工具／MCP 工具搜索），不要倾倒数 MB 的文本。任务短且封闭世界时，精选静态上下文可以更简单、更好审计。

### C7. 提示词缓存（架构师视角）

公开文档：提示词缓存降低重复前缀（系统提示词、大型参考文档、工具定义）的成本／延迟。缓存写入比普通输入贵；缓存**读取**有大幅折扣。TTL 常见有短的（例如约 5 分钟）与较长的（例如约 1 小时）选项——请确认现行文档。

**设计规则：**

- **稳定内容放前面**（可缓存前缀）。 
- **易变的用户内容放后面**。 
- 避免每次请求重排工具定义。 
- 变更思考预算／模式会使中断点失效——在热路径上稳定设置。 
- 记住：已缓存的 token **仍然消耗**上下文窗口容量。

### C8. 压缩（compaction）／上下文编辑

对长时间运行的 agent 与对话，公开平台功能包括**压缩**（接近上限时由服务器端摘要）与**上下文编辑**策略（例如清掉旧的工具结果）。架构师应该：

- 定义什么**永远**不可被摘要掉（安全政策、用户权益）。 
- 压缩发生时留下审计日志。 
- 压缩后测试 agent 质量——摘要漂移是真实的失效模式。

### C9. 上下文工程检查清单

- [ ] 上下文区段的优先级已文档化 
- [ ] 检索 top-k 与排序有理由 
- [ ] 工具目录大小有管理（工具搜索／允许清单） 
- [ ] 跨轮次的缓存断点稳定 
- [ ] 进入上下文的内容有个人识别信息（PII）／最小化规则 
- [ ] 上下文不足时有逃生口（`needs_more_data`）

## D 部分 —— 解决方案设计与架构模式

### D1. 端到端解决方案骨架

每一个配得上 CCAR-P 的设计都可以画成：

```
[Actors/Channels] → [Ingress & AuthN/Z] → [Orchestration layer]
 → [Claude calls / tools / retrieval]
 → [Validators & policy gates]
 → [Side effects / UX]
 → [Telemetry + eval feedback loop]
```

把每一格对到负责人（应用团队、平台、安全、数据）。缺少拥有者＝生命周期失败（见档 04）。

### D2. 模式目录（要冷背）

Anthropic 风格的教学（以及考试情境题）区分**预先定义的工作流程**与**自己决定路径的 agent**。

#### 1) 增强型 LLM（单次调用＋轻量工具）

一次 Claude 调用，也许带检索或一两项工具。 
**何时用：** 任务有界；一次推理即可。 
**优点：** 简单、便宜、容易评测。 
**缺点：** 多阶段审计弱；复原有限。

#### 2) 工作流程／提示词串接

代码拥有控制流：步骤 A → 验证 → 步骤 B → … 
**何时用：** 阶段已知、有序，且需要中间检查（采购报价萃取 → 政策验证 → 建议）。 
**优点：** 可审计、可按阶段重试、SLA 清楚。 
**缺点：** 延迟比单次调用高；工程量较大。

#### 3) 平行化

独立子任务并行跑；聚合器合并。 
**何时用：** 分支之间没有数据依赖。 
**陷阱：** 把有依赖的阶段平行化（萃取还没完成就验证）。

#### 4) 路由

分类器／路由器送到专精提示词、模型或工作流程。 
**何时用：** 异质意图共用一个前门。

#### 5) 评估器–优化器／评论循环

产生器产出；评估器依评分量规打分；迭代 N 次或直到通过。 
**何时用：** 质量变异大，且延迟允许。

#### 6) Agentic（模型驱动控制流）

Claude 规划、选择工具，并循环直到停止条件。 
**何时用：** 步骤无法完全写死；环境是开放式的（研究、为未知程序库调试）。 
**优点：** 弹性。 
**缺点：** 成本、非确定性、较难审计——需要预算、工具允许清单、高影响动作的人在回路中（HITL）。

#### 7) 多 agent

带交接的专精 agent（研究者／写作者／审查者）或监督者模式。 
**何时用：** 清楚的角色分离能提升质量或安全边界。 
**陷阱：** 多 agent 剧场——三个 agent 做一个工作流程就能做的事。

### D3. 模式选择表

| 情境 | 优先 | 避免 |
| --- | --- | --- |
| 固定阶段＋合规审计 | 工作流程＋闸门 | 完全自主的 agent |
| 开放式调查 | agent＋工具允许清单＋预算 | 脆弱的 12 步工作流程 |
| 独立文档区段 | 平行 map-reduce | 串行串接 |
| 混合意图 | 路由器 | 一个巨型提示词 |
| 高利害、不可逆动作 | 工作流程＋HITL 核准 | 写入工具不受限的 agent |
| 需要来自语料的引用来源 | RAG＋引用区块 | 纯参数式记忆 |

### D4. 拆解技术

1. **依商务阶段**（收件 → 充实 → 决定 → 行动 → 解释） 
2. **依风险**（只读研究 vs 写入动作） 
3. **依数据领域**（人力资源 vs 财务 agent，凭证分开） 
4. **依 SLA**（快路径 vs 深路径） 
5. **依信心**（自动 vs 人类队列）

在阶段之间写**接口**：schema、幂等键、错误码。考试情境题奖励能重试第 2 阶段而不重做第 1 阶段的设计。

### D5. 商务价值对齐

把架构连到可衡量的结果：

| 价值支柱 | 指标注例 | 设计杠杆 |
| --- | --- | --- |
| 效率 | 每案节省的分钟数 | 自动化率＋仅在例外时 HITL |
| 生产力 | 每人完成任务数／吞吐量 | copilot 采用、自动草稿、更快的审查循环 |
| 转型 | 解锁的新能力 | agent＋工具解锁先前只能手动做的研究 |
| 成本 | 每次成功任务的美元 | 缓存、较小模型、批量 API |
| 性能 | p95 延迟 | 平行、Haiku 路由器、较小上下文 |
| 质量*（不在指南的支柱清单里 —— 质量题干落在评测领域）* | 相对基准线的错误率 | 工作流程闸门、评测框架、困难路径用更强模型 |

若情境列出 SLA，你的答案必须**点名保护该 SLA 的杠杆**。

### D6. 非功能需求检查清单

- 可用性与降级模式 
- 每阶段延迟预算 
- 成本上限／紧急停止开关 
- 数据驻留与保留 
- 提示词／工具调用的审计日志（含屏蔽） 
- 密钥处理（永远不要放进提示词） 
- 速率限制与退避 
- 模型弃用／钉选策略 

### D7. 迷你情境演练（货运报价）

**需求：** 萃取报价字段 → 验证政策 → 建议承运人；可审计。 
**模式：** 固定**工作流程**，三个 Claude（或 Claude＋代码）阶段，中间有验证器。 
**不是：** 单一巨型自主 agent；也不是平行独立的萃取／验证／建议。 
**为什么：** 依赖＋审计。这个模式在公开练习说明里反复出现，并符合 Anthropic 的工作流程 vs agent 区分。

## 考试陷阱（平台与解决方案设计）

1. **到处都是 agent** —— 步骤已知时优先工作流程。 
2. **到处都用最大模型** —— 过量会在成本／延迟情境题失败。 
3. **平行设计忽略依赖。** 
4. **把提示词缓存当成免费上下文** —— 仍然算进窗口。 
5. **企业知识库用巨型上下文。** 
6. **系统要消费结果时没有输出 schema。** 
7. **跳过商务指标** —— 没有价值故事的架构。 
8. **忘记降级** —— Claude／API 挂了会怎样？ 
9. **多 agent 没有边界** —— 共用过度授权的工具。 
10. **每次请求都改缓存关键前缀。** 
11. **把密钥放进提示词或工具参数日志。** 
12. **把「叙述文字里的引用」等同于有依据的检索** —— 优先用公开文档的结构化引用／`search_result` 模式。

## 练习问答（25）

**Q1.** 何时应优先固定工作流程，而不是自主 agent？ 
**A.** 当阶段已知、有序，且需要中间验证／审计。

**Q2.** 系统必须先萃取、再验证、再建议。有人提案平行独立调用。错在哪？ 
**A.** 后面阶段依赖前面的输出；平行化会打破依赖。

**Q3.** 点名模型选择的三个输入。 
**A.** 任务复杂度／质量门槛、延迟 SLA、成本／量级（还有上下文大小、错误成本）。

**Q4.** 提示词缓存的 token 仍算进上下文窗口吗？ 
**A.** 是——缓存影响计费／延迟，不影响窗口占用。

**Q5.** 系统提示词的「输出契约」应包含什么？ 
**A.** schema／格式、必填字段、枚举、引用规则、不确定性处理。

**Q6.** 大型 MCP 工具目录如何伤害你？ 
**A.** 工具定义消耗上下文；优先允许清单或工具搜索／渐进式探索。

**Q7.** 什么是渐进式探索？ 
**A.** 从精简上下文开始；用检索或调用工具只拉需要的信息。

**Q8.** 何时最有理由用 few-shot 范例？ 
**A.** 用来锁定格式、语气或罕见边缘个案处理——不是用来代替事实检索。

**Q9.** 给一个多 agent 设计的正当用途。 
**A.** 用不同权限分开角色（例如研究者只读 vs 执行者写入需核准）。

**Q10.** 在生产环境提升到更大模型之前，你该做什么？ 
**A.** 在具代表性的评测集上证明质量缺口；衡量成本／延迟影响。

**Q11.** 为什么在生产架构里钉选模型 ID？ 
**A.** 避免行为突然改变；有意识地管理弃用。

**Q12.** 什么是评估器–优化器循环？ 
**A.** 产生 → 依评分量规打分 → 精炼直到通过或预算耗尽。

**Q13.** 给一个效率用例的商务价值指标。 
**A.** 平均处理时间、自动结案数，或每张工单节省的分钟数。

**Q14.** 易变的用户内容相对可缓存前缀应放在哪？ 
**A.** 稳定前缀之后（提示词末端），让缓存前缀保持稳定。

**Q15.** 何时单次增强型 LLM 调用就够？ 
**A.** 任务有界、不太需要中间审计、一次推理即可。

**Q16.** 压缩在长时间 agent 里引入什么风险？ 
**A.** 摘要漂移——若未保护，关键限制或事实可能丢失。

**Q17.** 如何在多阶段工作流程里保护 p95 延迟 SLA？ 
**A.** 每阶段预算、逾时、平行独立工作、简单阶段用较小模型、UX 允许时异步。

**Q18.** 为什么要把机器 JSON 与用户叙述文字分开？ 
**A.** 解析器需要稳定；UX 需要可读——混在一起会造成脆弱的集成。

**Q19.** 路由器模式适合什么？ 
**A.** 一个入口后面有异质意图，各自用不同提示词／模型／工作流程。

**Q20.** 给一个选择云端托管 Claude（Bedrock／Vertex／Foundry）而不是直连 API 的理由。 
**A.** 企业采购、既有云端承诺用量、数据驻留／合规控制（视情境而定）。

**Q21.** 阶段接口为了重试应包含什么？ 
**A.** 类型 schema、幂等键、明确错误码，以及验证过的输出。

**Q22.** 为什么在轮次之间变更思考／effort 设置可能很贵？ 
**A.** 它会使消息层级的提示词缓存断点失效（工具／系统前缀仍可缓存），增加延迟与花费。（注：固定 `budget_tokens` 思考预算在现行模型上已弃用／移除 —— 由自适应思考加上 `effort` 取代。）

**Q23.** 架构师对工具权限的默认立场是什么？ 
**A.** 最小权限原则——只给该角色／阶段需要的工具。

**Q24.** Skills 如何帮助团队？ 
**A.** 模块化可重用的指示／资源减少提示词蔓延，并提升一致性。

**Q25.** 利益相关者想要「完全自主」处理受监管的核准。你改提案什么？ 
**A.** 带政策检查与高影响核准的人在回路中的工作流程；若需要，agent 只做有界研究。

## F 部分 —— 更深的解决方案模式与反模式

### F1. 带程序闸门的提示词串接

生产级串接不是「三个提示词排成一列」。它是：

1. **确定性前置**（解析上传、规范化单位、加载租户设置）。 
2. **LLM 步骤**，契约狭窄。 
3. **程序化验证器**（schema、商务规则、允许清单）。 
4. **分支：** 通过 → 下一阶段；失败 → 修复提示词、有上限地重试，或人类队列。 
5. **幂等副作用**只在最终闸门之后。

这种 LLM＋代码的混合，正是 CCAR-P 情境题奖励的。纯 LLM 自我检查有帮助，但对合规叙事而言弱于有类型的验证器。

### F2. 文档上的 map-reduce

对大型文档包（建议邀请书、尽职调查卷宗）：

- **Map：** 每个切块／文档平行跑同一个萃取提示词（中／快速模型）。 
- **Reduce：** 更强模型带引用来源与冲突侦测做综合。 
- **Verify：** 抽查冲突字段；可选第二轮评论。

架构师关注：切块边界切断表格、mapper 之间 schema 一致，以及 reduce 阶段 token 爆炸。

### F3. 人在回路中作为架构组件

HITL 不只是安全主题（档 03）。在解决方案设计里它是**一等阶段**：

| 触发 | UX 模式 | 要给人类看的数据 |
| --- | --- | --- |
| 模型信心低 | 审查队列 | 最不确定之处＋来源片段 |
| 高影响动作 | 明确核准／拒绝 | 拟议写入的差异比较＋政策引用 |
| 新颖意图 | 专家升级 | 对话逐字稿＋用过的工具 |
| 评测回归 | 影子模式 | 旧 vs 新输出并排 |

设计队列的 SLA 与拥有权，否则这份「架构」会在生产环境失败。

### F4. 批量 vs 即时

公开的 Batch API 用延迟换成本／吞吐量。架构师在以下情况选 Batch：

- 工作是隔夜分析、脱机评测、语料充实。 
- 用户没有在同步 UI 上等。 

在即时与批量之间**维持相同的提示词与 schema**，让评测可转移。文档化不同的逾时与重试政策。

### F5. 反模式库（背名称）

1. **全能提示词** —— 一个提示词包办萃取、推理、行动与道歉。 
2. **工具蔓延** —— 把每一个 SaaS 动词都暴露给一个 agent。 
3. **上下文垃圾场** —— 整个 SharePoint 倾倒进系统提示词。 
4. **无评测上线** —— 「看到质量就会知道。」 
5. **没有预算的自主** —— 无界循环与花费。 
6. **静默后备** —— 换模型却没有日志／遥测。 
7. **schema 可选** —— 自由文本进企业资源规划（ERP）。 
8. **安全事后螺栓** —— 工具已经在写之后才做 authZ。 
9. **多 agent 角色扮演** —— 三个角色、一套共用过度授权的工具包。 
10. **延迟表演** —— 在是／否分类上做深度思考。

### F6. 容量与成本建模（粗估）

对阶段为 S1..Sn 的工作流程：

- Tokens ≈ sum(input_i + output_i) × requests × (1 + retry_rate) 
- 对稳定前缀套用缓存命中率 
- 套用升级到昂贵模型的路由器比例 
- 工具／RAG 基础设施成本另外加 

考试诀窍：若情境给了量级＋延迟，即使你也选对了模式，仍要**提到缓存、路由或批量**作为成本／延迟杠杆。

### F7. 迁移与模型升级 playbook（操作手册）

1. 钉选目前的模型 ID。 
2. 从生产日志（已屏蔽）创建影子流量或脱机重放。 
3. 比较任务指标＋安全指标。 
4. 带紧急停止开关的金丝雀百分比。 
5. 更新 runbook 与提示词快照。 
6. 然后才改钉选。

在受监管环境里，永远不要没有计划就「直接翻别名」。

### F8. 产品与平台团队之间的接口契约

定义：

- **提示词／Skill 拥有权**与审查节奏 
- **工具登录**拥有权与变更管制 
- **评测套件**拥有权与发布闸控 
- 模型行为异常的**事故严重程度**定义 

CCAR-P 会模糊进生命周期（档 04）；在设计答案里点名负责人会得分。

## G 部分 —— 提示词与上下文深技术

### G1. 分开指示、数据与不可信内容

架构师应在结构上分开：

- **可信指示**（系统／Skills／开发者） 
- **检索到的文档**（数据；可能恶意——注入风险） 
- **用户发言**（意图；可能对抗性） 
- **工具输出**（半可信，视工具而定）

用清楚的分隔符号、引用来源，并指示模型把检索内容当成**不可信数据**。搭配档 02／03 的技术控制（允许清单、输出编码、权限分离）。

### G2. 结构化推理但不泄漏思维链

有平台**思考**功能时，优先用它做隐藏推理。若必须向用户展示理由，提供经过整理的**面向用户的解释**字段——不是原始思维链——尤其在受监管 UX。

### G3. 确定性杠杆（务实，不是绝对）

LLM 调用是随机的。用以下方式降低变异：

- （仅旧模型）较低 temperature —— 现行 Claude 层级（Opus 4.7＋／Opus 5／Sonnet 5／Fable 5）会拒绝采样参数，因此改靠下面的杠杆 
- 严格 schema 
- few-shot 锚点 
- 工作流程闸门 
- 仅在成本允许时做集成／自我一致性 

不要在客户 SLA 里承诺字节完全相同的输出；承诺**流程 SLA**与质量指标。

### G4. 多模态设计笔记

当输入包含图像／PDF：

- 决定表格比较适合视觉模型调用 vs 光学字符识别（OCR）＋文本管线。 
- 为成本限制图像分辨率／数量。 
- 把 OCR 文本当成不可信的检索内容。 
- 用真实文档扫描做评测，不只干净的数字 PDF。

### G5. 国际化与语气

企业设计常需要多语支持。公开 Claude 模型具备多语能力；仍要：

- 把语言政策放进输出契约（「用用户的语言回答」）。 
- 按语言评测——质量不会凭空均一。 
- 小心混合语言的检索语料与向量嵌入／搜索缺口（档 02）。

## H 部分 —— 额外情境演练

### 情境 H1 —— 内部政策问答

**需求：** 员工问人力资源政策；答案必须引用政策；错误的法律建议风险高。 
**设计：** 对有版本的政策语料做渐进式 RAG＋必须引用来源的输出＋检索为空时拒绝＋把「例外／核准」意图另外路由到 HITL。中阶模型；缓存系统＋工具定义。 
**不是：** 只靠模型记忆的参数答案；也不是带寄信工具的完全自主 agent。

### 情境 H2 —— monorepo 的编码助理

**需求：** 帮开发者导览大型 repo、提案修补、跑测试。 
**设计：** 带存储库工具、测试执行器、以及严格写入权限到分支的 agent 模式——不是直接部署到生产。强编码模型。上下文用渐进式文件抓取，不是整座 monorepo 倾倒。企业 Claude Code 用服务器管理设置／已核准 MCP 工具（细节见档 04）。 
**评测：** SWE 风格任务套件＋安全回归（无密钥外泄）。

### 情境 H3 —— 客服 copilot

**需求：** 建议回复；由客服人员寄出。草稿 p95 < 2 秒。 
**设计：** 快速模型起草；检索账户＋宏；对愤怒／VIP 可选升级到中阶模型。工作流程，不是开放 agent。缓存宏／政策。HITL 就是人类客服（永远开着）。 
**指标：** 编辑距离、客户满意度（CSAT）、处理时间、事实字段的幻觉率。

### 情境 H4 —— 隔夜合约条款萃取

**需求：** 每晚 5 万份 PDF；对成本敏感；早上仪表板。 
**设计：** 批量 API＋map-reduce 工作流程＋schema 验证＋例外队列。不是交互式 Opus 级对话 UX。

## I 部分 —— 延伸练习问答（26–35）

**Q26.** 流程 SLA 与承诺相同的 LLM 字符串有何差别？ 
**A.** 流程 SLA 涵盖延迟、可用性与质量比率；相同字符串对生成模型不切实际。

**Q27.** 为什么对密集表格在纯视觉之前或改用 OCR？ 
**A.** 表格往往经 OCR＋结构管线萃取更可靠；无论哪条路都要用评测验证。

**Q28.** 模型升级金丝雀计划应包含什么？ 
**A.** 影子／重放指标、百分比推行上线、紧急停止开关、提示词钉选对齐、回滚负责人。

**Q29.** 如何防止「上下文垃圾场」？ 
**A.** 检索筛选、top-k 上限、相关性门槛、渐进式探索，以及定期语料卫生。

**Q30.** 何时批量 API 是错误选择？ 
**A.** 当最终用户需要交互、低延迟回应时。

**Q31.** 点名两种降低萃取变异的技术。 
**A.** JSON schema 验证＋few-shot 锚点（还有确定性后处理器）。temperature 调整在现行 Claude 层级不是杠杆 —— 那里会拒绝采样参数。

**Q32.** 为什么要把研究 agent 凭证与执行 agent 凭证分开？ 
**A.** 最小权限原则与爆炸半径控制，以防研究路径被提示注入。

**Q33.** 架构事故审查至少应记录什么？ 
**A.** 模型 ID、提示词／Skill 版本、工具调用（已屏蔽）、检索 ID、延迟，以及决策结果。

**Q34.** 一项设计用三个 agent，全都共用管理员 SaaS token。主要问题？ 
**A.** 过度授权／缺少安全边界——多 agent 没有隔离。

**Q35.** Skills 如何与缓存策略交互？ 
**A.** 稳定的 Skill 内容可以活在可缓存前缀里；谨慎做版本，让缓存与行为保持一致。

## J 部分 —— 主要学习深挖：架构决策情境题

把这些当计时演练。写 6–10 句决策，再核对评分键。

### 情境 J1 —— 3 天 SLA 下的理赔分案

**上下文：** 保险公司希望 Claude 把理赔周期从 11 天压到 3 天。量级为每天 8 千件理赔。监管要求可审计的决策轨迹。超过 5 千美元的给付需要人类签名。语料：保单 PDF＋结构化理赔表单。

**决定：** 每阶段模式、模型分层、HITL 位置、成功指标。

**评分键（偏好形状）：**
1. **工作流程**，阶段为：收件／OCR → 萃取字段 → 政策检索＋引用 → 建议 →（若给付 ≥ 5 千美元或信心低则 HITL）。 
2. **路由器：** 意图／信心用 Haiku 级；萃取＋建议用 Sonnet 级；只有评测证明值得时，才把困难争议升级到更高能力。 
3. 指标：周期时间、门槛以下的自动解决率、引用覆盖、人类推翻率、自动路径的 p95 延迟、每件理赔美元。 
4. 反模式：对支付系统有写入工具的单一自主 agent；巨型「把整本保单贴进去」的上下文。

### 情境 J2 —— 40 个 repo 组织的内部编码助理

**上下文：** 平台团队希望 Claude 横跨 IDE／CLI。密钥不得离开保管库。部分 repo 受监管。近似自动完成的说明延迟应有交互感；深度重构可以异步。

**决定：** 渐进式 vs 巨型上下文；Skills vs 巨型 `CLAUDE.md`；模型路由。

**评分键：** 经 repo `CLAUDE.md`＋文档检索＋仅核准工具的 MCP 做渐进式探索。把**交互**中阶路径与带预算的**深度 agent** 高能力路径分开。受监管 repo：更严的允许清单＋没有服务器网页工具。用组织 Skills 做 ADR／测试模板；避免一个 5 万 token 的全域提示词。

### 情境 J3 —— 带客户关系管理（CRM）工具的多语客服 copilot

**上下文：** 12 种语言，CRM 写入动作（案件备注、≤ 50 美元退款自动）。品牌语气关键。幻觉退款是灾难。

**决定：** 模式、输出契约、工具 authZ、评测焦点。

**评分键：** 增强型 LLM＋工具，退款放在**工作流程闸门**内（schema 验证＋政策引擎＋金额上限）。不要让模型单独「决定」退款资格——上限由代码强制执行。评测：语言质量抽样＋工具调用正确性＋超出政策时拒绝。引用来源不是主轴；**动作正确性**才是。

### 情境 J4 —— 隔夜批量合约条款萃取

**上下文：** 每晚 20 万份 PDF；结构化 JSON 进仓储；字段准确率目标 98%；对成本敏感。

**决定：** 批量 vs 即时 API；map-reduce；模型层级；验证。

**评分键：** 批量 API＋map-reduce（逐文档萃取 → schema 验证 → 隔离失败 → 抽样人工审计）。除非困难条款需要升级，优先带强 schema 的中阶模型。GA 前先做成本模型。不是交互式 agent。

## K 部分 —— 取舍对照表（桌上参考）

### K1. 能力 vs 延迟 vs 成本（操作者视角）

| 杠杆 | 改善 | 往往变差 | 考试线索 |
| --- | --- | --- | --- |
| 较高能力模型 | 困难推理、编码、判断 | 延迟、$ | 高利害脱机审查 |
| 较快／较便宜模型 | p95、吞吐量、$ | 边缘个案质量 | 分类／萃取／路由 |
| 思考／较高 effort | 多步骤正确性 | token、延迟、缓存稳定 | 困难数学／逻辑／规划 |
| 提示词缓存 | 稳定前缀上的 $ 与首个 token 延迟（TTFT） | 设计纪律（前缀顺序） | 大型静态系统＋工具 |
| 较小上下文 | 延迟、焦点 | 完整性 | 渐进式探索 |
| 平行阶段 | 墙钟时间 | $ 与合并复杂度 | 独立分支 |
| 批量 API | 单位经济 | 交互性 | 隔夜工作 |
| 更强评测闸门 | 质量、安全 | 出货时间 | 受监管 GA |

### K2. 模式 vs 可审计性

| 模式 | 可审计性 | 弹性 | 典型成本变异 |
| --- | --- | --- | --- |
| 增强型 LLM | 高（一次调用） | 低 | 低 |
| 工作流程 | 非常高（阶段日志） | 中 | 中 |
| agent | 中（需要追踪） | 高 | 高 |
| 多 agent | 需要 hop ID | 最高 | 最高 |

**经验法则：** 优先能满足需求的**最左侧**模式。只有评测显示左边失败时才往右移。

### K3. 上下文策略取舍

| 策略 | token 效率 | 完整性风险 | 运营复杂度 |
| --- | --- | --- | --- |
| 巨型倾倒 | 规模上差 | 低（若放得下） | 起初低，后来爆炸 |
| 渐进式 RAG | 好 | 检索遗漏 | 中 |
| 工具／MCP 探索 | 好 | 工具选择错误 | 中–高 |
| 混合：缓存核心＋动态 | 最佳常见情况 | 双路径错误 | 中 |

## O 部分 —— 延伸问答（36–40）

**Q36.** 利益相关者想用「一个巨型 agent」取代审计人员会检查的 7 阶段核保检查清单。最佳回应？ 
**A.** 提案对应检查清单的**工作流程**，并记录各阶段输出；agent 只留给开放研究子任务。这里可审计性胜过弹性。

**Q37.** 交互 UX 需要 p95 < 2 秒，但困难个案需要深度推理。最佳设计？ 
**A.** **路由器**：快路径用中／快速模型；深度思考走异步或「继续分析」路径；沟通 UX 预期。

**Q38.** 系统提示词很大，缓存命中率却只有 5%。最可能原因？ 
**A.** 易变内容或工具定义插在**稳定前缀之前**，或思考／设置每次调用都改中断点。

**Q39.** 对 500 份合约做 map-reduce，选两项：(a) 平行逐文档萃取 (b) 一次调用塞进所有 PDF (c) 各自做 schema 验证 (d) 单一 agent 无限制写入 ERP。 
**A.** **(a)** 与 **(c)**。

**Q40.** Skills vs 把专长塞进每一则用户消息——何时 Skills 胜出？ 
**A.** 当专长在许多请求间**稳定、可重用、有版本**；请求特有事实留在用户／工具信道。

## Q 部分 —— 模型路由与成本包络（带数字演练）

架构师需要粗估数学，不是背价目表（价格会变——请核对文档）。

### 成本包络工作单

```
Monthly tasks T
× tokens_in_avg × ($/M input) 
+ tokens_out_avg × ($/M output)
+ cache_write share × write_rate + cache_read share × read_rate
+ tool_overhead_tokens
= monthly model $
```

再加上：检索基础设施、HITL 人力、可观测性存储。对比每次成功任务的价值。

### 路由示例（示意比例）

| 路径 | 流量 % | 模型级 | 备注 |
| --- | --- | --- | --- |
| 分类／拒绝 | 40% | 快速 | 守门者 |
| 标准答案 | 45% | 中 | 已缓存政策前缀 |
| 困难推理／争议 | 15% | 高 | 思考打开；异步 OK |

若困难路径占成本 60% 却只占量 15%，评测中阶＋评论对某一切片是否更便宜。

### 何时批量 API 胜出

高量、对延迟不敏感、结构化工作（萃取、分类、隔夜报告）。不是给对话 UX。搭配 schema 验证与隔离队列。

### 钉选与升级

生产钉选模型 ID；升级走影子 → 评测闸门 → 金丝雀 → 全面。把提示词与模型当成**耦合**发布产物。
