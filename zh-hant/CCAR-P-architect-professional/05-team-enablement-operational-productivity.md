**CCAR-P 濃縮領域 5（專檔）**
**此處對應官方領域：**開發者生產力與營運賦能（**7%**）

7% 這個領域分量超過配分比重，因為一旦你懂團隊的 **控制平面**，錯答案就很明顯：如何推行上線 Claude Code（或類似建造者工具），帶 **強制安全**、**共享 Skills**、**標準化工作流程** 與 **營運 runbook（維運手冊）**——同時不要把每個開發者變成不受監督的生產憑證管理員。

5. 生產力工作流程（程式碼、測試、文件、除錯）

## Part A — 推行上線策略

### A1. 為什麼架構師要負責賦能設計

若平台／安全不鋪路，團隊就會採用消費級 AI，並養成把密鑰貼上的習慣。架構師要設計：

- 身分（單一登入（SSO））進入核可工具
- 資料處理規則（哪些程式碼／密鑰可以送出）
- 核可的 MCP／plugin 集合
- 密鑰經由 vault（密鑰庫）——不是聊天
- 採用 **以及** 事故的指標

### A2. 分階段推行上線

| 階段 | 對象 | 目標 |
| --- | --- | --- |
| 0 設計 | 平台＋安全 | 設定、Marketplace、日誌 |
| 1 試點 | 1–2 個志願團隊 | 摩擦紀錄；生產力訊號 |
| 2 擴大 | 全體工程師配訓練 | 預設安全設定 |
| 3 最佳化 | 全組織 | Skills 庫；內部開源 |
| 4 持續 | — | 版本升級；存取審查 |

每階段退出條件：安全發現已關閉；支援佇列可管理；量到的是有用採用（不是只看席位數）。

### A3. 賦能的成功指標

| 指標 | 意圖 |
| --- | --- |
| 有助理協助下首次合併 pull request（PR）所需時間 | 上手效能 |
| PR 週期時間／審查迭代 | 速度（小心干擾因素） |
| 涉及 AI 工具的密鑰掃描事故 | 安全 |
| 有 `CLAUDE.md` 的儲存庫％ | 標準化 |
| 只來自核可 Marketplace 的 MCP ％ | 供應鏈衛生 |
| 每 100 個席位的支援工單 | 賦能品質 |
| 開發者滿意度（問卷） | 鋪好的路的 UX |

## Part B — `CLAUDE.md`、Skills 與專案指示

### B1. 組織指示檔是做什麼的

公開 Claude Code 文件描述專案指引檔（常見為 `CLAUDE.md` 或同等專案指示），讓寫程式的 agent 對上：

- 儲存庫結構與慣例
- 建置／測試命令
- 程式碼風格與審查期望
- 禁止動作（例如沒有工單就不要動 `prod/`）
- 如何跑 linter／安全掃描器

**架構師指引：** 把這些檔當成 **有版本管理的產品程式碼**。在 PR 裡審查。裡面不要放密鑰。連到更深的文件，不要貼長篇小說（上下文預算）。

### B2. 分層指示

| 層 | 例子 | 範圍 |
| --- | --- | --- |
| 組織預設 | 公司編碼標準 Skill | 所有儲存庫 |
| 儲存庫 `CLAUDE.md` | 服務專屬架構 | 一個儲存庫 |
| 目錄提示 | `/payments` 更嚴的規則 | 子樹 |
| 個人 | 使用者偏好 | 只在本機——絕不能削弱安全 |

安全關鍵規則要放在 **強制設定** 裡，不能只放在模型可能權重不足的 markdown。

### B3. 給團隊的 Skills

Skills 把可重用指示／資源打包給反覆出現的任務：「加上 OpenTelemetry span」、「寫 ADR」、「遷移端點」。好處：

- 跨人一致性
- 每一輪更小的提示詞
- 可審查的產物

治理：Skill 審查負責人；語意化版本；棄用；針對外洩指示做安全掃描。

### B4. Hooks

Hooks（圍繞 agent 生命週期事件的自動化——格式器、密鑰掃描器、政策檢查）在提示詞偏軟的地方強制 **確定性的** 控制：

- 在 agent 迴圈中觸發的提交前／推送前風格檢查
- 擋住含密鑰的提交
- 自動跑格式器
- 特定路徑要求測試

考試主題：把 **軟指引**（`CLAUDE.md`）與 **硬 hooks／設定** 合在一起。

## Part C — 設定階層與強制執行

### C1. 優先順序心智模型

公開 Claude Code 企業功能描述一個階層：**伺服器受管理／組織受管理設定** 位於最高優先順序，**不能** 被專案、使用者、本機或 CLI 旗標覆寫。較低層提供預設與團隊慣例。

| 層（概念） | 使用者可覆寫？ | 用於 |
| --- | --- | --- |
| 伺服器／組織受管理 | 否 | 安全政策、拒絕的工具、環境限制 |
| Marketplace 限制 | 否／有限 | 核可 plugin 來源 |
| 共享專案建議 | 是（除非受管理） | 慣例 |
| 使用者／本機 | 是 | 個人開發者體驗（DX） |

**考試陷阱：**「在儲存庫發布建議設定 JSON，請團隊複製」——當需求是 **強制執行** 時不夠。優先受管理設定＋受管理 Marketplace。

### C2. 全組織該強制什麼

- 不允許的 MCP 來源／未經檢查的 plugin 安裝
- 安全要求的遙測／日誌基準線
- 環境變數政策
- agent shell 的命令允許／拒絕清單
- 在支援處施加對外流量限制
- 要求使用以 SSO 為後盾的安裝

### C3. 該留下彈性的東西

- 編輯器快捷鍵
- 核可集合內的非安全模型偏好
- 不授予工具的個人提示詞片段

### C4. 受管理 plugin Marketplace

中央目錄以散佈核可的：

- Skills
- Agents
- Hooks
- MCP 伺服器

支援版本管理、探索、更新與 **來源控制**——對上每個開發者去 curl 隨機 GitHub。搭配政策：公司裝置只裝 Marketplace。

## Part D — 建造者的 MCP 與憑證

### D1. 與生產執行環境分離

建造者環境必須 **不** 重用生產寫入憑證。提供：

- 範圍狹窄的開發／測試階段憑證
- 在有理據時的唯讀生產複本
- 破窗生產存取走既有特權存取管理（PAM）——不是 Claude 設定檔

### D2. 核可連接器集合

從小開始：工單追蹤、程式碼託管、內部文件搜尋、持續整合（CI）狀態。SaaS MCP 只在供應商審查後再加（檔案 03）。文件化每個連接器允許的資料類別。

### D3. 密鑰衛生訓練（強制）

- 絕不把 API 金鑰貼進提示詞
- 使用 vault＋短壽命 token
- 假設逐字稿可能依政策被保留
- 支援用的螢幕截圖要遮蔽

## Part E — 開發者生產力工作流程

### E1. 高 ROI 助理使用案例

| 工作流程 | AI 如何幫忙 | 護欄 |
| --- | --- | --- |
| 程式碼庫上手 | 解釋模組、找例子 | 引用檔案；驗證 |
| 功能鷹架 | 樣板＋測試 | 人類審查；架構適配 |
| 錯誤調查 | 把日誌對到程式碼 | 不要生產寫入 |
| 測試產生 | 邊界案例 | 仍在 CI 跑 |
| PR 說明／變更紀錄 | 摘要差異比較 | 作者課責 |
| 文件漂移修復 | 更新 README | 審查正確性 |
| 重構 | 機械轉換 | 要求測試 |

### E2. 反模式

- 沒讀就接受大型 AI 差異比較
- 因為「模型說它通過」就跳過測試
- 讓 agent 不安全地強制推送／改寫 git 歷史
- 為除錯把客戶 PII 貼進提示詞
- 沒有專家審查就產生加密／驗證程式碼

### E3. 審查文化升級

AI 增加差異比較的 **量** → 提高審查標準：

- AI 碰過的驗證／付款路徑要求測試
- 歸屬註記
- 更小的 PR
- 工具／MCP 變更的威脅模型檢查清單

### E4. 不說謊地量測生產力

小心「程式碼行數」虛榮。優先：

- 變更前置時間
- 變更失敗率
- 感知苦工下降問卷
- 上手到第一次有意義 PR 的時間

控制團隊成熟度與同時發生的流程變更。

## Part F — 營運賦能與 runbook

### F1. AI 輔助營運（安全模式）

用助理來：

- 摘要警示風暴
- 關聯日誌（在政策內）
- 起草事故時間線
- 建議儀表板查詢
- 起草事後檢討大綱

**不要** 第一天就把不受限的雲端管理員交給聊天 agent。

### F2. AI 功能的 runbook 範本

對每個生產 Claude 功能（產品執行環境——不只 IDE）：

1. 症狀
2. 儀表板
3. 功能旗標／釘定回滾
4. 區分模型 vs 檢索 vs 工具失敗
5. 安全事故分叉 → 安全 IR
6. 客戶溝通指向
7. 升級圖

賦能意指值班可以執行，不必每次都呼叫原始架構師。

### F3. 建造者工具的支援模式

| 層級 | 處理者 | 例子 |
| --- | --- | --- |
| L1 | IT／服務台 | 安裝、SSO、授權 |
| L2 | 平台 AI 賦能 | 設定、MCP 允許清單請求 |
| L3 | 安全＋架構師 | 疑似外洩、惡意 Skill |

知識庫：黃金 `CLAUDE.md` 例子、FAQ、已知失效模式、新 MCP 申請表。

### F4. 除錯生產力迴圈

教建造者標準迴圈：

1. 重現
2. 用 **最少** 敏感脈絡問助理
3. 對測試驗證
4. 若模式復現就文件化成 Skill

## Part G — 訓練與上手課程

### G1. 依角色路徑

| 角色 | 課程焦點 |
| --- | --- |
| 個人貢獻者（IC）開發者 | `CLAUDE.md`、提示詞衛生、帶 AI 的 PR 審查、密鑰 |
| 技術主管 | Skills 撰寫、hooks、指標、團隊規範 |
| SRE／營運 | runbook、安全營運助理、回滾 |
| 安全推動者 | MCP 威脅模型、設定強制執行、稽核 |
| 產品經理（PM）／工程經理（EM） | 生命週期指標、期望管理（檔案 04） |

### G2. 上手週大綱

- 第 1 天：帳戶、SSO、政策確認
- 第 2 天：走訪鋪好的路 Skills；在沙箱儲存庫完成實驗
- 第 3 天：配對真實任務，帶審查檢查清單
- 第 4 天：密鑰衛生＋注入意識迷你模組
- 第 5 天：office hours（開放諮詢時段）；回饋表

### G3. 實驗（原創構想）

1. 加上「從範本產生 ADR」的 Skill
2. 為 `.env` 提交設定封鎖清單 hook
3. 用 MCP 文件搜尋回答架構問題並附引用
4. 在玩具 RAG 裡故意打破租戶歸屬並修過濾器（搭配 `02`）
5. 在測試階段練習回滾提示詞釘定

### G4. 推動者網絡

各組織單位的志願推動者降低 L2 負擔；他們每兩週開會分享 Skills 與事故。架構師播下第一個 Skill 庫。

## 決策樹

### 強制 vs 建議

```
Could a developer override cause data leak or prod damage?
 YES → Org-managed enforced setting / hook / deny tool
 NO → Recommended project settings / CLAUDE.md guidance
```

### 新 MCP 請求

```
Vendor review + least scopes + stage credentials + Skill docs + owner?
 ALL YES → Marketplace publish
 ELSE → Reject or sandbox spike only
```

---

## 考試陷阱

1. 用建議的儲存庫設定取代組織強制政策。
2. 允許任意 plugin 安裝然後「稍後稽核」。
3. IDE MCP 設定裡的生產管理員憑證。
4. 充滿密鑰的 `CLAUDE.md` 長篇。
5. 只量測席位採用，不量測安全或成果。
6. 帶不受限雲端身分與存取管理（IAM）的 AI 營運機器人。
7. 沒有支援層級／知識庫——架構師永遠當 L1。
8. 沒有負責人或審查的 Skills。
9. 訓練只講提示詞，從不講 hooks／設定。
10. 被 agent 放大的強制推送文化。

## 練習問答（28）

**Q1.** 如何強制執行開發者無法覆寫的設定？
**A.** 使用位於最高優先順序的組織／伺服器受管理設定。

**Q2.** 為什麼「把建議設定放進 git」對強制安全不夠？
**A.** 團隊可以忽略或改掉它們；受管理設定無法被覆寫。

**Q3.** 受管理 Marketplace 該散佈什麼？
**A.** 核可的 Skills、hooks、agents、MCP 伺服器（有版本）。

**Q4.** 儲存庫專屬建置命令該放哪？
**A.** 有版本管理的專案指示（例如 `CLAUDE.md`），在 PR 裡審查。

**Q5.** 舉出兩個超出 markdown 指引的硬控制。
**A.** Hooks（密鑰掃描／格式）以及組織受管理拒絕清單／工具政策。

**Q6.** 為什麼要把建造者憑證與生產寫入金鑰分開？
**A.** 限制提示注入或 agent 誤動作的爆炸半徑。

**Q7.** 超出席位的好賦能指標？
**A.** 首次合併 PR 所需時間、密鑰事故、僅核可 MCP 的％、CSAT。

**Q8.** Skill 對團隊有什麼用？
**A.** 把反覆工作流程打包，以求一致與重用。

**Q9.** 誰該發布到組織 Marketplace？
**A.** 經審查的受控發布者——預設不是每個開發者。

**Q10.** AI 產生的驗證程式碼需要什麼額外步驟？
**A.** 專家人類審查（＋測試）；不要盲目信任。

**Q11.** Claude Code 的 L1 vs L2 支援？
**A.** L1 安裝／SSO；L2 平台設定／MCP 允許清單請求。

**Q12.** AI 功能值班 runbook 該放什麼？
**A.** 回滾釘定／旗標、儀表板、失敗區分、升級。

**Q13.** 為什麼要教使用 MCP 的開發者注入意識？
**A.** 不可信內容可以導向握有工具的 agent。

**Q14.** 該避開的虛榮生產力指標？
**A.** 原始產生的程式碼行數。

**Q15.** 推動者網絡是做什麼的？
**A.** 聯邦式賦能、Skill 分享、降低中央工單負擔。

**Q16.** 個人設定可以削弱組織安全政策嗎？
**A.** 絕不能——若管理正確，組織政策勝出。

**Q17.** 團隊請求新 SaaS MCP 時的第一步？
**A.** 安全／供應商審查＋範圍最小化（不是立刻安裝）。

**Q18.** Hooks 如何補足 `CLAUDE.md`？
**A.** Hooks 強制確定性檢查；markdown 是建議式脈絡。

**Q19.** 技術主管超出 IC 還需要什麼訓練？
**A.** Skills 撰寫、hooks、團隊規範、指標。

**Q20.** 為什麼用 AI 除錯前要遮蔽客戶 PII？
**A.** 隱私／政策合規；降低保留與外洩風險。

**Q21.** 破窗生產存取該走什麼？
**A.** 既有 PAM／特權工作流程——不是 agent 設定裡的長壽命金鑰。

**Q22.** 有 `CLAUDE.md` 的儲存庫％表示什麼？
**A.** agent 指引的標準化（領先賦能指標）。

**Q23.** 沒有負責人的 Skills 的風險？
**A.** 漂移、遺棄、潛在惡意的過期指示。

**Q24.** AI 該如何影響 PR 大小規範？
**A.** 保持 PR 可審查；不要合併沒人讀過的巨大 AI 傾倒。

**Q25.** 上手中 office hours 的目的？

## Part M — 主修深挖：鋪好的路賦能

領域配分比重只有 **7%**，但題目具體：設定優先順序、安全預設、`CLAUDE.md`／Skills／hooks、核可 MCP／plugins，以及營運除錯模式。錯答案通常違反 **最小權限原則**，或把 **建造者工具** 與 **生產執行環境** 搞混。

### M1. 控制平面心智模型

```
Org managed settings (non-overridable security)
 → Team / enterprise defaults
 → Repo CLAUDE.md + Skills (versioned)

```

**考試規則：** 安全相關控制要放在 **使用者無法繞過的最高優先順序**。生產力便利可以是建議預設。

### M2. 該強制 vs 建議（擴充）

| 控制 | 全組織強制 | 建議 |
| --- | --- | --- |
| 密鑰外洩護欄／hooks | 是 | — |
| 禁止未核可 MCP／Marketplace | 是 | — |
| 擋住貼上 `.env`／金鑰模式 | 是 | — |
| 要求 SSO | 是 | — |
| 互動用預設模型 | 常常 | 若政策允許可給進階使用者 |
| 提交訊息風格 Skill | — | 是 |
| 積極自動跑 shell | 預設拒絕 | 對受信任儲存庫謹慎啟用 |
| 工具使用的遙測／稽核 | 在合法處是 | — |

### M3. `CLAUDE.md` 設計指南

好的組織／儲存庫指示檔：
- 架構地圖與服務邊界
- 測試命令與「完成的定義」
- 安全絕對不要做（生產憑證、原始 PII）
- 如何提案新增 MCP／Skill
- 連到 runbook——不是密鑰

壞檔：
- 整份風格指南貼兩次
- 憑證
- 與組織受管理政策矛盾
- 18 個月前未維護的傳說

**分層：** 組織基準線 → 儲存庫細節 → 個人偏好（若允許）。在測試階段用刻意衝突測優先順序。

| --- | --- | --- |

## Part N — 經得起檢視的生產力工作流程

### N1. 高 ROI 迴圈（帶審查閘口）

1. **解釋 → 提案 → 修補 → 測試 → PR 摘要**，帶人類審查。
2. **失敗測試 → 根因假設 → 最小修復。**
3. **舊模組 → 重構前先做特徵化測試。**

### N2. 反模式

| 反模式 | 為什麼不好 | 換成 |
| --- | --- | --- |
| 盲目接受所有差異比較 | 送出弱點／密鑰 | 強制審查文化 |
| 把生產傾倒貼進對話 | 資料外洩 | 已遮蔽的測試夾具 |
| 指標＝產生行數 | 表演 | 週期時間＋變更失敗率 |
| 帶工具的未追蹤 Skills | 供應鏈 | 受管理 Marketplace |
| 筆電上一把共享 API 金鑰 | 歸屬／濫用 | SSO＋依使用者 |

### N3. 誠實量測生產力

優先：PR 週期時間、審查迭代、逃逸缺陷、密鑰掃描事故、開發者滿意度、新人到第一次有生產力 PR 的時間。
不信任：原始接受率、把 token 花費當「價值」、AI 程式碼行數。

### N4. 除錯與營運賦能

安全模式：AI 協助 **唯讀** 診斷；修復走既有變更系統。提供助理可檢索的 runbook；不要把雲端管理員 MCP 授給每位工程師筆電上的 agent。

Runbook 區段：症狀 → 蒐集（命令）→ 假設 → 緩解 → 驗證 → 升級 → 事後檢討連結。

## Part T — 延伸問答（49–60）

**Q49.** 「拒絕未核可 MCP」的最高優先順序位置？
**A.** **組織受管理／不可覆寫** 設定——不是單靠一行有希望的 `CLAUDE.md`。

**Q50.** 選 TWO 個賦能成功指標：密鑰掃描事故、只看席位數、首次合併 PR 所需時間、燒掉的原始 token。
**A.** 密鑰掃描事故與首次合併 PR 所需時間。

**Q51.** 帶生產資料庫管理員的建造者 MCP——可接受嗎？
**A.** **否**——用沙箱／唯讀角色；生產變更走受控執行環境。

**Q52.** Hooks vs Skills——擋住外洩命令的安全？
**A.** 優先 **hooks／強制控制**；Skills 是指示，不是硬強制。

**Q53.** 影子 AI 使用——最佳架構師動作？
**A.** 鋪好的路＋政策＋遷移，不是只禁。

**Q54.** `CLAUDE.md` 含 API 金鑰——動作？
**A.** 輪替金鑰、清除歷史、教 vault；加上密鑰掃描。

**Q55.** 選 THREE 個推行上線階段：設計控制、試點、擴大、安全拖到 GA、把密碼寄給團隊。
**A.** 設計、試點、擴大。

**Q56.** 為什麼要把生產 agent 憑證與 Claude Code MCP 分開？
**A.** 爆炸半徑、變更管制與歸屬需求不同。

**Q57.** 生產力表演例子？
**A.** 慶祝 AI 產生的程式碼行數，同時變更失敗率上升。

**Q58.** 受管理 plugin Marketplace 的目的？
**A.** 散佈 **核可** 工具／Skills；降低供應鏈風險。

**Q59.** 營運要 AI「直接修生產」。安全模式？
**A.** 唯讀診斷＋人類／受變更管理的修復。

**Q60.** 儲存庫指示與組織拒絕清單衝突——誰贏？
**A.** **組織強制設定**；修儲存庫檔。
