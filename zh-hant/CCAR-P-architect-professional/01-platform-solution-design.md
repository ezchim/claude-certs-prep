## 概覽

CCAR-P 要你用**生產環境架構師**的方式思考，而不是只會修修補補提示詞的人。在情境題裡，你會：

1. 把雜亂的商務問題翻成 **Claude 驅動的解決方案形狀**（輸入 → 處理 → 輸出 → 回饋）。
2. 在**工作流程**、**增強型 LLM**、**agentic（自主代理式）**與**多 agent** 模式之間做選擇，並把取捨講清楚。
3. 選擇**模型層級**（能力 vs 延遲 vs 成本 vs 上下文）並為選擇辯護。
4. 把**提示詞與上下文**工程做好，讓系統在 token、安全與重用限制下仍然可靠。
5. 把設計選擇連到**商務價值支柱** —— 用官方指南的措辭：效率、轉型、**生產力**、成本，以及效能服務水準協議（SLA）。

本檔深挖平台能力與解決方案設計。整合機制（模型上下文協定（MCP）接線、檢索增強生成（RAG）管線、評測框架）見檔 `02`；治理見 `03`；利害關係人／生命週期／賦能見 `04`。

## A 部分 —— 架構師要懂的 Claude 模型

### A1. 如何看待模型階梯

公開文件描述一個 **Claude 模型家族**，速度／智力／成本定位不同。精確的 ID 與價格會隨時間變動；對 CCAR-P 來說，要背的是**決策邏輯**，不是一張凍結的價目表：

| 決策因素 | 何時優先較高能力層級… | 何時優先較快／較便宜層級… |
| --- | --- | --- |
| 任務複雜度 | 多步驟規劃、困難編碼、含糊需求、高利害判斷 | 分類、萃取、路由、短重寫 |
| 延遲 SLA | 離線批次、非同步工作、人類審過的草稿 | 互動式使用者體驗（UX）、高每秒查詢數（QPS）守門者 |
| 上下文大小 | 大型程式庫、長文件、長達數小時的 agent 追蹤 | 短輪次、負載小的工具密集迴圈 |
| 成本包絡 | 低量／高價值（合約、架構審查） | 高量／邊際價值低 |
| 錯誤成本 | 答錯很貴或不安全 | 答錯很容易抓到／重試 |

**架構師規則：** 預設用**能在你的評測集上跨過品質門檻的最小模型**。只有評測證明有缺口時，才往上提升能力。當延遲／成本預算失敗、但品質仍然站得住時，就往下。

### A2. 設計裡會出現的能力旋鈕

架構師必須放對位置的公開平台功能：

- **上下文視窗：** 目前前沿 Claude 模型通常標榜**大**視窗（數十萬到支援的模型／平台上約 **~1M tokens**）。請求裡的一切都算：系統提示詞、訊息、工具定義、圖像／文件、工具結果，以及（若使用）思考 token。快取改變的是**價格**，不是 token 是否佔用視窗。
- **最大輸出：** 同步 Messages API vs 批次（Batch；批次可能透過文件記載的 beta header 支援延伸輸出——請核實現行文件）。
- **思考／自適應思考／effort（思考力度）：** 困難問題用更深的推理；用 **effort 等級**（`output_config.effort`）控制成本／延遲。自適應思考已取代固定思考預算 —— `budget_tokens` 在 4.6 世代已棄用，在現行模型上已移除（會以錯誤拒絕）。變更思考設定會使訊息層級的提示詞快取中斷點失效（工具／系統前綴仍可快取）——設計時要顧快取穩定。
- **視覺／多模態：** 產品需要截圖、圖表或掃描文件時，使用圖像輸入。
- **部署介面：** Claude API、Amazon Bedrock、Vertex AI、Microsoft Foundry、AWS 上的 Claude Platform——各自有 ID 命名與資料落地細微差異。架構師依企業採購、區域與合規來選——不是只憑品牌偏好。**完整的 CSP／交付路徑治理決策對照表在檔 `02` 第 D5 部分**（限制排除、ZDR 主題、模型 ID 陷阱、問答）。

### A3. 模型選擇決策樹

```
START: Define task + quality bar + p95 latency + monthly volume
 │
 ├─ Need long-running agentic coding / complex enterprise judgment?
 │ └─ YES → Start with high-capability model; measure cost on realistic traces
 │
 ├─ Need interactive speed + “good enough” intelligence?
 │ └─ YES → Mid-tier (Sonnet-class); escalate hard cases via router
 │
 ├─ High QPS classify/extract/route?
 │ └─ YES → Fast tier (Haiku-class); sample escalate to mid/high on low confidence
 │
 └─ Mixed workload?
 └─ YES → Explicit router (rules or small model) + per-route SLOs
```

**考試陷阱：** 在確定性的、類似擷取、轉換、載入（ETL）的管線每一步都選 Opus／Fable 級。優先用**工作流程＋較小模型**，並加驗證閘門。

### A4. 多模型架構

常見的生產形狀：

1. **路由器 → 專精者：** 便宜的分類器選擇萃取 vs 推理 vs 拒絕。 
2. **草稿 → 評論：** 中階模型起草；更強模型或評分量規評論者審查。 
3. **影子評測：** 新模型平行跑；切換上線前離線比較。 
4. **後備：** 主路徑逾時 → 降級模型或快取答案＋人類佇列。

記錄每一跳**為什麼**存在（品質、成本、安全）。沒有理由的跳會在審查失敗，也會在考試要你給最簡可行設計的情境題裡失敗。

## B 部分 —— 提示工程與行為控制

### B1. 系統提示詞是架構，不是詩

把系統提示詞當成**政策＋介面合約**：

| 區段 | 目的 | 內容示例（示意） |
| --- | --- | --- |
| 角色與範圍 | 框住工作 | 「你是貨運報價的採購助理。你不談判合約。」 |
| 工具政策 | 何時呼叫什麼 | 「建議之前先呼叫 `get_policy`。永遠不要發明政策條款。」 |
| 輸出合約 | schema／格式 | JSON schema、引用來源要求、嚴重程度列舉 |
| 安全／拒絕 | 局部護欄 | 禁止動作；升級用語 |
| 品質門檻 | 如何處理不確定性 | 「若信心低，提出澄清問題或回傳 `needs_review`。」 |
| 風格 | 受眾 | 高階簡報 vs 工程師除錯 |

**優先：** 明確限制＋結構化輸出。 
**避免：** 含糊的「要有幫助、要徹底」卻沒有成功準則。

### B2. 架構師應能正確點名的提示技術

| 技術 | 何時使用 | 失效模式 |
| --- | --- | --- |
| zero-shot（零樣本） | 任務清楚、基礎能力強 | 含糊格式會漂移 |
| few-shot（少樣本） | 格式、語氣、邊緣個案處理 | 壞範例變成法律；token 膨脹 |
| 思維鏈／結構化推理 | 多步驟邏輯（有平台思考功能時優先用） | 把鏈洩漏到面向使用者的通道；成本 |
| 提示詞內拆解 | 單次呼叫必須涵蓋子技能 | 對稽核而言仍弱於真正的工作流程閘門 |
| 強制工具（`tool_choice`） | 必須發生檢索或動作 | 可選工具存在時過度強制 |
| 憲法式／原則提示 | 局部安全／風格疊加 | 未經審查時與組織政策衝突 |

### B3. 輸出合約與機器消費者

若下游系統要解析 Claude 的輸出，設計時**機器優先**：

- 優先用 **JSON／型別 schema**，副作用前先驗證。 
- 把**面向使用者的敘述文字**與**機器欄位**分開。 
- 狀態用明確列舉（`ok`、`needs_review`、`refused`）。 
- 用程式碼驗證；永遠不要「希望」模型有遵守。

### B4. Skills 與模組化提示詞重用（公開產品概念）

公開 Claude 產品文件把 **Skills**（以及相關的模組化指示包）描述為可重用的專精指示／資源，讓團隊不必把巨型指示團塊貼進每一次請求。CCAR-P 的架構師要點：

- 把**穩定**的專長放進模組化可重用單位。 
- 把**請求特有**的資料留在使用者／工具通道。 
- 像程式碼一樣為 Skills 做版本控管；當 Skills 可能拉取外部內容時，審查提示注入面。

## C 部分 —— 上下文工程

### C5. 什麼算進視窗

送出去的一切都算。架構師必須編列預算：

1. 系統／Skills／靜態政策 
2. 工具定義（大型 MCP 工具目錄可能佔主導） 
3. 對話紀錄 
4. 檢索到的切塊／檔案 
5. 工具結果 
6. 思考 token（若啟用）

公開的 **token 計數 API** 可在送出前估算——在設計審查裡用它評估最壞情況提示詞。

### C6. 漸進式探索 vs 單體上下文

| 策略 | 想法 | 最適合 | 風險 |
| --- | --- | --- | --- |
| 單體上下文 | 把「一切可能相關的」塞進提示詞 | 小語料、強烈需要全域一致性 | 噪音、成本、中段遺失、快取抖動 |
| 漸進式探索 | 先精簡；用檢索／工具拉需要的 | 大語料、工具生態、agent | 檢索遺漏 → 答案不完整 |
| 混合 | 快取核心政策＋動態檢索 | 多數企業應用 | 兩條路徑的複雜度 |

**考試偏好：** 語料或工具集很大時，優先**漸進式探索**（RAG／工具／MCP 工具搜尋），不要傾倒數百萬位元組的文字。任務短且封閉世界時，精選靜態上下文可以更簡單、更好稽核。

### C7. 提示詞快取（架構師視角）

公開文件：提示詞快取降低重複前綴（系統提示詞、大型參考文件、工具定義）的成本／延遲。快取寫入比普通輸入貴；快取**讀取**有大幅折扣。TTL 常見有短的（例如約 5 分鐘）與較長的（例如約 1 小時）選項——請確認現行文件。

**設計規則：**

- **穩定內容放前面**（可快取前綴）。 
- **易變的使用者內容放後面**。 
- 避免每次請求重排工具定義。 
- 變更思考預算／模式會使中斷點失效——在熱路徑上穩定設定。 
- 記住：已快取的 token **仍然消耗**上下文視窗容量。

### C8. 壓縮（compaction）／上下文編輯

對長時間運行的 agent 與對話，公開平台功能包括**壓縮**（接近上限時由伺服器端摘要）與**上下文編輯**策略（例如清掉舊的工具結果）。架構師應該：

- 定義什麼**永遠**不可被摘要掉（安全政策、使用者權益）。 
- 壓縮發生時留下稽核日誌。 
- 壓縮後測試 agent 品質——摘要漂移是真實的失效模式。

### C9. 上下文工程檢查清單

- [ ] 上下文區段的優先順序已文件化 
- [ ] 檢索 top-k 與排序有理由 
- [ ] 工具目錄大小有管理（工具搜尋／允許清單） 
- [ ] 跨輪次的快取中斷點穩定 
- [ ] 進入上下文的內容有個人識別資訊（PII）／最小化規則 
- [ ] 上下文不足時有逃生口（`needs_more_data`）

## D 部分 —— 解決方案設計與架構模式

### D1. 端到端解決方案骨架

每一個配得上 CCAR-P 的設計都可以畫成：

```
[Actors/Channels] → [Ingress & AuthN/Z] → [Orchestration layer]
 → [Claude calls / tools / retrieval]
 → [Validators & policy gates]
 → [Side effects / UX]
 → [Telemetry + eval feedback loop]
```

把每一格對到擁有者（應用團隊、平台、資安、資料）。缺少擁有者＝生命週期失敗（見檔 04）。

### D2. 模式目錄（要冷背）

Anthropic 風格的教學（以及考試情境題）區分**預先定義的工作流程**與**自己決定路徑的 agent**。

#### 1) 增強型 LLM（單次呼叫＋輕量工具）

一次 Claude 呼叫，也許帶檢索或一兩項工具。 
**何時用：** 任務有界；一次推理即可。 
**優點：** 簡單、便宜、容易評測。 
**缺點：** 多階段稽核弱；復原有限。

#### 2) 工作流程／提示詞串接

程式碼擁有控制流：步驟 A → 驗證 → 步驟 B → … 
**何時用：** 階段已知、有序，且需要中間檢查（採購報價萃取 → 政策驗證 → 建議）。 
**優點：** 可稽核、可按階段重試、SLA 清楚。 
**缺點：** 延遲比單次呼叫高；工程量較大。

#### 3) 平行化

獨立子任務並行跑；彙整者合併。 
**何時用：** 分支之間沒有資料依賴。 
**陷阱：** 把有依賴的階段平行化（萃取還沒完成就驗證）。

#### 4) 路由

分類器／路由器送到專精提示詞、模型或工作流程。 
**何時用：** 異質意圖共用一個前門。

#### 5) 評估器–最佳化器／評論迴圈

產生器產出；評估器依評分量規打分；迭代 N 次或直到通過。 
**何時用：** 品質變異大，且延遲允許。

#### 6) Agentic（模型驅動控制流）

Claude 規劃、選擇工具，並迴圈直到停止條件。 
**何時用：** 步驟無法完全寫死；環境是開放式的（研究、為未知程式庫除錯）。 
**優點：** 彈性。 
**缺點：** 成本、非確定性、較難稽核——需要預算、工具允許清單、高影響動作的人在迴路中（HITL）。

#### 7) 多 agent

帶交接的專精 agent（研究者／寫作者／審查者）或監督者模式。 
**何時用：** 清楚的角色分離能提升品質或安全邊界。 
**陷阱：** 多 agent 流程表演——三個 agent 做一個工作流程就能做的事。

### D3. 模式選擇表

| 情境 | 優先 | 避免 |
| --- | --- | --- |
| 固定階段＋合規稽核 | 工作流程＋閘門 | 完全自主的 agent |
| 開放式調查 | agent＋工具允許清單＋預算 | 脆弱的 12 步工作流程 |
| 獨立文件區段 | 平行 map-reduce | 序列串接 |
| 混合意圖 | 路由器 | 一個巨型提示詞 |
| 高利害、不可逆動作 | 工作流程＋HITL 核准 | 寫入工具不受限的 agent |
| 需要來自語料的引用來源 | RAG＋引用區塊 | 純參數記憶 |

### D4. 拆解技術

1. **依商務階段**（收件 → 充實 → 決定 → 行動 → 解釋） 
2. **依風險**（唯讀研究 vs 寫入動作） 
3. **依資料領域**（人資 vs 財務 agent，憑證分開） 
4. **依 SLA**（快路徑 vs 深路徑） 
5. **依信心**（自動 vs 人類佇列）

在階段之間寫**介面**：schema、冪等鍵、錯誤碼。考試情境題獎勵能重試第 2 階段而不重做第 1 階段的設計。

### D5. 商務價值對齊

把架構連到可衡量的結果：

| 價值支柱 | 指標示例 | 設計槓桿 |
| --- | --- | --- |
| 效率 | 每案節省的分鐘數 | 自動化率＋僅在例外時 HITL |
| 生產力 | 每人完成任務數／吞吐量 | copilot 採用、自動草稿、更快的審查迴圈 |
| 轉型 | 解鎖的新能力 | agent＋工具解鎖先前只能手動做的研究 |
| 成本 | 每次成功任務的美元 | 快取、較小模型、批次 API |
| 效能 | p95 延遲 | 平行、Haiku 路由器、較小上下文 |
| 品質*（不在指南的支柱清單裡 —— 品質題幹落在評測領域）* | 相對基準線的錯誤率 | 工作流程閘門、評測框架、困難路徑用更強模型 |

若情境列出 SLA，你的答案必須**點名保護該 SLA 的槓桿**。

### D6. 非功能需求檢查清單

- 可用性與降級模式 
- 每階段延遲預算 
- 成本上限／緊急停止開關 
- 資料落地與保留 
- 提示詞／工具呼叫的稽核日誌（含遮蔽） 
- 祕密處理（永遠不要放進提示詞） 
- 速率限制與退避 
- 模型棄用／釘選策略 

### D7. 迷你情境演練（貨運報價）

**需求：** 萃取報價欄位 → 驗證政策 → 建議承運人；可稽核。 
**模式：** 固定**工作流程**，三個 Claude（或 Claude＋程式碼）階段，中間有驗證器。 
**不是：** 單一巨型自主 agent；也不是平行獨立的萃取／驗證／建議。 
**為什麼：** 依賴＋稽核。這個模式在公開練習說明裡反覆出現，並符合 Anthropic 的工作流程 vs agent 區分。

## 考試陷阱（平台與解決方案設計）

1. **到處都是 agent** —— 步驟已知時優先工作流程。 
2. **到處都用最大模型** —— 過量會在成本／延遲情境題失敗。 
3. **平行設計忽略依賴。** 
4. **把提示詞快取當成免費上下文** —— 仍然算進視窗。 
5. **企業知識庫用單體上下文。** 
6. **系統要消費結果時沒有輸出 schema。** 
7. **跳過商務指標** —— 沒有價值故事的架構。 
8. **忘記降級** —— Claude／API 掛了會怎樣？ 
9. **多 agent 沒有邊界** —— 共用過度授權的工具。 
10. **每次請求都改快取關鍵前綴。** 
11. **把祕密放進提示詞或工具參數日誌。** 
12. **把「敘述文字裡的引用」等同於有依據的檢索** —— 優先用公開文件的結構化引用／`search_result` 模式。

## 練習問答（25）

**Q1.** 何時應優先固定工作流程，而不是自主 agent？ 
**A.** 當階段已知、有序，且需要中間驗證／稽核。

**Q2.** 系統必須先萃取、再驗證、再建議。有人提案平行獨立呼叫。錯在哪？ 
**A.** 後面階段依賴前面的輸出；平行化會打破依賴。

**Q3.** 點名模型選擇的三個輸入。 
**A.** 任務複雜度／品質門檻、延遲 SLA、成本／量級（還有上下文大小、錯誤成本）。

**Q4.** 提示詞快取的 token 仍算進上下文視窗嗎？ 
**A.** 是——快取影響計費／延遲，不影響視窗佔用。

**Q5.** 系統提示詞的「輸出合約」應包含什麼？ 
**A.** schema／格式、必填欄位、列舉、引用規則、不確定性處理。

**Q6.** 大型 MCP 工具目錄如何傷害你？ 
**A.** 工具定義消耗上下文；優先允許清單或工具搜尋／漸進式探索。

**Q7.** 什麼是漸進式探索？ 
**A.** 從精簡上下文開始；用檢索或呼叫工具只拉需要的資訊。

**Q8.** 何時最有理由用 few-shot 範例？ 
**A.** 用來鎖定格式、語氣或罕見邊緣個案處理——不是用來代替事實檢索。

**Q9.** 給一個多 agent 設計的正當用途。 
**A.** 用不同權限分開角色（例如研究者唯讀 vs 執行者寫入需核准）。

**Q10.** 在生產環境提升到更大模型之前，你該做什麼？ 
**A.** 在具代表性的評測集上證明品質缺口；衡量成本／延遲影響。

**Q11.** 為什麼在生產架構裡釘選模型 ID？ 
**A.** 避免行為突然改變；有意識地管理棄用。

**Q12.** 什麼是評估器–最佳化器迴圈？ 
**A.** 產生 → 依評分量規打分 → 精煉直到通過或預算耗盡。

**Q13.** 給一個效率用例的商務價值指標。 
**A.** 平均處理時間、自動結案數，或每張工單節省的分鐘數。

**Q14.** 易變的使用者內容相對可快取前綴應放在哪？ 
**A.** 穩定前綴之後（提示詞末端），讓快取前綴保持穩定。

**Q15.** 何時單次增強型 LLM 呼叫就夠？ 
**A.** 任務有界、不太需要中間稽核、一次推理即可。

**Q16.** 壓縮在長時間 agent 裡引入什麼風險？ 
**A.** 摘要漂移——若未保護，關鍵限制或事實可能遺失。

**Q17.** 如何在多階段工作流程裡保護 p95 延遲 SLA？ 
**A.** 每階段預算、逾時、平行獨立工作、簡單階段用較小模型、UX 允許時非同步。

**Q18.** 為什麼要把機器 JSON 與使用者敘述文字分開？ 
**A.** 解析器需要穩定；UX 需要可讀——混在一起會造成脆弱的整合。

**Q19.** 路由器模式適合什麼？ 
**A.** 一個入口後面有異質意圖，各自用不同提示詞／模型／工作流程。

**Q20.** 給一個選擇雲端託管 Claude（Bedrock／Vertex／Foundry）而不是直連 API 的理由。 
**A.** 企業採購、既有雲端承諾用量、資料落地／合規控制（視情境而定）。

**Q21.** 階段介面為了重試應包含什麼？ 
**A.** 型別 schema、冪等鍵、明確錯誤碼，以及驗證過的輸出。

**Q22.** 為什麼在輪次之間變更思考／effort 設定可能很貴？ 
**A.** 它會使訊息層級的提示詞快取中斷點失效（工具／系統前綴仍可快取），增加延遲與花費。（註：固定 `budget_tokens` 思考預算在現行模型上已棄用／移除 —— 由自適應思考加上 `effort` 取代。）

**Q23.** 架構師對工具權限的預設立場是什麼？ 
**A.** 最小權限原則——只給該角色／階段需要的工具。

**Q24.** Skills 如何幫助團隊？ 
**A.** 模組化可重用的指示／資源減少提示詞蔓延，並提升一致性。

**Q25.** 利害關係人想要「完全自主」處理受監管的核准。你改提案什麼？ 
**A.** 帶政策檢查與高影響核准的人在迴路中的工作流程；若需要，agent 只做有界研究。

## F 部分 —— 更深的解決方案模式與反模式

### F1. 帶程式化閘門的提示詞串接

生產級串接不是「三個提示詞排成一列」。它是：

1. **確定性前置**（解析上傳、正規化單位、載入租戶設定）。 
2. **LLM 步驟**，合約狹窄。 
3. **程式化驗證器**（schema、商務規則、允許清單）。 
4. **分支：** 通過 → 下一階段；失敗 → 修復提示詞、有上限地重試，或人類佇列。 
5. **冪等副作用**只在最終閘門之後。

這種 LLM＋程式碼的混合，正是 CCAR-P 情境題獎勵的。純 LLM 自我檢查有幫助，但對合規敘事而言弱於有型別的驗證器。

### F2. 文件上的 map-reduce

對大型文件包（建議請求書、盡職審查活頁夾）：

- **Map：** 每個切塊／文件平行跑同一個萃取提示詞（中／快速模型）。 
- **Reduce：** 更強模型帶引用來源與衝突偵測做綜合。 
- **Verify：** 抽查衝突欄位；可選第二輪評論。

架構師關注：切塊邊界切斷表格、mapper 之間 schema 一致，以及 reduce 階段 token 爆炸。

### F3. 人在迴路中作為架構元件

HITL 不只是安全主題（檔 03）。在解決方案設計裡它是**一等階段**：

| 觸發 | UX 模式 | 要給人類看的資料 |
| --- | --- | --- |
| 模型信心低 | 審查佇列 | 最不確定之處＋來源片段 |
| 高影響動作 | 明確核准／拒絕 | 擬議寫入的差異比較＋政策引用 |
| 新穎意圖 | 專家升級 | 對話逐字稿＋用過的工具 |
| 評測回歸 | 影子模式 | 舊 vs 新輸出並排 |

設計佇列的 SLA 與擁有權，否則這份「架構」會在生產環境失敗。

### F4. 批次 vs 即時

公開的 Batch API 用延遲換成本／吞吐量。架構師在以下情況選 Batch：

- 工作是隔夜分析、離線評測、語料充實。 
- 使用者沒有在同步 UI 上等。 

在即時與批次之間**維持相同的提示詞與 schema**，讓評測可轉移。文件化不同的逾時與重試政策。

### F5. 反模式庫（背名稱）

1. **上帝提示詞** —— 一個提示詞包辦萃取、推理、行動與道歉。 
2. **工具蔓延** —— 把每一個 SaaS 動詞都暴露給一個 agent。 
3. **上下文垃圾場** —— 整個 SharePoint 傾倒進系統提示詞。 
4. **無評測上線** —— 「看到品質就會知道。」 
5. **沒有預算的自主** —— 無界迴圈與花費。 
6. **靜默後備** —— 換模型卻沒有日誌／遙測。 
7. **schema 可選** —— 自由文字進企業資源規劃（ERP）。 
8. **安全事後螺栓** —— 工具已經在寫之後才做 authZ。 
9. **多 agent 角色扮演** —— 三個角色、一套共用過度授權的工具包。 
10. **延遲表演** —— 在是／否分類上做深度思考。

### F6. 容量與成本建模（粗估）

對階段為 S1..Sn 的工作流程：

- Tokens ≈ sum(input_i + output_i) × requests × (1 + retry_rate) 
- 對穩定前綴套用快取命中率 
- 套用升級到昂貴模型的路由器比例 
- 工具／RAG 基礎設施成本另外加 

考試訣竅：若情境給了量級＋延遲，即使你也選對了模式，仍要**提到快取、路由或批次**作為成本／延遲槓桿。

### F7. 遷移與模型升級 playbook（操作手冊）

1. 釘選目前的模型 ID。 
2. 從生產日誌（已遮蔽）建立影子流量或離線重放。 
3. 比較任務指標＋安全指標。 
4. 帶緊急停止開關的金絲雀百分比。 
5. 更新 runbook 與提示詞快照。 
6. 然後才改釘選。

在受監管環境裡，永遠不要沒有計畫就「直接翻別名」。

### F8. 產品與平台團隊之間的介面合約

定義：

- **提示詞／Skill 擁有權**與審查節奏 
- **工具登錄**擁有權與變更管制 
- **評測套件**擁有權與發佈閘控 
- 模型行為異常的**事故嚴重程度**定義 

CCAR-P 會模糊進生命週期（檔 04）；在設計答案裡點名擁有者會得分。

## G 部分 —— 提示詞與上下文深技術

### G1. 分開指示、資料與不可信內容

架構師應在結構上分開：

- **可信指示**（系統／Skills／開發者） 
- **檢索到的文件**（資料；可能惡意——注入風險） 
- **使用者發言**（意圖；可能對抗性） 
- **工具輸出**（半可信，視工具而定）

用清楚的分隔符號、引用來源，並指示模型把檢索內容當成**不可信資料**。搭配檔 02／03 的技術控制（允許清單、輸出編碼、權限分離）。

### G2. 結構化推理但不洩漏思維鏈

有平台**思考**功能時，優先用它做隱藏推理。若必須向使用者展示理由，提供經過整理的**面向使用者的解釋**欄位——不是原始思維鏈——尤其在受監管 UX。

### G3. 確定性槓桿（務實，不是絕對）

LLM 呼叫是隨機的。用以下方式降低變異：

- （僅舊模型）較低 temperature —— 現行 Claude 層級（Opus 4.7＋／Opus 5／Sonnet 5／Fable 5）會拒絕取樣參數，因此改靠下面的槓桿 
- 嚴格 schema 
- few-shot 錨點 
- 工作流程閘門 
- 僅在成本允許時做集成／自我一致性 

不要在客戶 SLA 裡承諾位元組完全相同的輸出；承諾**流程 SLA**與品質指標。

### G4. 多模態設計筆記

當輸入包含圖像／PDF：

- 決定表格比較適合視覺模型呼叫 vs 光學字元辨識（OCR）＋文字管線。 
- 為成本限制圖像解析度／數量。 
- 把 OCR 文字當成不可信的檢索內容。 
- 用真實文件掃描做評測，不只乾淨的數位 PDF。

### G5. 國際化與語氣

企業設計常需要多語支援。公開 Claude 模型具備多語能力；仍要：

- 把語言政策放進輸出合約（「用使用者的語言回應」）。 
- 按語言評測——品質不會憑空均一。 
- 小心混合語言的檢索語料與向量嵌入／搜尋缺口（檔 02）。

## H 部分 —— 額外情境演練

### 情境 H1 —— 內部政策問答

**需求：** 員工問人資政策；答案必須引用政策；錯誤的法律建議風險高。 
**設計：** 對有版本的政策語料做漸進式 RAG＋必須引用來源的輸出＋檢索為空時拒絕＋把「例外／核准」意圖另外路由到 HITL。中階模型；快取系統＋工具定義。 
**不是：** 只靠模型記憶的參數答案；也不是帶寄信工具的完全自主 agent。

### 情境 H2 —— monorepo 的編碼助理

**需求：** 幫開發者導覽大型 repo、提案修補、跑測試。 
**設計：** 帶儲存庫工具、測試執行器、以及嚴格寫入權限到分支的 agent 模式——不是直接部署到生產。強編碼模型。上下文用漸進式檔案擷取，不是整座 monorepo 傾倒。企業 Claude Code 用伺服器管理設定／已核准 MCP 工具（細節見檔 04）。 
**評測：** SWE 風格任務套件＋安全回歸（無祕密外洩）。

### 情境 H3 —— 客服 copilot

**需求：** 建議回覆；由客服人員寄出。草稿 p95 < 2 秒。 
**設計：** 快速模型起草；檢索帳戶＋巨集；對憤怒／VIP 可選升級到中階模型。工作流程，不是開放 agent。快取巨集／政策。HITL 就是人類客服（永遠開著）。 
**指標：** 編輯距離、客戶滿意度（CSAT）、處理時間、事實欄位的幻覺率。

### 情境 H4 —— 隔夜合約條款萃取

**需求：** 每晚 5 萬份 PDF；對成本敏感；早上儀表板。 
**設計：** 批次 API＋map-reduce 工作流程＋schema 驗證＋例外佇列。不是互動式 Opus 級對話 UX。

## I 部分 —— 延伸練習問答（26–35）

**Q26.** 流程 SLA 與承諾相同的 LLM 字串有何差別？ 
**A.** 流程 SLA 涵蓋延遲、可用性與品質率；相同字串對生成模型不切實際。

**Q27.** 為什麼對密集表格在純視覺之前或改用 OCR？ 
**A.** 表格往往經 OCR＋結構管線萃取更可靠；無論哪條路都要用評測驗證。

**Q28.** 模型升級金絲雀計畫應包含什麼？ 
**A.** 影子／重放指標、百分比推行上線、緊急停止開關、提示詞釘選對齊、回滾負責人。

**Q29.** 如何防止「上下文垃圾場」？ 
**A.** 檢索過濾、top-k 上限、相關性門檻、漸進式探索，以及定期語料衛生。

**Q30.** 何時批次 API 是錯誤選擇？ 
**A.** 當終端使用者需要互動、低延遲回應時。

**Q31.** 點名兩種降低萃取變異的技術。 
**A.** JSON schema 驗證＋few-shot 錨點（還有確定性後處理器）。temperature 調整在現行 Claude 層級不是槓桿 —— 那裡會拒絕取樣參數。

**Q32.** 為什麼要把研究 agent 憑證與執行 agent 憑證分開？ 
**A.** 最小權限原則與爆炸半徑控制，以防研究路徑被提示注入。

**Q33.** 架構事故審查至少應記錄什麼？ 
**A.** 模型 ID、提示詞／Skill 版本、工具呼叫（已遮蔽）、檢索 ID、延遲，以及決策結果。

**Q34.** 一項設計用三個 agent，全都共用管理員 SaaS token。主要問題？ 
**A.** 過度授權／缺少安全邊界——多 agent 沒有隔離。

**Q35.** Skills 如何與快取策略互動？ 
**A.** 穩定的 Skill 內容可以活在可快取前綴裡；謹慎做版本，讓快取與行為保持一致。

## J 部分 —— 主要學習深挖：架構決策情境題

把這些當計時演練。寫 6–10 句決策，再核對評分鍵。

### 情境 J1 —— 3 天 SLA 下的理賠分診

**脈絡：** 保險公司希望 Claude 把理賠週期從 11 天壓到 3 天。量級為每天 8 千件理賠。監管要求可稽核的決策軌跡。超過 5 千美元的給付需要人類簽名。語料：保單 PDF＋結構化理賠表單。

**決定：** 每階段模式、模型分層、HITL 位置、成功指標。

**評分鍵（偏好形狀）：**
1. **工作流程**，階段為：收件／OCR → 萃取欄位 → 政策檢索＋引用 → 建議 →（若給付 ≥ 5 千美元或信心低則 HITL）。 
2. **路由器：** 意圖／信心用 Haiku 級；萃取＋建議用 Sonnet 級；只有評測證明值得時，才把困難爭議升級到更高能力。 
3. 指標：週期時間、門檻以下的自動解決率、引用覆蓋、人類推翻率、自動路徑的 p95 延遲、每件理賠美元。 
4. 反模式：對支付系統有寫入工具的單一自主 agent；單體「把整本保單貼進去」的上下文。

### 情境 J2 —— 40 個 repo 組織的內部編碼助理

**脈絡：** 平台團隊希望 Claude 橫跨 IDE／CLI。祕密不得離開金庫。部分 repo 受監管。近似自動完成的說明延遲應有互動感；深度重構可以非同步。

**決定：** 漸進式 vs 單體上下文；Skills vs 巨型 `CLAUDE.md`；模型路由。

**評分鍵：** 經 repo `CLAUDE.md`＋文件檢索＋僅核准工具的 MCP 做漸進式探索。把**互動**中階路徑與帶預算的**深度 agent** 高能力路徑分開。受監管 repo：更嚴的允許清單＋沒有伺服器網頁工具。用組織 Skills 做 ADR／測試範本；避免一個 5 萬 token 的全域提示詞。

### 情境 J3 —— 帶客戶關係管理（CRM）工具的多語客服 copilot

**脈絡：** 12 種語言，CRM 寫入動作（個案筆記、≤ 50 美元退款自動）。品牌語氣關鍵。幻覺退款是災難。

**決定：** 模式、輸出合約、工具 authZ、評測焦點。

**評分鍵：** 增強型 LLM＋工具，退款放在**工作流程閘門**內（schema 驗證＋政策引擎＋金額上限）。不要讓模型單獨「決定」退款資格——上限由程式碼強制執行。評測：語言品質抽樣＋工具呼叫正確性＋超出政策時拒絕。引用來源不是主軸；**動作正確性**才是。

### 情境 J4 —— 隔夜批次合約條款萃取

**脈絡：** 每晚 20 萬份 PDF；結構化 JSON 進倉儲；欄位準確率目標 98%；對成本敏感。

**決定：** 批次 vs 即時 API；map-reduce；模型層級；驗證。

**評分鍵：** 批次 API＋map-reduce（逐文件萃取 → schema 驗證 → 隔離失敗 → 抽樣人工稽核）。除非困難條款需要升級，優先帶強 schema 的中階模型。GA 前先做成本模型。不是互動式 agent。

## Q 部分 —— 模型路由與成本包絡（帶數字演練）

架構師需要粗估數學，不是背價目表（價格會變——請核對文件）。

### 成本包絡工作單

```
Monthly tasks T
× tokens_in_avg × ($/M input) 
+ tokens_out_avg × ($/M output)
+ cache_write share × write_rate + cache_read share × read_rate
+ tool_overhead_tokens
= monthly model $
```

再加上：檢索基礎設施、HITL 人力、可觀測性儲存。對比每次成功任務的價值。

### 路由示例（示意比例）

| 路徑 | 流量 % | 模型級 | 備註 |
| --- | --- | --- | --- |
| 分類／拒絕 | 40% | 快速 | 守門者 |
| 標準答案 | 45% | 中 | 已快取政策前綴 |
| 困難推理／爭議 | 15% | 高 | 思考開啟；非同步 OK |

若困難路徑佔成本 60% 卻只佔量 15%，評測中階＋評論對某一切片是否更便宜。

### 何時批次 API 勝出

高量、對延遲不敏感、結構化工作（萃取、分類、隔夜報告）。不是給對話 UX。搭配 schema 驗證與隔離佇列。

### 釘選與升級

生產釘選模型 ID；升級走影子 → 評測閘門 → 金絲雀 → 全面。把提示詞與模型當成**耦合**發佈產物。
