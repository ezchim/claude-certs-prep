## 概覽

若解決方案設計選定*形狀*，整合讓它在企業裡*成真*，評測證明它*有效*。CCAR-P 把整合權重放最高（19%），因為架構師在生產環境是栽在授權（authZ）、檢索品質、工具邊界、延遲與可觀測性上——不是栽在巧妙的敘述文字上。

本檔涵蓋：

1. 工具、MCP、agent 與企業連接器 
2. RAG／檢索架構與引用來源 
3. 身分驗證／授權（AuthN/Z）、最小權限原則、網路與資料路徑 
4. **雲端或服務路徑（CSP）／交付路徑治理**（直連 API vs Bedrock vs Vertex vs Azure／Foundry） 
5. 評測策略、資料集、A/B 與回歸——包括**模型裁判 vs 程式碼裁判** 
6. 最佳化（token、延遲、成本）與可觀測性 

開發者賦能／Claude Code 組織推行上線在 **`05`**。安全／治理深挖在 **`03`**。入口模型筆記在 **`01`**；本檔擁有企業**路徑選擇**決策對照表。

## A 部分 —— 整合原語

### A1. 整合堆疊

```
應用／編排器
 ├─ Claude Messages API（模型輸入／輸出）
 ├─ 用戶端工具（你的程式碼執行）
 ├─ 伺服器工具（Anthropic 託管，於啟用之處）
 ├─ MCP 伺服器（標準化的工具／資料連接器）
 ├─ 檢索系統（搜尋／索引／重排序）
 └─ 企業 IdP、機密資訊、網路、稽核
```

**合約提醒（公開工具使用模型）：** Claude 永遠不會自己執行你的工具。它發出 `tool_use`；**你的執行環境**（或 Anthropic，對伺服器工具）執行；你回傳 `tool_result`。架構師設計那個迴圈：逾時、重試、冪等與權限。

### A2. 用戶端工具 vs 伺服器工具

| 類型 | 誰跑程式碼？ | 示例（示意） | 架構師意涵 |
| --- | --- | --- | --- |
| 用戶端／使用者定義 | 你的應用 | 客戶關係管理（CRM）查詢、工單、內部 SQL | 你擁有 authZ、日誌、沙箱 |
| Anthropic 伺服器工具 | Anthropic | 網頁搜尋／擷取、程式碼執行、工具搜尋（依文件） | 刻意啟用；理解資料離開邊界 |
| Anthropic schema 的用戶端工具 | 你的應用，訓練友善的 schema | 等價時優先已知 schema | 往往比臨時雙胞胎更可靠 |

### A3. 模型上下文協定（MCP）

MCP 是把助理／agent 連到工具與資料的**開放標準**。公開文件強調：

- 本機行程、HTTP／伺服器推送事件（SSE）／可串流 HTTP，以及行程內傳輸層（生態會演進——請核實現行 MCP＋Claude Code 文件）。 
- 伺服器暴露工具／資源／提示。 
- **信任模型：** 把第三方伺服器當成供應鏈風險；經擷取內容的提示注入是真實的。 
- 大型工具集 → **工具搜尋**／延遲載入，讓定義不會吃掉上下文視窗。 
- 通道／事件（若支援）把外部訊號推進工作階段。

**何時選 MCP**

| 何時優先 MCP… | 何時優先直連 API／SDK 工具… |
| --- | --- |
| 許多系統、標準化探索 | 一兩項客製工具 |
| 要可在 Claude Code＋應用間重用的連接器 | 極度客製的延遲路徑 |
| 組織要連接器目錄 | 協定開銷不值得 |
| 夥伴已經出貨 MCP 伺服器 | 你必須留在鎖定的 RPC 結構裡 |

### A4. Agent 對 agent 與編排匯流排

多 agent 系統需要明確的**交接協定**：訊息 schema、共享記憶政策，以及權限邊界。優先：

- 清楚的監督者或擁有副作用的工作流程 
- 每個 agent 各自的憑證 
- 跨 hop 的追蹤 ID 

避免沒有預算、聊天式的自由形式 agent 蜂群。

### A5. CLI 與自動化介面

命令列工具（包括工程工作流程裡的 Claude Code CLI——見檔 05）適合持續整合（CI）、營運與開發者迴圈。面向客戶的產品優先用具 authZ 的服務 API。考試情境：選 CLI 給**建造者生產力**，選 API 給**產品執行環境**——除非產品*本身*就是開發者工具。

## B 部分 —— RAG 與檢索架構

### B1. RAG 參考管線

```
擷取 → 清洗／OCR → 切塊 → 向量嵌入／索引（＋關鍵字）→（選配知識圖）
查詢 → 改寫／分類 → 檢索 → 重排序 → 打包上下文 → Claude → 引用 → 驗證
```

### B2. 切塊決策

| 語料特徵 | 切塊偏向 | 備註 |
| --- | --- | --- |
| 帶編號章節的政策 | 感知章節的切塊＋標題 | 為引用來源保留條款識別碼 |
| 程式碼 | 感知符號／函式 | 不要盲目在函式中間切開 |
| 表格／財務 | 以表為單位或列群組 | 往往需要光學字元辨識（OCR）結構 |
| 對話日誌 | 帶時間戳的輪次視窗 | 個人識別資訊（PII）清洗關鍵 |
| 投影片 | 每張投影片＋標題 | 文字密度低 |

重疊有助連續性；重疊太多浪費 token 並複製噪音。

### B3. 混合檢索

生產 RAG 通常結合：

- **稠密／向量**，用於語意改寫 
- **BM25／關鍵字**，用於 ID、錯誤碼、SKU、法律條號 
- **中繼資料過濾**（租戶、產品、地區設定、生效日期） 
- **重排序器**，在低 k 時提高精確率 

知識圖有助多跳「誰擁有 X」問題，但增加營運成本——用評測增益來辯護。

### B4. 上下文打包與引用來源

公開 Messages API 模式支援**搜尋結果**內容區塊與引用來源，讓答案能歸因來源。架構師規則：

- 切塊回傳來源 id／title／uri 
- 事實錨定重要時，在輸出合約要求引用來源 
- 若檢索沒有相關結果，**拒絕或追問**——不要即興發明政策 
- 依 token 預算限制 top-k；優先較少但高品質的切塊 

### B5. 索引新鮮度與租戶歸屬

- 為文件做版本；政策優先用生效日期 
- 租戶隔離的索引或硬過濾（永遠不要「提示模型只用租戶 A」） 
- 刪除用墓碑；GDPR 抹除工作流程也要碰到索引 
- 衡量**過時服務水準目標（SLO）**（例如政策發佈後 15 分鐘內上線）

### B6. RAG 失效模式（考試黃金）

1. 切塊邊界錯誤 → 漏掉條款 
2. 模型變更後向量嵌入漂移，卻沒有重建索引計畫 
3. 經共享索引的跨租戶滲漏 
4. 檢索到的 HTML 裡的提示注入（「忽略政策…」） 
5. 引用表演（數字對不上來源） 
6. 過度檢索淹死模型 
7. 檢索不足 → 幻覺 

### B7. 把漸進式探索用到 RAG

不要傾倒語料。用：

1. 中繼資料路由（product=X） 
2. 檢索小 k 
3. 若信心低／使用者問得更深，再檢索更多或瀏覽階層式目錄工具 
4. agent 可呼叫 `search` 再 `fetch_section` 工具，而不是一次巨型上下文

## C 部分 —— 工具、agent 與生產控制

### C1. 工具設計檢查清單

- [ ] 名稱／描述清楚到足以路由 
- [ ] JSON schema 嚴格；列舉優於自由文字 
- [ ] 副作用工具用鍵做到冪等 
- [ ] 逾時與斷路器 
- [ ] authZ 在**工具伺服器**檢查，不只在提示詞 
- [ ] 參數日誌並做遮蔽 
- [ ] 每租戶速率限制 
- [ ] 破壞性操作有模擬執行／確認模式 

### C2. 最小權限原則模式

| 模式 | 描述 |
| --- | --- |
| 階段範圍工具 | 萃取階段不能 `refund_payment` |
| 角色範圍 agent | 客服 vs 財務憑證不同 |
| 讀／寫分離 | 研究 agent 唯讀；執行者有閘控 |
| 確認權杖 | 寫入要第二個人或第二因素 |
| 允許清單主機 | 對伺服器端請求偽造（SSRF）安全的擷取工具 |

### C3. Agent 迴圈控制

生產 agent 需要：

- **最大輪次／最大美元／最大牆上時間** 
- 停止條件（`task_complete`、`needs_human`） 
- 黏性追蹤 ID 
- 記憶政策（跨工作階段什麼會持久） 
- 程式碼執行的沙箱 

### C4. 延遲預算工作單

互動 UX p95 = 3.0 秒的示例：

| 階段 | 預算 |
| --- | --- |
| 驗證＋入口 | 50ms |
| 檢索 | 200ms |
| 重排序 | 50ms |
| Claude 首個 token 延遲（TTFT） | 800ms |
| Claude 完成 | 1500ms |
| 驗證＋渲染 | 100ms |
| 應變 | 300ms |

錯過預算？縮小上下文、快取前綴、較小模型、平行檢索，或非同步 UX（「答案串流＋工具在背景」）。

### C5. 可靠性模式

- 對 429／5xx 帶抖動重試 
- 逾時時後備模型 
- 常見問答意圖用快取的上次正確答案 
- 長工具用佇列＋工作者 
- 毒化工具偵測（反覆失敗 → 停用工具、警示）

- 含 PII 的提示詞做**日誌遮蔽**

## D5 部分 —— CSP／交付路徑治理（P0）

架構師**不會**因為投影片看起來現代就選「X 上的 Claude」。他們刪去違反**身分、落地、日誌／保留、採購與模型 ID**限制的路徑——再在倖存者裡依營運適配與功能落差來選。

公開介面（請核實現行文件；產品會演進）：

| 路徑 | 它是什麼（公開框架） |
| --- | --- |
| **直連 Anthropic API** | 第一方 Messages API（`platform.claude.com`）；Anthropic 營運的推論 |
| **Amazon Bedrock** | 經 AWS Bedrock 的 Claude；AWS 管理的邊界／區域控制（依文件為 Messages 及／或舊式 Invoke／Converse 路徑） |
| **Google Vertex AI** | 經 Google Cloud Vertex 的 Claude；GCP IAM＋區域端點 |
| **Azure／Microsoft Foundry** | Microsoft Foundry 裡的 Claude；Azure 託管及／或 Anthropic 託管選項，部署類型不同 |
| **AWS 上的 Claude Platform** *（相關）* | Anthropic 營運、AWS Marketplace 風格路徑的 Claude——**不等同**於 Bedrock；落地／推論釘選不同——考試題幹不要混為一談 |

### D5.1 公開層可講的決策對照表

把儲存格當成**要在現行合約／文件核實的主題**，不是永恆保證。ZDR 與商業夥伴協議（BAA）是**企業選項**——設計前先確認權利，不要當成一定存在。

| 維度 | 直連 Anthropic API | Amazon Bedrock | Google Vertex AI | Azure／Microsoft Foundry |
| --- | --- | --- | --- | --- |
| **身分／驗證** | API 金鑰／組織與工作區控制；應用仍擁有使用者→工具身分 | **AWS IAM**（角色、SCP、PrivateLink 模式）；對 CloudTrail 友善 | **GCP IAM**＋Vertex 權限；組織政策 | **Entra ID／Azure 角色型存取控制（RBAC）**＋Foundry 專案控制 |
| **資料落地／推論釘選** | 支援模型上的 `inference_geo`（例如 global vs `us`）——查文件 | **區域端點**／地理推論設定檔；區域選擇就是釘選 | **區域／端點**選擇決定推論在哪跑 | **Global Standard** vs **US Data Zone Standard**（文件記載處，美國釘選類似 `inference_geo: us`）；託管選項（Azure vs Anthropic）有差 |
| **日誌／保留姿態** | Anthropic 保留與濫用監控條款；**ZDR** 可能作為企業選項提供——**核實** | 主要由 **AWS／Bedrock** 資料保護文件＋你的帳戶日誌治理；不要假設 Anthropic ZDR 措辭 1:1 對應 | 由 **Google Cloud／Vertex** 資料處理＋你的日誌匯流治理 | Anthropic 處理者條款＋Azure 側保留；安全標記內容路徑可能因託管而異——**讀現行 Foundry Claude 文件** |
| **採購／BAA／FedRAMP 主題** | 與 Anthropic 直簽主服務協議（MSA）／資料處理協議（DPA）；BAA／FedRAMP 僅在**你的**交易與產品支援時 | 經 **AWS Marketplace／Bedrock** 購買；靠既有 AWS 承諾用量、AWS 合規產物、組織 SCP——仍要把受保護健康資訊（PHI）／FedRAMP 對到**該特定** Bedrock Claude 產品 | 經 **GCP** 購買；重用 GCP 承諾用量與組織政策；同一條「產物 ≠ 自動 BAA」規則 | 經 **Azure Marketplace／Foundry** 購買；重用 Microsoft EA；對你實際佈建的**部署類型**確認 HIPAA／FedRAMP |
| **模型 ID 差異** | Anthropic 模型 ID（例如 Messages API 裡帶日期的 `claude-…` 字串） | Bedrock **模型 ID／推論設定檔 ID／Amazon 資源名稱（ARN）**（以及啟用時的 Messages 路徑 ID）——**不是**第一方 ID 的複製貼上 | Vertex 發行者模型 ID／版本——**平台特有** | Foundry **部署名稱**＋模型版本（託管選項編碼在內）——應用設定不得寫死另一個 CSP 的 ID |
| **功能／API 落差主題** | 往往**最早**取得新 Messages 功能、beta、伺服器工具 | 可能落後或以 Bedrock 形狀的 API 暴露；承諾功能前查對等 | GCP 上類似的對等／落差故事 | 對等取決於 Azure 託管 vs Anthropic 託管部署——功能矩陣不同 |
| **架構師何時選這條** | 最大功能速度；簡單 SaaS；落地可經 `inference_geo`＋合約解決；團隊已在 Anthropic 計費 | 以 AWS 為中心的資產；IAM／PrivateLink 強制；經 AWS 區域落地；採購必須留在 AWS 內 | 以 GCP 為中心的資產；Vertex 是已核准的 AI 平面；組織政策擋住其他對外流量 | 以 Azure 為中心的資產；Entra＋Foundry 是已核准的 AI 平面；需要 US Data Zone 或 Azure 託管邊界 |

**每條路徑永遠成立：** 你的**應用**仍擁有租戶 authZ、工具最小權限原則、提示詞／日誌遮蔽，以及評測閘門。換 CSP 修不好「authZ 寫在提示詞裡」。

### D5.2 限制排除法（考試方法）

```
1. 列出題幹的硬性約束（IdP、落地地理、日誌／ZDR、BAA／FedRAMP、雲端承諾用量、PrivateLink、功能 X 下個衝刺必須出貨）。
2. 刪去無法滿足任一硬性約束的路徑（核實假設——不要憑空捏造 FedRAMP）。
3. 在倖存者中評分：營運熟悉度、模型識別碼／營運工具適配、功能對等風險、成本可預測性。
4. 把被否決的路徑記成一行 ADR（「否決直連 API：本組織沒有路徑能達到要求的 VPC 端點模式」）。
```

**感覺（不及格）：** 「大家都用 Bedrock。」／「直連 API 永遠最快創造價值所以選它。」／「選 Foundry 因為我們喜歡 Copilot。」 
**限制排除（及格）：** 「題幹要求歐盟處理且落在既有 GCP 組織政策內 → Vertex 區域端點；直連 API 的全球預設出局。」

### D5.3 模型 ID 與設定可攜性陷阱

- 抽象一個**供應商轉接層**：設定裡的 `model_ref` → 依環境解析 ID。 
- 永遠不要把一個寫死的 Bedrock ARN 共用到「開發走直連 API」。 
- 生產釘選**有版本**的 ID；經功能旗標＋評測閘門控制升級。 
- 落地參數依路徑而異（`inference_geo` vs 區域 URL vs Data Zone 部署）——在測試環境用刻意錯誤設定測試釘選。

### D5.4 日誌／ZDR 考試紀律

- **ZDR**＝限制供應商保留提示詞／完成的合約／API 姿態（在有提供之處）。它**不是**你應用的保留、安全資訊與事件管理系統（SIEM）或向量嵌入／評測快取抹除的替代（見檔 03）。 
- 濫用監控／安全標記的對外流量在供應商條款下仍可能存在——設計時假設「ZDR ≠ 對所有安全系統隱形」，直到法務／文件另有說明。 
- 雲端路徑：你的 CloudTrail／Cloud Logging／診斷日誌可能保留你設定的**中繼資料，有時還有酬載**——架構要管匯流，不只模型廠商故事。

### D5.5 考試陷阱 —— 交付路徑

1. 憑品牌偏好選 CSP，卻忽略題幹裡的落地。 
2. 把 **AWS 上的 Claude Platform** 等同於 **Bedrock**（營運者／邊界不同）。 
3. 未經核實就假設每條路徑都有 BAA／FedRAMP／ZDR。 
4. 把 Anthropic 模型 ID 複製貼上到 Bedrock／Vertex／Foundry 呼叫。 
5. 因為「模型很聰明」就把雲端 IAM 當成可選。 
6. 承諾所有 CSP 第一天功能對等。 
7. 題幹要求釘選地理時，仍用直連 API 全球推論。 
8. 相信單靠選 CSP 就滿足 GDPR／HIPAA——資料地圖與應用控制仍然需要。

### D5.6 迷你 ADR 範本（複製／改編）

```
決策：經 <路徑> 交付 Claude
限制：<落地、IdP、採購、功能>
已否決：<路徑＋一行原因>
驗證：<IAM／API 金鑰模式>
落地釘選：<參數／區域／部署類型>
日誌：<供應商姿態＋我方日誌匯流＋ZDR 狀態：已核實／未取得權利>
模型識別碼：<轉接層對應>
回滾：<替代路徑或先前的模型釘選>
```

### D5.7 問答 —— CSP／交付路徑（73–80）

**Q73.** 題幹：「推論必須留在美國；已標準化 Azure AD＋Foundry。」最佳預設方向？ 
**A.** 依現行文件用 **US Data Zone**（或等價美國釘選）部署類型的 Azure／Foundry——不是預設直連 API 全球。

**Q74.** 選兩項：在僅 AWS、受監管的資產裡優先 Bedrock 而不是直連 API 的理由。 
**A.** 重用 **IAM／SCP／PrivateLink** 模式，並把採購／合規證據留在組織已營運的 **AWS** 邊界內。

**Q75.** 為什麼「我們會用 Anthropic 文件裡的 Bedrock 模型 ID `claude-sonnet-…`」是陷阱？ 
**A.** Bedrock 用**平台特有**的模型／推論設定檔識別碼；第一方 ID 不可攜。

**Q76.** 供應商已啟用 ZDR——你可以略過從應用日誌遮蔽 PII 嗎？ 
**A.** **不行。** ZDR 處理的是供應商保留姿態；你的日誌、倉儲與評測儲存仍需要最小化／保留設計。

**Q77.** 產品下週需要全新 Messages API beta；資產是多雲且沒有硬落地釘選。哪條路徑往往勝出，為什麼？ 
**A.** **直連 Anthropic API**——通常最早取得功能；確認 beta 權利，仍要文件化落地／日誌。

**Q78.** 類似 FedRAMP 的題幹列出「僅限已授權雲端 AI 服務」。你先做什麼？ 
**A.** 用客戶的已授權服務清單／邊界文件做**限制排除**——然後在倖存者內設計（日誌、變更管制），不是「加一個更安全的提示詞」。

**Q79.** 當 GCP 組織政策擋住對外到非 Google AI 端點時，Vertex vs 直連 API？ 
**A.** **Vertex**——在該組織政策下直連 API 可能不可達／不合規，與模型品質無關。

**Q80.** 憑感覺選 vs 限制排除——各給一個考試辨識點。 
**A.** 感覺：答案只引用人氣／速度。限制排除：答案引用一條**使其他路徑失格**的題幹限制，然後才最佳化。

## E 部分 —— 評測、測試與最佳化

### E1. 要衡量什麼

| 類別 | 指標示例 |
| --- | --- |
| 任務成功 | 精確比對、F1、pass@k、評分量規分數 |
| 錨定（事實依據） | 引用精確率／召回率、缺乏依據主張率 |
| 安全 | 政策違規率、注入成功率 |
| 延遲 | TTFT、總計、每路徑 p95／p99 |
| 成本 | 每次成功任務美元、每次任務 token |
| UX | 讚踩、編輯距離（copilot）、升級率 |
| 營運 | 錯誤率、工具失敗 %、快取命中率 |

**架構師規則：** 指標必須對上**商務工作**。客服 copilot ≠ 程式碼 agent ≠ RAG 法律問答。

### E2. 資料集設計

1. **黃金標準集** —— 有標註、有版本、具代表性 
2. **對抗性集** —— 注入、越獄、刁鑽實體 
3. **回歸集** —— 過去的生產失敗 
4. **切片集** —— 語言、租戶、文件類型 

把訓練／提示調校範例**排除**在保留評測集之外。

### E3. 自動化 vs 人工評測

| 方法 | 優勢 | 弱點 |
| --- | --- | --- |
| 精確／schema 檢查 | 便宜，對萃取精準 | 錯過細微之處 |
| 評分量規 LLM-as-judge | 可擴展 | 裁判偏見；要校準 |
| 人工審查 | 細微之處的黃金標準 | 成本／延遲 |
| 成對 A/B | 適合偏好 | 需要流量／樣本量 |
| 安全探測 | 抓住注入 | 必須更新攻擊 |

混合是常態：自動化閘控每一次 pull request（PR）；人類每週抽樣＋審查高嚴重程度切片。

**P0 擴充：** 見 **M7 部分 —— 模型裁判 vs 程式碼裁判＋校準**，了解何時確定性評分者勝過 LLM-as-judge、如何對人工黃金標籤校準，以及如何在偷看實驗結果**之前**凍結門檻。

### E4. 實驗紀律

- 診斷時一次只改**一個**主要變數 
- 記錄模型 ID、提示詞雜湊、索引版本、工具版本 
- 對 A/B 用統計常識（不要用 20 則對話加冕贏家） 
- 切換上線前先影子模式

### E5. 診斷常見失敗

| 症狀 | 可能原因 | 槓桿 |
| --- | --- | --- |
| 幻覺事實 | 弱檢索／沒有拒絕路徑 | 提高召回、要求引用來源、空結果時拒絕 |
| 格式崩潰 | 鬆散提示詞 | schema＋驗證器＋few-shot |
| 高延遲 | 肥上下文／大模型 | 快取、路由、縮小 k、較快模型 |
| 成本暴衝 | 迴圈／肥工具定義 | 最大輪次、工具搜尋、快取 |
| 品質不一致 | 政策／合約規格不足 | 澄清合約、schema＋few-shot 錨點（現行層級拒絕取樣旋鈕） |
| 工具選錯 | 描述差／工具太多 | 重寫描述、允許清單、路由器 |
| 離線好、生產差 | 分布偏移 | 把生產切片加進評測 |

### E6. 最佳化 playbook（操作手冊）（順序重要）

1. **正確性優先**（評測閘門） 
2. **拿掉浪費的上下文** 
3. **快取穩定前綴** 
4. **把簡單流量路由到較便宜／較快模型** 
5. **平行化獨立工作** 
6. **然後才**微調提示詞措辭與 few-shot 錨點 

過早把模型降級而打破安全／品質，會在列出合規限制的考試情境失敗。

### E7. 可觀測性架構

最低可行遙測：

- 請求／追蹤 ID 
- 路徑／意圖 
- 模型＋提示詞／Skill 版本 
- 檢索查詢＋回傳的文件 ID 
- 工具名稱、延遲、狀態 
- token 用量分解（輸入／快取／輸出／思考） 
- 結果標籤（自動、人類編輯、失敗） 
- 安全旗標 

小心儲存原始提示詞（PII、保留）。長期儲存優先指標＋已遮蔽片段。

儀表板：品質每週、延遲／成本每小時、安全即時警示。

### E8. 持續整合／持續交付（CI/CD）裡的持續評測

```
PR → 工具單元測試 → 離線評測套件閘口 → 預備環境影子 → 金絲雀 → 生產環境
```

在關鍵切片上有統計意義的回歸就讓建置失敗（例如引用精確率、PII 外洩探測）。

## 考試陷阱

1. 把整個知識庫傾倒進上下文，而不是 RAG。 
2. authZ「只寫在提示詞裡」。 
3. 工具無界、沒有最大輪次預算的 agent。

14. 未經核實權利就假設路徑上有 ZDR 或 BAA。
15. 偷看 A/B 結果之後才凍結評測通過門檻。

## 練習問答（28）

**Q1.** 誰執行用戶端工具呼叫？ 
**A.** 你的應用執行環境——不是模型行程本身。

**Q2.** 為什麼 MCP 工具搜尋可能重要？ 
**A.** 大型工具目錄消耗上下文；搜尋只載入需要的工具。

**Q3.** 點名混合搜尋用的兩種檢索方法。 
**A.** 稠密／向量與 BM25／關鍵字（再加上中繼資料過濾／重排序）。

**Q4.** 若 RAG 對政策問題沒有回傳相關切塊，應該怎樣？ 
**A.** 拒絕、提出澄清問題，或升級——不要發明政策。

**Q5.** `create_refund` 工具的授權必須在哪強制執行？ 
**A.** 在工具伺服器／後端政策層（最小權限原則），不只在敘述文字指示裡。

**Q6.** 給三個 agent 迴圈控制。 
**A.** 最大輪次、最大成本、最大牆上時間（還有停止條件、允許清單）。

**Q7.** 引用精確率大致在衡量什麼？ 
**A.** 被引用的來源是否真的支撐所做主張。

**Q8.** 為什麼要保留對抗性評測集？ 
**A.** 在攻擊者／客戶之前抓住注入、越獄與刁鑽實體。

**Q9.** 離線評測好、生產差——第一個懷疑？ 
**A.** 分布偏移；把生產切片加進評測套件。

**Q10.** 提示詞快取如何幫助整合架構？ 
**A.** 降低穩定系統提示詞、工具定義與政策前綴的成本／延遲。

**Q11.** 毒化工具模式的回應是什麼？ 
**A.** 偵測反覆失敗，停用／斷路該工具，警示操作者。

**Q12.** 為什麼要在索引裡隔離租戶？ 
**A.** 防止跨租戶檢索滲漏；單靠提示詞指示不夠。

**Q13.** 何時伺服器工具是設計關注？ 
**A.** 當資料對外流量／到 Anthropic 託管執行的信任邊界對合規有關時。

**Q14.** 高階正確排序最佳化。 
**A.** 正確性／安全 → 縮小浪費 → 快取 → 路由到較便宜 → 平行化。

**Q15.** 除錯錯誤工具選擇時，哪些遙測欄位必要？ 
**A.** 追蹤 ID、工具描述版本、模型 ID、對話片段、`tool_use` 參數／結果（已遮蔽）。

**Q16.** Map-reduce RAG 的 reduce 階段把 token 炸了——你做什麼？ 
**A.** 限制 mapper 輸出、階層式 reduce，或用 schema 摘要中間筆記。

**Q17.** 為什麼索引要與提示詞一起做版本？ 
**A.** 讓評測與事故能重現行為；檢索變更會改變答案。

**Q18.** 擷取工具的 SSRF 風險是什麼？ 
**A.** 模型／工具誘發對內部 IP／中繼資料端點的請求——用允許清單緩解。

**Q19.** 何時 CLI 整合適當？ 
**A.** 開發者／營運自動化；通常不是終端客戶產品路徑，除非產品就是 CLI。

**Q20.** 定義提示詞變更的成功 A/B。 
**A.** 預先登錄的指標、足夠樣本、沒有其他同時變更、回滾計畫。

**Q21.** 如何阻止引用表演？ 
**A.** 驗證器檢查引用 ID 存在於提供的切塊；評分量規懲罰缺乏依據的主張。

**Q22.** 工具豐富的 agent 裡什麼是漸進式探索？ 
**A.** 從少數工具／上下文開始；需要時經搜尋／瀏覽再擷取更多。

**Q23.** 為什麼要把建造者 MCP 憑證與執行環境產品憑證分開？ 
**A.** 爆炸半徑——IDE agent 不應握有生產寫入權力。

**Q24.** 除了引用精確率，再點名一個錨定指標。 
**A.** 缺乏依據主張率／忠實度分數／檢索召回率@k。

**Q25.** schema 驗證器在工具參數裡防止什麼？ 
**A.** 副作用前的畸形呼叫、意外列舉、缺少必填欄位。

**Q26.** 延遲 p95 只在工具密集意圖失敗——往哪裡看？ 
**A.** 工具扇出、序列工具鏈、冷 MCP 連線、工具前過度檢索。

**Q27.** 夜間評測工作應包含什麼？ 
**A.** 黃金＋對抗性套件、回歸案例、成本／延遲快照、對差異警示。

**Q28.** 你可以靠模型「只呼叫安全工具」嗎？ 
**A.** 不行——強制允許清單與伺服器端 authZ；提示詞不是控制措施。

| TTFT | 首個 token 延遲 |
| 影子模式 | 候選系統平行打分、不影響使用者 |
| 斷路器 | 暫時停止呼叫失敗的依賴 |
| 租戶隔離 | 在檢索／行動路徑硬性分開客戶資料 |
| 工具搜尋 | 延遲探索工具以節省上下文 |
| 冪等鍵 | 確保副作用工具可安全重試 |
| 黃金標準集 | 有標註的評測資料集 |
| LLM-as-judge | 用模型依評分量規為輸出打分 |
| SSRF | 經類似擷取的工具的伺服器端請求偽造 |
| CSP（交付） | 提供 Claude 的雲端／服務路徑（直連 API、Bedrock、Vertex、Foundry、…） |
| ZDR | 零資料保留——要在合約核實的供應商保留姿態 |
| 推論釘選 | 限制推論可在哪跑的控制（地理參數、區域、資料區） |

## G 部分 —— 深挖：企業驗證、網路與資料平面

### G1. 身分傳遞

當模型路徑「變成使用者」並握有全能權杖時，企業整合會失敗。優先：

1. 使用者向你的應用驗證（OIDC／SAML）。 
2. 應用取得受限於該使用者範圍的**下游 token**（OAuth 代表（on-behalf-of）、token 交換）。 
3. 工具用那些 token 呼叫 API。 
4. 稽核日誌把動作歸到人類＋服務主體。

服務帳戶給帶分開控制的批次工作——不是互動 agent 的捷徑。

### G2. 網路模式

| 模式 | 用途 |
| --- | --- |
| 公開 Claude API 對外流量 | 最簡單；經代理／資料外洩防護（DLP）控制 |
| 你租戶裡的雲端 AI（Bedrock／Vertex／Foundry） | 資料平面更靠近既有雲端控制 |
| PrivateLink／VPC 端點 | 減少公開網際網路暴露 |
| 帶允許清單的反向代理 | 集中檢查／記錄／阻擋 |

文件化**提示詞與向量嵌入住在哪**（向量資料庫區域、日誌儲存區域）。落地問題會出現在架構師情境題。

### G3. 同步產品 vs 非同步工作者

互動使用者在等 → 緊的工具逾時、串流文字、把慢工具延後成「還在處理」工作。後台自動化 → 佇列工作者、批次 API、較長工具預算。不要把兩者硬塞進同一延遲等級。

### G4. 工具的合約測試

對每一項工具：

- schema 單元測試 
- authZ 負向測試（沒有該角色的使用者必須失敗） 
- 冪等測試 
- 逾時行為測試 
- 為評測重放錄下範例追蹤 

把工具當微服務——LLM 只是另一個用戶端。

### G5. 檢索評測細節

衡量要超越「答案品質」：

- 相關文件的 **Recall@k** 
- 排序品質的 **nDCG** 
- **切塊利用率**（Claude 有用你檢索到的嗎？） 
- **新鮮度落後** 
- **過濾正確性**（租戶／產品）

許多「模型問題」其實是檢索問題。先修索引，再換巨型模型。

### G6. 線上評測與回饋

捕捉隱性訊號：編輯、重新產生、讚踩、升級。把低信心或高嚴重程度流量路由到人工標註。每週把迴圈關進回歸集。沒有這個，離線黃金標準集會腐壞。

### G7. 成本異常偵測

在以下情況警示：

- 每次任務 token 週週跳升 >N% 
- agent 輪次計數分布偏移 
- 快取命中率崩潰（前綴抖動） 
- 單一租戶主導花費（失控迴圈）

把警示綁到 runbook（維運手冊）：凍結 agent 最大輪次、還原提示詞、停用工具。

### G8. 多區域主動-主動關注

一致釘選模型版本；用衝突規則複製索引；對話狀態用黏性工作階段；從公開文件理解雲端端點全球 vs 區域路由取捨。驗證失敗時關閉，可選充實工具失敗時柔性降級。

### G9. 額外情境

**情境：** 製造公司希望 Claude 查詢監控與資料擷取系統（SCADA）歷史。 
**答案形狀：** 永遠不要從 SaaS agent 直連原始廠區網路。用隔離區（DMZ）讀取 API、允許清單指標、致動要人類核准——起初優先沒有寫入工具。手冊 RAG＋遙測摘要的讀取工具。

**情境：** 法務想「跟所有合約聊天」。 
**答案形狀：** 租戶隔離的混合 RAG、感知條款的切塊、強制引用來源、依案件的存取控制清單（ACL）過濾、日誌上的 DLP、義務幻覺評測、紅線修改要 HITL。

**情境：** MCP 推行上線後成本爆炸。 
**答案形狀：** 檢查工具定義的 token 佔比、啟用工具搜尋、縮小允許清單、快取系統＋工具前綴、加最大輪次、修反覆呼叫搜尋的迴圈。

### G10. 延伸問答（29–36）

**Q29.** 為什麼代表 token 交換比共用全能權杖好？ 
**A.** 保留使用者範圍的 authZ 與可歸屬的稽核軌跡。

**Q30.** 點名一個可以很高、但使用者答案仍失敗的檢索指標。 
**A.** Recall@k 看起來可以，但切塊打包／引用／提示工程仍會讓答案失敗——也要衡量端任務指標。

**Q31.** 切塊利用率在告訴你什麼？ 
**A.** 檢索到的證據是否真的影響答案，還是只在浪費 token。

**Q32.** 如何測試工具的 authZ？ 
**A.** 負向測試：缺少角色的身分必須被工具伺服器拒絕。

**Q33.** 「小小改一下提示詞」之後快取命中率為什麼可能崩潰？ 
**A.** 前綴位元組變了（或工具順序／思考設定），使中斷點失效。

**Q34.** 可選充實的柔性失敗是什麼？ 
**A.** 可選工具／RAG 逾時時仍回傳核心答案，並帶明確的部分狀態——不是硬 500。

**Q35.** 受監管人資資料的向量嵌入應住在哪？ 
**A.** 在已核准區域／系統，與來源人資資料受同一套落地控制。

**Q36.** 任何寫入工具的第一個整合問題是什麼？ 
**A.** 誰被允許、如何稽核，以及若被提示注入，爆炸半徑是什麼？

## H 部分 —— 生產強化敘事（考試風格）

### H1. 冪等與恰好一次的*效果*

LLM 會重試；使用者會連點；佇列會再投遞。副作用工具必須**至少一次安全**：

- 用戶端提供冪等鍵（ticket_id＋動作＋雜湊）。 
- 工具伺服器把鍵 → 結果存 TTL。 
- 重放回傳原始結果，不二次扣款／雙重出貨。

考試錯誤答案：「Claude 會記得它已經退過款了。」

### H2. 對話狀態儲存

明確選擇：

| 儲存 | 優點 | 缺點 |
| --- | --- | --- |
| 用戶端擁有的歷史重放 | 簡單、透明 | 提示詞大；PII 蔓延 |
| 伺服器工作階段儲存 | 截斷／壓縮控制 | 一致性與保留義務 |
| 摘要＋近期視窗 | token 效率 | 摘要漂移 |

長時間工作階段搭配平台壓縮功能（見檔 01）。永遠定義對齊法律保全的保留。

### H3. AI 路徑的功能旗標

能救事故的旗標維度：

- 模型釘選 
- 提示詞／Skill 版本 
- 檢索索引版本 
- 工具允許清單集合 
- agent 最大輪次上限 
- 是否需要 HITL 

回滾是翻旗標——不是希望。

### H4. AI 功能的 SLO

寫使用者感受得到的 SLO：

- `/assist` 的可用性 
- p95 草稿延遲 
- 有依據答案率 
- 安全探測的無害回應率 
- 每 1000 次成功任務成本 

可用性／延遲／安全呼叫 on-call；品質在營業時間審查，除非嚴重程度高。

### H5. 夥伴／廠商 MCP 供應鏈

啟用廠商 MCP 伺服器前：

1. 威脅模型（它能讀／寫什麼資料） 
2. 驗證方法（OAuth 範圍最小化） 
3. 變更紀錄與版本釘選政策 
4. 在合成資料上沙箱試用 
5. 資料離開邊界時的法務審查 
6. 設定裡的緊急停止開關 

「它在目錄裡」不是控制措施。

### H6. 串流 UX＋工具

為感知效能串流文字；**動作**仍要等工具結果驗證後才放行。永遠不要根據尚未完成、尚未驗證的工具呼叫序列，就執行以部分串流計畫為基礎的寫入。

### H7. 多輪 agent 的評測

單輪黃金標準集會低估 agent。加上：

- 腳本化多輪目標 
- 干擾工具 
- 對話中途政策變更 
- 預算耗盡行為 
- 工具錯誤後的復原 

打分打**任務完成**，不是口才。

### H8. 資料標註工作流程

誰標註？用什麼評分量規？校準場次？困難切片雙人標註？有追蹤標註者間一致性嗎？忽略標註品質的架構師會出貨虛假信心。

### H9. 跨職能 RACI（責任指派矩陣）片段

| 活動 | 架構師 | 工程 | 資料 | 資安 | 營運 |
| --- | --- | --- | --- | --- | --- |
| 工具 authZ 模型 | A/C | R | C | A | I |
| 評測閘門門檻 | A | R | R | C | I |
| 索引租戶歸屬 | C | R | A | A | I |
| on-call runbook | C | C | I | C | R/A |

（RACI：R＝負責，A＝課責，C＝諮詢，I＝知會）

### H10. 更多陷阱

13. 假設串流的部分輸出可以安全據以行動。 
14. 支付／工單工具沒有冪等。 
15. 產品是 agentic 時只評測單輪。 
16. 未經範圍審查就啟用廠商 MCP。 
17. 品質呼叫把 on-call 燒盡在不可行動的瑣碎上。

### H11. 問答 37–45

**Q37.** 為什麼 Claude 不能自己「記得」跨重試的退款？ 
**A.** 無狀態工具副作用需要伺服器端冪等鍵。

**Q38.** AI 回滾有哪些旗標維度重要？ 
**A.** 模型、提示詞／Skill、索引、工具允許清單、預算、HITL 要求。

**Q39.** 點名兩項多輪 agent 評測補充。 
**A.** 干擾工具；工具錯誤後的復原（還有預算耗盡、政策中途變更）。

**Q40.** 什麼是摘要漂移？ 
**A.** 壓縮／摘要後的歷史省略或扭曲限制／事實。

**Q41.** 誰應對索引租戶歸屬控制課責？ 
**A.** 通常資料＋資安課責；工程負責實作——依 RACI。

**Q42.** 為什麼要釘選 MCP 伺服器版本？ 
**A.** 防止工具 schema／行為突然變更打斷 agent／評測。

**Q43.** 安全探測套件應有什麼 SLO？ 
**A.** 無害回應／攻擊攔截率，帶警示門檻。

**Q44.** token 串流到 UI，但何時提交資料庫寫入？ 
**A.** 只在驗證過的完整工具流程之後——不是部分計畫文字。

**Q45.** 什麼是標註校準場次？ 
**A.** 標註者用範例對齊評分量規，在打分前提高一致性。

## I 部分 —— 整合模式速查表

### I1. Claude 前面的 API 閘道

放一個 AI 閘道，用於：驗證、配額、提示詞大小限制、PII 遮蔽 hooks、模型路由，以及集中追蹤。應用團隊呼叫閘道，不是原始供應商金鑰。集中輪替金鑰；用團隊標籤歸屬成本。

### I2. 事件驅動的工具結果

長工具（報告產生）應立刻確認、推送完成事件，就緒時用 `tool_result` 恢復 agent／工作流程。沒有產品理由時，不要讓 HTTP 請求開著好幾分鐘。

### I3. 向量嵌入模型變更協定

1. 凍結寫入或雙寫。 
2. 離線重建索引。 
3. 影子查詢比較舊／新。 
4. 切流量。 
5. 回滾窗口結束前保留舊索引。

永遠不要在生產 RAG 系統下靜默變更向量嵌入模型。

### I4. 問答 46–50

**Q46.** 為什麼在供應商 API 前面放 AI 閘道？ 
**A.** 集中驗證、配額、遮蔽、路由與成本歸屬。

**Q47.** 10 分鐘的報告工具應如何與 agent 整合？ 
**A.** 非同步工作＋事件／回呼恢復——不是沒有設計的單次阻塞 HTTP 呼叫。

**Q48.** 重建索引期間的雙寫是什麼？ 
**A.** 遷移期間把向量嵌入寫進舊與新索引，以允許切換上線／回滾。

**Q49.** 點名三個對 FinOps（雲端與 AI 成本營運紀律）有用的閘道標籤。 
**A.** 團隊、產品、環境（還有用例、模型路徑）。

**Q50.** 靜默變更向量嵌入模型的風險？ 
**A.** 檢索品質偏移卻沒有可重現版本——會破壞評測，也讓事故更難追查。

### J1. 工具描述品質評分量規

差：`search` —— 「搜尋東西。」 
好：`search_policies` —— 「對呼叫者租戶的人資政策做語意＋關鍵字搜尋。參數：query（字串）、product（列舉）、top_k（1–20）。回傳 clause_id、title、snippet。不搜尋其他租戶。」

### J2. 對話記憶 vs 紀錄系統

永遠不要把聊天記憶當成餘額、權益或庫存的真相來源——決策當下**用工具擷取**。記憶只能放偏好與任務狀態。

### J3. 背壓

若工具或模型延遲上升，捨棄可選充實、縮小 k、降級到常見問答範本，或排隊並給使用者可見狀態。在設計審查裡定義這些模式。

### J4. 問答 51–55

**Q51.** 多重限制整合答案出現哪四個成分？ 
**A.** 模式、控制、證明／評測、效能槓桿。

**Q52.** 為什麼要重新擷取餘額，而不是信任聊天記憶？ 
**A.** 記憶會過時／可幻覺；紀錄系統才是權威。

**Q53.** 檢索變慢時背壓的例子？ 
**A.** 降低 top-k、跳過重排序，或提供帶部分狀態的快取常見問答。

**Q54.** 什麼讓工具描述「好」？ 
**A.** 清楚的範圍、參數、回傳，以及明確的非目標（例如租戶歸屬）。

**Q55.** 引用驗證器最低檢查什麼？ 
**A.** 被引用的 ID 存在於提供給模型的檢索集合中。

## K 部分 —— 主要學習深挖：整合（19%）

整合是最重的官方領域。把每一個企業連接當成**信任邊界**加上**延遲預算**加上**可觀測性介面**。

### K1. 傳輸層決策矩陣（展開）

| 機制 | 最佳適配 | authZ 故事 | 誤用時的失效模式 |
| --- | --- | --- | --- |
| 直連 Messages API＋用戶端工具 | 帶 1–N 項客製工具的產品執行環境 | 應用身分＋每工具伺服器檢查 | 臨時工具蔓延、沒有目錄 |

| Agent 對 agent（A2A） | 跨服務清楚的角色分裂 | 每 agent 憑證＋hop 稽核 | 沒有預算或擁有者的聊天式蜂群 |

### K2. 能力膨脹分析（考試最愛）

工具／agent 膨脹的症狀：
- 模型在近重複工具中選錯 
- 上下文視窗被工具 JSON schema 主導 
- 第一次有用動作前延遲就上升 
- 安全審查無法枚舉能力 

緩解：
1. 依 agent 角色的**允許清單**（客服 ≠ 管理員）。 
2. **合併**重疊工具（`get_order` 而不是五個變體）。 
3. **漸進式探索／工具搜尋**，讓定義按需載入。 
4. **描述品質評分量規**：名稱、何時用、何時不用、副作用、冪等。 
5. 在真實逐字稿上**評測**工具選擇準確度。

### K3. AuthN/Z 缺口檢查清單（每個設計走一遍）

- [ ] 使用者身分有傳遞（不是所有租戶共用一個全能服務帳戶） 
- [ ] 工具執行在*你的*程式碼檢查**資源層級** authZ——不是「Claude 小指許諾」 
- [ ] 租戶 ID 來自已驗證 token，永遠不要單靠模型產出的參數 
- [ ] 祕密在金庫／環境——永遠不要在提示詞、Skills，或提交到 git 的 MCP URL 
- [ ] 讀 vs 寫工具憑證分開 
- [ ] 破窗管理員路徑是人類＋有工單，不是 agent skill 
- [ ] 稽核日誌：誰、哪個工具、哪個資源、關聯識別碼、成功／失敗 

### K4. 準確度–延遲設定取捨

| 旋鈕 | 準確度↑？ | 延遲↑？ | 備註 |
| --- | --- | --- | --- |
| 較高能力模型 | 往往 | 是 | 在困難切片衡量 |
| 更多檢索 k | 有時 | 是 | 噪音風險 |
| 重排序器 | 往往精確率↑ | 輕微 | 對常見問答／政策值得 |
| 思考／effort | 困難任務↑ | 是 | 快取互動 |
| 額外評論迴圈 | 是 | 是 | 限制迭代 |
| 串流 | UX 感受↑ | 首個位元組延遲（TTFB）↓，總計≈ | 工具仍會阻塞 |
| 平行工具呼叫 | 牆鐘時間↓ | 扇出成本 | 僅當獨立時 |

每個旋鈕都用**指標＋預算**辯護。盲目把所有旋鈕開到最大，會在情境題失敗。

### K5. 規模上的可觀測性

最低可行 AI 可觀測性：
1. **請求追蹤**：入口 → 模型 → 工具 → 驗證器 → 出口 
2. **token 與 $**：每路徑輸入／輸出／快取／思考 
3. **品質代理**：讚踩、編輯距離、人類推翻、引用覆蓋 
4. **安全**：注入命中、DLP 封鎖、拒絕率 
5. **飽和**：佇列深度、工具 p95、速率限制 429 

沒有追蹤，「幻覺」工單就不可行動。


### M5. 最佳化順序（不要隨便打亂）

1. 修正正確性錯誤（錯誤工具、壞檢索）。 
2. 縮小上下文（更好檢索、更少工具）。 
3. 快取穩定前綴。 
4. 把簡單流量路由到較便宜／較快模型。 
5. 然後才考慮批次、平行、蒸餾式模式。

正確性之前最佳化成本，會創造靜默錯誤的系統。

### M7. 模型裁判 vs 程式碼裁判＋校準（P0）

LLM-as-judge 是**衡量儀器**，不是感覺神諭。架構師選評分者就像選單元測試框架：合約機器可檢查時優先**確定性檢查**；品質開放時用**模型裁判**——並且在分數驅動出貨／不出貨**之前校準**。

#### 何時程式碼／確定性斷言勝過模型裁判

| 程式碼勝出的訊號 | 示例 |
| --- | --- |
| 精確或結構化輸出 | JSON schema 有效；必填欄位存在；列舉成員 |
| 錨定機制 | 引用 ID ⊆ 檢索切塊 ID；URL 允許清單；配額算術 |
| 工具正確性 | 選對工具名稱；參數通過 schema；冪等鍵存在 |
| 政策引擎已存在 | 退款 ≤ 上限；權益檢查布林；PII 正規表示式／DLP 命中 |
| 帶已知字串的安全探測 | 禁止子字串；祕密模式；對 link-local IP 的 SSRF |
| 格式 SLA 回歸 | 字／字元限制；語言代碼；「必須包含免責聲明 X」 |

**規則：** 若初級工程師不用讀作文就能寫 pytest，**就不要**為裁判燒 token。

#### 何時需要模型裁判

| 評分量規裁判有幫助的訊號 | 示例 |
| --- | --- |
| 開放式品質 | 同理心、清晰、教學品質、摘要有用性 |
| 多因素評分量規 | 「有幫助＋無害＋符合品牌」，可部分給分 |
| 改寫等價 | 許多正確措辭；精確比對太脆 |
| 比較偏好 | A/B 成對「哪個草稿更適合這個人格設定」 |
| 細微忠實度 | 引用偏敘述文字時，軟檢查主張是否有依據 |

即使如此：與程式碼閘門結合（schema、引用 ID ⊆ 檢索），讓裁判永遠不要把垃圾 JSON 打成「美麗」。

#### 對人工黃金標籤校準（信任前）

```
1. 依意圖／難度分層抽樣 N 個項目（先約 50–200 個；高利害時加大規模）。
2. ≥2 位合格的人類用同一份評分量規打分；衡量一致性（例如 Cohen’s κ／完全一致百分比）。
3. 讓候選裁判（模型＋提示詞＋effort／思考設定＋參照政策）在相同項目上盲測。
4. 比較裁判與人類：相關性、系統性偏見（寬鬆／嚴格）、切片失敗。
5. 只有一致性越過預設門檻才晉升裁判；否則修評分量規／範例，或繼續用人工。
6. 模型升級、評分量規修改或領域漂移時重新校準——像程式碼一樣為裁判做版本。
```

**考試陷阱：** 「提示詞微調後裁判分數升了 8% → 出貨。」未經校準，你可能教會裁判愛冗長。

#### 門檻與回滾 —— 在看到實驗資料**之前**凍結

| 預先登錄（先寫下來） | 為什麼 |
| --- | --- |
| 主指標＋方向 | 阻止指標購物 |
| 最小提升／最大允許下降 | 出貨門檻 |
| 護欄指標（安全、延遲、成本） | 防止品質贏了卻合規失敗 |
| 樣本量／評測集識別碼 | 可重現性 |
| 回滾準則 | 例如「任何安全探測失敗」或「p95 +20%」→ 自動還原旗標 |

偷看結果再選門檻是 **p-hacking**。架構師把評測設定當成 git 裡受控的產物。

#### M7 問答（81–88）

**Q81.** 退款工具參數必須是 `{order_id, amount_cents}` 且金額 ≤ 政策上限。優先程式碼還是模型裁判？ 
**A.** **程式碼**（schema＋政策引擎）。模型裁判是可選的敘事潤飾，不是控制措施。

**Q82.** 為什麼要在 CI 閘控前對人類校準 LLM-as-judge？ 
**A.** 為了衡量偏見／一致性；未校準的裁判可能獎勵風格勝過正確性，並創造虛假出貨訊號。

**Q83.** 選兩項屬於預先登錄評測計畫的。 
**A.** 帶門檻的主指標**以及**回滾／護欄準則——在看實驗結果前寫下。

**Q84.** 只靠精確字串比對為摘要打分，好的改寫一直失敗。你做什麼？ 
**A.** 對必須包含的事實／引用來源保留程式碼檢查；為改寫品質加**已校準**評分量規裁判（或人工抽樣）——不要放棄事實斷言。

**Q85.** 你把裁判換成與產生器同一模型家族後，裁判分數上升。顧慮？ 
**A.** **共享偏見／自我偏好**；對人類重新校準，並考慮不同裁判模型或成對協定。

**Q86.** 健全回滾準則的例子是什麼？ 
**A.** 「若對抗性注入 ASR > X% 或引用 ID 驗證失敗率 > Y% 在金絲雀上，自動停用旗標」——在金絲雀**之前**設定。

**Q87.** 離線黃金標準集看起來很好；生產倒讚暴衝。第一個評測動作？ 
**A.** 懷疑**分布偏移**；把生產失敗抽進新切片；不要只重調裁判提示詞去迎合讚／踩。

**Q88.** 即使有已校準裁判，何時仍需要人類小組？ 
**A.** 高利害／不可逆領域、新穎失效模式，以及對裁判本身的定期稽核——自動化補充、不取代課責性。

## N 部分 —— 架構決策情境題（整合＋評測）

### N1. CRM＋計費＋知識庫的 MCP vs 直連 API

若三個以上應用（客服機器人、Claude Code、內部 agent）需要同一套連接器且你會維護目錄，**優先 MCP**。 
若只有一個延遲關鍵服務需要兩項緊密客製的工具，**優先直連工具**。 
**混合**常見：長尾系統用 MCP；最熱路徑用直連。

### N2. 帶退款與政策 RAG 的客服 agent

工作流程：檢索政策 → 起草 → **政策引擎驗證退款** → 工具執行。 
評測：政策引用有據程度＋退款決策精確性＋延遲。 
authZ：退款工具有上限；金額來自程式碼，不是未經檢查的自由形式模型浮點。

### N3. 正式發佈（GA）後缺少可觀測性

症狀：「錯誤答案」工單上升，沒有追蹤。 
修復方法：加關聯識別碼、儲存已遮蔽提示詞／工具 I/O、建重放框架、從工單凍結回歸集。

### N4. 準確度上升、延遲壞了

你加了評論迴圈＋k=20 檢索＋opus 級。 
回滾到基準線；每個旋鈕做 A/B；只保留每 +100ms 有證明提升的槓桿。

## Q 部分 —— 延伸問答（56–65）整合＋評測

**Q56.** 選兩項能力膨脹症狀：(a) 錯誤工具選擇 (b) 更快 p95 (c) 上下文裡巨大的工具定義 (d) 更高快取命中率。 
**A.** **(a)** 與 **(c)**。

**Q57.** 強制「使用者只能看到自己組織的工單」的最佳位置？ 
**A.** 用已驗證身分在工具／資料庫查詢上做**伺服器端 authZ**——不是單靠系統提示詞。

**Q58.** RAG 回傳極好的切塊，答案卻發明條款。第一個槓桿？ 
**A.** 強化**錨定指示＋必須引用來源＋缺乏依據則拒絕**；加有據程度評測。

**Q59.** 何時 agent 對 agent 比一個工作流程有正當性？ 
**A.** 當專精角色需要**分開的憑證／上下文**且監督者擁有副作用——不是給化妝式「多 agent」展示。

**Q60.** 品質可接受後的最佳化順序？ 
**A.** 縮小上下文 → 快取 → 路由到較便宜模型 → 安全處批次／平行。

**Q61.** 複選：CI 應在以下擋住（選三項）：schema 破壞、黃金回歸下降、安全包失敗、單靠虛榮 n-gram 上升、CSS 顏色變更。 
**A.** schema 破壞、黃金下降、安全失敗。

**Q62.** 漸進式探索 vs 單體——大型 MCP 目錄？ 
**A.** **漸進式／工具搜尋**；需要時載入定義。

**Q63.** 混合檢索在何時幫助最大… 
**A.** 查詢混合**語意改寫**與**精確 token**（ID、代碼、條款編號）。

**Q64.** 客服 copilot 的線上評測訊號？ 
**A.** 人類編輯率／推翻率／連到追蹤 ID 的 CSAT——不只離線 BLEU。

**Q65.** HIPAA 工作區裡的伺服器工具網頁擷取——架構師動作？ 
**A.** **停用或緊密閘控**，搭配 DLP 與資料處理審查；優先私有檢索。

## S 部分 —— 端到端參考情境（整合＋評測最重演練）

### S1. 企業政策助理（全堆疊）

**需求：** 4 萬員工、1 萬 2 千份政策文件、多地區設定、工會敏感人資政策、標準問答 p95 < 4 秒、引用來源強制、人資資料不可跨區域混合。

**架構草圖：**
1. 收件用感知章節切塊＋生效日期＋地區設定＋ACL 標籤。 
2. 混合檢索＋重排序；硬過濾 ACL＋地區設定。 
3. 中階 Claude，已快取人資作答政策；要求引用來源。 
4. 空檢索 → 澄清／拒絕。 
5. 評測：有據程度、引用精確率、ACL 紅隊、延遲、成本。 
6. 可觀測性：trace_id、引用的文件版本、快取命中率。
