# 加速器與智慧財產貢獻

> **免責聲明：** 原創備考筆記。這些筆記**不**重製官方課程內容。它們提供原創、對考試有用的指引：可重用 agent、Skills 打包、`CLAUDE.md` 範本、評測框架重用，以及交接文件——依據公開的 Claude Code、模型上下文協定（MCP）、API 與工程實務。

**主要對應：** 應用與整合（可重用設定與範本）· Agent 與工作流程（打包好的 agent）· 評測（框架重用）。
**次要：** Claude Code（Skills、範本）· 工具／MCP（模組化伺服器）· 資安（套件中的安全預設）。

---

## 1. 概覽

加速器是**可重用的建構積木**，幫助下一位工程師更快交付 Claude 解決方案，不必照抄口耳相傳的 Slack 傳說。在考試與合作夥伴交付中，強的答案會打包：

1. 帶有釘定模型與安全權限的預設架構。
2. 帶有清楚擴充點的提示詞與 `CLAUDE.md` 範本。
3. 給重複程序用的 Skills 或 playbook（操作手冊）。
4. 帶有允許清單與驗證模式的 MCP 或工具模組。
5. 一套評測框架與一套黃金入門集。
6. 交接文件：如何運行、如何修改、如何回滾。

智慧財產貢獻，意思是把一次性的客戶勝利，變成別人可以採用的**模組化資產**，並遵循你組織使用的授權與貢獻規則。這一檔教的是工程實質；實際提交請遵循你公司的法務與合作夥伴計畫規則。

## 2. 關鍵地圖

資產類型：agent 範本 — 它編碼的是：迴圈、預算、工具、驗證器。
資產類型：Skill — 它編碼的是：Claude Code 的按需程序。
資產類型：`CLAUDE.md` 範本 — 它編碼的是：精簡的常駐倉庫指引。
資產類型：設定包 — 它編碼的是：權限、hooks（勾子機制）、MCP 閘門。
資產類型：MCP 模組 — 它編碼的是：帶驗證與錯誤處理的領域工具。
資產類型：評測框架 — 它編碼的是：執行器、評分器、持續整合（CI）閘門。
資產類型：runbook（維運手冊） — 它編碼的是：操作、事故、升級步驟。
資產類型：參考應用程式 — 它編碼的是：端到端的精簡垂直切片。

## 3. 深入筆記 — 打包可重用 agent

### 3.1 什麼讓一個 agent 可重用

清楚的輸入與輸出。寫成文件的工具。帶覆寫 hooks 的釘定預設。內含預算與停止條件。跟著 agent 一起走的評測案例。預設安全的權限。不內嵌密鑰。有版本的發布。

### 3.2 設定面

分開：
- **政策**（安全規則、拒絕項）
- **產品提示詞**（語氣、任務框架）
- **環境**（端點、模型釘定）
- **密鑰**（注入，絕不打包）

使用方覆寫環境與產品提示詞的頻率，應高於政策。

### 3.3 參考 agent 骨架（概念）

進線訊息 schema。
可選的規劃步驟。
帶允許清單的工具註冊表。
帶最大步數與牆鐘時間的迴圈。
驗證器 hooks（schema、測試、政策）。
升級路徑。
遙測 hooks。
評測入口。

### 3.4 agent 打包的反模式

寫死的客戶名稱。密鑰放進倉庫。工具沒有上限。沒有版本。沒有評測。文件只寫「跑 main」。為了讓 demo 跑得快而開啟 bypass permissions（略過權限模式）。

## 4. 深入筆記 — Skills 打包（Claude Code）

### 4.1 Skills 對 `CLAUDE.md` 對 hooks

`CLAUDE.md`：簡短的常駐脈絡。
Skill：在相關時才被呼叫的程序；讓常駐脈絡保持精簡。
hook 或權限：必須強制執行的閘門。

適合打包成 Skill 的候選：發布檢查清單、新增 HTTP 端點、安全地撰寫遷移、分類不穩定測試、準備 pull request（PR）描述。

### 4.2 Skill 品質門檻

說明前置條件。列出步驟。點名涉及的工具。宣告停止條件。連結到測試。註明危險變體。包含好結果與壞結果的範例。

### 4.3 Skills 的版本管理

語意化版本，或標註日期的變更紀錄。註明破壞性變更。把 Skills 放在倉庫裡，讓 PR 可以審查它們。團隊加速器要避免只屬於個人的 Skills。

### 4.4 外掛式打包

團隊使用 Plugins 或共享套件包的地方，要包含：設定建議、Skills、hook 腳本、範例 `CLAUDE.md`，以及一份解釋信任邊界的 README。使用方在啟用之前，仍然應該審查 MCP 與權限。

## 5. 深入筆記 — `CLAUDE.md` 範本

### 5.1 精簡範本段落

1. 用三行說明倉庫用途
2. 目錄地圖
3. 標準指令
4. 慣例（錯誤、測試、API）
5. 危險區域
6. 深度文件的連結
7. 明確的非目標（不要憑空發明基礎設施）

### 5.2 範本變體

monorepo（單一儲存庫）根範本，加上巢狀套件範本。
函式庫範本對服務範本。
帶筆記本與評測註記的資料科學範本。
強調計畫模式、並對生產環境 apply 設有封鎖清單的基礎設施範本。

### 5.3 什麼不該放進範本

密鑰。客戶個人識別資訊（PII）。會變動的時間戳。整份架構決策紀錄（ADR）。多位作者互相矛盾、沒有歸屬人的規則。

### 5.4 維護

指派一位負責人。每季審查。把更新綁在壞掉的評測或事故上。連結優於貼上。

## 6. 深入筆記 — 評測框架重用

### 6.1 為什麼框架是智慧財產

框架編碼了你的組織如何衡量 Claude 品質。重用它，可以防止每個團隊各自發明不一致的評分儀式。

### 6.2 要打包的框架元件

案例 schema。測試資料載入器。模型與提示詞釘定介面。工具模擬器。評分器（精確、模糊、評分量規、副作用）。報表格式。CI 範例。範例黃金標準集（非敏感）。

### 6.3 擴充點

自訂評分器。自訂工具模擬。各領域的案例包。主機轉接器（API、Bedrock、Vertex）。

### 6.4 治理

比較期間凍結案例。把評分器納入變更管制。對任何隨框架出貨的真實流量取樣工具，做隱私審查。

## 7. 深入筆記 — MCP 與工具模組作為加速器

交付領域 MCP 伺服器或工具函式庫時，要附：
- 窄化的工具，不是原始 HTTP 直通
- 使用環境密鑰的驗證範例
- 結構化錯誤
- 合約測試
- 允許清單建議
- 一頁的威脅模型

伺服器要有版本。寫上升級註記。並提供一段給 Claude Code 用的、預設拒絕的入門權限片段。

## 8. 深入筆記 — 交接文件

### 8.1 最小可行交接包

README：它是什麼、什麼時候用、什麼時候不要用。
快速入門：十五分鐘以內達到第一次成功。
一頁架構說明，圖用文字形式表達。
設定參考：釘定、環境變數、權限。
資安註記：密鑰、拒絕項、威脅模型摘要。
維運：儀表板、警示、緊急停止開關、值班提示。
評測：如何運行、如何解讀、如何擴充。
變更紀錄與升級指南。
歸屬人與支援管道。

### 8.2 交接反模式

只能在展示機上跑、換到乾淨機器就失敗的示範腳本。
需要知道上週 Zoom 內容才看得懂的文件。
沒有回滾段落。
密鑰的螢幕截圖。
生產路徑裡沒有文件的模型別名。

### 8.3 受眾切分

為三種讀者而寫：實作的工程師、審查的資安工程師，以及未來值班的你。每種人需要不同段落，但一份交接包加上清楚的標題，就能服務全部三種人。

## 9. 決策樹

### 9.1 這該不該變成加速器？

如果同一個模式交付過三次以上，是。
如果只有一個奇特的客戶需要它，也許寫一篇案例研究就好，不要做產品化的加速器。
如果它內嵌客戶密鑰或專有資料，先淨化，否則不要發布。
如果評測沒有跟著走，它就還沒準備好。

### 9.2 Skill 對範本對參考應用程式

需要常駐慣例：`CLAUDE.md` 範本。
需要偶爾用到的程序：Skill。
需要端到端的學習路徑：精簡參考應用程式加上評測框架。
需要可強制執行的規則：設定與 hooks 包。

### 9.3 安全貢獻檢查清單樹

密鑰移除了嗎？評測包含了嗎？授權與合作夥伴規則查過了嗎？威脅模型寫了嗎？預設權限是最小權限原則嗎？釘定有文件嗎？負責人指名了嗎？只要有任何一題是否，就先不要貢獻。

## 10. 考試陷阱

1. 把加速器當成沒有評測的提示詞貼上桶。
2. 為了讓 demo 順暢而出貨 bypass permissions。
3. 把密鑰放進範例設定。
4. 以為官方智慧財產貢獻模組是公開的（它們不是）。
5. 巨大的 `CLAUDE.md` 範本，把整個 wiki 抄進去。
6. 暴露原始超級使用者 API 的 MCP 模組。
7. 沒有版本管理或變更紀錄。
8. 交接文件沒有回滾。
9. 用檔案數量衡量貢獻，而不是用重用與安全。
10. 因為「只是個加速器」就跳過資安審查。

## 11. 自我檢核問答（20）

Q1. Skill 和 `CLAUDE.md` 差在哪裡？Skills 是按需程序；`CLAUDE.md` 是精簡的常駐指引。
Q2. 舉出三樣絕對不能放在加速器套件裡的東西。密鑰、真實的客戶 PII、把 bypass-permissions 當預設。
Q3. 為什麼評測要跟著 agent 範本走？這樣採用者才能在自訂之後，證明範本仍然有效。
Q4. 什麼時候參考應用程式比單獨一個 Skill 更好？當學習者需要包含設定與測試的端到端垂直切片時。
Q5. 交接包的資安註記該放什麼？威脅模型摘要、密鑰注入模式、預設拒絕項，以及審查清單。
Q6. 如何讓 `CLAUDE.md` 範本可維護？負責人、每季審查、連結優於貼上、精簡段落。
Q7. 為什麼要把政策設定和產品提示詞設定分開？使用方改語氣的頻率高於改安全政策；較安全的預設能留得住。
Q8. MCP 加速器的合約測試是什麼？不需要完整用戶端應用程式就能跑的 schema 與驗證行為測試。
Q9. 這一章的範圍？官方智慧財產貢獻步驟可能存在於受管制的官方計畫裡；這些筆記只涵蓋可移植的工程實務。
Q10. 選一個好的加速器成功指標。採用它且評測通過的團隊數量——不是程式碼行數。
Q11. 為什麼在範本裡釘定模型？給採用者與 CI 的可重現性。
Q12. 危險區域段落是什麼？明確標出遷移、計費、生產環境 apply 等類似的高爆炸半徑區域。
Q13. 範例該如何處理 API 金鑰？佔位符，加上密鑰管理器說明——絕不放真實金鑰。
Q14. 什麼時候該在 monorepo 加速器裡巢狀放置 `CLAUDE.md` 範本？當各套件有不同的指令與慣例時。
Q15. 什麼讓設定包有價值？共享的 hooks 與拒絕項，把辛苦學來的安全教訓編碼下來。
Q16. 為什麼要包含「何時不該使用」段落？防止在錯誤的問題類型上誤用。
Q17. 這裡說的模組化智慧財產是什麼？可重用、有版本、有文件、別人可以組合的資產。
Q18. 加速器與「應用與整合」領域配分有何關係？可重用設定、釘定、MCP 模組與交接品質，就是整合能力。
Q19. 資安對新加速器的第一個審查問題？如果模型被攻陷，它能做什麼？
Q20. 把第 05 章對應到官方領域。整合、Agent、評測、Claude Code、工具／MCP，加上資安預設。

## 14. 打包實作範例（原創）

### 範例 A — 客服 copilot 加速器

## 15. 貢獻品質評分量規（每項 0–2 分）

用途清晰度。釘定預設。安全預設。評測完整性。文件完整性。可擴充性。營運就緒。版本紀律。密鑰衛生。重用證據／歸屬清晰度。

**出貨門檻：** 總分至少 14／20，且安全或密鑰衛生**不得有任何一項為零**。

## 18. 在團隊內建立加速器路線圖

階段 1：從最近幾個專案辨識重複的交付模式。
階段 2：抽出一條帶評測的精簡垂直切片。
階段 3：加上安全預設與交接文件。
階段 4：與第二個團隊做試點；收集摩擦註記。
階段 5：有變更紀錄與負責人的 1.0 版。
階段 6：然後才廣泛宣傳，或依你的規則貢獻到合作夥伴目錄。

## 22. 情境實驗室

情境：你的團隊為一個客戶做了一個出色的事故分診 agent。領導層想把它變成智慧財產。
步驟：淨化資料與品牌；抽出設定；加上預算與拒絕項；寫威脅模型；用合成事故建立黃金案例；寫交接包；與另一小隊試點；定版本；依組織規則貢獻。

情境：一份 `CLAUDE.md` 範本在人們貼上 ADR 之後變成 4,000 行。
步驟：砍成精簡摘要；把程序搬到 Skills；連結 ADR；加上負責人；衡量脈絡變少之後 agent 表現是否改善。

情境：一個 MCP 加速器在範例 compose 檔裡用了共享管理員 token。
步驟：停止散佈；輪換 token；改成環境佔位符；加上提交前密鑰掃描；加上 `SECURITY.md`；重新發布。

## 24. 詳細 `CLAUDE.md` 入門（說明用，原創）

段落「用途」：本倉庫為 Y 使用者實作 X。agent 應優先使用 `/packages/core` 既有函式庫，不要憑空發明新工具。

段落「佈局」：`/apps` 放可部署服務，`/packages` 放共享函式庫，`/evals` 放黃金標準集，`/.claude` 放設定與 Skills。

段落「指令」：測試、lint 與型別檢查使用 `CONTRIBUTING` 記載的 task runner。除非那些失敗且你寫下原因，否則不要發明替代指令。

段落「慣例」：偏好型別化介面。測試與程式碼放在一起。對齊既有錯誤分類法。不要為了讓任務變簡單而放寬權限。

段落「危險區域」：沒有計畫模式與人工審查，不要編輯資料庫遷移。沒有測試與人在迴路中（HITL），不要改計費計算。不要從 agent 工作階段對生產環境套用基礎設施變更。

段落「指標」：架構細節在 `/docs/architecture`。API 合約在 `/docs/openapi`。刻意讓本檔保持短。

## 28. 內部加速器目錄的營運模型

維護者每週依評分卡審查提交。資安對預設有否決權。每項資產有負責人與支援管道。已棄用資產給落日日期與遷移註記（「大聲棄用」）。採用指標出現在儀表板上——包括採用者的首次安全部署所需時間。開 office hours（開放諮詢時段）；永不接受帶密鑰的 PR。壞掉的採用者可以開議題，並作為下一版的閘門。

當題幹問合作夥伴或平台團隊如何規模化 Claude 交付品質時，這個營運模型在考試上很重要——答案是打包好的預設＋評測＋歸屬，不是更多投影片。

## 33. 主要研讀加深 — 加速器與可重用智慧財產

第 05 章涵蓋打包與貢獻主題，其中部分可能並非完全公開。這些筆記仍是原創備考材料，談可重用 agent、Skills、`CLAUDE.md` 範本、評測框架、MCP 套件與交接文件——這些能力仍會出現在應用、Agent、Claude Code 與評測情境裡。


### 33.1 這裡的加速器是什麼意思

加速器是有版本、有文件、可評測的套件，幫助另一位工程師更快交付 Claude 能力，而不必複製密鑰或一次性雪花設定。

| 屬性 | 門檻 |
| --- | --- |
| 清楚的問題陳述 | 給誰用／不給誰用 |
| pin bundle 預設 | 模型／effort／提示詞／工具版本 |
| 安全預設 | 危險工具預設拒絕 |
| 評測冒煙 | 至少一小片黃金切片 |
| 交接文件 | README＋SECURITY＋如何回滾 |
| 擴充點 | 有文件，不是只能 fork |

### 33.2 打包可重用 agent

讓它可重用：模型釘定、預算、工具允許清單用設定勝過程式碼；工具介面搭配參考 MCP／伺服器轉接器；明確的停止條件與人工閘門 hooks；遙測 hooks（已遮蔽）。

反模式：寫死的生產 URL／金鑰；只在我們的 monorepo 能跑、沒有轉接器；沒有評測；內嵌客戶資料的 Skills。

參考骨架：
```text
/agent
 README.md
 SECURITY.md
 EVALS.md
 config/pin.defaults.yaml
 prompts/system.vN.md
 tools/schema.vN.json
 harness/golden/
 src/runtime/
```

### 33.3 Skills 打包（Claude Code）

| 構件 | 何時用 |
| --- | --- |
| `CLAUDE.md` | 常駐團隊指引 |
| Skill | 被呼叫的工作流程，例如 `/review-pr` |
| Hook | 圍繞事件的硬性強制 |
| Plugin | 散佈 Skills／hooks／MCP 套件包 |
| `settings.json` | 權限／模型預設 |

Skill 品質門檻：單一用途；輸入清楚；範例；失敗模式；沒有密鑰；若會改程式碼則連結評測。把 Skills 當 API 做版本——破壞性變更升 major；保留變更紀錄。

### 33.4 作為智慧財產的 `CLAUDE.md` 範本

精簡段落：用途、建置／測試指令、程式碼風格、資安不變量、審查清單、何時問人類。

變體：服務倉庫、資料／ML 倉庫、基礎設施倉庫、文件倉庫。

不要放：API 金鑰、客戶 PII、未經查證的傳聞、更適合在設定裡強制的互相矛盾絕對句。

維護：負責人；每季審查；綁到事故。

### 33.5 評測框架重用

框架是高槓桿智慧財產：執行器＋評分＋報表格式；測試資料佈局慣例；安全切片永遠開著；外掛式評分器（schema、任務成功、裁判）；為整合回歸捕捉成本／延遲。治理：框架評分變更需要升版本，讓歷史比較保持誠實。

### 33.6 MCP 與工具模組作為加速器

出貨：帶驗證模式的伺服器雛形；工具 schema 加上封鎖清單範例；合約測試；一段威脅模型；給 Claude Code 設定用的允許清單片段。陷阱：為了方便而發布過度授權 OAuth 範圍的伺服器。

### 33.7 交接文件

最小包：README（快速入門）、SECURITY、OPERATIONS（釘定、儀表板、回滾）、EVALS、CODEOWNERS／支援管道。

反模式：只有螢幕截圖的安裝；Slack 傳說；沒有文件的損壞；聯絡 Bob。

受眾切分：採用工程師、資安審查者、值班。

### 33.8 決策樹

這該不該變成加速器？
```text
Used successfully >=2 times in different contexts?
 NO -> keep as example
 YES -> Can you remove secrets and snowflakes?
 NO -> extract patterns only
 YES -> package + evals + docs
```

Skill 對範本對參考應用程式：
```text
Always-on guidance -> CLAUDE.md template
Invoked workflow -> Skill
Full runtime + tools -> Reference app/agent kit
```

### 33.9 考試陷阱（打包風味）

1. 出貨內嵌密鑰的加速器。
2. 沒有安全預設（以為採用者之後會收緊）。
3. 把受管制官方課程當成公開內容。
4. 默默變更權限的 Skills。
5. 只檢查語氣的評測。
6. 帶全開放範例的 MCP 套件。
7. 與已強制設定互相矛盾的範本。
8. 沒有版本管理——團隊間默默漂移。

### 33.10 額外問答（Q31–Q45）

**Q31.** 資安審查者打開加速器的第一個檔是什麼？
**A31.** `SECURITY.md`／威脅模型與預設允許清單——然後才是 schema。

**Q32.** 為什麼每個 agent 套件都要帶一小片黃金評測？
**A32.** 證明 pin bundle 能跑；抓住採用者設定錯誤；錨定回歸。

**Q33.** 什麼時候 `CLAUDE.md` 範本有害？
**A33.** 當它長到或矛盾到團隊直接忽略，或當它假裝在強制控制時。

**Q34.** 如何安全散佈一個 Skill？
**A34.** 程式碼審查、沒有密鑰、釘定版本、清楚列出必要權限——不是默默升級。

**Q35.** 加速器成功指標？
**A35.** 採用者的首次安全部署所需時間，加上評測通過率——不是星標。

**Q36.** 為什麼要把 `pin.defaults` 和 `pin.prod` 範例分開？
**A36.** 預設是安全入門；生產釘定依環境而異，絕不能盲目跨主機複製。

**Q37.** `OPERATIONS.md` 該放什麼？
**A37.** 儀表板、警示、回滾、速率限制聯絡窗口、主機矩陣。

**Q38.** 第 05 章內容會出現在 CCDV-F 嗎？
**A38.** 會以整合／Agent／Code／評測對可重用設定的判斷出現——不是合作夥伴智慧財產流程冷知識。讀工程實質。

**Q39.** 外掛裡打包的 hook 每次編輯都刪除 `node_modules`——問題？
**A39.** 危險預設；hooks 必須是最小權限，且破壞性動作要選擇加入。

**Q40.** 什麼是好的擴充點？
**A40.** 自備 `search_kb` 工具轉接器，而不是 fork 整個 agent。

**Q41.** 如何在套件裡為提示詞做版本？
**A41.** `system.vN.md` 加上釘定檔參照加上變更紀錄；永不默默覆寫。

**Q42.** 為什麼要包含 MCP 的封鎖清單範例？
**A42.** 教導採用者：連接器不是全有或全無。

**Q43.** 參考 agent 對生產服務？
**A43.** 參考教模式；生產加上租戶、服務水準目標（SLO）、合規——不要把 demo 當成生產。

**Q44.** 貢獻就緒評分卡會有哪一項？
**A44.** 密鑰已掃描、評測綠燈、文件完整、負責人列出、授權清楚。

**Q45.** 把加速器工作對應到官方領域。
**A45.** 應用（可重用設定／釘定）、Agent（打包迴圈）、Claude Code（Skills／範本）、評測（框架重用）、資安（安全預設）。
