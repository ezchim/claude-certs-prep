# 生產工程、評測與資安

> **免責聲明：** 原創備考筆記。依據公開的 Anthropic 安全與產品模式、常見 LLM 應用評測實務，以及公開報導的 CCDV-F 領域：資安與安全防護（8.1%）與評測／測試／除錯（2.6%），再加上應用與整合（33.1%）的生產切片。獨立內容；非正式課程教材。

**主要對應：** 資安 8.1% · 評測／測試／除錯 2.6% · 生產整合。
**次要：** Agent 可靠性 · 以評測證明模型選擇與最佳化（MSO）合理性 · 模型上下文協定（MCP）與工具強化。

---

## 1. 概覽

交付 Claude 上線是一個營運問題，有三個密不可分的目標：

1. 讓它正確——評測、黃金標準集、回歸閘門。
2. 讓它安全——密鑰、個人識別資訊（PII）、注入防禦、破壞性動作閘門、抗濫用。
3. 讓它可營運——服務水準目標（SLO）、追蹤、事故回應、成本控制、變革管理。

評測與資安在紙面上的配分比重很小，但它們扮演過濾器，能在多領域題幹中淘汰掉原本看似合理的設計。把它們當作決策約束來讀，而不是選修章節。

---

## 2. 關鍵地圖

支柱：評測 — 行為在真實任務上真的改善了嗎？控制：黃金標準集、評分量規、副作用斷言。
支柱：除錯 — 這條追蹤為什麼失敗？控制：重播、差異比較、工具日誌。
支柱：資安 — 如果模型錯了或被攻擊了怎麼辦？控制：封鎖清單、授權、遮蔽、人在迴路中（HITL）。
支柱：安全防護 — 輸出會造成傷害或違反政策嗎？控制：過濾器、分類器、拒答。
支柱：生產工程 — 它能在預算內持續運作嗎？控制：SLO、佇列、上限、runbook（維運手冊）。

## 3. 深入筆記 — 評測

### 3.1 為什麼評測勝過憑感覺

大型語言模型（LLM）的變更容易交付、卻難以察覺。評測把意見轉換成可衡量的差異。CCDV-F 敘述預期你在生產環境中變更模型、提示詞或工具之前，都要先拿出評測證據。

### 3.2 評測類型

單元式檢查：schema 有效性與工具引數形狀。快速偵測破損。
黃金標準集：帶標籤的案例，用精確或模糊比對標準。
評分量規或 LLM 當裁判：質性品質，要搭配校準與人工稽核。
副作用測試：呼叫了哪些工具；對 agent 至關重要。
對抗性測試包：注入與越獄；與資安重疊。
線上方法：影子流量、A/B、在真實流量上做金絲雀。
成本與延遲預算與品質成對——永遠不要單獨衡量。

### 3.3 打造黃金標準集

隱私審查之後，抽樣真實任務。標註預期答案或可接受的評分量規。納入邊界案例與已知失敗。為集合做版本管理，並在比較期間凍結它。按難度與意圖切片，讓平均分數不會掩蓋困難切片上的回歸。

### 3.4 Agent 評測的特別之處

斷言最終答案品質、用了哪些工具與哪些沒被使用、步驟數在預算內、沒有禁用工具，以及重試之下的冪等行為。在一次違禁刪除之後，就算段落寫得正確，仍然是失敗。

### 3.5 LLM 當裁判的陷阱

裁判可能和生成者共享同樣的弱點。成對比較會出現位置偏見。模糊的評分量規會製造雜訊。按計畫定期用人工抽查。

### 3.6 部署閘門

持續整合（CI）跑單元 schema 檢查，加上小型黃金標準集。預備環境跑完整黃金標準集，加上對抗性測試包。金絲雀盯著線上指標與安全監控。全機群推行上線時持續監控，並備好回滾。

### 3.7 除錯迴圈

擷取一條遮蔽過的失敗追蹤。用釘定版本重現。比對提示詞、工具、模型與設定的差異。在脈絡問題、工具錯誤、政策衝突與容量問題之間形成假設。用最小變更修復。把回歸案例加進黃金標準集。還沒讀追蹤就跳升模型層級，是經典考試陷阱。

### 3.8 重要的指標

任務成功率、schema 失敗率、工具錯誤率、拒答正確率（誤拒對誤放）、注入抵抗率、p95 延遲、每次成功成本，以及人工升級率。

## 4. 深入筆記 — 資安與安全防護

### 4.1 威脅模型主題

提示注入，直接的，以及經由文件、工具與網頁的間接注入。
脈絡中的密鑰或經由對外工具的資料外洩。
未授權動作：模型說服工具越權。
API 邊緣的濫用與詐欺。
來自 MCP 伺服器、外掛與相依套件的供應鏈風險。
圍繞日誌中 PII 與保留政策的隱私問題。
過度拒絕或拒絕不足的政策錯誤。

### 4.2 縱深防禦

邊緣的身分驗證、授權與速率限制。
輸入過濾與大小限制。
不可被覆寫的系統政策。
對不受信任內容做分隔。
工具允許清單加上伺服器端授權。
相關之處使用 Claude Code 權限與 hooks（勾子機制）。
輸出過濾與 PII 清除。
稽核日誌與異常偵測。

沒有任何單一一層是夠的，尤其一個客氣的系統提示詞絕對不夠。

### 4.3 密鑰管理

密鑰管理器、環境注入，或雲端身分與存取管理（IAM）。永遠不要放進提示詞，永遠不要放進 `CLAUDE.md`，永遠不要放進提交進版控的設定。從日誌與追蹤中遮蔽。外洩時輪換。範圍保持狹窄，按環境、按工具切分。

### 4.4 PII 處理

在提示詞中最小化 PII。在工具轉接層中遮罩。定義保留政策。必要時使用區域性託管。對評測資料集做存取控制。標籤允許時，優先使用合成資料。

### 4.5 破壞性動作閘門

讀取：在授權之下允許。
更新：授權加上稽核。
刪除、付款與對外電子郵件：HITL，或工具內部的強政策引擎。
Shell 執行：對自主 agent 預設拒絕；必要時在沙箱中執行。

### 4.6 護欄模式

針對毒性、PII 或越獄嘗試的獨立分類器——要知道它們兩個方向都會出錯。
工具內部的硬性上限。
高風險動作的雙人控制。
安全的補全與清楚的拒答路徑。
永遠不要在沒有衡量的情況下，為了修復過度拒絕而拆掉所有護欄。

### 4.7 MCP 與外掛供應鏈

信任之前先審查程式碼。釘定版本。在企業中使用受管理的允許清單。使用最小權限的 token。監控對外流量。把專案交付的 MCP 設定當作可執行的相依套件來對待。

### 4.8 資安測試

對抗性評測應包含：忽略先前指令的攻擊、工具外洩嘗試、社交工程，以及惡意的工具描述。

### 4.9 事故

透過停用有風險的工具來圍堵。保存遮蔽過的追蹤。找出攻擊途徑。修補分隔符與授權。若可能已外洩，就輪換密鑰。按政策通知利害關係人。新增評測案例。謹慎地重新開放。

## 5. 深入筆記 — 生產工程

### 5.1 SLO

例子：可用性、成功率、p95 延遲、成本上限、安全事故次數。錯誤預算決定要凍結功能還是繼續交付。

### 5.2 容量與速率限制

把工作排進佇列。互動式流量優先於批次。用帶抖動的退避。執行租戶公平性，讓一個客戶不能餓死其他客戶。

### 5.3 成本工程營運

每日異常警示。按功能的預算。緊急停止開關。快取命中儀表板。把模型與 effort（思考力度）政策保存為有版本的設定，而不是部落知識。

### 5.4 變革管理

提示詞、工具與模型的變更需要 pull request（PR）審查、評測差異與金絲雀——和應用程式碼同一套紀律。

### 5.5 資料落地與多區域

按政策路由。理解各託管平台之間的功能對等。不要為了一個更亮眼的模型 SKU（產品型號）而破壞資料落地規則。

### 5.6 降級與災難復原（DR）

常見問題的快取答案。純人工模式。延遲的批次處理。能快速停用生成式路徑的功能旗標。

### 5.7 值班訊號

在工具錯誤飆升、schema 失敗、成本燃燒、安全分類器飆升，以及代表失控迴圈的步驟數爆炸時呼叫值班。

## 6. 決策樹

### 6.1 自動化安全嗎？

若存在不可逆的外部影響，要求 HITL，或工具內的硬政策引擎。
若環境中的憑證比任務所需的更廣，先收窄再提高自主程度。
若對抗性評測覆蓋薄弱，保持密切的人工監督。
若黃金標準集是綠的、監控也就位，考慮更高的自主程度；否則不要開啟全自動駕駛。

### 6.2 評測充分性

改提示詞、工具或模型，至少需要一個離線黃金差異。
交付 agent 寫入，需要副作用斷言加上對抗性測試包。
受監管領域還需要人工審查的樣本與稽核軌跡。

### 6.3 疑似注入事故

透過停用有風險的工具來圍堵。保存遮蔽過的追蹤。確認途徑是文件、工具酬載，還是網頁擷取。修補分隔符與授權。需要時輪換密鑰。新增評測案例。謹慎地重新開放。

## 7. 考試陷阱

1. 對硬性風險只用提示詞做資安。
2. 只在沒有副作用的順利路徑聊天上做評測。
3. 為了方便而記錄密鑰。
4. 全自動駕駛配上 shell 存取與生產憑證。
5. 最終文字看起來不錯，就忽略副作用。
6. 把一次手動測試當成評測套件。
7. 為了修復過度拒絕而停用護欄，卻沒有衡量。
8. 分享仍含有 PII 的評測資料。
9. 僅僅因為 MCP 伺服器能在內部域名系統（DNS）上解析，就信任它們。
10. 因為評測領域只有 2.6% 的比重就跳過它。

## 8. 自我檢核問答（25）

Q1. 生產提示詞微調之前，最低的評測？有版本的黃金比較，加上冒煙——不是憑感覺。
Q2. 答案文字是對的，但 `delete_user` 被呼叫了——算通過嗎？因副作用而失敗。
Q3. API 金鑰放在哪裡？密鑰管理器、環境或 IAM——永遠不在提示詞或倉庫裡。
Q4. 間接提示注入的例子？藏在擷取回來的 PDF 或網頁裡的惡意指令。
Q5. 讓生產資料表永遠不被刪除，最好的控制？沒有 DROP 的資料庫角色、工具允許清單，以及拒絕規則——不只是提示詞裡的一行字。
Q6. 裁判分數上升，但人類不同意——怎麼辦？稽核裁判與評分量規；不要只憑裁判就交付。
Q7. 凌晨 3 點成本在燃燒——第一步？緊急停止開關，或停用非必要 agent；檢查失控迴圈與快取崩潰。
Q8. 為什麼要遮蔽追蹤？提示詞與工具酬載常常含有 PII 或密鑰。
Q9. 資安對安全防護的速記？資安聚焦攻擊者與系統濫用；安全防護聚焦有害或違反政策的輸出；兩者重疊。
Q10. 金絲雀對影子？金絲雀影響一部分真實使用者；影子在設計得當時，做比較而不產生使用者可見的變化。
Q11. 什麼時候必須凍結評測集？在比較兩個系統的期間。
Q12. 在共享 CI runner 上用 bypass permissions？危險的預設——避免。
Q13. 黃金標準集中的 PII——控制？最小化、遮罩、存取控制清單（ACL）、保留，或改用合成資料。
Q14. 工具描述要求把資料送到未知主機——風險？惡意供應鏈；審查、釘版本、允許清單。
Q15. 收緊過濾器之後出現過度拒絕——回應？衡量誤拒；用評測調校；不要盲目移除過濾器。
Q16. schema 失敗飆升——怎麼除錯？比對最近的模型、提示詞與工具版本；抽樣追蹤。
Q17. LLM 功能的錯誤預算是什麼？在可靠性工作取得優先權之前，所允許的不可靠程度。
Q18. 為什麼要租戶速率限制？公平性與濫用隔離。
Q19. 為什麼大量發信要求 HITL？高度的聲譽與法律爆炸半徑。
Q20. 資安加評測的比重？8.1% 加 2.6%——很小，但有決定性。
Q21. 什麼時候新增回歸案例？每一次抓到生產失敗之後。
Q22. temperature 零是完全確定性嗎？不是——仍要釘住模型；工具仍然是非確定性的；評測仍然必要。
Q23. 資料落地擋住了一個只在美國提供的模型——路徑？使用核准的區域 SKU；功能缺了就重新設計。
Q24. 哪些監控能抓到 agent 迴圈？每個工作階段的步驟數、重複的工具呼叫、每個工作階段的成本、持續時間。
Q25. 一個新工具的第一個資安問題？如果模型被完全攻陷，還剩下什麼授權？

## 10. 詞彙表

黃金標準集：帶標籤的評測資料集。
評分量規：結構化的評分標準。
LLM 當裁判：為輸出評分的模型。
金絲雀：有限度的真實使用者推行上線。
影子流量：不影響使用者的平行評測。
提示注入：操縱模型行為的不受信任指令。
資料外洩：資料經由模型輸出或工具流出。
護欄：圍繞模型的過濾器或政策層。
HITL：人在迴路中的核准。
遮蔽：從日誌與追蹤中移除敏感資料。
錯誤預算：在優先順序轉移之前所允許的不可靠程度。
緊急停止開關：LLM 功能的緊急停用。
誤拒：擋掉一個善意、被允許的請求。
誤放：放行一個不被允許的請求。

## 11. 延伸生產 playbook（操作手冊）

### 11.1 上線前審查會的問題

工具被濫用時能做什麼？
有什麼評測證據？
爆炸半徑是什麼？
回滾計畫是什麼？
PII 流向哪裡？
誰值班？
使用者看到的降級是什麼樣子？

### 11.2 對抗性測試包的類別

直接越獄。文件中的間接注入。工具名稱社交工程。政策衝突請求，例如忽略退款上限。混淆伎倆。相關時的多語言規避樣本。過度代理請求，例如執行所有 shell 命令。

### 11.3 評測框架架構

案例庫。釘住模型、提示詞與工具的執行器。評分器。報告發布器。CI 閘門。儀表板。建一次，跨團隊重用——打包見第 05 章。

### 11.4 資安控制矩陣範例

API 金鑰：竊取風險——密鑰管理器與輪換。
客戶 PII：洩漏風險——遮罩與保留。
Shell 工具：程式碼執行風險——拒絕或詢問，加上沙箱。
遠端 MCP：供應鏈風險——允許清單與釘版本。
日誌：敏感儲存風險——遮蔽。
批次結果儲存桶：過廣存取風險——ACL。

### 11.5 除錯敘事

星期一品質下降：檢查星期日的部署差異——別名搬動、提示詞編輯、工具 schema 變更、時間戳造成的快取未命中，或 MCP 更新。
安全過濾器擋掉合法內容：用帶標籤的誤拒集；謹慎調校，需要時請領域審查。
agent 隔夜花了一大筆錢：缺失的預算、迴圈、巨大的工具酬載，或快取被停用；用緊急停止開關；加上限。

### 11.6 合規導向的設計筆記

預期稽核日誌、最小權限、資料落地、保留政策，以及高風險的人工監督，會以設計需求的形式出現。你不需要背法條；你需要選出符合那些主題的控制。

### 11.7 與模型選擇的連結

評測決定更便宜的模型是否可接受。沒有品質指標的成本警示會造成有害的刪減。永遠把經濟性與任務成功配對。

## 12. 額外問答（26–40）

Q26. 什麼是冒煙評測？每次建置都跑的一個微小關鍵路徑集合。
Q27. 為什麼把安全指標和有用性分開？最佳化其中一個，可能拖垮另一個。
Q28. 可以把原始生產追蹤當黃金資料嗎？只有經過隱私審查與標註管線才可以。
Q29. bash 工具有哪些容器顧慮？強化沙箱；拒絕危險的命名空間；最小權限。
Q30. 輸出上的正規表達式密鑰過濾器夠嗎？有幫助但不完整；防止密鑰進入脈絡，並封鎖外洩工具。
Q31. 關掉功能旗標對模型回滾？旗標停用功能；回滾還原模型或提示詞版本。
Q32. 為什麼在評測報告中對設定做雜湊？可重現性與稽核。
Q33. 什麼時候在 MCP 對外流量上套用資料外洩防護（DLP）？當工具能對外傳送資料時；這常常是企業預設。
Q34. 單元測試只模擬工具的危險是什麼？會漏掉整合授權錯誤——加上預備環境的合約測試。
Q35. 選出三個寫入工具強化的例子：伺服器端授權、稽核日誌、HITL 或政策上限，再加上冪等。
Q36. 可以把聊天的 p95 套到隔夜批次上嗎？SLO 類別錯了。
Q37. 輸出中不被允許的建議由哪些層處理？政策提示詞、安全系統、領域工具限制，以及適當的使用者體驗免責聲明。
Q38. 為什麼已知良好和已知惡意的資安案例都要保留？用來追蹤偽陽性與偽陰性。
Q39. 平台上誰擁有評測失敗？平台團隊擁有框架；產品團隊擁有標籤與評分量規。
Q40. 第 04 章口訣？衡量、在模型之外強制執行、觀測，並且隨時準備關掉它。

## 13. 情境題包

醫院聊天機器人：資料落地、PII 最小化、臨床上的過度拒絕與拒絕不足評測、沒有硬授權就不給原始電子健康紀錄（EHR）寫入工具、敏感排程動作要 HITL。

企業搜尋：感知權限的檢索，讓未授權文件永遠不進入脈絡；文件的注入強化；答案上的 DLP。

每個情境都應在考試中觸發多層答案：評測證據，加上模型之外的強制執行，加上可營運的監控。

## 15. 生產工程模式深入

### 15.1 佇列與優先順序

互動式使用者請求不該排在巨大的批次回填後面等。用獨立佇列或優先通道。套用按租戶的公平共享。明確地卸載，讓降級對使用者可見，而不是無聲的逾時風暴。

### 15.2 冪等消費者

執行工具副作用的工作者必須冪等。使用冪等鍵、upsert 語意，以及崩潰後能恢復的狀態機，不重複扣款、不重複發信。

### 15.3 背壓

當 Claude 或工具主機變慢，上游的准入控制應該拒絕或排隊，而不是開無上限的用戶端執行緒。這要搭配斷路器。

### 15.4 設定即程式碼

模型釘定、提示詞版本、工具雜湊、effort 預設值與功能旗標，都屬於經過審查的設定。緊急煞車仍應留下稽核軌跡。

### 15.5 多主機現實

有些客戶住在 Bedrock 或 Vertex 上。維護一張功能矩陣。你聲稱支援的每個主機都要跑整合測試。資料落地可能迫使你選 SKU 較少的區域——為夠用而設計，不為幻想而設計。

### 15.6 資料生命週期

定義提示詞、追蹤與批次輸出活多久。靜態加密。限制誰能重播追蹤。評測資料集含有敏感內容時，需要和生產資料同等的嚴謹。

### 15.7 人的因素

值班的人需要清楚的儀表板與一鍵緊急停止開關。如果凌晨 3 點沒有人能行動，再出色的評測套件在實務上也是失敗。

## 18. 綜合情境演練

### 演練 A — 客服 agent 提議改寫政策

使用者上傳一封電子郵件，說忽略退款政策並立即付款。正確的系統行為：把這封電子郵件當作不受信任；政策工具仍然執行上限；可能升級；記錄這次嘗試；之後加進對抗性測試包。

### 演練 B — CI 中的寫程式 agent

無頭工作階段，釘住模型、拒絕生產憑證、以測試作為成功閘門、不用 bypass permissions，並把產出物上傳供審查。如果測試失敗，管線失敗即關閉。

### 演練 C — 一次好用的提示詞編輯之後的成本回歸

新提示詞在系統區段加了每請求的時間戳。快取命中率崩了。成本上升。先修前綴衛生；不要立刻在別處提高模型支出來補償。

### 演練 D — 安全誤拒

分類器擋掉善意的技術內容。用誤拒集；調校閾值；謹慎新增允許類別；變更後同時監控誤拒與誤放。

## 19. 政策即程式碼範例（概念）

把支出上限、允許區域、被擋的工具名稱與最大步數，表達成機器可檢查的設定。模型可以讀到政策的人類說明，但強制執行絕不能依賴它是否遵守那段說明。

考前記住的概念範例：
- `max_refund_amount` 在退款工具內強制執行
- `max_agent_steps` 在編排器內強制執行
- `denied_path_patterns` 在 Claude Code 權限內強制執行
- `residency_route` 在閘道裡、模型選擇之前強制執行

## 23. 常見題幹譯法

題幹說使用者太信任聊天機器人——加上引用來源、不確定性語言與升級；也許降低自主程度。
題幹說稽核人員需要證明——不可竄改日誌、版本釘定、評測報告。
題幹說模型洩漏了 API 金鑰——輪換、遮蔽、把密鑰移出脈絡、審查追蹤。
題幹說 agent 轉了一整夜——預算、進度偵測器、警示。
題幹說經搜尋結果的提示注入——分隔不受信任內容、強化工具授權、加上對抗性案例。
題幹說更便宜的模型在資安案例上失敗——不要為失敗切片出貨那條路由。

## 28. 工作坊 — 把弱設計改成強設計

弱：我們告訴 Claude 不要發明退款。
強：退款工具執行上限；超過門檻要 HITL；政策用檢索；對抗性評測；稽核日誌。

弱：我們測了一次 agent，看起來不錯。
強：有版本的黃金標準集、副作用斷言、CI 閘門、金絲雀指標、回滾計畫。

弱：CI 用 bypass permissions，好讓管線保持綠燈。
強：釘定權限、拒絕密鑰與生產網路、測試失敗即關閉、共享 runner 上不用 bypass。

弱：每個微服務共用一把全域 API 金鑰。

## 35. 主要研讀加深 — 生產工程、評測、資安

第 04 章是資安與安全防護（8.1%）與評測／測試／除錯（2.6%）的主要研讀，再加上應用與整合（33.1%）的營運那一半。


### 35.1 把評測當成工程系統

為什麼評測勝過憑感覺：生產流量很吵；離線黃金標準集在客戶之前抓住回歸；線上指標抓住評測錯過的漂移。

| 類型 | 衡量什麼 | 弱點 |
| --- | --- | --- |
| 單元式黃金提示詞 | 精確或評分量規分數 | 窄 |
| schema／驗證器測試 | 結構正確性 | 不是語意 |
| 工具／agent 任務成功 | 端到端目標 | 建置成本高 |
| LLM 當裁判 | 細緻品質 | 偏見；需要校準 |
| 對抗性／紅隊 | 安全 | 永遠不完整 |
| 線上 A/B 或影子 | 真實分布 | 不安全時有風險 |

黃金標準集工藝：涵蓋順利路徑、邊界、對抗性、相關時的多語言，以及工具失敗路徑。凍結輸入；為預期行為做版本。按產品介面保留切片。從生產事故抽樣困難負例（已遮蔽）。

Agent 評測的特別之處：評任務成功，不是口才。包含環境狀態（倉庫測試資料、模擬 API）。限制步數；超過預算即失敗。斷言安全不變量，例如從未呼叫 `delete_prod`。

LLM 當裁判的陷阱：裁判看到洩漏的答案或規劃者的思維鏈，因而產生偏見。未校準的評分量規會灌水分數。用成對或錨定參考的評分量規；用人工抽查。

部署閘門：必過 schema 測試、安全拒絕、關鍵黃金切片；應過品質評分量規，落在基準線的 epsilon（容差）內；監控成本、延遲、快取命中、升級率。

除錯迴圈：用釘定組合重現；檢查逐字稿加上 `stop_reason` 加上工具追蹤；分類提示詞／工具／模型／編排／資料；修一層；加回歸案例；然後才考慮模型升級。

### 35.2 資安與安全防護深入筆記

威脅主題：經由使用者、檢索文件或工具結果的提示注入；模型擁有使用者不該有的工具時的混淆代理人；經由提示詞、日誌或 MCP 的密鑰外洩；來自 MCP 伺服器、外掛與 Skills 的供應鏈風險；破壞性自動化；資料落地與保留政策的誤用。

縱深防禦堆疊：
1. 身分與密鑰：金庫裡的金鑰；永不放進提示詞或 `CLAUDE.md`。
2. 允許清單：工具、路徑、網路、MCP。
3. 權限與 hooks：Claude Code 裡用戶端強制；應用程式裡伺服器驗證器。
4. 輸入分隔符，以及不信任工具結果。
5. 需要時對 PII／密鑰做輸出過濾。
6. 不可逆類別的人工核准。
7. 帶遮蔽的稽核日誌。
8. 評測與紅隊持續進行。

破壞性動作閘門：為動作分類；若不可逆，要求明確的人工確認構件 **且** 權限允許 **且** 高嚴重程度時可選雙人控制；否則在政策下允許。計畫模式與「我會小心」的提示詞不是閘門。

PII：最小化；遮蔽日誌；提示詞裡優先用 token／ID 而不是原始資料；文件化保留政策。

MCP 與外掛供應鏈：審查指令／URL；釘定版本；最小權限；信任 UX；生產倉庫預設拒絕。

### 35.3 生產工程（應用營運）

SLO：可用性、首個 token 延遲（TTFT）／p95 延遲、任務成功、模型中斷的錯誤預算。

容量：速率限制、佇列、跨租戶公平性、隔離評測流量。

成本工程營運：每次成功美元的儀表板；快取命中；升級；輸出長度；每週釘定審查。

變革管理：釘定組合；金絲雀；把提示詞／工具／模型連到變更紀錄；回滾 runbook。

資料落地：區域端點；從公開雲端文件主題理解全球對區域路由的取捨。

降級與 DR：後援模型；範本模式；重播佇列；中斷後的批次回補。

值班訊號：拒答飆升、工具錯誤、快取未命中、成本、偵測器、人工升級。

### 35.4 偏整合的資安與評測情境

情境 A — 客服 agent 提議改寫政策。當作高影響內容；要求人工發布；評測不安全建議；不要自動合併進說明中心。

情境 B — CI 中的寫程式 agent。拒絕網路與生產憑證；允許測試指令；hooks 擋住密鑰提交；黃金失敗測試必須變綠。

情境 C — 提示詞編輯後的成本回歸。比對前綴差異；檢查快取；衡量回合；回滾釘定；在框架裡加上成本斷言。

情境 D — 誤拒。為善意的醫療／法律常見問題準備安全評測切片；謹慎調整政策，不要關掉真正的拒絕。

情境 E — MCP 在資料裡回傳敵意指令。工具結果加分隔；忽略資料中的系統覆寫宣稱；允許清單動作；加上紅隊測試資料。

### 35.5 決策樹

自動化安全嗎？
```text
不可逆或跨租戶嗎？
 是 -> 人工關卡＋預設拒絕的工具
 否 -> 爆炸半徑小且可逆嗎？
 是 -> 帶稽核＋預算來自動化
 否 -> 先模擬／分階段推行
```

評測足以出貨嗎？
```text
關鍵安全測試綠燈嗎？
 否 -> 不要出貨
 是 -> 黃金品質在容差內嗎？
 否 -> 不要出貨／只以金絲雀推行並備妥緊急停止開關
 是 -> 出貨金絲雀 -> 盯線上指標
```

疑似注入事故：
```text
圍堵（停用工具／收緊允許清單） ->
保存日誌（已遮蔽） ->
識別途徑（使用者／檢索／工具） ->
修補＋新增評測 ->
若有客戶影響則對外溝通
```

### 35.6 考試陷阱

1. 憑感覺出貨。
2. 對資金移動只用提示詞做安全。
3. 為了除錯而記錄原始密鑰。
4. 為了修復誤拒而停用安全過濾器，卻沒有衡量。
5. 裁判模型為自己未經驗證的計畫打分。
6. 把批次折扣當成資安邊界。
7. 一次成功 demo 之後就把 MCP 改成全開放。
8. 提示詞變更沒有回滾計畫。
9. 把生產金鑰混進評測執行器。
10. 以為 `CLAUDE.md` 的「永不刪除」就能擋住刪除。

### 35.7 額外問答（Q41–Q55）

**Q41.** 變更生產系統提示詞的最低門檻是什麼？
**A41.** 版本升級、黃金評測通過、金絲雀、回滾註記——不是 playground 裡看起來比較好。

**Q42.** 如何評測會花錢的 agent？
**A42.** 模擬總帳；在模擬執行套件中斷言工具從未被呼叫；另做帶上限的分階段整合。

**Q43.** 行銷大量發信功能期間出現速率限制錯誤——架構修復方法？
**A43.** 佇列加上退避；不要盲目提高並行；若離線可考慮 Message Batches（批次 API）。

**Q44.** 護欄與權限的差別？
**A44.** 護欄常是模型／過濾器層；權限是硬的用戶端／伺服器強制。縱深防禦需要兩者。

**Q45.** 為什麼對抗性評測要小但永久？
**A45.** 它們能快速抓住安全回歸；又大又吵的集合會被忽略——整理高訊號攻擊。

**Q46.** 線上指標在離線評測之前先動——信任哪個？
**A46.** 兩邊都查；線上可能有干擾因素；離線可能過時。沒有歸因就不要盲目出貨或還原。

**Q47.** Claude Code 設定裡 API 金鑰該放哪？
**A47.** 環境或密鑰管理器——不是 `CLAUDE.md`、不是提交的設定、不是對話日誌。

**Q48.** 重構 agent 的成功指標是什麼？
**A48.** 測試通過加上 lint 乾淨加上範圍內的差異加上沒有碰禁用路徑——不是改了幾行。

**Q49.** 快取會造成資安問題嗎？
**A49.** 快取不會授予工具，但把密鑰快取進前綴或日誌是資料處理錯誤；多租戶系統絕不能共享內嵌租戶密鑰的前綴。

**Q50.** 多租戶提示詞快取設計規則？
**A50.** 共享前綴只等於非敏感的全域指令／工具；租戶資料放在不快取的回合裡。

**Q51.** 為什麼要隔離紅隊運行？
**A51.** 攻擊性提示詞與工具嘗試不該共享生產配額或生產憑證。

**Q52.** 擋住 git push，用 hook 還是權限？
**A52.** 兩者都能用；權限的 deny／ask 是宣告式的；hooks 允許自訂邏輯／稽核。常常併用。

**Q53.** 即時網頁工具造成評測不穩定——修復方法？
**A53.** CI 黃金運行中模擬網路；另留一小段即時冒煙。

**Q54.** 模型品質的錯誤預算是什麼？
**A54.** 回滾之前允許的回歸容忍——例如關鍵切片最多下降 X%。

**Q55.** 舉出資安審查中三個整合構件。
**A55.** 工具允許清單、MCP 伺服器清冊、釘定組合加上日誌遮蔽政策。

### 35.11 應用營運模式（額外深度）

佇列與優先順序：互動式使用者流量不該排在大批量評測工作後面挨餓。用獨立佇列或加權公平共享。

冪等消費者：帶工具的工作者必須能在至少一次交付下存活。把冪等鍵貫穿退款、工單更新與發信。

背壓：當模型 API 回 429，讓生產者變慢；不要熱重試去放大風暴。

設定即程式碼：把釘定組合放進 git；經 PR 晉升；禁止默默把 playground 複製到生產。

多主機現實：同一個應用可能呼叫 Anthropic API 與 Bedrock；抽象用戶端，但保留明確的主機釘定與功能旗標。

資料生命週期：為提示詞、工具追蹤與評測測試資料定義保留；按排程清除或匿名化。

人的因素：值班 runbook 必須寫回滾到哪個釘定，而不只是打開哪個儀表板。
