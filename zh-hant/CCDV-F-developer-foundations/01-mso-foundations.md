# MSO 基礎
## 模型選擇與最佳化基本功

> **免責聲明：** 為精讀而寫的原創備考筆記。依據**公開** Anthropic 文件中關於選模型、effort、上下文視窗、定價概念，以及快取／批次成本槓桿的內容——模型 ID 與價格會變；記住*決策準則*，考前再核對當前模型卡。

**主要對應：** 模型選擇與最佳化（**16.8%**）。
**也餵給：** 應用與整合（當題幹是「為成本／延遲挑 API 路徑」時）。

**怎麼讀：** 先學會三軸取捨（能力 × 延遲 × 成本），再練習在一個硬限制之下逼出唯一最佳答案。大多數 MSO 題是限制謎題，不是「哪個模型最聰明」。

---

## 1. 概覽

MSO（模型選擇與最佳化）是把工作**路由到正確智慧預算**的技能。在 Claude 上，這份預算透過下列方式表達：

1. **模型家族／層級**（前沿對中階對快速／便宜）。
2. **Effort／思考設定**（*同一個*模型要多認真）。
3. **上下文與輸出上限**（視窗大小、最大輸出 token）。
4. **服務路徑**（互動式 Messages 對串流對 Message Batches 對已快取前綴）。
5. **營運旋鈕**（釘定版本、別名對完整 ID、區域／雲端主機）。

公開文件把模型選擇框成平衡**能力、速度與成本**。近期的 Opus／Sonnet 等級模型多了一個 **effort** 參數，能在*同一個*模型裡用智慧換延遲／成本——常常是比跳層級更好的第一個槓桿。

**考試姿態：** 優先選能通過評測品質閘門的**最小且足夠**的模型／effort。當題幹強調成本或 p95 延遲時，過度購買智慧是常見的錯誤答案。

## 2. 關鍵地圖（閃卡）

| 概念 | 一句意思 | 考試觸發詞 |
| --- | --- | --- |
| 模型層級 | 能力階級（前沿／均衡／快速） | 「complex refactor」、「classify at scale」、「chat UI」 |
| Effort | 單一模型內部的測試時運算 | 「same model, better answers」、「lower latency same model」 |
| 上下文視窗 | 提示詞＋歷史能塞進多少 | 「long repo」、「1M context」、「truncate」 |
| 提示詞快取 | 重用前綴，讓重複呼叫更便宜／更快 | 「stable system+tools」、「multi-turn agent」 |
| Message Batches | 非同步大批量，有折扣 | 「overnight eval」、「latency tolerant」 |
| 串流 | 逐 token 的使用者體驗／提前取消 | 「TTR」、「user-facing chat」 |
| 釘定 | 凍結模型字串以求可重現 | 「prod regression」、「version drift」 |
| 別名 | 指向「最新 sonnet／opus／…」的會移動指標 | 「always newest」、「dev sandbox」 |

## 3. 深入筆記

### 3.1 三軸決策框架

每一個正式環境選擇都坐在一個三角形上：

```text
 能力
 /\
 / \
 / \
 / ? \
 /________\
 成本 延遲
```

- 當失敗很貴時，往**能力**移動（安全審查、跑數小時的 agent、困難的寫程式）。
- 當人類在等首個 token 或完整答案時，往**延遲**移動（客服聊天、編輯器行內建議）。
- 當量主導時，往**成本**移動（分類、萃取、夜間批次）。

**考試經驗法則：** 找出題幹硬限制的是哪一個頂角，然後刪去忽略它的選項。

### 3.2 模型家族心智模型（即使名稱會變仍然穩定）

公開選模型指引（2026）大致依工作負載形態組織：

| 工作負載形態 | 優先（概念上） | 為什麼 |
| --- | --- | --- |
| 數小時 agent、深度推理、大型重構、視覺很重的企業工作 | 前沿 Opus 等級（例如公開文件裡的 Claude Opus 5 家族） | 最高自主性與推理空間 |
| 每日寫程式、資料分析、內容、扎實的 agentic 工具使用 | Sonnet 等級 | 大多數應用最好的預設平衡 |
| 高 QPS 例行分類、簡單轉換、便宜迴圈 | Haiku 等級 | 速度與單位經濟 |
| 最長／最難的前沿 agent 執行（有提供時） | Fable 等級（坐在 Opus 之上的模型家族；Claude Code 的 `best` 別名會互動式解析到頂層） | 明確給最難的長時間任務 |

**不要背行銷口號。** 要背**適配**：

- **工具很重的寫程式 agent** → 中階到前沿＋適當 effort。
- **對黃金 schema 做結構化萃取** → 常常是中階＋嚴格 schema／工具；只有評測失敗才升級。
- **面對使用者的低延遲助理** → 更快層級，或同一層級配更低 effort；加串流。

### 3.3 Effort 作為模型內部旋鈕

公開文件把近期 Opus／Sonnet 模型上的 **effort** 描述成用智慧換延遲與成本。預設常常是 **high**；更高設定（例如有提供時的 `xhigh`、`max`）幫助吃重的 agentic／寫程式工作；更低設定幫助例行任務。

**營運模式：**

1. 釘定一個模型。
2. 從該模型**文件記載的預設**開始。
3. 只有當評測顯示系統性推理不足時，才提高 effort。
4. 當 p95 延遲／成本預算破掉、而品質仍然通過時，降低 effort。

**考試陷阱：** 題幹說「為了快取穩定／合約而保持同一個模型 ID」時仍去換模型——答案通常是**改 effort**，不是改模型。

**快取備註：** 改變思考設定會讓**訊息層級**的快取中斷點失效；工具／系統前綴那一段仍然可快取。預熱與正式流量之間對齊 effort／思考仍是安全營運規則——對不齊的預熱，會讓你的訊息層級條目沒被讀到。

### 3.4 上下文視窗與輸出上限

把上下文當**預算**，不要當垃圾場：

| 壓力 | 症狀 | MSO 回應 |
| --- | --- | --- |
| 歷史太長 | 截斷、指示遺失 | 壓縮摘要；把持久規則移出聊天 |
| 工具 schema 巨大 | 浪費前綴 token | 工具搜尋／延遲載入；更少工具 |
| 每回合都送大型文件 | 成本爆炸 | 快取穩定文件；檢索切片 |
| 需要長輸出 | JSON 做到一半被截斷 | 提高 `max_tokens`；結構化串流；任務切塊 |

公開材料強調大視窗（包括部分模型上的 **1M** 等級視窗）以及前沿模型上的高最大輸出。考試在乎的是：你**知道何時**該請求大視窗別名（長工作階段／大型儲存庫），何時檢索加快取比把所有東西塞進去更便宜。

### 3.5 仍然算「MSO」的成本槓桿

MSO 不只是「挑 Opus 還是 Sonnet」。有成本意識的答案常常組合：

1. **更小模型**（若品質撐得住）。
2. **更低 effort**（若品質撐得住）。
3. **提示詞快取**（穩定前綴：系統、工具、參考文件）。
4. **Message Batches**（延遲可以等時；公開文件：非同步大批量、相對同步有折扣；快取可疊加，但命中是盡力而為）。
5. **更短輸出**（要求簡潔；用 schema 約束）。
6. **避免改寫已快取前綴**（打亂工具順序、系統提示詞裡的時間戳、工作階段中途換模型）。

**批次對即時決策樹：**

```text
是否有使用者正在等這個回應（數秒內）？
 是 → 同步 Messages（若使用者體驗需要提早拿到 token，就加串流）
 否 → 是否有大量獨立請求、且 SLA 可容忍數小時？
 是 → Message Batches（＋共用的 cache_control，若有提供則偏好較長 TTL）
 否 → 同步加快取；考慮佇列＋工作者
```

值得記住的公開批次限制：沒有串流結果路徑、沒有僅限同步的速度模式、不能在批次裡面用 `max_tokens: 0` 預熱、有狀態的對話串參數通常不適用。

### 3.6 延遲槓桿

| 槓桿 | 效果 | 副作用 |
| --- | --- | --- |
| 更快的模型層級 | 更低 TTFT／總時間 | 可能掉品質 |
| 更低 effort | 更快 | 可能掉品質 |
| 串流 | 更好的*感知*延遲 | 總運算大致不變 |
| 提示詞快取命中 | 更快預填 | 需要穩定前綴 |
| 更小提示詞 | 更快 | 可能需要更好的檢索 |
| 平行工具呼叫（有支援時） | 牆鐘時間勝利 | 更多並行複雜度 |

**考試細微處：** 串流修的是**使用者體驗的等待**，不是單位成本。如果題幹講的是**帳單**，單靠串流很少是答案。

### 3.7 品質槓桿（表現不足時）

除非題幹禁止，否則按這個順序升級：

1. 修好**提示詞／上下文**（缺的限制、壞的例子、吵雜的工具）。
2. 加上**工具／模型上下文協定（MCP）**，讓模型能抓事實依據。
3. 提高 **effort**。
4. 升級**模型層級**。
5. 改**架構**（多步驟 agent、驗證模型、人工閘門）。

直接跳到最大模型是常見的干擾選項。

### 3.8 版本釘定對上別名

| 作法 | 何時用 | 風險 |
| --- | --- | --- |
| 完整帶日期／明確模型 ID | 正式環境、評測、合規 | 你必須規劃升級 |
| 別名（`sonnet`、`opus`、`haiku`、`best`、…） | 開發、「永遠最新」的沙箱 | 安靜的行為漂移 |
| Claude Code 別名（`opusplan`、`sonnet[1m]` 等） | 工作階段的工作流程偏好 | 為了 CI 可重現性仍應釘定 |

**正式環境檢查清單：** 在設定裡釘定模型字串；記進評測報告；艦隊升級前先做金絲雀；若依賴提示詞快取，絕不要在對話中途改模型。

### 3.9 路由模式（架構碰上 MSO）

**A. 靜態路由：** 產品介面用一個模型。操作簡單，最佳化有限。

**B. 分層路由：** 分類器或規則把容易的流量送到 Haiku 等級，困難的送到 Sonnet／Opus 等級。

**C. 級聯／升級：** 先試便宜路徑；信心低或 schema 驗證失敗時，在昂貴路徑上重試。

**D. 雙模型驗證：** 中階上的生成器；同一層或更高層的評論／驗證模型，用於高風險輸出。

題幹提到「90% 瑣碎工單、10% 新奇事故」時，幾乎總是要**分層或級聯**，不是「全部走前沿」。

### 3.10 雲端託管仍然貼著 MSO

公開 Academy 主題包括 Bedrock 與 Vertex／Agent Platform。會出現在情境題裡的選擇差異：

- **模型 ID 格式**依主機而異（Anthropic API 名稱對 Bedrock 推論設定檔 ARN 對 Vertex 版本名稱）。
- **功能落差／對等** — 確認該主機上的工具、快取、批次與 beta 可用性。
- **資料落地／IAM** — 即使另一個區域有更新的 SKU，也可能被迫待在某個區域。

若題幹的硬限制是**資料落地**，正確的模型選擇是「已核准的區域 SKU」，不是全球最新的 ID。

### 3.11 迷你情境演練

**情境 A — 客服聊天機器人，p95 < 2s，中等品質。**
優先快速／中階層級、較低到預設 effort、串流、快取系統＋工具前綴。避免前沿＋max effort。

**情境 B — 過夜評測 5 萬則提示詞。**
Message Batches；相同的 `cache_control` 區塊；若有提供則用較長快取 TTL；除非評測需要前沿，否則用中階。

**情境 C — 自主、跑數小時的寫程式 agent。**
前沿或強 Sonnet／Opus 等級配提高的 effort；視需要用大上下文；快取工具；執行中途不要抖動換模型。

**情境 D — 「在系統提示詞加上時間戳」之後成本暴衝。**
快取破壞。修好前綴穩定；不要先跳到更便宜的模型。

### 3.12 證明 MSO 決策的指標

一起追蹤，否則你會最佳化錯的軸：

| 指標 | 在問 |
| --- | --- |
| 任務成功／評分量規分數 | 品質有撐住嗎？ |
| 每次成功任務成本 | 不是每次原始呼叫的成本 |
| p50／p95 延遲 | 人類在等的路徑 |
| 快取命中率 | 前綴工程健康度 |
| 升級率 | 路由有校準嗎？ |
| 安全事故率 | 更便宜的路徑有跳過過濾器嗎？ |

## 4. 決策樹與表格

### 4.1 主選擇樹

```text
起點：若我們選錯，最先壞掉的是什麼？
│
├─ 安全／法務／高爆炸半徑的失敗
│ → 更高能力＋強護欄；需要時加上人工關卡
│
├─ 有人在等（互動式）
│ → 偏好更快層級或更低 effort；串流；快取前綴
│ → 只有在品質評測失敗時才升級模型
│
├─ 大批量／離線
│ → 批次＋共用快取；用評測樣本把模型調到剛好
│
└─ 長時間 agentic 寫程式
 → 有能力的模型＋足夠 effort；穩定工具；釘定版本
```

### 4.2 Effort 對上換模型

| 觀察 | 第一個動作 | 避免 |
| --- | --- | --- |
| 同一個模型，多步驟計畫很弱 | 提高 effort | 只是隨機把提示詞拉長 |
| 同一對話串做模型 A／B 測試後快取未命中 | 不要在對話串中途換 | 「第 12 回合就試 Opus」 |
| 簡單任務太貴 | 降低 effort 或更小模型 | 什麼都留在前沿 |
| 困難的 5% 出現品質斷崖 | 把困難的 5% 往上路由 | 升級 100% 流量 |

### 4.3 成本堆疊（小心組合）

| 堆疊元素 | 典型收益 | 需要 |
| --- | --- | --- |
| 更小模型 | 大 | 評測對等 |
| 更低 effort | 中 | 評測對等 |
| 提示詞快取讀取 | 在 agent 上很大 | 穩定、有序的前綴 |
| 批次折扣 | 在大批量上很大 | 能容忍延遲 |
| 更短輸出 | 中 | 清楚指示／schema |

## 5. 考試陷阱

1. 題幹強調成本或延遲時，仍**挑最聰明的模型**。
2. 把**串流當省錢手段**（它不是）。
3. 把 **Batches 用在聊天 UI**（延遲階級錯了）。
4. 依賴快取時，仍在**對話中途改工具或模型**。
5. 把**易變資料**（時間戳、每用戶機密）放進已快取的系統前綴。
6. 正式環境用**別名**卻沒有釘定＋金絲雀故事。
7. **忽略主機／區域限制**（Bedrock／Vertex 資料落地）。
8. 最佳化**每 token 成本**而不是**每次成功任務成本**。
9. 用**提高 max_tokens** 去「修」壞結構——應優先用 schema 與切塊。
10. 把 **effort 與模型層級當成同一個旋鈕**——它們是分層的。

## 6. 自測問答（20）

**Q1.** 產品需要 FAQ 聊天達到亞秒級感知回覆。中階層級模型的品質已經「夠好」。最佳的第一個最佳化是什麼？
**A1.** 保留中階層級模型，啟用**串流**，確保穩定系統／工具前綴的提示詞**快取**命中，若品質評測仍通過則考慮**更低 effort**。不要跳到前沿。

**Q2.** 你必須在明天早上前為 20 萬份文件評分；沒有使用者在等。最佳 API 模式？
**A2.** **Message Batches**，可選擇搭配共用已快取上下文，以及有提供時用較長快取 TTL。

**Q3.** 部署後快取命中率崩掉。差異比較顯示工具定義每次請求都隨機排序。根因？
**A3.** **前綴不匹配**——非確定性的工具順序會破壞提示詞快取。把工具確定性地序列化。

**Q4.** 評測顯示模型在困難寫程式任務上規劃不足；採購要求模型 ID 必須固定。槓桿？
**A4.** 提高 **effort**（並改善提示詞／工具）。若限制禁止，不要改模型。

**Q5.** 為什麼在對話串中途從 Sonnet 換到 Opus，對 agent 工作階段的傷害會超過原始價格？
**A5.** 快取是**以模型為範圍**的；切換會讓已快取前綴失效，並可能讓行為不穩。

**Q6.** 儘管 QPS 很高，何時 Haiku 等級仍是*錯誤*答案？
**A6.** 當題幹需要深度多步驟自主性、細緻政策判斷，或評測顯示小模型撐不住的高答錯代價推理時。

**Q7.** CI 裡的別名 `sonnet` 在一次安靜升級後開始失敗。如何預防？
**A7.** 在 CI／正式環境**釘定**明確模型 ID；只在可接受漂移的地方用別名。

**Q8.** 批次工作有 `cache_control` 但快取命中仍低。可能漏了什麼？
**A8.** 各項目前綴不完全相同、快取 TTL 對非同步處理太短，或期待保證命中（文件：批次裡是**盡力而為**）。

**Q9.** 批次處理需要串流嗎？
**A9.** 不需要——批次結果是以已完成結果／檔案取回，不是即時 token 串流。

**Q10.** 有 1M 上下文選項。每個應用都該啟用嗎？
**A10.** 不該——只在工作階段／儲存庫真正需要時用；否則檢索加快取常常更便宜、更清楚。

**Q11.** 級聯路由：什麼訊號該觸發升級？
**A11.** 驗證失敗、低自我信心分數、政策風險旗標，或評分量規失敗——不是「隨機 10%」。

**Q12.** 每次呼叫成本下降了，但使用者抱怨上升。缺了哪個指標？
**A12.** **任務成功／每次成功任務成本**（也可能是安全事故）。

**Q13.** 用 `max_tokens: 0` 預熱——目的？
**A13.** 填入提示詞快取但不產出答案（同步路徑）；依公開批次限制，批次裡面不可用。

**Q14.** 預熱與正式流量的思考／effort 不同。症狀？
**A14.** 在一種思考設定下寫入的訊息層級快取條目，對不上正式流量（工具／系統前綴仍可能命中）→ 看起來像「快取壞了」的部分未命中。對齊設定。

**Q15.** 只走 Bedrock 的客戶被鎖在某個區域。最新 Anthropic API 模型那邊沒列出。正確動作？
**A15.** 選符合政策的**已核准區域**模型／設定檔；規劃對等測試——不要違反政策去發明跨區域呼叫。

**Q16.** 「讓它更便宜」題幹；agent 每回合用 40 個工具。強的 MSO 動作？
**A16.** 保持工具清單穩定，但用**延遲載入／工具搜尋**模式，讓完整 schema 不必總是展開——再加上快取穩定的 stub 前綴。

**Q17.** 雙模型驗證模式——何時合理？
**A17.** 高風險輸出（法律／醫療摘要、正式環境遷移），且驗證成本 < 答錯代價時。

**Q18.** p95 延遲很差；快取命中率 5%。第一個調查？
**A18.** 前綴穩定（系統／工具排序、易變系統文字），不是立刻「用更大實例去買同一個錯誤」。

**Q19.** 為什麼提高 effort 可能讓成本增加超出預期？
**A19.** 更多 token／工具迴圈／思考——帳單隨測試時運算上升，不只是價目表價格。

**Q20.** 把這一章對應到考試配分比重。
**A20.** **模型選擇與最佳化 16.8%** 的核心，再加上其實是成本／延遲路由題的整合題。

## 9. 擴充深挖 — 生產環境 MSO playbook

### 9.1 寫一份 MSO 政策文件（資深工程師真正會出貨的東西）

一個「在 PR 裡臨時挑模型」的團隊，會在整合風格情境題裡失敗。編碼一份簡短的 **MSO 政策**：

1. 互動式產品介面的**預設模型**。
2. 離線評分的**批次模型**。
3. 工具迴圈寫程式／維運 agent 的 **agent 模型**。
4. 失敗／高嚴重程度的**升級模型**。
5. 各介面的 **effort 預設**。
6. **釘定規則**（正式環境用完整 ID；別名只允許在個人沙箱）。
7. **評測關卡** — 沒有黃金標準集差異報告，就不改艦隊模型。
8. **快取合約** — 有序工具、凍結系統區段、前綴變更的負責人。

考試喜歡聽起來像**治理**、不是氛圍的答案：「更新釘定設定＋金絲雀＋評測報告」，不是「在聊天 UI 裡換成 Opus」。

### 9.2 不必背價目表的 token 經濟

你不需要精確的美元圖表。你需要**相對**推理：

- 公開 Anthropic 定價頁上，輸出 token 通常比輸入 token 貴——所以**冗長**會傷。
- 快取**寫入**比快取**讀取**貴（概念上：付錢填入，重用時省下）。
- 批次折扣適用於合格的大批量工作；它們不會神奇修好膨脹的提示詞。
- 工具結果會再進入上下文——話多的工具是隱藏的成本放大器。

**實用考試啟發式：** 若兩個選項都「能用」，選那個能減少**重複的未快取預填**或**不必要輸出**的，不是那個只在系統提示詞裡換形容詞的。

### 9.3 長上下文策略矩陣

| 策略 | 最適合 | 失敗模式 |
| --- | --- | --- |
| 把完整文件塞進提示詞 | 很小、穩定的參考 | 成本＋分心 |
| 提示詞快取穩定語料 | 許多請求共用文件 | 一改就破壞 |
| RAG／檢索切片 | 大型、會變的語料 | 切塊差 → 答錯 |
| 摘要記憶 | 跨越多日的長 agent | 摘要漂移 |
| 1M 等級視窗 | 真正巨大的單一工作階段 | 成本；仍不是塞垃圾上下文的藉口 |

**教學重點：** 更大視窗不能替代**上下文工程**。考試上的公開提示與上下文主題，把「什麼該進上下文」當成貼著 MSO 的一等技能。

### 9.4 Agent 迴圈成本控制

Agentic 工作階段會把回合數乘上去。成本驅動因子：

1. **工具 schema 大小 × 回合數**（這就是延遲載入／工具搜尋重要的原因）。
2. **每回合重讀大型檔案**卻沒有快取策略。
3. **無界迴圈**，沒有步驟預算或停止條件。
4. 每個微步驟都用**過高 effort**（分類、再計畫、再編輯——不是每一步都需要 max effort）。

**模式：** 用有能力的模型做**計畫**回合；只有在你接受複雜度時，才考慮用更便宜模型做**狹窄機械**回合——許多團隊為了快取穩定而維持一個模型。除非題幹明確要求路由，考試常常偏好**一個穩定模型＋effort／提示詞紀律**，而不是聰明的多模型抖動。

### 9.5 當評測與直覺不一致

假設線上使用者「喜歡」更聰明的模型，但離線評分量規分數持平、成本卻 +40%。CCDV-F 風格的判斷：

- 優先採對齊業務結果的標註集上的**可量測**品質。
- 分段評測（易／難）。也許只有困難區段值得前沿。
- 分開看**安全**指標——一個會洩漏 PII 的有趣模型，不是升級。

### 9.6 遷移 playbook（模型升級）

```text
1. 凍結黃金評測集＋正式流量的影子樣本
2. 在金絲雀設定中釘定候選模型
3. 比較：成功率、延遲、每次成功成本、安全旗標、快取命中率
4. 若 effort 預設不同，先調 effort，再怪模型
5. 備妥回滾 ID 後再向前推行
6. 更新 runbook 與 CLAUDE.md／服務設定文件
```

錯誤答案模式：「週五全域改別名。」

### 9.7 互動對分析對 agentic 設定檔（速查表）

| 設定檔 | 延遲 | 成本敏感度 | 典型旋鈕 |
| --- | --- | --- | --- |
| 互動式使用者體驗 | 關鍵 | 中 | 串流、快速層級／effort、緊湊提示詞 |
| 分析大批量 | 低 | 關鍵 | Batches、快取、把模型調到剛好 |
| Agentic 工具 | 中 | 中高 | 穩定工具、快取、步驟預算、有能力的模型 |
| IDE／Claude Code 工作階段 | 中 | 中 | 給人類的別名可以；CI 無頭模式要釘定 |

### 9.9 反模式畫廊

1. **什麼都用神模型** — 摧毀毛利；掩蓋糟糕提示。
2. **過早的多模型網** — 沒有評測證據的營運複雜度。
3. **把快取當成可選** — 對 agent 把快取當可有可無。
4. **無評測替換** — 經典正式環境停機啟動包。
5. **延遲劇場** — 微調 TTFT，同時 agent 做 30 次不必要的工具呼叫。
6. **上下文囤積** — 「以防萬一」貼上整份 wiki。
7. **正式環境的別名輪盤** — 說不清楚的週一回歸。

### 9.13 再五題問答

**Q21.** 為什麼 `opusplan` 風格別名會出現在 Claude Code，卻不該出現在你的後端 API 服務？
**A21.** 它編碼的是**工作階段工作流程**（用一個模型計畫、用另一個執行）。後端服務通常需要明確釘定的 ID 與刻意的路由邏輯，而不是互動式別名。

**Q22.** 你的同步路徑用自動快取；預熱用了帶頂層自動快取的佔位使用者訊息。命中失敗。為什麼？
**A22.** 自動快取可能以**最後一個**區塊（那個佔位）為鍵。預熱應在共用系統／工具前綴上用**明確**中斷點，對齊正式流量。

**Q23.** 降低 `max_tokens` 一定降低成本嗎？
**A23.** 它上限了**潛在**輸出成本並防止失控，但若模型仍吐到接近上限，品質可能受害；搭配「要簡潔」與 schema。它不降低輸入／快取成本。

**Q24.** 利害關係人要求用「最強模型」做分類器，Haiku 等級已經有 99.5%。回應？
**A24.** 留在 Haiku 等級；把力氣花在那 0.5% 錯誤的資料／規則上，或只對那些案例級聯——MSO 是限制之下的足夠性。

**Q25.** 說出兩個 Bedrock 與 Anthropic API 功能對等對 MSO 重要的理由。
**A25.** （1）某個快取／批次／工具功能可能不可用，因而改變最佳設計；（2）模型 SKU 名稱不同，所以釘定與 runbook 必須依主機而定。

## 11. 主要學習深化 — 給應用與整合題幹的 MSO

應用與整合佔 CCDV-F 的 **33.1%**。那些題很多是*打扮成 API 設計的 MSO 決策*：要釘定哪個模型字串、要不要串流、要不要批次、如何讓快取保持熱、如何避免設定漂移。這一節訓練那個重疊，讓第 01 章成為主要學習來源，不是快速瀏覽。

### 11.1 模型身分機制（考試穩定概念）

公開 Anthropic 模型文件強調：

| 想法 | 對建造者的意思 | 考試觸發 |
| --- | --- | --- |
| 釘定快照 ID | 你可以重現的特定模型發行 | 「prod regression」、「no surprise upgrades」 |
| 便利別名（舊模式） | 可能解析到帶日期 ID 的指標 | 「always latest」、「sandbox only」 |
| 較新世代的不帶日期 ID | 仍是**釘定快照**，不是常青會移動目標 | 不要假設不帶日期＝自動升級 |
| 主機特定 SKU | Bedrock／Vertex／Foundry ID 與 Claude API 不同 | 多雲客戶；資料落地 |
| Models API 內省 | 查詢 `max_input_tokens`、`max_tokens`、能力 | 不必寫死的能力閘控 |

**主要學習規則：** 正式環境在設定裡釘定明確模型識別碼。別名與「最新」行銷名稱屬於實驗室與互動式 Claude Code 工作階段，除非你刻意接受漂移。

### 11.2 Effort、自適應思考與延伸思考（概念地圖）

近期公開文件區分：

1. **Effort**（`output_config.effort`／相關介面）——旋鈕控制模型有多認真；API 預設是 **high**，而 Claude Code 預設是 **xhigh**（寫程式／agentic 工作的甜蜜點）。
2. **自適應思考** — 模型自己決定何時思考（較新的 Opus／Sonnet／Fable 線）。
3. **延伸思考**（`thinking.type: "enabled"`） — 部分模型上仍存在的較舊／明確思考控制（例如公開比較表裡的 Haiku 4.5）。

**決策紀律：**

```text
要在同一個模型 ID 上得到更好的答案？
 → 先提高 effort／放寬思考預算
要在同樣的品質門檻下降低延遲／成本？
 → 降低 effort；若評測仍然通過，再考慮更小的層級
需要不同的能力類別（視覺等邊緣能力、自主性、最便宜的高 QPS）？
 → 改模型層級——並把它當成一場遷移（釘定、快取、評測）
```

**快取耦合：** 思考設定變更會讓**訊息層級**快取中斷點失效（工具／系統前綴仍可快取）。讓預熱與正式思考／effort 對齊，快取每一層才真的會被讀到。

### 11.3 服務路徑矩陣（整合 × MSO）

| 路徑 | 人類在等？ | 成本姿態 | 串流？ | 典型用途 |
| --- | --- | --- | --- | --- |
| 同步 Messages | 是／近即時 | 完整同步費率 | 可選 | 聊天、agent、線上工具 |
| 同步＋串流 | 是 — 使用者體驗在乎 TTFT | 同一運算階級 | 是 | 面對使用者的助理 |
| 同步＋提示詞快取 | 是，重複前綴 | 預熱後更便宜 | 可選 | 有穩定系統＋工具的 agent、應用 |
| Message Batches | 否（數小時可以） | 折扣非同步 | 否 | 評測、分類、大批量生成 |
| 批次＋快取 | 否 | 折扣可以**疊加**；命中盡力而為 | 否 | 共用前綴的夜間工作 |

**當成判斷記住、不是 trivia 的公開批次限制：**

- 批次結果生成時不能串流。
- 批次裡的快取命中是**盡力而為**（並行非同步工人）。
- 用 `max_tokens: 0` 預熱是**同步**模式——不要預期在批次裡面。
- 部分模型經 beta header 支援延伸批次最大輸出（核對現行文件）；考試上不要發明 header——要知道同步與批次上限可以不同。

### 11.4 提示詞快取作為 MSO 槓桿（深度）

快取不會縮小上下文；它折扣**重複的前綴 token**，且命中時常常改善 TTFT。

**前綴順序（概念上）：** tools → system → messages，直到 `cache_control` 中斷點。

**TTL 主題（公開）：**

- 預設短暫生命期常被討論成約 **5 分鐘**，讀取時刷新。
- 較長 TTL（例如 **1 小時**）在命中間隔很長時可用，但有額外成本。
- 生命期從寫入／讀取的那次請求起算——長串流回應會消耗 TTL 牆鐘。

**什麼會讓快取失效或未命中（學習清單）：**

- 已快取前綴位元組的任何變更（系統文字、工具 JSON 順序／名稱、插入的時間戳）。
- 對話串中途改模型 ID。
- 思考／effort 設定與你寫入的條目不匹配（讓訊息層級中斷點失效；工具／系統前綴不受影響）。
- 自動快取以預熱佔位使用者回合為鍵（預熱應在共用系統／工具上用**明確**中斷點）。
- 把工具集重排當成「模式切換」。

**MSO 考試句：** 若題幹說成本在「我們為除錯在系統提示詞加上時間戳」之後暴衝，修正是從已快取前綴拿掉易變欄位——不是買更便宜的模型。

### 11.5 上下文視窗策略作為最佳化

公開模型卡顯示現行 Opus／Sonnet／Fable 線有 **1M** 等級視窗，部分快速模型視窗較小。考試在乎*策略*：

| 情況 | 優先 |
| --- | --- |
| 帶大型儲存庫的數小時 agent | 大視窗模型＋壓縮＋檢索；不要每回合傾倒整個 monorepo |
| 穩定政策＋文件 | 快取它們；檢索易變切片 |
| 50+ 工具 | 工具搜尋／延遲載入＋快取 stub 清單 |
| 便宜高 QPS 萃取 | 更小／更快模型＋嚴格 schema；大視窗若你填滿它才是浪費錢 |

**規則：** 更大視窗是允許你多拿一些——不是要求你多送一些。

### 11.6 以 MSO＋整合出現的路由架構

1. **靜態路由：** 產品介面一個釘定模型。
2. **級聯：** Haiku／Sonnet 嘗試 → 低信心／驗證器失敗時升級到 Opus。
3. **分段路由：** 依租戶層級、地區或風險階級用不同模型。
4. **計畫／執行拆分：** 更強模型計畫；更快模型執行工具呼叫（Claude Code 別名互動式編碼這個；服務要明確實作）。
5. **離線／線上拆分：** 分析用 Batches；使用者體驗用同步。

**陷阱：** 沒有預算的級聯會變成意外的到處都是 Opus。永遠上限升級次數並記錄原因。

### 11.7 考試出題者喜歡的成本會計

用**單位經濟**想，不是發票截圖：

```text
success_adjusted_cost = (input + output + cache_write + cache_read + tool_overhead) / successful_task
```

- 快取**寫入**比基礎輸入貴；它們在命中時回本。
- 批次折扣適用於合格 token；與快取疊加被允許，但命中是機率性的。
- Agent 迴圈把回合數乘上去——「便宜」模型用 3× 回合，可能輸給 1× 回合的更強模型。
- 輸出 token 常常比輸入貴——schema 與「要簡潔」是 MSO 控制。

### 11.8 釘定、棄用與遷移

公開文件維持棄用／遷移指引。主要學習習慣：

1. 在環境／設定裡釘定模型 ID，不要散落在原始碼檔案。
2. 為每個主機維持一份**相容性矩陣**（API 對 Bedrock 對 Vertex 功能旗標）。
3. 遷移順序：黃金評測 → 影子流量 → 金絲雀釘定 → 完整切換上線 → 刪除舊釘定。
4. 沒有二分除錯計畫時，絕不要在同一發行同時改模型、提示詞與工具。

### 11.9 整合×MSO 情境演練（原創）

**情境 A — 客服聊天，p95 TTFT SLA。**
串流；優先 Sonnet 或 Haiku 等級；品質撐得住就用中／低 effort；快取穩定系統＋工具；**不要**批次。

**情境 B — 夜間對 200 萬張工單做已遮蔽 PII 的分類。**
Message Batches；最小足夠模型；在指示＋標籤分類法上共用 `cache_control`；接受盡力而為的快取命中；不要串流。

**情境 C — 寫程式 agent 碰上不穩定的困難錯誤。**
釘定 Opus 等級；跳到更稀有頂層模型之前先提高 effort；為快取保持工具 schema 穩定；壓縮歷史；用測試（工具）驗證，不是氛圍。

**情境 D — 多雲企業，歐盟資料落地。**
MSO 包括推論跑在**哪裡**。即使全球路由更快，也要選滿足政策的區域端點；確認該主機上的功能對等（快取／批次／工具）。

**情境 E — 「有幫助」的重構後快取未命中風暴。**
對請求前綴做差異比較；找工具重排、動態日期、插入系統文字的實驗旗標，或 SDK 升級後的 effort 預設變更。

| 指標 | 為什麼 |
| --- | --- |
| 任務成功率（評測＋線上） | 品質閘門 |
| p50／p95 TTFT 與總延遲 | 使用者體驗／SLA |

### 11.11 額外問答（Q26–Q35）

**Q26.** 產品經理為了「一致性」想用同一個模型做聊天與過夜評測。MSO 反駁是什麼？
**A26.** *品質門檻*的一致性可以用共用評分量規與重疊評測；服務路徑不同。聊天需要同步／串流；過夜應批次。若品質需要，你仍可在兩條路徑釘定同一個模型 ID——但不要強迫一種服務模式。

**Q27.** 何時選 1 小時快取 TTL 而不是預設短 TTL？
**A27.** 當共用前綴的請求間隔長過短 TTL（尖峰流量、僅營業時間的工具），且額外寫入／儲存成本勝過重複完整預填未命中時。

**Q28.** 你的 Bedrock 部署缺少你在 Claude API 用過的 beta 工具功能。正確回應？
**A28.** 依該主機的功能矩陣重新設計（或把那一切片跑在支援它的主機上）。不要假設 SKU 名稱對等就代表功能對等。

**Q29.** 串流更便宜嗎？
**A29.** 本質上不是。它改善感知延遲並允許取消；產生的輸出仍按 token 計費。

**Q30.** SDK 升級後 effort 預設變了、成本上升。第一個檢查？
**A30.** 在設定裡明確把 effort 設回先前已驗證的值；重跑評測；確認快取命中率（不匹配也可能讓快取未命中）。

**Q31.** 大上下文視窗但 Haiku 等級模型——何時仍是錯的？
**A31.** 當任務需要評測顯示 Haiku 失敗的前沿推理／自主性時——視窗大小不能替代能力層級。

**Q32.** Agent 迴圈燒預算時，第一個 MSO 動作是什麼？
**A32.** 加上停止條件、工具預算與進度檢查；然後才考慮能用更少回合完成的更強模型。

**Q33.** 為什麼在 Claude Code 與後端服務釘定方式不同？
**A33.** Code 工作階段可能用工作流程別名與使用者 `/model` 切換；後端需要為 SLO、快取與稽核做確定性釘定。

**Q34.** 快取寫入加價對命中節省——何時第一天就該快取？
**A34.** 當同一個前綴會被很快重用時（agent、多輪應用、共用工具 schema）。一次性獨特提示詞可能回不了本。

**Q35.** 說出三個會改變你選哪個模型的整合功能。
**A35.** 需要串流使用者體驗；需要批次成本結構；需要只在某些模型線上穩定的工具／MCP 功能——再加上主機／區域限制。

## 12. LLM 基礎入門（考試藍圖技能 5.2%）

*2026-08-23 新增——官方 LLM 基礎陳述測驗「token、上下文視窗、取樣、非確定性、下一個 token 生成……以及基本提示技術（zero-shot、single-shot、multi-shot）」。這份入門補上那個缺口。*

### 12.1 模型實際上怎麼生成

- **Token** 是一切的單位：模型讀寫 token（子詞塊——英文平均大約一個字的 3/4），計費、上下文視窗與 `max_tokens` 都用它們計數。程式碼、JSON 與非英文文字的分詞效率低於普通英文敘述文字。
- **下一個 token 生成：** 模型一次產出一個 token，每個選擇都以整個可見上下文（提示詞＋目前已生成的一切）為條件。沒有在 token 之外的前瞻「計畫」；長結構化輸出會在結尾失敗，因為每一步都會複合。
- **取樣與非確定性：** 每一步模型對可能的下一個 token 有機率分布，並從中*取樣*——這就是為什麼兩次相同請求可以產出不同答案。歷史上，`temperature`／`top_p`／`top_k` 塑造那個分布。**現況：** 在 Opus 4.7+、Opus 5、Sonnet 5 與 Fable 等級模型上，這些取樣參數已**移除**（帶它們的請求會被拒絕）；它們只留在較舊模型上（4.6 世代、Haiku 4.5）。
- **確定性陷阱：** `temperature: 0` 從不保證位元組完全相同的輸出，而且在現行模型上這個旋鈕根本不存在。若題幹需要可重複結構，正確槓桿是 **schema／結構化輸出、驗證器，以及 few-shot 錨點**——不是取樣設定。

### 12.2 樣本數術語（精確定義這些）

| 術語 | 意思 | 何時用 |
| --- | --- | --- |
| **Zero-shot（零樣本）** | 只有指示；沒有做過的例子 | 任務對模型來說常見／容易；讓提示詞短且可快取 |
| **Single-shot（單樣本／one-shot）** | 恰好一個做過的例子 | 格式不尋常但一致；一個例子便宜地錨定形狀 |
| **Multi-shot（few-shot，少樣本）** | 數個做過的例子 | 邊界案例、標籤邊界或內部風格重要；挑多樣、高訊號的例子（邊界案例 > 快樂路徑） |

**MSO 角度：** 例子活在提示詞裡，所以每一槍都在每次呼叫上花 token——把例子區塊**穩定**放在已快取前綴裡，並修剪不再賺回 token 的例子。

### 12.3 自測問答（Q36–Q40）

**Q36.** 為什麼兩次相同的 API 呼叫會回不同措辭？
**A36.** 輸出是從下一個 token 機率分布**取樣**的——非確定性是固有的，不是錯誤。

**Q37.** 同事在現行 Opus 等級模型上設 `temperature: 0`「為了確定性 JSON」。兩個問題？
**A37.** 取樣參數在現行模型上已移除（請求會出錯），而且即使歷史上 temp 0 也不保證相同輸出。用 schema＋驗證。

**Q38.** 分類提示詞只在模糊邊界案例失敗。不是升級模型的 zero-shot 修正？
**A38.** 改走 **multi-shot**：加上幾個正好坐在令人困惑邊界上的例子。

**Q39.** 為什麼 2,000 字英文提示詞可能比 500 行 JSON 花更少 token？
**A39.** 分詞效率不同——敘述文字比稠密結構化文字更能壓進 token。

**Q40.** 高流量已快取端點的 few-shot 例子該放哪？
**A40.** 放在穩定的已快取前綴（與系統／工具一起），請求之間不變——編輯一個例子會破壞快取。

## 13. 快速模式（考試藍圖具名的模型選項——要知道它存在以及何時用）

*2026-08-23 新增。官方 LLM 基礎陳述把 **快速模式** 與延伸思考、自適應思考、effort 並列；本包先前省略了它。下列事實快取於 2026-08——研究預覽功能，考前請核對當前文件。*

**它是什麼：** **同一個模型**以最高約 2.5× 的輸出 token／秒運行，採**溢價定價**（例如 Opus 5 fast 大約是標準 Opus 5 每 MTok 費率的 2×）。它是同一智慧上的*速度／價格*交易——不是更小模型，不是品質變更。

**機制（概念上）：** 只在 **Claude Opus 5 與 Opus 4.8** 上作為研究預覽提供。請求按呼叫選擇加入：beta messages 端點＋快速模式 beta 旗標＋頂層 `speed: "fast"` 參數；回應用量會回報實際服務的速度。快速模式有**自己的速率限制**，與標準流量分開。

**它不可用的地方（高訊號考試事實）：**

- 不在 Bedrock／Vertex／Foundry——只在 Claude API（以及託管 agent 工作階段）。
- 不能與 **Batch API** 併用（批次是能容忍延遲的路徑；快速模式是延遲關鍵的路徑）。
- 不能與優先容量層級併用。

**營運判斷：**

```text
有人在等、且輸出長度主導延遲、且預算允許溢價？
 是 → 快速模式候選（同一模型，約 2.5× 輸出速度、約 2× 價格）
 否 → 先用更便宜的槓桿：串流（感知延遲）、快取命中（TTFT）、
 更低 effort、更快層級
遇到快速模式 429：依指示的延遲重試，或退回標準速度——
 並記住切換速度會讓提示詞快取條目失效。
```

**何時它勝過降層級：** 任務需要前沿品質（降級會讓評測失敗），但使用者感覺得到生成時間——例如長程式碼審查或即時串流給等待中專家的草稿文件。

### 13.1 自測問答（Q41–Q45）

**Q41.** 快速模式對上換成 Haiku 等級——核心差異是什麼？
**A41.** 快速模式在更高輸出速度與更高價格下保持**同一個模型的品質**；換層級是用品質換速度／成本。

**Q42.** 你能用快速模式跑過夜 20 萬文件批次來「更快做完」嗎？
**A42.** 不能——快速模式不能與 Batch API 併用，而且批次工作本質上能容忍延遲；它是錯的槓桿。

**Q43.** 只走 Bedrock 的企業要求快速模式。回應？
**A43.** 那邊沒有（Claude API 研究預覽，只限 Opus 5／Opus 4.8）——改在他們的主機上提供串流、快取、effort 調校或層級選擇。

**Q44.** 快速模式請求開始回 429，而標準 Opus 流量沒事。為什麼可能？
**A44.** 快速模式有**自己分開的速率限制**；等指示的延遲後重試，或降回標準速度（接受速度切換造成的快取失效）。

**Q45.** 題幹說「降低帳單」——快速模式會是答案嗎？
**A45.** 不會。快速模式為速度提高單位價格。成本題幹要更小模型、更低 effort、快取、批次、更短輸出。
