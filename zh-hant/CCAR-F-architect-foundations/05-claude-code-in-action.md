# Claude Code 實戰 — 主要備考筆記

> **免責聲明：** 這些是用於 Claude 認證準備的**原創**備考筆記。它們對齊 [Claude Code in Action](https://academy.claude.com/courses/claude-code-in-action) 的**公開**課程大綱（僅目標與模組主題）。它們**不是** Claude Academy 課堂傾倒、逐字稿或投影片原文。完成官方課程仍是小考的真相來源。請在現行 Claude Code 文件核對 CLI 旗標與 UI 標籤——名稱會演進。

**適合對象：** 已經在用 Claude Code 處理單次提示、想要更長、更少監督、全團隊適用工作流程的開發者。

**先修（課程）：** 用 Claude Code 做一次性任務；基本 Git 與命令列。

**如何使用這些筆記：** 一次讀一個大節，然後不回頭翻頁、直接回答自我檢核。把表格當閃卡。階梯 **掌舵 → 設定 → 自動化 → 驗證／分享** 是大多數情境題的主幹。

---

## 1. 課程地圖（公開目標）

公開頁面把內容框成四個成果群組（約 9 堂課、1 次小考）：

1. **掌舵工作** — 計畫模式、定向壓縮、倒回、親手操作對上自主的目標／迴圈執行、安全的平行化。
2. **設定 Claude** — 精簡的 `CLAUDE.md`、Skills、權限模式、給不能跳過的規則用的 hooks。
3. **把重複工作自動化** — Anthropic 基礎設施上的例行排程、你管線裡的無頭模式、PR／GitHub Action 接線。
4. **驗證與分享** — 按照你監督得多少，等比例地驗證無人監督的執行；用真正的測試把關；把受信任的設定打包成 Plugin。

**心智模型：** Claude Code 是一個帶工具的 agentic 編碼迴圈（檔案編輯、bash、搜尋等）。考試裡你的任務不是「寫更長的提示詞」，而是針對工作的風險**選對控制面**。

| 層 | 它回答的問題 | 強項 |
| --- | --- | --- |
| 掌舵 | *這個工作階段*該做什麼？ | 暫時性控制 |
| 設定 | Claude *永遠*該知道／被允許什麼？ | 持久 |
| 自動化 | 這件事如何不用我打字就能跑？ | 維運 |
| 驗證／Plugins | 我們如何信任並重用這個設定？ | 保證＋可攜性 |

記住：很多考試型題目問的是哪一層**建議**、哪一層**強制執行**。

## 2. 掌舵長時間的工作階段

### 2.1 計畫模式

對於不簡單的修改，從**計畫模式**開始。Claude 可以讀取儲存庫、執行探索性命令，但在你核准計畫之前，它**不應該修改原始碼**。在這些時候用它：

- 程式碼庫你不熟悉
- 修改觸及很多檔案或模組
- 你需要先做架構決策再寫程式
- 爆炸半徑包含遷移、身分驗證、計費或部署腳本

在 CLI 裡循環切換模式（常見是 **Shift+Tab**）。學的是每個模式的*意圖*，而不是任何單一 UI 字串——標籤會改；從「唯讀探索」到「自動核准編輯」再到「略過提示」的光譜不會改。

**考試框架：** 計畫模式是一個*掌舵*選擇，不是永久的專案設定。核准計畫之後，你通常切換到一個在你信任的權限下允許實作的模式。

### 2.2 壓縮

長時間的工作階段會填滿上下文視窗。Claude Code 會**壓縮**較舊的輪次（在很多設定裡你也可以手動觸發壓縮，例如 `/compact`）。摘要會丟掉細節。

**壓縮後存活得很差的東西：** 一次性的聊天規則（「永遠用 pytest」）、暫時性的命名決定、你仍需要當反例的失敗實驗路徑。

**應該靠設計存活的東西：**

- 持久慣例 → **`CLAUDE.md`**／`.claude/rules/`
- 按需程序 → **Skills**
- 硬性停止 → **hooks**／封鎖規則

當你*定向*壓縮（保留 X、丟掉 Y）時，優先保留：已核准的計畫、未決的決策、限制、失敗測試的名稱。丟掉：冗長的工具傾倒、已放棄的鑽牛角尖路線、重複的檔案清單。

**考試陷阱：** 「壓縮弄丟了我們的編碼標準」→ 根本原因是標準只活在聊天裡，沒有活在 CLAUDE.md。

### 2.3 倒回

當工作階段漂移，**倒回**到之前一個乾淨的點，而不是在被污染的脈絡上疊加互相矛盾的修正。然後重新陳述**一個**清楚的目標。

倒回對上壓縮：

| 動作 | 最適合何時 | 誤用的風險 |
| --- | --- | --- |
| 倒回 | 錯誤路線／互相矛盾的指示 | 倒得太遠會丟掉後來有用的工作 |
| 壓縮 | 上下文已滿但方向仍然正確 | 丟掉細節；若聊天很亂，可能強化糟糕的摘要 |

**模式：** 漂移 → 倒回 → 單一目標 →（可選）再次進入計畫模式 → 實作。

### 2.4 親手操作對上自主

| 風格 | 何時用 | 控制 |
| --- | --- | --- |
| 親手掌舵 | 新穎／高爆炸半徑 | 你核准編輯並盯著每一輪 |
| 目標＋迴圈／自主 | 受信任、範圍明確的任務 | Hooks、測試、更嚴格的權限模式 |
| 平行 agent | 彼此獨立的子任務 | **Git worktree**（或各自獨立的簽出） |

**考試小抄：** 平行 agent 共用一個有未提交修改的工作樹，是錯誤模式；用 worktree 隔離才是安全答案。

### 2.5 掌舵對上自主的決策樹

```text
任務是新穎的或高爆炸半徑嗎？
 是 → 親手操作 + 計畫模式；核准計畫之後才用 default/manual 或 accept-edits
 否 → 該程序是否重複且已驗證過？
 是 → Skill + hooks；考慮例行排程
 否 → 仍是互動式；過程中把學到的東西寫進 CLAUDE.md

需要你筆電上的密鑰、私有網路或自訂管線嗎？
 是 → 在你自己的 CI／agent 主機上跑無頭模式
 否 → Anthropic 基礎設施上的例行排程可能就夠

CI 裡每次執行的結果必須完全相同嗎？
 是 → 裸／確定性的無頭旗標 + 釘定的權限
 否 → 互動式或 auto 模式搭配驗證即可

多個 agent 有幫助嗎？
 是 → 拆成獨立工作；用 worktree 隔離
 否 → 單一 agent、清楚的目標

工作階段走偏了嗎？
 → 先倒回；然後才重新提示
```

## 3. 設定面（建議式對強制式）

| 表面 | 性質 | 強度 |
| --- | --- | --- |
| 聊天提示詞 | 暫時 | 建議式 |
| `CLAUDE.md`／規則 | 永遠開著的專案脈絡 | 建議式但持久 |
| Skills | 按需程序 | 載入時建議式 |
| 權限規則／模式 | 工具允許／詢問／封鎖 | **由 Claude Code 強制執行** |
| Hooks | 生命週期腳本 | **被強制執行的保證** |

**核心區別：** 在 `CLAUDE.md` 裡寫「永遠不要編輯 `.env`」是客氣的請求。一條**封鎖**規則，或擋住 `.env` 的 **PreToolUse hook**，才是保證。指示塑造意圖；規則與 hooks 改變什麼被允許。

### 3.1 精簡的 CLAUDE.md

保持短到 Claude 真的會遵守。公開指引與好的考試答案收斂到：

- 專案目的、技術棧、目錄結構（幾則短句）
- 重要的命令（測試、lint、建置）
- 關於密鑰、遷移、force-push 的硬性可做／不可做
- 指向 Skills／文件的指標，供冗長程序使用——**不要**貼進一本小說

把每一類內容放到對的表面上：

| 內容類型 | 表面 |
| --- | --- |
| 永遠為真的事實與慣例 | CLAUDE.md |
| 按路徑限定範圍的慣例 | `.claude/rules/`（功能可用時） |
| 多步驟／偶發的工作流程 | Skills |
| 必須在事件執行的保證 | Hooks |
| 工具允許／封鎖 | 權限規則 |

`/init`（或其等價物）掃描儲存庫並產生 CLAUDE.md 初稿；再用 Claude 單靠程式碼發現不了的東西去精煉。

**反模式：** 一份 2,000 行的 CLAUDE.md，複製了 README、wiki 和每一份編碼標準 PDF。Claude 會打折扣地遵守它；考試獎勵*精簡*的記憶。

**CLAUDE.md 維護迴圈：** 在一次痛苦的工作階段之後，問：「有什麼東西不應該需要從零重新發現？」把那個事實提升進 CLAUDE.md。如果它是一個程序，就改為提升成 Skill。

### 3.2 Skills

**Skills** 打包重複的程序（從一個執行真正檢查的驗證 Skill 開始）。概念上，典型 Skill 內容包括：

- 什麼時候套用
- 步驟／命令
- 成功標準
- 可選的、給呼叫那一輪的 allowed-tools 授權（仍受限於基線權限）

Skills **按需**載入（被呼叫，或在相關時被自動選用）。這就是它們勝過把每個程序都塞進 CLAUDE.md 的原因。

**考試對比：**

- CLAUDE.md = 永遠在脈絡裡 → 保持短小
- Skill = 需要時載入 → 細節沒關係
- Hook = 不管 Claude 的「意見」都會執行 → 不可妥協的事項用它

團隊的好第一批 Skills：「跑驗證套件」、「帶檢查清單建立 PR」、「安全地遷移資料庫」、「安全審查接觸點」。

### 3.3 Plugins

**Plugins** 打包 CLAUDE.md 片段＋Skills＋hooks＋相關設定（有時還有 MCP／子代理），讓全團隊安裝同一份受信任的設定。Plugins 談的是**可攜性**，不是新的模型能力。

何時分享：設定已驗證、hooks 用真正的測試把關、權限是最小權限原則，而且上手成本從「讀一份 wiki」降到「安裝 Plugin」。

Plugin 衛生檢查清單：

1. 把必要的環境變數與密鑰注入點寫成文件
2. 測試跑不了時失敗即關閉
3. 幫 Skills 加上命名空間，讓多個 Plugin 可以共存
4. 幫 Plugin 加上版本；破壞性變更需要變更紀錄
5. 團隊 Plugin 永遠不要預設略過權限

## 4. 權限模式（讓模式配合風險）

模式在允許／詢問／封鎖規則之前設定基線。名稱會演進；認識光譜：

| 模式（概念） | 行為 | 典型工作 |
| --- | --- | --- |
| 預設／手動 | 第一次使用工具時提示 | 互動式結伴 |
| Accept edits | 自動接受常見工作區編輯 | 受信任的本地功能開發 |
| Plan | 探索；計畫核准前不改原始碼 | 先設計再實作 |
| Auto（分類器） | 核准例行動作；擋住有風險的 | 帶護欄的更快互動 |
| Don't ask | 嚴格；除非預先允許通常拒絕 | 受控的非互動執行 |
| Bypass／don't ask 的危險變體 | 略過大多數提示 | **僅限**隔離的 CI／沙箱 |

**評估順序（心智模型）：** 封鎖 → 詢問 → 允許；先命中者勝。封鎖勝過允許。一個以阻擋決定結束的 PreToolUse hook，仍然可以攔下呼叫，即使允許規則或 bypass 模式本來會放行——在許多設計裡，hooks 是最後一道硬閘口。

**權限決策樹：**

```text
互動式結伴／正在熟悉程式碼庫？
 → Default/manual 或 plan
核准計畫之後的受信任本地功能？
 → Accept edits（或帶分類器的 auto）
CI／無頭搭配釘定的允許清單？
 → Don't ask + 明確允許 + hooks
拋棄式容器、沒有密鑰、檔案系統用完即丟？
 → Bypass 也許可以接受
筆電上有生產憑證？
 → 永遠不要 bypass；最小權限 + 拒絕規則
```

**考試陷阱：**

- 在持有生產憑證的筆電上，把 bypass 型模式當預設 → 錯
- 以為 CLAUDE.md 會覆蓋權限封鎖 → 錯
- 對一個受信任、規格已明確的單行改名使用計畫模式 → 過於緩慢但不「不安全」；通常 accept-edits 或 auto 就行
- 以為 auto 模式可以取代 `.env` 的封鎖規則 → 錯；分類器是機率性的，封鎖是絕對的

管理員可以在團隊設定裡停用 bypass——要知道組織政策可以移除這個逃生口。

## 5. Hooks：不可跳過的控制

Hooks 在固定的生命週期點觸發。值得背起來的例子（確切事件名稱可能演進——學的是*職責*）：

| 生命週期職責 | 範例用途 |
| --- | --- |
| 工作階段開始 | 注入環境事實、儲存庫分支警告 |
| 工具使用前 | 擋住 `.env`、對 `rm -rf` 強制詢問、拒絕生產部署 |
| 權限請求 | 在非互動執行中自動決定 |
| 壓縮前 | 把關鍵限制重新注入摘要 |
| 停止／一輪結束後 | 跑 linter；測試見紅就立即中止（fail closed） |
| 檔案／規則載入 | 稽核什麼進入了脈絡 |

模式：

1. 封鎖受保護路徑（`.env`、生產設定、私鑰）
2. 用**真正的**測試執行器為一輪把關（紅了就失敗即關閉）
3. 對敏感 Bash 強制提示，即使 Bash 大致上被允許
4. 壓縮之後重新注入關鍵脈絡
5. 以權限決定 JSON／結束碼回傳允許、拒絕或詢問

**Hooks 強制執行；提示詞只是建議。**

**非互動提醒：** 在無頭 `-p` 執行裡，互動式權限提示可能根本不存在。依賴 PreToolUse hooks 與預先宣告的允許／封鎖規則——不要假設會有人類去按「允許」。

**給考試的 hook 設計提示：**

- 安全檢查優先失敗即關閉（測試執行器不存在 = 拒絕）
- 保持 hooks 快速；慢的 hooks 會讓互動使用挫折，然後被停用
- 記錄拒絕時要帶足夠稽核用的細節，但不要傾倒密鑰
- 不要把不可逆的破壞性能力，只放在軟性詢問後面

## 6. 自動化光譜

一旦任務受信任，就不要再親手啟動：

1. **例行排程（Routines）** — 在 Anthropic 管理的基礎設施上排程提示詞（維運最少）。
2. **無頭模式（Headless）** — `-p`／`--print`：一次性、沒有 TUI；stdin／stdout 給管線與持續整合（CI）。
3. **精簡／確定性旗標** — 當 CI 需要可重複、低變異的執行時優先使用。
4. **Agent SDK** — 把 Claude Code 嵌進你的 TypeScript／Python 產品。
5. **PR／GitHub Action 接線** — 受管的審查模式；把 Claude 接進 pull request 迴圈。

**決策規則：** 從例行排程開始；當工作需要*你的*環境或周圍腳本邏輯時，降到無頭模式；當 agent *就是*產品的一部分時，用 Agent SDK。

```text
需要 Anthropic 託管的排程、自訂環境很少？
 → 例行排程（Routine）
需要本機密鑰、Docker、私有套件、自訂腳本？
 → 在你的 runner 上跑無頭模式
需要 agent 嵌進產品 UX？
 → Agent SDK
需要 PR 評論／檢查？
 → GitHub Action／受管審查整合
```

沒有等比例驗證的自動化是不完整的——這句話本身就是考試答案。

**值得記住的無頭細節：**

- 非互動意味著權限迴圈裡沒有人
- 經由 stdin 或引數送入提示詞；擷取 stdout 當日誌
- 搭配明確的權限允許清單與 PreToolUse hooks
- 當 CI 不穩定失敗代價很高時，優先用確定性設定

## 7. 驗證無人監督的工作

**你盯得越少，驗證得越多。**

| 無人監督程度 | 最低驗證 |
| --- | --- |
| 互動式結伴 | 抽查差異比較 |
| Accept-edits 本地執行 | `git diff`＋煙霧測試 |
| Auto 模式長工作階段 | 差異審查＋針對性測試＋hook 閘口 |
| 無頭／排程／bypass | 強制自動化測試、危險工具的封鎖規則、高風險路徑的人工審查 |

永遠不要相信 Claude「測試通過了」的宣稱——在 hook 或 CI 步驟裡執行執行器。

**驗證 Skill 模式：** 把「跑單元＋lint＋型別檢查；印摘要；失敗時非零結束」打包成 Skill，並且把同一組命令接到無人值守執行的 Stop／PreToolUse 閘口。

**依風險分級的審查：**

- 低：格式、註解、文件 → 自動化檢查可能就夠
- 中：應用邏輯 → 測試＋掃一眼差異
- 高：身分驗證、付款、遷移、IAM → 不論 CI 是不是綠的，都強制人工審查

## 8. 實務端到端工作流程（認證檢查清單）

1. 初始化／掃描儲存庫（`/init` 或其等價物）。
2. 在要求功能之前，餵入相關檔案／指向子系統。
3. 計畫（不寫程式碼）然後核准然後實作。
4. 當品質重要時，優先用有測試意識的迴圈。
5. 把持久規則編碼進 CLAUDE.md；程序進 Skills；硬性停止進 hooks。
6. 依工作風險選擇權限模式。
7. 只有驗證穩固之後才自動化；經由 Plugin 分享。
8. 若漂移：倒回，然後一個目標，然後繼續。
9. 出貨 Plugin 之前：用一次故意變紅的測試證明 hooks 會失敗即關閉。

**工作階段衛生習慣：**

- 每一段自主工作只有一個目標
- 大型自主執行之前先 commit 或 stash，讓倒回或 git restore 容易
- 使用 worktree 時把分支取清楚的名字
- 壓縮之後，用一句話重述目前計畫

## 9. 反模式（高報酬考試辨識）

| 反模式 | 為什麼失敗 | 優先改用 |
| --- | --- | --- |
| 安全只活在聊天或 CLAUDE.md | 建議式；壓力下被忽略 | 封鎖加上 PreToolUse hook |
| 筆電上 bypass 加上生產憑證 | 巨大爆炸半徑 | 沙箱 CI 加上最小權限原則 |
| 測試還不存在就自動化 | 大規模無人監督垃圾 | 先寫閘口 |
| 兩個 agent、一條髒分支 | 合併混亂或丟掉工作 | Worktree |
| 相信模型宣稱測試通過 | 幻覺出來的驗證 | Hook 執行執行器 |
| CLAUDE.md 裡的小說 | 稀釋；打折扣遵守 | Skills 加上精簡 CLAUDE.md |
| 矛盾之後用壓縮代替倒回 | 糟糕摘要把混亂鎖死 | 倒回 |
| 永遠待在計畫模式 | 永遠出不了貨 | 核准計畫然後進入實作模式 |
| 預設 bypass 的 Plugin | 散播不安全預設 | 最小權限預設 |
| 忽略 Stop-hook 失敗 | 把壞掉的程式碼漂綠 | 失敗即阻斷（fail closed） |

## 10. 比較：控制面深挖

把 Claude Code 設定想成分層防禦：

```text
[Chat instructions] advisory, ephemeral
 |
[CLAUDE.md / rules] advisory, durable
 |
[Skills] advisory, on-demand depth
 |
[Permission modes/rules] enforced allow/ask/deny
 |
[Hooks] enforced lifecycle guarantees
 |
[CI / human review] external verification
```

考試喜歡這種情境：學生選了比需要更高的層（例如，需要封鎖規則時卻往 CLAUDE.md 加一本小說），或比需要更低的層（希望單靠聊天擋住 force-push）。

**走完的情境 A — 密鑰檔保護**

- 錯：在聊天裡請它不要碰密鑰檔
- 較好：CLAUDE.md 註記，單靠它仍不夠
- 對：對密鑰環境檔的編輯／寫入設封鎖規則，加上擋住那些路徑的 PreToolUse hook

**走完的情境 B — 每週相依套件升級**

- 錯：每週一手動重下提示，筆電上用 bypass
- 對：已驗證的 Skill 加上例行排程或無頭 CI 工作，加上測試，加上給人類合併的 PR

**走完的情境 C — 不熟悉的付款重構**

- 錯：auto 模式隔夜跑
- 對：計畫模式、設計審查、範圍收緊的 accept-edits、測試、付款路徑的人工審查

## 11. 考試提示

- 把情境對應到掌舵／設定／自動化／驗證。
- 每次都辨識建議式對強制式控制。
- 不熟悉或多檔案工作優先用計畫模式。
- 平行 agent 優先用 worktree。
- 優先用例行排程，直到你真正需要無頭模式或 SDK。
- 沒有 CLAUDE.md 的壓縮會弄丟慣例——那個失敗模式可考。
- 沒有隔離的 bypass 是錯誤的安全答案。
- Hooks 即使在模式寬鬆時也能擋住——要知道那個順序故事。
- Plugins 打包信任；它們不取代驗證。
- 沒有 hooks 的無頭模式，對無人值守安全來說是不完整的答案。

## 12. 自我檢核問答（附答案）

**Q1.** CLAUDE.md 說永遠不要提交密鑰，但一個密鑰環境檔還是被加入暫存區。什麼擋得住它？
**A.** 封鎖權限規則與／或 PreToolUse hook——不是那句 markdown 句子本身。

**Q2.** 什麼時候計畫模式是正確的預設？
**A.** 在大型或不清楚的編輯之前：探索並提案，核准前不改原始碼。

**Q3.** 多次失敗嘗試之後工作階段混亂了。下一步？
**A.** 倒回（或小心壓縮），然後一個清楚的目標——避免互相矛盾的疊加指示。

**Q4.** 每週一同一個提示詞。第一個自動化選擇？
**A.** 例行排程；若需要本機環境或自訂管線再降到無頭模式。

**Q5.** 為什麼用 CLAUDE.md 而不是只靠聊天？
**A.** 聊天會被壓縮掉；CLAUDE.md 是持久的專案指示面。

**Q6.** 兩個 agent 在同一條分支——更安全的模式？
**A.** 用 git worktree／各自獨立的簽出隔離。

**Q7.** 無頭 `-p` 提供什麼？
**A.** 非互動、可腳本化的執行，給管線與管線串接。

**Q8.** 完全無人值守的執行要多少驗證？
**A.** 最大：測試閘口、危險工具的封鎖規則，以及與零人類盯著成比例的審查政策。

**Q9.** 一份 20 步的發佈檢查清單，用 Skill 還是 CLAUDE.md？
**A.** Skill（按需程序）；讓 CLAUDE.md 保持精簡，加一個指標。

**Q10.** 在開發者機器上做受信任的本地功能開發，accept-edits 對上 bypass？
**A.** Accept-edits（或帶分類器的 auto）。Bypass 屬於隔離沙箱／CI，不是筆電預設。

**Q11.** PreCompact hook 常常該做什麼？
**A.** 重新注入關鍵限制，讓壓縮摘要不要丟掉不可妥協的事項。

**Q12.** Plugin 對上 Skill？
**A.** Skill = 一個打包的程序／知識單元。Plugin = 可安裝的 Skills、hooks、設定組合包（可攜層）。
**Q13.** Auto 模式仍然做了危險的事。你的下一步加固？
**A.** 為那類動作加上明確的封鎖規則與／或 PreToolUse hook——不可妥協的事項不要單靠分類器。

**Q14.** 什麼時候選 Agent SDK 而不是無頭 CLI？
**A.** 當編碼 agent 嵌在你的產品 TypeScript／Python 應用程式裡，而不只是從 shell 管線呼叫。

**Q15.** GitHub Action 在每個 PR 上跑 Claude。必須先有什麼？
**A.** 等比例驗證：真正的測試、範圍收緊的權限，以及高風險路徑的審查——沒有閘口的自動化是不完整的。

**Q16.** 允許與封鎖都符合同一個工具路徑時，評估順序？
**A.** 封鎖勝出（先命中心智模型：封鎖在允許之前）。

**Q17.** 為什麼 bypass 模式裡 hooks 仍然重要？
**A.** PreToolUse hooks 可以不管權限模式就拒絕——它們強制執行使用者無法靠翻模式跳過的政策。

**Q18.** 平行 agent 編輯同一個檔案——正確嗎？
**A.** 不正確。拆成獨立工作；隔離工作樹；刻意合併。

**Q19.** `/init` 之後，CLAUDE.md 又大又泛。你怎麼做？
**A.** 修剪成永遠為真的事實；把程序移到 Skills；只加入無法從程式碼發現的慣例。

**Q20.** 無人值守工作需要私有套件登錄憑證。例行排程還是無頭？
**A.** 無頭（或你的 CI），密鑰與網路住在那裡——不是單靠雲端例行排程，除非那份基礎設施有那些密鑰。

**Q21.** 打造團隊 Claude Code 成熟度的階梯順序是什麼？
**A.** 掌舵，然後設定，然後自動化，然後驗證／分享。

**Q22.** 抽查差異對排程的隔夜重構夠嗎？
**A.** 不夠——要求自動化測試加上 hooks，加上高風險差異的人工審查。

**Q23.** 不可逆的「永遠不准」規則屬於哪裡？
**A.** 權限封鎖規則與 hooks——不是只在 CLAUDE.md。

**Q24.** 定向壓縮應優先保留什麼？
**A.** 已核准的計畫、未決的決策、限制，以及失敗測試——丟掉嘈雜的失敗實驗傾倒。

**Q25.** 若 CI 已經跑測試，為什麼驗證 Skill 仍然有價值？
**A.** 本地互動迴圈更早抓到失敗；同一組命令也應把關無人值守的 Stop／PreToolUse hooks，以保持一致。

## 14. 詞彙表

- **權限模式** — 工具核准行為的基線。
- **允許／詢問／封鎖規則** — 明確的工具權限政策。
- **例行排程（Routine）** — Anthropic 基礎設施上受管的排程執行。
- **無頭模式（Headless）** — 給管線用的 print／一次性 CLI（`-p`）。
- **Agent SDK** — 把 Claude Code 迴圈嵌進你的應用程式。
- **Plugin** — 可分享的 Claude Code 設定組合包。
- **Worktree** — 隔離平行 agent 用的獨立 Git 工作樹。
- **驗證閘口** — 失敗即關閉的真正測試／lint 命令。

- **分類器 auto 模式** — 由模型協助核准例行動作，並擋住風險。
- **失敗即關閉** — 若安全檢查跑不了，視為失敗／拒絕。

## 15. 額外深度：子代理、MCP 與團隊推行

### 子代理（概念）

Claude Code 可以為隔離工作生成專門的子代理（explore、plan 或自訂）。隔離避免把主工作階段撐脹。考試：當子任務不需要完整對話時用子代理；把危險工具約束住；記住非互動模式裡的背景子代理無法顯示互動提示——由 hooks 與封鎖決定。

### Claude Code 裡的 MCP

MCP 伺服器擴展編碼 agent 可用的工具／資源／提示。把 MCP 工具當成任何其他工具：權限規則與 hooks 仍然適用。不要因為 MCP 伺服器「只是設定」就假設它安全——它可以暴露強大的副作用。

### 團隊推行順序（實務）

1. 一個儲存庫試點：精簡 CLAUDE.md＋驗證 Skill＋封鎖密鑰
2. 為受保護路徑與測試閘口加上 PreToolUse hooks
3. 標準化互動對上 CI 的權限預設
4. 打包成 Plugin；安裝到第二個儲存庫
5. 為一件無聊的每週任務加上例行排程／無頭
6. 衡量：較少嘈雜的權限提示、較少事故、更快的 PR 檢查
7. 然後才擴大自主程度（auto 模式、更多例行排程）

### 真正重要的指標（不是虛榮）

- 從 issue → 綠的 PR 的時間
- 擋下真正錯誤的 hook 拒絕率
- 驗證閘口的不穩定失敗率
- 新工程師帶著 Plugin 的上手時間
- 涉及無人監督編輯的事故

### 讀書節奏

第 1 天：第 1–5 節（掌舵＋設定）。閃卡建議式對強制式。
第 2 天：第 6–10 節（自動化＋驗證＋反模式）。大聲走決策樹。
第 3 天：全部問答閉書，然後檢查清單。只重讀漏掉的項目。

## S1. CLAUDE.md 層級、@import 與 /memory（任務 3.1）

**考試點名的三層：**

| 層級 | 位置 | 共享？ |
| --- | --- | --- |
| **使用者** | `~/.claude/CLAUDE.md` | 否——個人，套用到你所有專案，**不在**版本控制裡 |
| **專案** | `./CLAUDE.md`（根目錄）或 `./.claude/CLAUDE.md` | 是——經由版本控制，全團隊 |
| **目錄** | 子目錄裡的 `CLAUDE.md` | 是——當 Claude 處理該目錄裡的檔案時**按需**載入 |

檔案**串接**（較廣範圍先、較靠近工作的後讀）；它們不會互相覆寫。*（現行文件在使用者之上加了一層受管／組織政策層——全組織、無法排除——以及給個人單專案註記用、被 gitignore 的 `CLAUDE.local.md`；知道它們存在。）*

**考試喜歡的診斷情境：** 新隊友的 Claude 忽略「團隊的」指示 → 那些指示活在某人**使用者層**的 `~/.claude/CLAUDE.md`，而不是**專案層**設定，所以版本控制從來沒把它們送出去。

**`@import` 語法：** 從 CLAUDE.md 用 `@path/to/file` 參照外部檔案——被匯入的檔案在啟動時展開進脈絡。用它讓 CLAUDE.md 保持模組化，例如每個套件的 CLAUDE.md 只匯入與它相關的標準檔。*（細節已核實：相對路徑相對*匯入檔*解析；匯入遞迴最多 **四跳**（依現行官方文件，2026-08-23 核實）；把路徑包在反引號裡可以*提及*而不匯入。）*

**`/memory`** 列出跨範圍的記憶檔（CLAUDE.md 與夥伴檔），並讓你打開／編輯它們——用它**核實載入了哪些記憶檔，並診斷跨工作階段的不一致行為**。*（現行文件：`/context` 另外確認這一輪實際載入了什麼。）*

## S2. 自訂 slash command 與 Skills（任務 3.2）

**Commands — 範圍規則（官方範例題 Q4 就卡在這）：**

| 位置 | 範圍 |
| --- | --- |
| 儲存庫裡的 **`.claude/commands/`** | 專案——**納入版本控制，clone／pull 後自動對每位開發者可用** |
| **`~/.claude/commands/`** | 使用者——個人，不共享 |

一個 markdown 檔 `.claude/commands/review.md` 定義 `/review`。團隊標準工作流程 → 專案範圍；個人助手 → 使用者範圍。*（現行文件註：自訂 commands 已併入 Skills——`.claude/commands/deploy.md` 與 `.claude/skills/deploy/SKILL.md` 都會建立 `/deploy`；既有 commands 繼續可用。考試面對「團隊共享的 /review command」的答案，仍然是專案儲存庫裡的 `.claude/commands/`。）*

**Skills** 住在 `.claude/skills/<name>/SKILL.md`（專案）或 `~/.claude/skills/`（個人）。考試點名、且已核實現行的 frontmatter 鍵：

| Frontmatter 鍵 | 它做什麼 |
| --- | --- |
| **`context: fork`** | 在**隔離的子代理脈絡**裡跑 Skill，避免冗長的 Skill 輸出（程式碼庫分析、腦力激盪）**污染主對話** |
| **`allowed-tools`** | Claude 在 Skill **呼叫那一輪**可以**不經權限提示**使用的工具——限縮到 Skill 需要的（例如只寫檔，以防止破壞性動作） |
| **`argument-hint`** | 自動完成提示，顯示預期引數（例如 `[issue-number]`），當開發者呼叫 Skill 卻沒帶它們時 |

**不影響團隊的個人變體：** 在 `~/.claude/skills/` 下用**不同名稱**建立你自己的版本，讓團隊的專案 Skill 保持原樣。

**Skills 對上 CLAUDE.md（考試的分界線）：** Skills = **為任務特定工作流程按需呼叫**（本體只在使用時載入）；CLAUDE.md = **永遠載入的通用標準**。一段已經變成*程序*、還在長大的 CLAUDE.md 區塊，應搬到 Skill。

## S3. 路徑特定規則 — `.claude/rules/`（任務 3.3）

規則檔是 **`.claude/rules/`** 裡的 markdown，帶 **YAML frontmatter，其 `paths:` 欄位放 glob 模式**：

```markdown
---
paths:
 - "src/api/**/*"
 - "**/*.test.tsx"
---
# API + test conventions
- All endpoints validate input
- Tests use the team fixture factory
```

- 規則**只在 Claude 處理符合其 glob 的檔案時載入**——不相干的慣例待在脈絡外面，節省 token（*沒有* `paths` 的規則每個工作階段都載入，像 CLAUDE.md）。
- **當慣例跨目錄時，glob 勝過目錄層 CLAUDE.md**（官方範例題 Q6）：測試檔散落在整棵樹的原始碼旁邊，所以 `**/*.test.tsx` 全部抓得到——每個目錄一份 CLAUDE.md 做不到，根目錄 CLAUDE.md 加標題靠推論，Skills 需要被呼叫。帶 glob 的規則才是確定性、自動的答案。
- 指南自己的練習例子：`paths: ["terraform/**/*"]`，讓 Terraform 慣例只在編輯 Terraform 時載入。

## S4. 計畫模式、直接執行，與 Explore 子代理（任務 3.4）

具名決策規則（上方第 2.1 節涵蓋工作流程；考試要的是*標準*原文）：

- **計畫模式** — 複雜任務：大規模變更、**多種有效作法**、架構決策、多檔案修改（單體→微服務；45 個檔案的函式庫遷移）。在**承諾變更之前**安全探索與設計，避免昂貴的返工（範例題 Q5 的正確 A）。
- **直接執行** — 簡單、範圍明確的變更：帶清楚堆疊追蹤的單檔錯誤修正；加上一個驗證條件。
- **組合它們：** 調查用計畫模式，計畫好的實作改用直接執行。
- **Explore 子代理**隔離**冗長的探索輸出**並回傳摘要，在多階段工作中**保住主對話脈絡**——當題目描述程式碼庫探索期間上下文耗盡時，點它的名。（連到領域 5.4 子代理委派。）

## S4b. 迭代式精煉技巧（任務 3.5）

- 當自然語言對轉換的描述被不一致地解讀時，**具體的輸入／輸出例子勝過敘述文字**——提供 **2–3 對例子**，展示輸入與預期輸出。
- **測試驅動迭代：** 先寫測試套件（預期行為、邊界情況、效能），然後透過**分享測試失敗**來引導漸進改善；帶例子輸入／預期輸出的具體失敗案例，能修好邊界處理（例如遷移腳本裡的空值）。
- **訪談模式：** 在不熟悉的領域，讓 Claude **先問你問題**，把你還沒預料到的考量（快取失效策略、失敗模式）浮出來，*然後*才實作。
- **互相影響對上獨立問題：** 會**互相影響**的修正 → 一則詳細訊息一次處理全部；**獨立**問題 → 循序迭代沒問題。

## S5. CI／CD 整合旗標（任務 3.6）

| 機制 | 考試事實 |
| --- | --- |
| **`-p`／`--print`** | 以**非互動**方式跑 Claude Code：處理提示詞、寫到 stdout、結束——當管線工作「卡住等互動輸入」時的修復方法（範例題 Q10；像 `CLAUDE_HEADLESS=true` 或 `--batch` 這類干擾選項是**不存在的功能**） |
| **`--output-format json`** | print 模式的機器可解析輸出（`text`、`json`、`stream-json`） |
| **`--json-schema`** | print 模式旗標，產出**通過驗證、符合你 schema 的 JSON**——結構化發現結果，準備好自動貼成 PR 評論 |
| **CI 裡的 CLAUDE.md** | 給 CI 呼叫的 Claude 專案脈絡的機制：測試標準、測試夾具慣例、審查準則——更好的測試產生、較少低價值案例 |
| **工作階段脈絡隔離** | **產生**程式碼的那個工作階段，較不擅長**審查**它（它保留自己的推理脈絡，不會質疑自己的決策）——把審查當**獨立實例**跑（連到領域 4.6 多實例審查） |
| **重審不重複** | 新 commit 之後重跑時，把**先前的審查發現結果**放進脈絡；指示 Claude 只回報新的或仍未處理的問題 |
| **產生測試不重複** | 把**既有測試檔**放進脈絡，讓產生的測試跳過已經涵蓋的情境 |

## S6. 補充問答

**SQ1.** *（＝官方範例題 Q4）* 一個 `/review` command 必須在 clone／pull 時到達每位開發者。檔案放哪裡？
**A.** 專案儲存庫裡的 `.claude/commands/`——納入版本控制的專案範圍。`~/.claude/commands/` 是個人的；CLAUDE.md 放指示，不是 command 定義；帶 commands 陣列的 `.claude/config.json` 不存在。

**SQ2.** *（＝官方範例題 Q6）* React、API 與資料庫慣例不同；測試檔到處坐在原始碼旁邊，且共享一套慣例。最可維護的機制？
**A.** `.claude/rules/` 檔加上 YAML frontmatter glob 模式（`**/*.test.tsx`）——有條件、自動、與位置無關。根目錄 CLAUDE.md 標題靠推論；每個目錄一份 CLAUDE.md 跨不了整棵樹；Skills 需要被呼叫。

**SQ3.** 新隊友拿不到「團隊的」指示。可能原因？
**A.** 指示活在使用者層 `~/.claude/CLAUDE.md`（不經版本控制共享），而不是專案層 `CLAUDE.md`／`.claude/`。

**SQ4.** 如何讓每個套件的 CLAUDE.md 保持模組化？
**A.** `@import` 語法（`@docs/standards.md`）——每個套件的 CLAUDE.md 只匯入相關標準檔。

**SQ5.** 哪個命令核實載入了哪些記憶檔？
**A.** `/memory`（`/context` 確認這一輪載入了什麼）。

**SQ6.** 一個程式碼庫分析 Skill 用輸出淹沒主對話。Frontmatter 修復方法？
**A.** `context: fork`——在隔離的子代理脈絡裡跑 Skill。

**SQ7.** 把 Skill 限縮成只寫檔以防止破壞性動作——哪個鍵？
**A.** SKILL.md frontmatter 裡的 `allowed-tools`（為呼叫那一輪授予範圍收緊、免提示的工具使用）。

**SQ8.** 開發者呼叫 `/deploy` 卻沒帶必要參數。哪個鍵提示他們？
**A.** `argument-hint`（例如 `[environment] [version]`）。

**SQ9.** 你想要團隊 Skill 的個人變體，又不影響隊友。
**A.** 在 `~/.claude/skills/` 下用**不同名稱**建立它。

**SQ10.** Skill 還是 CLAUDE.md：20 步發佈程序對上「我們用 2 空白縮排」？
**A.** 程序 → Skill（按需）；通用標準 → CLAUDE.md（永遠載入）。

**SQ11.** 有 `paths:` 範圍的規則何時載入？
**A.** 只在 Claude 處理符合 glob 的檔案時；沒有 `paths` 的規則每個工作階段都載入。

**SQ12.** 單體→微服務重整：計畫模式還是直接？
**A.** 計畫模式——大規模、多種有效作法、架構決策（範例題 Q5）。帶堆疊追蹤的單檔錯誤修正 → 直接執行。

**SQ13.** 多階段任務在探索期間耗盡上下文。具名解法？
**A.** Explore 子代理——冗長探索被隔離，摘要被回傳。

**SQ14.** CI 工作卡住：「Claude Code 正在等互動輸入。」修復方法？
**A.** `claude -p "..."` — `-p`／`--print` 旗標就是文件化的非互動模式（範例題 Q10；`CLAUDE_HEADLESS`／`--batch` 不存在）。

**SQ15.** 來自 CI、結構化、機器可張貼的審查發現結果——哪些旗標？
**A.** `--output-format json` 搭配 `--json-schema`（print 模式）。

**SQ16.** 為什麼寫程式碼的那個工作階段不該審查它？
**A.** 工作階段脈絡隔離：它保留產生時的推理，不會質疑自己的決策——用獨立審查實例。

**SQ17.** 新 commit 之後重跑審查，重複評論洗版。修復方法？
**A.** 把先前發現結果放進脈絡，並指示：只回報新的或仍未處理的問題。

**SQ18.** 產生的測試重複既有覆蓋。修復方法？
**A.** 把既有測試檔放進脈絡，讓產生避開已涵蓋的情境。
