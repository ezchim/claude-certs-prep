# 用 Claude API 打造應用 — 備考筆記

> **免責聲明：** 這些是為考試／認證準備撰寫的**原創備考筆記**。它們**不是** Anthropic 官方課程材料、逐字稿或課文原文。主題對齊 [Building with the Claude API](https://academy.claude.com/courses/building-with-the-claude-api) 的公開大綱。API 細節請一律以官方 Anthropic 文件為準（[platform.claude.com／docs.anthropic.com](https://docs.anthropic.com)）。

**應交叉核對的主要來源（此處不複製）：** Messages API、工具使用、串流、結構化輸出、提示詞快取、Message Batches、視覺／檔案、速率限制／錯誤。

## 概覽

公開課程頁面把這條路徑定位成生產導向，給已經會 Python 與 JSON 的軟體工程師。載明成果包括：驗證身分並呼叫 Anthropic API；跑單回合與多回合對話；使用系統提示詞、temperature、串流與結構化輸出；有系統地評測提示詞；呼叫工具（自訂與內建）；建置檢索增強生成（RAG）管線；使用延伸功能（思考、視覺、PDF、引用來源、快取）；整合模型上下文協定（MCP）；以及設計 agent 工作流程（平行化、串接、路由）。

**課程形狀（公開模組）：** 用 API 存取 Claude → 提示工程 → 工具使用 → RAG 與 agentic 搜尋 → 模型上下文協定 → Anthropic 應用（Claude Code、Computer Use）→ Agent 與工作流程。

**如何使用這些筆記：** 把每一節當閃卡叢集。讀完後不回頭做自我檢核問答。API 變更時，參數名以官方文件為準。

**考試姿態：** 評分者在乎你能不能*正確操作* Messages 迴圈（角色、停止原因、tool_result 的 id、串流組裝）、診斷成本／延遲（快取、批次、模型選擇），以及刻意選擇工作流程 vs agent 模式——不是你有沒有背行銷口號。

## 關鍵概念（速查表）

| 概念 | 記住 |
|------|----------|
| Messages API | 對話回合，角色為 `user`／`assistant`；messages 裡**沒有** `system` 角色 — 用頂層 `system` |
| 驗證 | API 金鑰經環境變數／密鑰存放處；送出必填版本標頭；絕不提交金鑰 |
| `max_tokens` | 生成 token 的必填上限；截斷 vs 完整答案 |
| Temperature | 較高 → 較多樣；較低 → 較確定性；與評測配對 |
| 串流 | 伺服器推送事件（SSE）事件串流；組裝增量；工具的 `input_json_delta` 需特別處理 |
| 停止原因 | `end_turn`、`max_tokens`、`tool_use`、`stop_sequence`、`pause_turn`、`refusal` — 各需不同下一步 |
| 工具 | 模型發出 `tool_use`；你的應用執行工具；下一回合回傳 `tool_result` |
| 平行工具 | 一個助理回合可有多個 `tool_use` 區塊；依每個 id 回傳一個結果 |
| 結構化輸出 | 受 schema 約束的 JSON（及／或嚴格工具），用於可靠管線 |
| RAG | 檢索相關切塊 → 注入上下文 → 帶引用來源／錨定生成 |
| 提示詞快取 | 快取穩定前綴（工具 → 系統 → 訊息）以降低延遲／成本 |
| 批次 | 非同步 Message Batches，用於大型離線工作；相對同步通常有折扣 |
| Agent | 工作流程 vs 自由型 agent；平行／串接／路由模式 |
| MCP | 跨主機標準化工具／資源／提示（見配套 MCP 筆記） |

> **時效註記（2026-08）：** (1) *Temperature* — 取樣旋鈕（`temperature`／`top_p`／`top_k`）在**現行前沿模型上已移除**（Opus 4.7+、Opus 5、Sonnet 5、Fable 5 會回 400）；在 4.6 及更舊模型上仍有效。確定性建議改靠 schema／結構化輸出。(2) *System 角色* — 「`messages` 裡沒有 `system` 角色」仍是基礎考試答案，但最新 Opus／Fable 層級模型確實接受附加到 `messages` 的**對話中途** `{"role": "system"}` 訊息（對快取友善的操作者通道）；`messages[0]` 仍然不能是這種訊息。

## 依主題的深入筆記

### 1. 用 API 存取 Claude

#### 身分驗證與設定

- 在 Anthropic Console 建立 API 金鑰；存在環境變數或密鑰管理器（`ANTHROPIC_API_KEY`），絕不放進版控或用戶端應用。
- 可能時用官方 SDK（Python／TypeScript）：它們處理標頭、重試與串流輔助。
- HTTP 用戶端必須送出 API 金鑰與 API 版本標頭（常見為 `anthropic-version`）。把版本標頭當成契約的一部分：錯誤／缺失會大聲失敗。
- 典型請求欄位：`model`、`max_tokens`、`messages`，可選 `system`、`temperature`、`tools`、`stream`、`tool_choice`、快取控制、思考設定等。
- 依能力對上成本／延遲選模型。對認證準備：知道*為什麼*分類或路由會挑更快／更便宜的模型，困難推理或工具編排會挑更強的模型。
- **伺服器端 vs 用戶端金鑰：** 瀏覽器應用絕對不能持有長效 API 金鑰。把對 Claude 的呼叫放在你的後端後面。

**原創範例 — 最小心智請求形狀**

```text
POST /v1/messages
Headers: x-api-key, anthropic-version, content-type: application/json
Body: {
 model: "<current-model-id>",
 max_tokens: 1024,
 system: "You are a careful support triage bot. Reply in JSON.",
 messages: [
 { role: "user", content: "Order #4421 never arrived." }
 ]
}
```

#### 模型與選擇啟發式

| 工作負載 | 優先選 | 為什麼 |
|----------|--------|-----|
| 意圖路由／便宜分類 | 較小／較快的模型 | 量大、歧義低 |
| 困難推理、長工具鏈 | 更強的模型 | 工具犯錯較少、規劃較好 |
| 批次離線標註 | 夠強 + Batches API | 成本 + 吞吐量 |
| 互動式 UI 聊天 | 中／強 + 串流 | 感知延遲 + 品質 |

考試陷阱：「永遠用最大的模型。」正確答案是依任務**調整規模**，並用評測衡量。

#### 訊息與多回合上下文

- 每則訊息有 `role` 與 `content`（字串或內容區塊）。
- 使用者／助理回合交替。你的應用擁有歷史：修剪、摘要或丟掉舊回合，以待在上下文限制內。
- 內容可以是多模態：文字加上影像或 API 支援的文件輸入。
- 陷阱：把「系統」訊息塞進 `messages` 並把角色設成 `system` — Messages API 期望的是頂層 `system` 參數。*（時效註記：最新 Opus／Fable 層級模型接受附加到 `messages` 的對話中途系統訊息；考試層級規則——系統指示放頂層 `system`——仍然成立。）*
- 工具之後繼續時，附加完整助理回合（含 `tool_use` 區塊），以及一則放 `tool_result` 區塊的使用者回合。不要發明假的助理文字來代替工具結果。

**歷史衛生模式**

1. **滑動視窗：** 保留最近 N 個回合；丟掉更舊的使用者／助理配對。
2. **摘要並替換：** 定期把早期回合換成精簡摘要訊息。
3. **釘住關鍵事實：** 把持久政策放進 `system`；把工作階段事實放進短的釘住使用者／助理前言。
4. **只要仍需可稽核性，就絕不默默改寫工具逐字稿**——即使為模型做了摘要，也把原始工具日誌存在離線處。

#### 系統提示詞

- 系統文字設定角色、規則、輸出格式、安全邊界與工具使用政策。
- 使用提示詞快取時讓系統提示詞保持穩定；把易變的使用者資料放進使用者訊息。
- 寧可給明確指示（「永遠回傳符合 schema X 的 JSON」）也不要模糊感覺（「請幫幫忙」）。
- 用標過名的區段組織長系統提示詞（XML 風格標籤是常見模式）：`<role>`、`<rules>`、`<output_format>`、`<examples>`。
- 工具政策也屬於這裡：何時呼叫工具、何時問使用者、何時拒絕。

#### Temperature、max_tokens 與輸出控制

- Temperature（及相關取樣旋鈕）在創意與一致性之間取捨 — **在它們仍然存在的模型上**。現行前沿模型（Opus 4.7+、Opus 5、Sonnet 5、Fable 5）已**移除** `temperature`／`top_p`／`top_k`（送出會回 400）；在 4.6 及更舊模型上仍有效。
- 對評分、萃取與工具參數生成，優先把 **schema／結構化輸出**當主要一致性槓桿（較低 temperature 只在支援它的舊模型上再用）。
- 務必用心設定 `max_tokens`：太低會在 JSON 中途截斷；太高且你不需要長答案時會浪費預算。
- `max_tokens` 是**上限**，不是目標。模型常較早以 `end_turn` 停止。
- 自訂 `stop_sequences` 可在哨兵字串上停下生成；此時 `stop_reason` 變成 `stop_sequence`。少用——結構化工作通常 schema 勝過脆弱的停止字串。

#### 串流（伺服器推送事件，簡稱 SSE）

- 設 `stream: true` 以在模型生成時接收伺服器推送事件。
- 典型事件流：`message_start` →（`content_block_start` → 增量 → `content_block_stop`）* → `message_delta` → `message_stop`（加上適用的 `ping`／`error` 事件）。
- 對 UX：立刻渲染文字增量；把工具 JSON 緩衝到區塊完成（或小心遵循細粒度工具串流規則）。
- 考試提示：串流**不改變**最終語意結果；它改變交付方式以及你如何組裝訊息。
- 工具串流細節：`tool_use` 區塊常以空的 `input: {}` 開始；參數以 `input_json_delta`／`partial_json` 片段到達。把片段串接起來，然後在 `content_block_stop` 之後解析。
- 思考串流（若啟用）可能在思考區塊關閉前發出 `thinking_delta` 與 `signature_delta`——把簽章當完整性中繼資料，不是給使用者看的敘述文字。
- SDK 通常提供輔助（`text_stream`、`get_final_message`／`finalMessage`），除非你在建裸 HTTP 用戶端，否則不必手解 SSE。
- 優雅處理未知事件類型（版本可能新增事件）。

#### 停止原因（必記表）

| `stop_reason` | 意義 | 典型下一步 |
|---------------|---------|---------------------|
| `end_turn` | 自然完成 | 顯示／使用回覆 |
| `max_tokens` | 撞上你的輸出上限 | 提高 `max_tokens` 或繼續生成 |
| `tool_use` | 模型要用戶端工具 | 執行工具；送出 `tool_result` |
| `stop_sequence` | 撞上你的自訂停止字串 | 處理哨兵；可能繼續 |
| `pause_turn` | 伺服器端迴圈暫停（例如長伺服器工具／思考） | 依文件繼續回合（常重送助理內容） |
| `refusal` | 政策拒絕 | 安全浮出；不要用同一提示盲目重試 |

考試陷阱：把每個未完成答案都當模型失敗。先查 `stop_reason` 與 `usage`。

#### 結構化輸出

- 用受 schema 約束的 JSON，讓下游程式碼不必靠脆弱正規表示式解析。
- 嚴格工具 schema 同樣減少無效工具參數。
- 把結構化輸出與評測結合：斷言形狀*以及*語意正確。
- 可用時優先用官方結構化輸出／JSON schema 功能，而不是只靠「請用 JSON 回覆」。
- 若 schema 在正式環境失敗：記錄原始文字，關鍵路徑解析失敗即關閉，只有安全時才回退到修復提示。

#### 錯誤、重試與速率限制

- 預期 HTTP 類失敗：驗證（401）、錯誤請求（400）、找不到（404）、速率限制（429）、過載／容量（例如 529 類）、5xx。
- 遇到 429：有 `retry-after` 就遵守；用指數退避 + 抖動；多租戶時隔離每租戶預算。
- 區分**請求速率** vs **token 速率**限制（每分鐘請求數（RPM） vs 每分鐘輸入／輸出 token）。「小型」聊天應用仍可能用巨大 RAG 脈絡炸掉每分鐘輸入 token（ITPM）。
- 冪等心態：重試不得讓副作用雙重計費——讓工具執行冪等，或依 tool_use id 去重。
- 串流錯誤可能在串流中途以 SSE `error` 事件到達；你的用戶端必須乾淨中止，並決定是否恢復。

#### Message Batches（非同步規模）

- Message Batches API 非同步提交許多 Messages 風格請求——適合離線評測集、大量分類、隔夜富化。
- 同樣 token 通常比同步 Messages 便宜；結果稍後擷取（不是即時聊天 UX）。
- 每筆需要 `custom_id`，才能把結果接回來源列。
- 仍受批次特定速率／佇列限制；未及時處理的請求可能過期（文件提到長外層視窗，例如約 24h 處理邊界——考試前核對現行數字）。
- 功能對等範圍廣（工具、視覺、快取常支援），但在批次內用 `max_tokens: 0` **預熱快取**適配差，因為短暫快取可能在後續跑之前就過期。
- 設計模式：互動使用者走同步路徑；回填與評測掃描走批次路徑。

### 2. 提示工程與評測

**考試會出現的技巧**

- **清楚指令：** 說要做什麼、不要做什麼，以及輸出合約。
- **XML／標籤區段：** 把指示、脈絡、範例與使用者輸入分開，讓模型能把注意力放在對的區塊。
- **Few-shot（少樣本）範例：** 展示符合期望風格與邊界案例的輸入→輸出配對。
- **思維鏈（適當時）：** 對困難問題要求有推理步驟；對結構化萃取，優先用 schema 而不是開放漫談。
- **角色提示：** 把專業與限制放進 `system`。
- **分隔符衛生：** 絕不把不可信的使用者文字在沒有清楚邊界的情況下接到指示旁邊——降低指示注入風險。

**原創迷你模式（僅供研讀）**

```text
system:
 <role>You extract invoice fields.</role>
 <rules>If a field is missing, use null. Never invent tax IDs.</rules>
 <output>JSON object with keys vendor, total, currency, due_date.</output>

user:
 <document>
... raw OCR text...
 </document>
```

**評測心態**

- 正式環境不要「用眼睛看」提示詞。建一小份案例資料集（快樂路徑、邊界、對抗性）。
- 自動化評分：精確比對、評分量規分數，或帶固定評分量規的模型當裁判。
- 迭代：一次只改一個提示變數；追蹤回歸。
- 產生合成測試案例，再人工抽查真實性。
- 把**提示回歸**與**模型版本**回歸分開——評測執行釘住 model id。
- 品質之外也追蹤成本與延遲；品質提升 2% 卻讓 token 變成三倍，可能是產品損失。

**評測迴圈（記住）**

1. 把任務成功準則寫下來。
2. 收集 30–200 筆已標註案例（從小開始）。
3. 凍結評分者（指令碼或評分量規）。
4. 跑基準線 → 改一件事 → 比較。
5. 只有品質↑且成本／延遲可接受才晉升。

### 3. 用 Claude 做工具使用

**核心迴圈**

1. 送出使用者訊息 + 工具定義（`name`、`description`、JSON `input_schema`）。
2. 模型可能回傳一個或多個 `tool_use` 區塊（id、name、input）。
3. 你的應用執行工具（並強制授權！）。
4. 附加綁到每個 `tool_use` id 的 `tool_result` 區塊；繼續對話直到模型用純文字回答（或再呼叫更多工具）。

**設計提示**

- 描述是提示詞的一部分：精確說明何時呼叫工具、每個欄位是什麼意思。
- 寧可要許多小型、可組合的工具，也不要一個參數含糊的巨型工具。
- 處理平行／批次工具呼叫：安全執行（冪等、逾時、部分失敗）。
- 內建／伺服器工具（例如網頁搜尋、程式碼執行、依產品介面而異的電腦操作變體）與用戶端執行的工具不同：知道哪一邊跑程式碼。
- `tool_choice` 可以輕推或強制工具使用（`auto`／`any`／指定工具／none——在現行文件確認確切列舉）。
- 對嚴格參數有效性，有提供時啟用 schema 嚴格工具模式。

**平行工具檢查清單**

- 一則助理訊息可含多個 `tool_use` 區塊。
- 在下一則使用者訊息為每個 id 回傳**一個** `tool_result`（可以是同一則使用者訊息的內容陣列）。
- 失敗：仍回傳帶錯誤負載的結果，讓模型能恢復——不要省略 id。
- 並行：只平行化可以安全一起跑的工具（沒有衝突寫入）。

**用戶端工具 vs 伺服器工具**

| 種類 | 誰執行？ | 你的工作 |
|------|---------------|----------|
| 用戶端工具 | 你的應用／MCP 伺服器／後端 | 跑函式；送出 `tool_result` |
| 伺服器工具 | Anthropic 基礎設施 | 常在串流中以伺服器工具使用 + 結果區塊出現；你仍可能需要在 `pause_turn` 上繼續 |

**常見失敗**

- 忘了為每個 `tool_use` id 回傳結果。
- 執行使用者無權跑的工具。
- 上下文緊時把巨大原始工具傾印不加摘要就餵回去。
- 把幻覺出來的工具名稱當真實——對照你的登錄表驗證。
- 在 `content_block_stop` 之前解析中途的部分 JSON。
- 沒有最大迭代／預算護欄的無限工具迴圈。

**原創範例 — 天氣工具往返（概念）**

```text
Assistant content:
 [tool_use id=toolu_1 name=get_weather input={location:"Singapore"}]

Your next user content:
 [tool_result tool_use_id=toolu_1 content="31°C, thunderstorms"]

Then model produces end_turn text for the user.
```

### 4. RAG 與 agentic 搜尋

**為什麼要 RAG：** 上下文視窗有限；私有語料會變；你要帶來源的錨定答案。

**管線積木**

- **切塊：** 依大小／結構（標題、段落）切文件；重疊有助連續性。
- **向量嵌入 + 向量搜尋：** 模糊查詢的語意相似度。
- **BM25／詞彙搜尋：** 對精確詞、ID、罕見 token 很強。
- **混合檢索：** 結合詞彙 + 稠密；常再加**重排序**。
- **脈絡化檢索：** 用文件層脈絡豐富切塊，讓檢索較少歧義。
- **多索引：** 依語料或模態分開索引；路由查詢。

**注入模式**

```text
system: Answer ONLY using <sources>. If missing, say you don't know.
user:
 <question>...</question>
 <sources>
 [1]...chunk...
 [2]...chunk...
 </sources>
```

**Agentic 搜尋模式**

- 不是一次檢索→回答，而是讓模型（或規劃器）發出後續搜尋、精煉查詢，證據夠了再停。
- 永遠保留引用軌跡：哪些切塊 ID 支撐哪些主張。
- 為迴圈設預算：最大搜尋次數、最大 token、最大牆鐘時間。

**評測拆分（考試常考）**

| 層 | 指標構想 |
|-------|----------------|
| 檢索 | Recall@k、MRR、引用命中率 |
| 生成 | 忠實度、答案正確性、格式有效性 |
| 系統 | 延遲 p95、每次查詢成本、工具錯誤率 |

**陷阱**

- 切塊太大（雜訊）或太小（意義流失）。
- 檢索到相關文字，卻埋在弱提示下（「若有幫助請用脈絡」）。
- 不把檢索命中率與生成品質分開評測。
- 在 CMS 更新文件卻忘了重新索引。
- 讓模型引用未檢索到的來源（幻覺引用來源）。

### 5. Claude 延伸功能

- **延伸思考／推理模式：** 對困難多步驟問題有用；理解成本／延遲取捨，以及依 API 介面，思考內容可能與最終答案可分離。
- **影像與 PDF：** 以內容區塊傳入；要求結構化萃取；留意大型文件的 token／成本意涵。
- **視覺輸入：** 常見來源類型含 base64、URL 或 Files API 參照；媒體類型通常含 jpeg／png／gif／webp——確認現行限制。
- **文件／PDF：** 重複分析時優先經 Files API 上傳一次並以 id 參照；頁數限制與 token 成本對考試「規模下什麼會壞？」很重要。
- **引用來源：** 可用時，優先能把引文錨到來源跨度的功能，以做出可信 UX。
- **提示詞快取：** 標記穩定前綴；衡量快取命中率；不要把每請求機密或唯一 ID 放進會破壞重用的快取前綴。

#### 提示詞快取 — 操作細節

- 要記住的可快取前綴順序：**工具 → 系統 → 訊息**（以及到快取中斷點為止的納入內容區塊）。
- 把 `cache_control` 放在你期望重用的**最後一個共享區塊**——不要放在會讓快取鍵變差的唯一佔位使用者訊息上。
- 監控用量欄位，例如快取建立 vs 快取讀取 token（回應裡名稱如 `cache_creation_input_tokens`／`cache_read_input_tokens`）。
- TTL／短暫行為：知道快取條目會過期；高翻攪前綴會在重複寫入上浪費錢。
- 某些形式存在預熱（含用 `max_tokens: 0` 填快取的模式）——只有後續流量很快會命中時才用。

#### 檔案、視覺與文件 — 設計檢查清單

1. 品質允許時，上傳前先縮放／壓縮巨大影像。
2. 寧可要檔案 id，也不要反覆運送百萬位元組的 base64 負載。
3. 對 PDF：版面簡單時抽文字；版面重要時走文件／視覺路徑。
4. 建稽核軌跡時要求結構化欄位 + 頁碼參照。
5. 螢幕截圖進日誌或提示詞之前先遮蔽機密。

### 6. MCP（課程模組 — 高階）

這門 API 課也涵蓋建 MCP 伺服器／用戶端，讓工具與資源可跨主機重用。要深入，讀專用 MCP 筆記（`04-introduction-to-mcp.md`）。考試相關對應：

- 主機應用 ↔ MCP 用戶端 ↔ MCP 伺服器。
- 原語：**工具**（動作）、**資源**（唯讀資料）、**提示**（可重用指示模板）。
- 許多應用需要同一套整合時優先用 MCP；一次性原型優先用內嵌工具。
- 生命週期：初始化／協商能力 → 列出原語 → 呼叫工具／讀資源 → 乾淨關閉。
- 安全：使用者同意、最小權限，以及清楚邊界，即使工具經 MCP 到達而不是寫死的 JSON schema，仍然適用。

### 7. Anthropic 應用：Claude Code 與 Computer Use

- **Claude Code：** 終端機／IDE 裡的 agentic 程式助理；加速儲存庫任務；常整合 MCP 做專案工具。
- **Computer Use：** 模型驅動的 UI 自動化（螢幕截圖 + 動作）；強大且有風險 — 沙箱、最小權限、敏感步驟要人類核准。
- 認證框架：知道*用例*與*安全邊界*，不是產品行銷文案。
- 對應到 API 知識：Computer Use 是工具使用 + 視覺的極端形式；Claude Code 是帶權限、hooks 與 MCP connectors 的 agent 主機。

### 8. Agent 與工作流程

**工作流程 vs agent**

- **工作流程：** 你定義圖（步驟、分支）；模型填節點。確定性控制，較易測試。
- **Agent：** 模型用工具決定下一步，直到停止條件。彈性，較難評測。

**核心模式**

- **平行化：** 把獨立子任務扇出；合併結果。
- **串接：** 步驟 N 的輸出成為 N+1 的輸入（萃取 → 轉換 → 驗證）。
- **路由：** 分類意圖，再送到專門提示／模型／工具路徑。
- **除錯：** 記錄每次工具呼叫、中間狀態、token 用量；加逾時與最大迭代上限，防止失控迴圈。

**對照表**

| 模式 | 控制 | 最適合 | 失敗模式 |
|---------|---------|----------|--------------|
| 串接 | 高 | 像擷取、轉換、載入（ETL）的 LLM 步驟 | 沒有驗證器時錯誤串聯 |
| 平行 | 中 | Map-reduce 風格任務 | 合併衝突／不一致 schema |
| 路由 | 高 | 多領域助理 | 誤路由 → 錯的專家 |
| 自由 agent | 低 | 開放式研究 | 迴圈、支出暴衝、稽核困難 |

**正式環境護欄（考試寫這些）**

1. 最大工具迭代／最大牆鐘。
2. 每工具授權與允許清單。
3. 不可逆動作要人類核准。
4. 結構化日誌（request id、tool id、token、stop_reason）。
5. 失敗工具副作用的死信佇列。
6. 啟用新工具前先有評測套件。

**原創路由草圖**

```text
User message
 → cheap classifier (billing | technical | cancel)
 → billing prompt + CRM tools
 → technical prompt + docs RAG
 → cancel workflow (deterministic steps + confirmation)
```

### 9. 端到端請求解剖（研讀圖）

分層想，考試情境才不會糊成一團：

1. **傳輸／驗證層** — HTTPS、API 金鑰、版本標頭、可選 beta header。
2. **取樣層** — model id、temperature、`max_tokens`、停止序列、思考設定。
3. **上下文層** — `system`、先前 `messages`、檢索到的 RAG 切塊、影像／檔案。
4. **能力層** — `tools`／MCP 發現的工具、`tool_choice`、結構化輸出 schema。
5. **交付層** — `stream` 開／關；用戶端事件組裝；逾時。
6. **控制平面層** — 你的重試、速率限制預算、agent 迭代上限、授權。

若有東西失敗，先定位層。用戶端解析錯誤不是「模型品質」問題；沒有結果的 `tool_use` 不是 temperature 問題。

### 10. 值得記住的多回合對話模式

**A. 純對話**
使用者 → 助理（`end_turn`）→ 使用者 → …

**B. 工具中斷的回合**
使用者 → 助理（`tool_use`）→ 使用者（`tool_result`）→ 助理（`end_turn` 或更多工具）

**C. 平行工具**
使用者 → 助理（`tool_use` A + `tool_use` B）→ 使用者（`tool_result` A + `tool_result` B）→ …

**D. RAG 增強回合**
檢索器（使用者查詢）→ 使用者（問題 + 來源）→ 助理錨定答案

**E. 路由工作流程**
分類器 → 分支特定的系統／工具集 → 專門答案

**F. 批次離線**
把 N 筆獨立 Messages 參數入佇列 → 依 `custom_id` 輪詢／擷取結果

原創練習提示：給一份錯誤報告（「助理問了天氣卻從未回答」），對到模式 B，再問哪一跳壞了（模型沒呼叫工具／應用沒執行／應用沒回傳結果／第二次模型呼叫缺失）。

### 11. 提示詞快取實作範例（概念）

假設每張客服工單共享：

- 同一套 3 個工具（CRM 查詢、退款計算機、政策搜尋），
- 同一份 2,000 token 的政策系統提示詞，
- 但工單本文唯一。

**好：** 快取工具 + 系統（也許再加一份靜態政策資源）。只把工單文字放在中斷點之後、會變的使用者訊息裡。

**差：** 把 `Ticket #{{id}}` 放進被快取的系統字串——每張工單寫一個新前綴。

**衡量習慣：** 記錄快取寫入 token vs 快取讀取 token。功能「有用快取」但讀取接近零，是表演。

**失效直覺：** 改工具 schema、系統文字、思考／effort 設定，或中斷點位置，可能錯過先前的快取條目。想命中的請求之間，讓被快取的位元組保持位元組穩定。

### 12. 結構化輸出與工具 — 選合約

| 需求 | 優先選 | 註記 |
|------|--------|-------|
| 最終答案必須是可解析 JSON | 結構化輸出／JSON schema 模式 | 最適合給客戶的 API 回覆 |
| 模型必須呼叫你的函式 | 工具 + input_schema（+ 有則嚴格） | 最適合副作用 |
| 兩者都要 | 動作用工具 + 結構化最終文字／schema | 常見 agent 模式 |
| 只要軟格式 | 提示指示 | 脆弱；只用於原型 |

考試陷阱：「工具只用於副作用，從不用於 JSON。」歷史上，工具*也被*用來強制 JSON 形狀；現代結構化輸出功能對最終答案可能更乾淨——兩種故事都要知道，並查現行文件。

### 13. 速率限制、錯誤與韌性 playbook（操作手冊）

**為失敗分類**

| 訊號 | 可能類別 | 第一回應 |
|--------|--------------|----------------|
| 401／403 | 驗證／權限 | 修金鑰／範圍；不要盲目重試 |
| 400 | 請求形狀／參數 | 修負載；記錄主體（已遮蔽） |
| 404 | 路徑錯／缺資源 | 修端點或檔案 id |
| 429 | 速率限制 | 退避；卸載；減少 token |
| 5xx／過載 | 容量 | 帶抖動重試；政策允許則回退模型 |
| SSE `error` 事件 | 串流中途失敗 | 乾淨中止 UI；可選恢復策略 |

**韌性模式**

- 每租戶 token bucket。
- 互動流量與批次流量分開佇列。
- 錯誤率暴衝時用斷路器。
- 非關鍵路徑回退到較小模型。
- 工具觸發的退款／郵件周圍用冪等鍵。

### 14. RAG 正式環境檢查清單（超越快樂路徑）

1. **語料治理：** 誰能加文件？個人識別資訊（PII）清洗？
2. **切塊策略有紀錄：** 大小、重疊、切分器版本——才能重現索引。
3. **向量嵌入模型版本釘住。**
4. **混合權重**在已標註查詢集上調，不是靠感覺。
5. 提示前**把 top-n 重排序**。
6. **提示強制引用來源**只能來自提供的 id。
7. **檢索為空時拒絕。**
8. **時效：** 發布時重新索引；相關時向使用者顯示文件更新時間。
9. **投毒覺察：** 不可信的使用者上傳文件可能指示模型——沙箱並標記它們。
10. **成本護欄：** 上限檢索 token；不要傾倒整本手冊。

### 15. Agent 除錯情境（考試風格）

**情境 1 — 支出暴衝。** 日誌顯示每回合 40 次工具呼叫。修復方法：最大迭代、工具允許清單、昂貴工具要求先計畫再行動。

**情境 2 — 不穩定的 JSON。** 物件中途 `stop_reason=max_tokens`。修復方法：提高上限、縮小 schema，或繼續；寫入資料庫前驗證。

**情境 3 — 選錯工具。** 描述重疊（「search」vs「search_users」）。修復方法：改名、收窄描述、加「何時不要用」註記、減少工具數量。

**情境 4 — 錨定落空。** 答案聽起來自信卻沒有來源。修復方法：檢索評測；加強「只用來源」系統規則；可用則加引用來源功能。

**情境 5 — 快取從不命中。** 中斷點在唯一使用者回合上。修復方法：把中斷點移到共享系統／工具。

### 16. API 建造者的安全與合規註記

- 把提示詞 + 工具結果當**資料存放處**：它們可能含機密；清洗日誌。
- 把**模型信任**與**工具信任**分開：即使模型要求 `delete_all_users`，你的授權層也必須拒絕。
- 經檢索文件或網路工具結果的提示注入是真的——不可逆動作優先用允許清單工具與確認。
- 對 Computer Use／瀏覽器工具：專用 VM、沒有正式環境憑證、要求時錄製工作階段供稽核。
- 資料保留：知道你的組織是否要求零資料保留選項或區域處理（雲端課程另講 Bedrock／Vertex 落地）。

### 17. 把課程模組對應到你必須能示範的技能

| 模組 | 要能憑記憶示範的技能 |
|--------|---------------------------|
| 存取 API | 驗證、messages、system、串流、結構化輸出 |
| 提示工程 | 標籤提示 + 評測迴圈 |
| 工具使用 | 完整用戶端工具迴圈 + 平行 + 伺服器工具覺察 |
| RAG／agentic 搜尋 | 混合檢索 + 引用 + 迭代 |
| MCP | 何時把工具／資源／提示外置 |
| Claude Code／Computer Use | 用例 + 安全邊界 |
| Agent／工作流程 | 串接／平行／路由 + 護欄 |

## 考試提示

1. **Messages vs Completions 心智模型：** Claude 的公開 API 路徑以 Messages 為中心；系統在頂層。
2. **工具迴圈完整性：** 每個 `tool_use` 需要對應的 `tool_result`（或刻意中止策略）。
3. **串流組裝：** 文字增量 vs 工具的部分 JSON — 除非你知道它完整，否則不要在串流中途 `json.loads`。
4. **評測勝過感覺：** 預期會考資料集、評分者，以及改提示時的回歸。
5. **RAG 是兩套系統：** 檢索品質與生成品質失敗方式不同 — 分開診斷。
6. **快取與成本：** 知道快取*什麼*（穩定前綴）以及*為什麼*（延遲 + 支出）。
7. **安全：** 金鑰、工具授權、computer-use 沙箱，以及日誌裡的 PII，對「這個設計哪裡不對？」都是公平考題。
8. **MCP 指引：** 若題目提到跨主機標準化可重用工具，想到 MCP — 不是臨時複製 schema。
9. **重試前永遠先讀 `stop_reason`。**
10. **Batches ≠ 串流聊天。** 產品形態不同。
11. **平行工具：** 對 id，不要只對名稱。
12. **速率限制：** 退避 + 抖動；把 RPM 與 token 預算分開。

## 考試陷阱（常見錯答）

| 陷阱 | 為什麼錯 | 較好答案 |
|------|----------------|---------------|
| 把 `role: "system"` 放進 `messages` | Messages API 形狀錯誤 | 頂層 `system` |
| 假設串流改變答案品質 | 交付 ≠ 取樣語意 | 同一請求參數 → 同一最終內容意圖 |
| 丟掉失敗的工具 id | 模型永遠等／出錯 | 為該 id 回傳錯誤 `tool_result` |
| 把唯一使用者問題當前綴快取 | 毀掉命中率 | 快取工具／系統／靜態文件 |
| 一個巨型工具 `do_anything` | 參數含糊、授權困難 | 小型工具、清楚 schema |
| RAG 只量最終答案準確度 | 掩蓋檢索失敗 | 分開量檢索與生成 |
| 沒有最大 agent 迭代 | 成本／失控風險 | 硬上限 + 緊急停止開關 |
| 把 API 金鑰放進行動應用 | 金鑰遭竊 | 後端代理 |

*（第 1 列時效註記：最新 Opus／Fable 層級模型現在接受對話中途 `{"role": "system"}` 訊息 — 但「頂層 `system`」仍是基礎考試對系統指示該住哪的正確答案。）*

## 自我檢核問答

**Q1. 系統指示在 Messages API 放哪裡？** 
**A：** 頂層 `system` 參數 — 不是角色為 `system` 的訊息。

**Q2. Claude 回傳 `tool_use` 區塊後，你的應用必須做什麼？** 
**A：** 執行已授權工具，然後用對應的 `tool_result` 內容區塊（依 tool use id）繼續對話。

**Q3. 舉一個要串流回覆的理由。** 
**A：** 較低的感知延遲／漸進 UI 更新；最終組裝的訊息應與非串流語意相符。

**Q4. 為什麼 RAG 要把 BM25 與向量嵌入結合？** 
**A：** 詞彙搜尋抓住精確 token／ID；稠密搜尋抓住語意改寫；混合 + 重排序常勝過單獨任一方。

**Q5. 用一句話說明提示評測工作流程？** 
**A：** 固定測試案例 + 自動評分，讓提示變更可衡量、回歸可被抓住。

**Q6. 何時確定性工作流程比開放式 agent 更好？** 
**A：** 當步驟已知、合規／可稽核性重要，或你需要可靠的服務水準協議（SLA）與更便宜的除錯。

**Q7. 提示詞快取前綴該放什麼？** 
**A：** 跨請求重用的穩定內容（長系統提示詞、工具定義、靜態文件）— 不是會毀掉命中率的每使用者唯一負載。

**Q8. MCP 與這門 API 課有何關係？** 
**A：** 它標準化主機如何發現並呼叫外部工具／資源／提示，而不是每個應用重發明 schema。

**Q9. `stop_reason: "max_tokens"` 意味著什麼？** 
**A：** 輸出撞上你的上限；提高 `max_tokens` 或繼續生成——不要把截斷的 JSON 當完整。

**Q10. `input_json_delta` 做什麼用？** 
**A：** 串流部分 JSON 片段，在內容區塊停止後組裝成工具的 `input` 物件。

**Q11. 用戶端工具 vs 伺服器工具——誰跑程式碼？** 
**A：** 用戶端工具在你的環境跑；伺服器工具在 Anthropic 那邊跑（你的應用仍可能需要繼續回合）。

**Q12. 為什麼需要 `max_tokens`？** 
**A：** 它限制生成成本／長度；模型可能較早停，但你永遠設天花板。

**Q13. 點名兩個速率限制維度。** 
**A：** 每分鐘請求與每分鐘 token（輸入／輸出）；429 需要退避。

**Q14. 何時會用 Message Batches？** 
**A：** 大型非同步工作（評測、回填），不需要互動延遲，且折扣定價有幫助。

**Q15. 如何處理平行 `tool_use` id？** 
**A：** 執行每個已授權工具，並在後續使用者回合為每個 id 回傳一個 `tool_result`。

**Q16. 萃取用的安全 temperature 預設是什麼？** 
**A：** 在舊模型（4.6 及更早）：低 temperature 加上 schema。現行前沿模型已移除取樣參數 — schema／結構化輸出**就是**確定性槓桿。

**Q17. 視覺影像應如何提供？** 
**A：** 作為影像內容區塊，經支援來源（例如 base64、URL 或 Files API id）——不是假裝的文字路徑。

**Q18. 脈絡化檢索想修什麼？** 
**A：** 缺文件層脈絡的歧義切塊，會傷害向量嵌入匹配品質。

**Q19. 為什麼評測要釘住 model id？** 
**A：** 這樣提示變更才不會跟默默的模型升級混在一起。

# CCAR-F 領域 4 缺口卡（2026-08-23 新增）

> 精簡補充，對準**考試指南任務 4.3／4.4／4.6** 的細節，上文只輕觸。對照官方任務陳述的原創綜合整理。

## G1. 對抗捏造的 schema 設計（任務 4.3）

- **可空／可選欄位防止捏造：** 若來源文件可能缺某欄，**必填** schema 欄會強迫模型捏造一個值來滿足 schema。改成**可選／可空**，模型才能回傳 null — 這是考試對「模型捏造值」的標準修復方法。
- **可擴充列舉：** 對歧義案例加 `"unclear"`，對列舉外類別加 `"other"` **外加一個細節字串欄** — 封閉列舉會強迫誤分類。
- **經 tool_use 的嚴格 schema 只消除*語法*錯誤** — 從不消除*語意*錯誤（明細加總對不上所稱總額、正確值放錯欄）。語意檢查是驗證層工作（G2）。
- 來源格式會變時，在嚴格輸出 schema 旁邊把**格式正規化規則放進提示詞**。

## G2. 驗證、重試與回饋迴圈（任務 4.4）

- **帶回饋錯誤重試：** 驗證失敗時，後續請求包含**原始文件、失敗的萃取，以及具體驗證錯誤** — 模型對具名錯誤自我修正，遠勝於光說「再試一次」。
- **重試的限制（會考）：** 重試修**格式／結構**錯誤；當資訊**不在來源裡**（或住在你沒提供的文件裡）時無效。燒掉重試前先診斷你有*哪一類*失敗。
- **自我修正流：** 同時萃取 `calculated_total` 與 `stated_total` 以標記差異；對不一致來源資料加 `conflict_detected` 布林值。
- **`detected_pattern` 欄位：** 為每個發現標上觸發它的程式構建／模式，讓被駁回的發現能系統分析誤報模式（餵進 4.1 精確率迴圈）。

## G3. 多實例與多遍次審查（任務 4.6）

- **自我審查限制：** 產生程式碼的模型**保留其推理脈絡**，不太可能在同一工作階段質疑自己的決定。「仔細審查你的工作」指示或延伸思考，都不能替代獨立性。
- **獨立審查實例：** 第二個**沒有產生者推理脈絡**的 Claude 實例，能抓住自我審查漏掉的細微問題（與檔案 05 補充篇的持續整合（CI）工作階段隔離點成對）。
- **多遍次審查：** 把大型審查拆成**逐檔本地遍次 + 跨檔整合遍次** — 造成單遍次審查不一致的是注意力稀釋，不是上下文大小（見 08 §6）。
- **校準後路由：** 讓審查者在每個發現旁自我回報**信心**以啟用審查路由 — 然後在信任那些分數前先校準（見 09 §5）。

## G4. 缺口卡問答

**GQ1.** 模型填了一個文件沒有的發票欄位。Schema 修復方法？
**A.** 把該欄改成可選／可空 — 必填欄強迫捏造。

**GQ2.** 嚴格 tool-use schema 消除哪些錯誤，什麼會留下來？
**A.** JSON 語法錯誤被消除；語意錯誤（加總錯誤、放錯欄的值）留下來，需要驗證邏輯。

**GQ3.** 描述帶回饋錯誤重試。
**A.** 後續請求 = 原始文件 + 失敗的萃取 + 具體驗證錯誤，引導針對性自我修正。

**GQ4.** 何時重試永遠修不好萃取？
**A.** 當所需資訊不在提供的來源裡 — 那是資料問題，不是格式問題。

**GQ5.** 為什麼獨立實例比「徹底審查你自己的程式碼」更好？
**A.** 產生者保留其推理脈絡，不會質疑自己的決定；獨立性拿掉那種偏見。

**GQ6.** 審查發現裡 `detected_pattern` 欄的用途？
**A.** 讓你能系統分析哪些構建觸發被駁回的發現 — 這是削減誤報類別的原料。

**Q20. 什麼是路由工作流程？** 
**A：** 分類請求，再送到專門提示／模型／工具路徑。

**Q21. Agent 回合該記錄什麼？** 
**A：** 訊息 id、stop_reason、工具名稱／id／輸入（已遮蔽）、結果狀態、token 用量、延遲。

**Q22. 要記住的快取前綴順序？** 
**A：** 工具，然後系統，然後訊息——直到快取中斷點。

**Q23. `pause_turn` 在發什麼訊號？** 
**A：** 長時間伺服器端回合暫停；依文件繼續，而不是當硬失敗。

**Q24. 為什麼工具描述是「提示工程」？** 
**A：** 模型用它們決定*何時*與*如何*呼叫工具——含糊描述造成錯誤呼叫。

**Q25. 把巨大 SQL 傾倒當 tool_result 有什麼問題？** 
**A：** 上下文膨脹與分心；摘要或分頁結果，原始資料留在伺服器端。

**Q26. 拒絕與空答案有何不同？** 
**A：** `stop_reason: "refusal"` 表示政策拒絕——用安全 UX 處理，不要對同一內容無限重試。

**Q27. 舉一個 Computer Use 安全控制。** 
**A：** 沙箱／最小權限／敏感 UI 動作要人類核准。

**Q28. 串接與平行化有何差異？** 
**A：** 串接是序列依賴；平行化把獨立工作扇出再合併。

**Q29. 為什麼把檢索指標與答案指標分開？** 
**A：** 糟糕答案可能是好文筆蓋在壞切塊上——或好切塊配弱提示；修復方法不同。

**Q30. 工具使用「卡住」時的第一個除錯步驟是什麼？** 
**A：** 檢查每個 `tool_use` id 是否收到 `tool_result`，並檢查 `stop_reason`／迭代上限。

## 快速實驗檢查清單（練習時不要複製課程實驗）

把這當私人操練清單，同時研讀官方文件／SDK：

1. **Hello Messages：** 單次使用者訊息 → 印出助理文字；然後加第二則使用者回合，並保留先前助理訊息。
2. **系統消融：** 同一使用者問題配三份不同系統提示詞；記下語氣與限制遵守。
3. **串流組裝：** 串接文字增量；可能時斷言與同一 seed／設定的非串流輸出相等。
4. **工具往返：** 假天氣工具；驗證 `tool_result` 上 id 吻合；若模型發出兩個工具，強制平行雙呼叫。
5. **結構化解析：** `{ "sentiment": enum, "confidence": number }` 的 schema；解析丟例外就讓建置失敗。
6. **迷你 RAG：** 三個 markdown 檔 → 切塊 → 向量嵌入或 BM25 → 帶「sources:」行回答。
7. **快取健全性：** 把長靜態系統提示詞放在快取控制後面；比較請求 1 vs 請求 2 的延遲。
8. **Agent 預算：** 最多 5 次工具迭代；迴圈時回「budget exceeded」而不是卡住。
9. **停止原因操練：** 故意把 `max_tokens` 設很小，確認你偵測到截斷。
10. **批次模擬執行設計：** 草擬 100 列分類列，帶 `custom_id` 與結果接回器（即使不呼叫 API）。
11. **429 模擬器：** 寫一個帶指數退避 + 抖動與最大重試上限的重試輔助。
12. **視覺萃取：** 一張螢幕截圖／收據影像 → 結構化 JSON 欄位；確認你沒有寫死假光學字元辨識（OCR）。

這些操練強化考試機制；它們不能取代 Anthropic 的計分測驗。
