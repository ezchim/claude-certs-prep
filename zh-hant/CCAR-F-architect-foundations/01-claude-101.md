# Claude 101 — 備考筆記

> **免責聲明：** 這些是原創備考筆記 — **非** Anthropic 官方材料。課程大綱來源：https://academy.claude.com/courses/claude-101。功能細節已對照公開的 Anthropic Help Center 文章核對；產品 UI 與方案閘門可能變動——考試前請再核對。

## 概覽

Claude 101 是 Anthropic 把 Claude 帶進日常工作的入門路徑。公開課程頁面描述為 **13 堂課與 1 次測驗**（約 2.5 小時），結束時會拿到完成徽章。它面向任何有 Claude 帳號的人（Free 到 Enterprise）。少數功能（例如 Cowork 與 Enterprise Search）需要付費或 Team／Enterprise 方案才能動手試；概念對考試仍然重要。

**讀完這份材料之後，你應該能做這些事**

- 解釋 Claude 是什麼，並進行一場有用的第一輪對話
- 寫出更清楚的提示詞，在結果不如預期時迭代，並把提示連到 AI 流暢度的 4D
- 在桌面應用程式的三種「工作形態」之間做選擇：逐輪 Chat、交辦工作（Cowork），以及打造軟體（Code）
- 用 Projects、Artifacts 與 Skills 組織脈絡與可重複的工作
- 用 Connectors、Enterprise Search 與 Research 擴大觸及範圍
- 把 Claude 對應到常見角色，並認識相鄰產品（Claude Code、Claude Tag、Claude Design、Claude for Microsoft 365、Claude in Chrome）

**典型模組路線（對齊公開大綱）**

1. 認識 Claude — 它是什麼；第一場對話
2. 拿到更好的結果 — 提示；Chat／Cowork／Code
3. 組織工作與知識 — Projects、Artifacts、Skills
4. 擴大觸及範圍 — Connectors、Enterprise Search、Research
5. 整合起來 — 角色用例；其他與 Claude 共事的方式

這些筆記以原創語言重寫概念，供閱讀與 Claude 認證備考。它們**不是**課程逐字稿。請把這裡的原創備考措辭當完整版使用；不要把它當成 Academy 課文。

**如何把本檔當主要研讀來源**

1. 先把關鍵概念地圖掃一遍
2. 按順序讀深入筆記（功能彼此堆疊）
3. 反覆操練決策樹／對照表，直到能不假思索挑對工具
4. 走一遍常見考試陷阱
5. 不偷看先做自我檢核，再對答案
6. 考前一晚用快速複習清單
7. 搭配 `02-ai-fluency.md` — Claude 101 應用框架；流暢度解釋框架

## 關鍵概念地圖

| 概念 | 一句話意義 | 流暢度連結 |
|------|------------------|--------------|
| 提示詞模式 | 給角色／舞台、任務與規則（脈絡、格式、限制） | 描述（Description） |
| 迭代 | 第一份輸出是草稿；用具體回饋精修 | 描述–明辨迴圈 |
| Chat | 在對話中逐輪協作 | 增強（Augmentation）預設 |
| Cowork | 交辦涉及檔案／應用程式的多步驟工作（受方案閘門限制） | 偏向自主代理的自動化 |
| Code | 打造軟體的工作形態 | 實作的自主代理 |
| Projects | 帶有知識 + 指示、跨對話持續的工作區 | 常駐的描述（Description） |
| Artifacts | 側邊面板裡的獨立輸出（文件、程式碼、應用程式） | 看得見的交付物 |
| Skills | Claude 可執行的可重複使用*操作程序* | 程序面的描述（Process Description） |
| Connectors | 連到網路服務或本機桌面工具 | 平台觸及範圍 |
| Enterprise Search | 公司知識檢索（Team／Enterprise） | 內部錨定 |
| Research | 超越單次對話猜測的、更廣的多來源調查 | 多步驟搜尋自主代理 |
| 4D 流暢度 | 委派（Delegation）、描述（Description）、明辨（Discernment）、盡責（Diligence） | 整套實踐 |
| 檢索增強生成（RAG，專案） | 知識變大時檢索相關切塊 | 容量但不超載 |
| 漸進式揭露（skills） | 需要時才載入相關 skill 片段 | 上下文衛生 |

**記憶掛鉤：** *形態 → 脈絡 → 交付物 → 程序 → 觸及範圍*

- 形態 = Chat／Cowork／Code
- 脈絡 = Projects（+ 指示）
- 交付物 = Artifacts
- 程序 = Skills
- 觸及範圍 = Connectors／Enterprise Search／Research

## 依主題的深入筆記

### 1. Claude 是什麼（以及不是什麼）

Claude 是 Anthropic 的 AI 助理，用於寫作、分析、程式協助、研究與協作解題。把它當**有能力的協作者**，不是神諭。它依訓練中的模式，加上你放進當前對話與已連線脈絡的內容，預測有幫助的回覆。

**考試風格要點：** 語氣上的自信 ≠ 正確。高風險事實需要獨立驗證、引用來源，或網路錨定。

**實務提示：** 每個新領域開頭先寫一份短「合約」：目標、受眾、限制，以及「完成」長什麼樣子。這會在你追逐巧妙措辭之前先把描述（Description）設好（見 AI 流暢度）。

**陷阱：** 丟一句模糊請求（「寫點 Q3 相關的東西」）然後怪模型。模糊進 → 空泛出。

**原創實作範例 — 第一份合約**

差：「幫忙做入職。」

較好：「你在協助一位新任 CS 經理入職。交付一份第 1 週用的 1 頁檢查清單。受眾：討厭空話的經理。必須包含：權限申請、夥伴會議、第一次工單跟班。避免：勵志語錄。若有任何歧義，起草前先問我 3 個澄清問題。」

**若考試問 X，想到 Y**

- X：「為什麼 Claude 捏造了一個統計數字？」→ Y：LLM 生成流暢的續寫；沒有錨定／工具時可能捏造。要驗證。
- X：「Claude 語氣自信時是否永遠正確？」→ Y：否。語氣 ≠ 真相。需要明辨。

### 2. 有效的第一輪對話

強的第一則訊息通常包含：

1. **你是誰／角色**（或 Claude 應扮演誰）
2. **你需要什麼**（具體交付物）
3. **脈絡**（受眾、利害、先前決策）
4. **格式與限制**（長度、結構、語氣、必須包含／必須避免）

公開課文常把簡單模式寫成 **角色 + 任務 + 脈絡 + 格式**，或舞台、任務與規則的三部分框架。記住*精神*，不要背品牌口號：**定向 → 指定 → 約束**。

**自我檢核習慣：** 送出前問自己「一個聰明的新進員工只靠這則訊息能否成功？」若不能，補脈絡。

**反模式**

| 反模式 | 為什麼失敗 | 修復方法 |
|--------------|--------------|--------|
| 單字請求 | 沒有交付物 | 點名產物 |
| 隱藏限制 | 語氣／長度錯了 | 寫出必須避免 |
| 整串郵件串全丟進去 | 雜訊 > 訊號 | 摘要利害 + 只貼關鍵摘錄 |
| 「扮成專家」但沒有任務 | 角色表演 | 角色 + 具體輸出 |
| 從不迭代 | 卡在草稿 1 | 精準回饋 |

**原創實作範例 — 改寫郵件**

提示詞骨架：

```text
角色：你是幫我改客戶信件的編輯。
任務：把下面的草稿改寫成一封語氣平靜的道歉信。
脈絡：客戶已經等了 6 天；我們沒達成 SLA；退款已核准。
格式：120–150 字；主旨列 + 本文；不要法律術語腔；以一個明確的下一步收尾。
規則：不要責怪客戶；不要捏造政策；凡無法從我的草稿核對的主張都要標記出來。
[貼上草稿]
```

### 3. 拿到更好的結果：常見修復方法

輸出不如預期時，先診斷失敗模式：

| 症狀 | 可能原因 | 修復方法 |
|---------|--------------|-----|
| 太空泛 | 脈絡太薄 | 補受眾、限制、歷史 |
| 長度錯了 | 期望沒說清楚 | 設字數／段落上限 |
| 結構錯了 | 沒展示格式 | 給骨架或範例 |
| 語氣錯了 | 預設「有幫助的專業人士」 | 點名語氣；貼一份樣本 |
| 聽起來合理但錯了 | 幻覺風險 | 驗證；要求來源／信心；用搜尋／Research |
| 過度附和 | 過度迎合（sycophancy） | 要求批評／對立觀點 |
| 對話串一團亂 | 轉折太多 | 用清理過的提示詞開新對話 |

**迭代心態**

- 把草稿 1 當起點
- 回饋要**精準**（「刪第 1 段；讓行動呼籲（CTA）具體」），不要只說「寫好一點」
- 若對話串糾纏，**開一場乾淨對話**並用更清楚的提示詞

**輕量評測（明辨的實務）**

對重複性工作：

1. 收集 5–10 份你已經信任的過去好範例
2. 寫出能重現它們的提示詞
3. 把 Claude 的輸出跟你的黃金範例比較
4. 記下缺口；把缺的規則烘進提示詞、Projects 或 Skills
5. 然後才把工作流程用在新資料上

這與「委派盡責迴圈」同一思路：先在已知答案上測試，再信任新答案。

**原創實作範例 — 每週指標短文的評測**

- 黃金標準集：你已發布的最近 4 篇週五寫作
- 輸入：同一份原始 CSV + 同一套專案指示
- 評分：事實吻合、長度、圖表標註、沒有捏造驅動因素
- 發現的缺口：Claude 在沒有資料時捏造「季節性」→ 加規則「只宣稱數字或我筆記裡出現的驅動因素」
- 把規則烘進專案指示；再測一次；然後上線使用

**若考試問 X，想到 Y**

- X：「輸出很空泛」→ Y：描述（Description）薄弱／缺受眾
- X：「不靠更好的『提示魔法』怎麼改進？」→ Y：迭代 + 評測 + Projects／Skills

### 4. 三種工作形態（桌面應用程式）

公開目標強調三種協作模式：

1. **逐輪（Chat）** — 來回起草、問答、在對話中分析。適合你每一步都要緊密控制時。
2. **交辦工作（Cowork）** — 較長的工作階段，Claude 較自主地操作檔案與應用程式。適合多步驟營運任務。通常受方案閘門限制（付費方案）。工作階段可以整理檔案、綜整研究、跑排程任務，並使用為 Cowork 範圍化的 projects。
3. **打造軟體（Code／Claude Code）** — 以實作為導向的工作：儲存庫、agent、程式工作流程。

**考試提示：** 對齊*任務形態*，不是閃亮模式。探索式腦力激盪 → Chat。「清理這個發票資料夾並摘要」→ Cowork 式交辦。「在儲存庫交一個功能」→ Code。

**陷阱：** 對仍需要逐輪判斷的任務使用 agentic 交辦（敏感客戶郵件、法律措辭）。

**決策樹 — 選形態**

```text
主要目標是逐句寫作／判斷語氣嗎？
 是 → Chat
 否 ↓
主要目標是可以放手讓它跑的多步驟檔案／應用程式操作嗎？
 是 → Cowork（若方案允許）
 否 ↓
主要目標是儲存庫裡的軟體／coding agent 工作流程嗎？
 是 → Code
 否 → 預設用 Chat，任務變大再升級
```

**對照 — Chat vs Cowork vs Code**

| 維度 | Chat | Cowork | Code |
|-----------|------|--------|------|
| 每步控制 | 最高 | 中等（先計畫再跑） | 中–高，靠引導 |
| 最適合 | 草稿、問答、判斷 | 跨檔案／應用程式的營運 | 實作 |
| 自主程度 | 低 | 較高 | 在儲存庫裡較高 |
| 方案閘門 | 存取最廣 | 常需付費 | 獨立的程式介面 |
| 誤用風險 | 浪費時間 | 無人看管的副作用 | 糟糕的提交／範圍蔓延 |
| 盡責焦點 | 審查文字 | 審查動作 + 檔案 | 審查差異比較 + 測試 |

**反模式**

- 為改寫一段話啟動 Cowork
- 用 Code 模式「想策略」卻沒有儲存庫
- 在不可逆動作上讓 Cowork 無人看管、沒有檢查點

### 5. Projects — 知識中樞

**Projects** 是專用工作區，帶有：

- 自己的對話紀錄
- **專案知識**（上傳後 Claude 可重複使用的文件）
- **專案指示**（語氣、專業、常駐規則）
- 可選的團隊分享同一份共享脈絡（Team／Enterprise）

公開 Help Center 框架：Projects 廣泛可用（含 Free，Free 有較小的專案數量上限）。付費方案上，大型知識庫可轉入 **RAG 模式**——Claude 檢索相關切塊，而不是把一切塞進視窗，擴大容量同時維持品質。

**何時用 Projects：** 你有穩定領域（產品文件、品牌聲音、客戶簡報），許多對話都應共享。

**不要跟 Skills 搞混：** Projects 存放 Claude 應*知道什麼*；Skills 編碼*如何*跑一套程序。Help Center 對比：Projects = 該工作區載入的靜態背景知識；Skills = 動態啟用、可跨 Claude 運作的專門程序。

**原創實作範例 — 「Acme Support」Project**

- 知識：FAQ PDF、嚴重度矩陣、退款政策、語氣範例
- 指示：「絕不捏造政策。引用政策標題。法律主張升級給人類。語氣：平靜、白話。」
- Project 內的對話：工單改寫、巨集草稿、每週主題摘要
- Project 外：**不要**期望同樣的政策錨定

**反模式**

- 一個巨型 Project 塞進每個客戶（脈絡滲漏）
- 上傳你不會放進共享雲端硬碟的機密
- 沒有指示，然後怪「Claude 忘了我們的聲音」
- 把專案知識當成永遠完整「在腦裡」，而 RAG 可能選擇性檢索——問尖銳問題；引用檔案

**若考試問 X，想到 Y**

- X：「如何跨對話重用品牌聲音？」→ Y：專案知識 + 指示
- X：「知識變很大——概念上會發生什麼？」→ Y：檢索相關切塊（RAG 風格），尤其在付費方案

### 6. Artifacts — 獨立輸出

**Artifacts** 出現在對話旁邊的專用面板。與其把長 HTML／程式碼／文件區塊埋在對話串裡，Claude 會渲染一份你可以預覽、複製、下載或迭代的東西。

當內容重要、自成一體、可編輯／可重用，且之後可能被引用時，Claude 傾向建立 artifact（通常比短對話回覆更長／更有結構）。

常見類型（概念上）：

- 文件（markdown／文字報告、計畫、貼文）
- 可直接複製的程式碼片段
- 互動／視覺件（簡單應用、圖表、計算機、SVG／圖解、React 元件）

**提示**

- 若卡在對話裡，明確要求：「把這個做成 artifact」
- 除錯時在預覽與底層程式碼之間切換
- 用 Artifacts 做可分享的交付物；把對話留給協商與批評
- 版本選擇器有助探索方向而不丟掉先前工作
- 發布／分享與進階行為（AI 驅動的 artifacts、artifacts 內的模型上下文協定（MCP）、持久儲存）依方案與設定而定——知道它們存在；考試細節請核對線上文件
- 現代 artifact 工作流程常需要程式碼執行／檔案建立能力

**原創實作範例**

要求把「定價比較計算機」做成 artifact → 在面板裡迭代 UI → 穩定後下載或分享。把協商（「要不要含年繳折扣？」）留在對話裡。

**反模式**

- 把 200 行程式的 HTML 應用只留在對話氣泡裡
- 每次整檔重貼來編輯，而不是針對 artifact
- 發布前不檢查儲存是個人還是共享（隱私）

### 7. Skills — 程序性機器

**Skills** 是可重複使用的指示集（常是指示、指令碼與資源的資料夾），用於多步驟工作流程：品牌流程、PDF 包裝、通話準備儀式、部落格管線等等。它們靠**漸進式揭露**提升一致性——Claude 載入相關部分，而不是把每個 skill 都倒進上下文。

高階需認得的類型：

- Anthropic 維護的 skills（例如更強的文件建立流程）
- 你撰寫的自訂 skills（Markdown 指示；可選指令碼）
- 組織佈建的 skills（Team／Enterprise）
- 目錄裡的合作夥伴 skills（常搭配 MCP connectors）

**Projects vs Skills（考試常考）**

| | Projects | Skills |
|--|----------|--------|
| 用途 | 存放知識 | 定義程序 |
| 最適合 | 長期脈絡、團隊參考 | 可重複的方法論 |
| 持續性 | 該專案內跨對話 | 當 skill 被叫用／相關時 |
| 隱喻 | 圖書館 + 家規 | playbook（操作手冊）／標準作業程序（SOP） |
| 載入 | 該工作區的背景 | 動態／隨需 |

它們很適合搭配：一套「客戶通話準備」Skill 可以從 Project 的知識庫拉取檔案。

**Skills vs Connectors／MCP（短）**

- Connectors／MCP = 對工具與資料的*存取*
- Skills = *如何*為一套工作流程使用那些工具
- 兩者並用：MCP 開門；Skills 教舞步

**Skills vs 自訂指示**

- 自訂指示 = 廣泛、永遠開啟的偏好
- Skills = 任務特定、相關時才載入

**陷阱：** 把一次性 trivia 編成 Skill，或把巨型 SOP 塞進沒有程序的 Project。

**原創實作範例 — 「每週狀態」Skill**

程序步驟：從筆記抽出主題 → 依風險分組 → 起草條列 → 請人類確認阻礙 → 格式化給 Slack。只有這套儀式每週重複時才附加。

**若考試問 X，想到 Y**

- X：「跨對話每次同一套程序」→ Y：Skill
- X：「工作區裡每次同一批文件與聲音」→ Y：Project
- X：「需要即時 Asana 資料」→ Y：Connector／MCP（+ 工作流程用的 Skill）

---

### 8. Connectors — 擴大觸及範圍

**Connectors** 把 Claude 連到外部工具。

- **網頁連接器** — 雲端應用（Drive、Notion、Slack、Asana、Gmail 等），常經 MCP 風格整合
- **桌面擴充功能** — 經桌面應用程式操作本機檔案與原生應用

設定模式：在目錄找到 → 連接 → 驗證身分 → 授予最小權限 → 用「你看得到 X 嗎？」測試。

**盡責角度：** 只安裝可信的 connectors；權限可撤銷；把已連線資料當成隱私審查的範圍。

**反模式**

- 「以防萬一」全部連上
- 沒有核准關卡就請 Claude 對外寄信
- 假設 connector 存取 = 無限的組織全域可見性（驗證與範圍很重要）

---

### 9. Enterprise Search 與 Research

- **Enterprise Search** — 觸及公司知識（通常是 Team／Enterprise）。常呈現為專用的組織知識工作區（例如「Ask Your Org」風格的 project），帶引導式 connectors 與針對搜尋最佳化的行為。適合答案住在內部文件、而非公開網路時。針對相對快速、帶引用來源的內部檢索做最佳化。
- **Research** — 單次對話猜測不夠時，跨來源的多步驟、agentic 調查；適合文獻式或競品掃描並做錨定。通常是付費方案；必須能用網頁搜尋。可用網路 + 已連線的內部脈絡；產出帶可核對引用來源的詳盡答案；可能較快耗盡用量上限。

**對照（考試常考）**

| | Enterprise Search | Research | 對話中的一般網頁搜尋 |
|--|-------------------|----------|-----------------------------|
| 主要工作 | 快速找內部知識 | 深度多步驟綜整 | 快速外部事實 |
| 典型來源 | 已連線的公司工具 | 網路 + 整合，多步驟 | 網路 |
| 深度 | 針對性檢索 | 廣調查 | 輕 |
| 方案註記 | Team／Enterprise | 付費方案常見 | 依設定而定 |

**考試提示：** 時效或來源錨定重要時用 Research／Search；仍要套用明辨——來源可能不完整或互相衝突。

**原創實作範例**

- 「我們的特休政策在哪？」→ Enterprise Search／內部 connectors
- 「比較三家競爭對手定價頁，並摘要自上季以來的變更」→ Research
- 「今年新加坡大獎賽幾點？」→ 對話中的網頁搜尋可能就夠

**若考試問 X，想到 Y**

- X：「內部 Slack + Drive 的答案」→ Y：Enterprise Search／connectors
- X：「幾分鐘內做出帶引用來源的多角度報告」→ Y：Research
- X：「一個快速公開事實」→ Y：網頁搜尋，不是完整 Research

### 10. 角色導向使用與產品導覽

課程收尾通常展示 Claude 跨角色（行銷行事曆、後續追蹤、分析、營運），並指向專門介面：

- **Claude Code** — 程式 agent／軟體工作
- **Claude Tag／Design** — 標記或設計導向工作流程（產品命名可能演變；知道它們作為相鄰工具存在即可）
- **Claude for Microsoft 365** — 在 M365 介面內工作
- **Claude in Chrome** — 瀏覽器脈絡協助

對考試：知道**何時**每種形態有幫助，不是每個 UI 點擊。

### 11. 把 Claude 101 對應到 AI 流暢度 4D

| 功能／習慣 | 最強的 D | 為什麼 |
|-----------------|-------------|-----|
| 在 Chat vs Cowork vs Code 之間選擇 | 委派（Delegation） | 任務拆分 + 平台覺察 |
| 提示詞合約、Projects、Skills | 描述（Description） | 目標、程序、行為 |

## 常見考試陷阱

1. **Projects = Skills** — 錯。知識／工作區 vs 程序。
2. **Artifacts 只是漂亮的對話** — 錯。側邊面板的獨立交付物。
3. **更多自主 = 更少監督** — 錯。Cowork／Code／Research 需要*更多*明辨與盡責。
4. **自信語氣 = 已驗證事實** — 錯。
5. **Free 方案能做每個動手示範** — 錯。Cowork／Enterprise Search／部分 Research 行為受方案閘門限制；定義仍可考。
6. **Connectors 取代 Skills** — 錯。存取 ≠ 程序。
7. **Enterprise Search = Research** — 錯。快速內部檢索 vs 深度多步驟調查。
8. **自訂指示 = Skills** — 錯。永遠開啟的廣泛偏好 vs 任務特定、載入的程序。
9. **RAG 表示 Claude 每次完整讀完每個檔案** — 誤導。知識很大時，檢索只拉相關切塊。
10. **所有客戶共用一個 Project 沒問題** — 有風險。脈絡滲漏；敏感事項宜分開。
11. **「寫好一點」是好回饋** — 弱。要精準。
12. **發布 artifact 沒有隱私面向** — 錯。共享儲存／組織分享規則很重要。
13. **流暢度只是提示把戲** — 錯。4D 協作技能（見課程 02）。
14. **Claude 起草了你就可以跳過人類課責** — 錯。工作產物由你擁有。

## 擴充自我檢核（問答）

**Q1.** 同事說 Projects 與 Skills 一樣，因為兩者都「給 Claude 脈絡」。你如何糾正？

**A1.** Projects 主要在工作區內跨對話保存可重用的*知識與常駐指示*。Skills 編碼*可重複程序*，相關時被叫用或載入。知識 vs 程序；兩者互補。

**Q2.** 你需要一頁客戶道歉信，且必須控制每一句。哪種桌面「工作形態」最合適，為什麼？

**A2.** Chat（逐輪）。高判斷與語氣控制偏好對話式迭代，而不是長交辦。

**Q3.** Claude 的市場統計看起來精緻，但你無法核對。該怎麼做？

**A3.** 當成可能是錯的；獨立驗證；要求來源／信心；為當前事實啟用網路／Research 錨定。

**Q4.** 舉一個描述（Description）薄弱的症狀與一個修復方法。

**A4.** 例如：空泛輸出 → 補受眾、限制與格式範例。

**Q5.** 每週指標寫作的輕量評測是什麼？

**A5.** 拿上個月已知良好的寫作，用同一批原始輸入提示 Claude，跟你的原文比較，再把缺的規則烘進提示詞／Project／Skill，然後才用在新資料上。

**Q6.** 專案知識變很大時，什麼概念轉變有助容量？

**A6.** 從把所有檔案載入上下文，轉為只檢索相關切塊（RAG 風格），讓答案保持錨定又不溢出視窗（付費方案特別強調）。

**Q7.** 網頁連接器 vs 桌面擴充功能——關鍵差異？

**A7.** 網頁連接器連雲端服務；桌面擴充功能經桌面應用程式在本機跑，用於檔案／原生應用。

**Q8.** 「我對最終報告課責，被問時會揭露 AI 協助」對應哪一個流暢度 D？

**A8.** 盡責（Diligence）（責任、透明度、合乎倫理的使用）。

**Q9.** 何時應偏好 Research 而不是單次網頁搜尋答案？

**A9.** 當你需要多步驟、多來源綜整，帶系統性探索與引用來源——而不只是一個快速事實。

**Q10.** Enterprise Search 與一般 Project 有何不同？

**A10.** Enterprise Search 專門做組織知識檢索（常自動佈建、針對搜尋最佳化、有引導式 connectors）。一般 Projects 是通用工作區，帶使用者可自訂的指示與知識。

**Q11.** 舉一個誤用 Cowork 的例子。

**A11.** 交辦仍需句級人類判斷的敏感法律信函、卻沒有緊密檢查點——或在沒有審查的情況下跑不可逆檔案操作。

**Q12.** Skills vs MCP connectors，各一句。

**A12.** Skills 教*如何*執行一套工作流程；MCP／connectors 提供對外部工具與資料的*存取*。

**Q13.** 專案指示 vs 專案知識該放什麼？

**A13.** 指示 = 常駐規則／語氣／角色行為。知識 = Claude 應取用的參考檔與事實。

**Q14.** 舉三種常見 artifact 內容類型。

**A14.** 任三：文件、程式碼片段、HTML 頁、SVG／圖解、互動元件／計算機。

**Q15.** 為什麼開新對話，而不是繼續一團亂的對話串？

**A15.** 糾纏的脈絡造成漂移；目標澄清過的乾淨提示詞，往往勝過沒完沒了的補丁。

**Q16.** 把 Artifacts 對應到一個流暢度概念。

**A16.** 它們讓描述（Description）的*產物*看得見、可編輯——支援對具體交付物的明辨。

**Q17.** Free 方案考試陷阱：即使你點不到每個功能，哪些概念仍然重要？

**A17.** Cowork、Enterprise Search、Research 等的定義與適配任務的推理，仍是公平考題。

**Q18.** Skills 的漸進式揭露是什麼？

**A18.** Claude 只載入與任務相關的 skill 資訊，降低上下文超載。

**Q19.** 你需要 Claude 每週五遵循同一套 PDF 包裝步驟。Project 或 Skill——主要選擇？

**A19.** Skill（程序）。品牌資產可選擇放在 Project。

**Q20.** 「AI 寫的，所以我不負責。」哪個 D 失敗了？

**A20.** 盡責（Diligence）——人類仍對 AI 協助的工作課責。

**Q21.** 選工具：從已連線的 Slack + Drive 摘要主題，回答「定價我們決定了什麼？」

**A21.** Enterprise Search／組織知識 connectors（內部）。若還需要深度外部競品綜整，再用 Research。

**Q22.** 什麼回饋比「寫好一點」更好？

**A22.** 精準指示：刪什麼、加什麼、語氣目標、長度、必須保留的事實。

**Q23.** 為什麼把客戶事項分到不同 Projects？

**A23.** 降低脈絡滲漏；把紀錄、檔案與指示隔開，兼顧準確與機密。

**Q24.** Code vs Chat，用於「解釋這份堆疊追蹤並提出修補」，而你不在儲存庫 agent 工作流程裡時？

**A24.** Chat 可以分析並提出建議；當你要在實際儲存庫做 agentic 實作時再切到 Code。

**Q25.** 如何在一套工作流程裡組合 Project + Skill + Artifact？

**A25.** 例如：Project 保存產品文件；Skill 跑「發行說明儀式」；Artifact 是你預覽並分享的最終 markdown 說明。
