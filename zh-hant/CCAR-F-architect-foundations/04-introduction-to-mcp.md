## 概覽

模型上下文協定（MCP）是一套開放標準，用來把 AI 主機（Claude Desktop、整合開發環境（IDE）、自訂 agent）連到外部工具與資料，**不必**為每一種應用程式×服務組合親手寫一份獨一無二的 JSON 工具 schema。入門課程公開的學習目標強調：架構（把工具定義／執行移到專門伺服器）；與傳輸層無關的訊息傳遞；端到端請求流程；用 Python SDK 打造伺服器（裝飾器對上手寫 JSON schema）；文件風格工具；MCP Inspector；**資源**（直接型＋模板型）；用戶端讀取資源與 MIME 類型；**提示**作為可重用工作流程；在工具／資源／提示之間做選擇；以及自動完成、上下文注入等整合模式。

**公開模組形狀：** 導論 → 動手做 MCP 伺服器 → 連接 MCP 用戶端。

**公開點名的先修：** 基礎 Python、async/await、API 素養。

**這份筆記與 API 課程的關係：** Building with the Claude API 教的是*單一*應用程式內部的 Messages／工具迴圈。MCP 教的是許多應用程式如何透過共同協定，共享同一組外部能力。考試時，若看到「跨主機重用」或「Inspector」，就想到 MCP。

## 關鍵概念（速查表）

| 概念 | 一句話 |
|---------|-----------|
| **主機（Host）** | 使用者看到的 AI 應用程式（編排用戶端、UI、模型呼叫） |
| **用戶端（Client）** | 主機內的連接器；與單一 MCP 伺服器**一對一** |
| **伺服器（Server）** | 暴露工具、資源與／或提示的行程／服務 |
| **工具（Tools）** | 模型控制的動作（允許副作用；類似函式呼叫） |
| **資源（Resources）** | 應用程式控制、大致唯讀、以統一資源識別碼（URI）定址的資料 |
| **提示（Prompts）** | 使用者控制、預先打造的指示模板 |
| **傳輸層（Transport）** | JSON-RPC 訊息如何移動（本機常見 **STDIO**；遠端為 Streamable HTTP／SSE） |
| **資料層（Data layer）** | JSON-RPC 方法、生命週期、原語、通知 |
| **Inspector** | 瀏覽器輔助工具，用來列出／呼叫工具並為伺服器除錯 |
| **能力協商** | initialize 握手，雙方聲明各自支援什麼 |

**心智模型：** 主機問模型該做什麼 → 模型可能選一個工具 → 用戶端呼叫 MCP 伺服器 → 伺服器與真實系統交談 → 結果回流進模型上下文。

## 分主題深入筆記

### 1. MCP 為什麼存在

沒有 MCP，每個 AI 應用程式都要為 GitHub、Slack、資料庫、檔案系統等重複寫整合程式碼。有了 MCP：

- **N 台伺服器**（每台對應一個系統或能力領域）＋ **M 個主機／用戶端**，勝過 **M×N** 個客製轉接器。
- 伺服器擁有後端的身分驗證、輸入驗證，以及領域邏輯。
- 主機專心做使用者體驗、政策與模型編排。

考試用語要記住：MCP 把工具定義與執行的負擔，從你那個單體應用伺服器**轉移**到**專門的 MCP 伺服器**。

**比喻：** USB 標準對上各家專有線材。主機講 MCP；伺服器講 MCP；後端留在伺服器轉接層後面。

**MCP 不是什麼**

- 不是 Claude Messages API 的替代品（主機仍然呼叫模型）。
- 本身不是資料庫，也不是向量嵌入（embedding）儲存。
- 不保證安全——範圍訂得太鬆的伺服器仍然危險。
- 不是「只給 Anthropic 用」；它是開放協定，許多主機都能實作。

### 2. 架構：主機、用戶端、伺服器

```
User ↔ Host (LLM app) ↔ Client₁ ↔ Server₁ (e.g. docs)
 ↔ Client₂ ↔ Server₂ (e.g. calendar)
```

- **主機職責：** 生成／管理用戶端；把提示／資源呈現給使用者；決定哪些上下文送到模型；強制執行使用者同意與安全政策；運行或呼叫大型語言模型（LLM）。
- **用戶端職責：** 能力協商／工作階段生命週期；把主機需求翻譯成 MCP 請求；把一台伺服器與另一台隔開。
- **伺服器職責：** 宣告並實作原語；保持聚焦（單一領域比較容易保全與測試）。

**一對一規則：** 每個用戶端恰好只跟一台伺服器說話。使用三台伺服器的主機，就跑三個用戶端。這種隔離是考試最愛。

**本機對上遠端伺服器**

| | 本機（常為 STDIO） | 遠端（常為 Streamable HTTP） |
|--|---------------------|--------------------------------|
| 行程 | 主機啟動子行程 | 獨立服務 |
| 典型扇出 | 每個行程一個用戶端 | 許多用戶端連到同一服務 |
| 驗證故事 | 作業系統使用者權限 | HTTP 驗證／OAuth／token |
| 失敗模式 | 當機殺掉那一台伺服器 | 網路分區、版本落差 |

安全邊界提醒：被攻陷或權限過大的伺服器很危險——最小權限原則、清楚的 roots／路徑，以及敏感工具要使用者核准，即使在「本機」STDIO 設定裡也成立。

### 3. 分層：資料層對上傳輸層

官方架構把 MCP 分成：

1. **資料層** — JSON-RPC 2.0 訊息語意：生命週期、工具／資源／提示、通知，以及用戶端功能如取樣／詢問請求（elicitation）（進階）。
2. **傳輸層** — 位元組如何移動：STDIO 對上 Streamable HTTP（可選 SSE）、訊框處理，以及傳輸層驗證。

入門考試標準：你要能解釋**同一套** JSON-RPC 方法可以跑在不同傳輸層上。進階課程才深入講正式環境的 HTTP 擴展。

### 4. 訊息流程（請求 → Claude → 工具 → 回來）

典型的一輪：

1. 使用者在主機裡問一個問題。
2. 主機組裝上下文（對話紀錄、選定的資源、選定的提示模板）。
3. 主機呼叫 Claude，帶上從 MCP 伺服器發現的可用工具定義。
4. Claude 回傳一個工具呼叫（名稱＋引數）。
5. 主機／用戶端向對的伺服器送出 MCP `tools/call`。
6. 伺服器執行（讀檔、編輯文件、查詢 API）並回傳結構化結果。
7. 主機把工具結果附加進對話，再次呼叫 Claude。
8. Claude 產出使用者看得到的答案（或更多工具呼叫）。

要分清**請求／結果**成對（RPC 呼叫）與**通知**（單向事件）。更深的訊息分類出現在 Advanced Topics 課程。

**原創序列圖（文字）**

```text
User → Host: "Summarize Q3 plan doc"
Host → Client(docs): resources/read docs://q3-plan
Client → Server: resources/read
Server → Client: text/markdown body
Host → Claude: messages + tool defs + injected resource
Claude → Host: tool_use edit_section(...)
Host → Client: tools/call edit_section
Server → Client: ok
Host → Claude: tool_result
Claude → Host: final summary for user
```

### 5. 生命週期（入門深度）

MCP 工作階段不是「先亂射方法」。概念上的生命週期：

1. **連接**傳輸層（啟動 STDIO 行程或打開 HTTP 工作階段）。
2. **Initialize** — 交換協定版本、`clientInfo`／`serverInfo`，以及能力。
3. **initialized 通知** — 用戶端宣告自己準備好了。
4. **操作** — `tools/list`、`tools/call`、`resources/list`、`resources/read`、`prompts/list`、`prompts/get` 等。
5. **關閉** — 關閉串流／終止子行程；不要洩漏子行程。

**能力協商的直覺**

- 伺服器可以宣告支援工具、資源、提示，以及清單會不會變（`listChanged`）。
- 用戶端可以宣告支援伺服器稍後可能請求的功能（取樣、詢問請求——進階）。
- 呼叫不支援的方法是協定上的怪味——先探索。

考試提示：若被問「`tools/list` 之前發生什麼？」回答 **initialize／協商**，不是「立刻呼叫工具」。

### 6. 打造 MCP 伺服器（Python SDK 心態）

入門課程重點：用 SDK，這樣你就**不必**親手寫巨型 JSON schema。

- 裝飾器／型別提示／`Field` 描述會變成模型看到的工具中繼資料。
- 好的描述會大幅改善工具選擇——把它們當成提示工程。
- 公開大綱的範例領域：**文件管理**——讀取與編輯文件的工具。
- 工具要窄：`read_document(id)` 與 `update_section(id, section, text)` 勝過含糊的 `do_anything(payload)`。

**原創裝飾器風格草圖（示意，不是 SDK 傾倒）**

```python
# Conceptual only — verify current SDK APIs before coding
@server.tool()
def read_document(doc_id: str) -> str:
 """Return the full text of a document by id. Use when the user asks what's inside a doc."""
...

@server.tool()
def update_section(doc_id: str, section: str, text: str) -> str:
 """Replace one named section. Prefer this over rewriting the entire document."""
...
```

**描述寫作檢查清單**

- 工具做什麼，一句話。
- 什麼時候用／什麼時候不用。
- 單位、id 格式、副作用。
- 模型該預期的失敗模式。

**Inspector：** 跑起伺服器，在瀏覽器打開 MCP Inspector，列出工具、發射呼叫、檢查酬載，之後再接完整主機。這是考試題「如何為伺服器除錯」的絕佳答案。

### 7. 資源：直接型對上模板型

**資源**暴露以讀取為導向的資料，由*應用程式*（不是模型自己）決定要擷取並注入。

- **直接資源：** 靜態 URI，例如 `docs://index` 或 `config://app-settings`。
- **模板資源：** 帶參數的 URI 模板，例如 `docs://{doc_id}`——由用戶端填入參數。

用戶端讀取檢查清單：

- 用 URI 請求資源。
- 處理 **MIME 類型**（例如 `application/json` 對上 `text/plain`），才能正確解析。
- 刻意把內容注入模型上下文（整份文件對上摘錄）。

**何時用資源、何時用工具？** 若主要是「為上下文擷取資料」、沒有有意義的副作用 → 資源。若改變狀態或執行動作 → 工具。

**URI 設計提示**

- 每個伺服器領域用清楚的 scheme（`docs://`、`db://`、`config://`）。
- id 保持 URL 安全；把模板參數寫成文件。
- 注入提示時，優先用不可變快照，以便可稽核性。

**MIME 處理範例**

| MIME | 用戶端行為 |
|------|-----------------|
| `text/plain` | 當文字注入；或許截斷 |
| `text/markdown` | 同樣處理，可能的話保留標題 |
| `application/json` | 解析；或許美化列印選定欄位 |
| `image/png` | 主機可路由到具備視覺能力的訊息區塊 |

考試陷阱：忽略 MIME，永遠 `json.loads`——二進位或純文字會炸掉。

### 8. 提示作為 MCP 原語

**提示**是可重用、高品質的指示模板，用於常見工作流程（課程公開提到的例子包括文件格式化）。

- **使用者控制：** 通常從選單挑選（「把選取內容格式化成 RFC 風格備忘錄」），而不是由模型默默發明。
- 可以參數化欄位（標題、語氣、受眾）。
- 幫團隊跨主機共享最佳實務指示。

**原創提示模板草圖**

```text
Name: format_as_adr
Args: title, status, context
Body:
 Write an Architecture Decision Record titled {title}.
 Status: {status}.
 Context: {context}.
 Use sections: Context, Decision, Consequences.
```

主機使用者體驗：使用者挑提示 → 填入引數 → 主機展開 → 送給模型（可選擇附上相關資源）。

### 9. 在工具、資源、提示之間做選擇

| 原語 | 誰主導？ | 典型用途 | 有副作用？ |
|-----------|-------------|-------------|---------------|
| 工具 | 模型 | 搜尋、編輯、送出、運算 | 常常有 |
| 資源 | 應用程式／主機邏輯 | 把檔案、設定、資料集載入上下文 | 通常沒有 |
| 提示 | 使用者 | 用審過的指示啟動已知工作流程 | 沒有（只有指示） |

考試陷阱：什麼都叫「工具」。評分者要看的是上面那個控制平面區分。

**分類操練（背起來）**

- 「把 README 載入上下文」 → **資源**
- 「建立 GitHub issue」 → **工具**
- 「套用 ADR 模板」 → **提示**
- 「搜尋文件然後編輯」 → **工具**（已知 URI 時或許加上資源）
- 「出示公司風格指南」 → **資源**或**提示**，取決於它是原始資料還是工作流程模板

### 10. 傳輸層（入門程度）

MCP 在訊息層是**與傳輸層無關**的（JSON-RPC 風格訊息）。常見選項：

- **STDIO：** 用戶端把伺服器當子行程啟動；透過 stdin／stdout 溝通。適合本機桌面／IDE 整合。一般呼叫之前需要正確的**初始化握手**（細節在 Advanced Topics 講得更多）。
- **HTTP + SSE／Streamable HTTP：** 給遠端／連網伺服器；伺服器可以推送事件；想想工作階段、驗證與擴展的取捨。現代文件強調 **Streamable HTTP**（用戶端對伺服器發 HTTP POST，可選 SSE 做串流），且通常建議用 OAuth 處理 token。

入門考試標準：說出傳輸層名稱，並說明何時選本機 STDIO、何時選遠端 HTTP。雙連線 SSE 細節與無狀態水平擴展留給進階課程。

**傳輸層選擇備忘（原創）**

當伺服器必須碰本機檔案系統或開發者筆電的密鑰庫，而且主機能管理子行程時，用 STDIO。當全公司多個主機要共享一個受管整合（需要真正的驗證、稽核日誌與集中更新）時，用 Streamable HTTP。

### 11. 實務整合模式

- **上下文注入：** 主機讀取資源 → 把相關文字附到模型請求上。
- **自動完成／探索：** 列出工具、資源與提示，讓 UI 能建議動作。
- **生命週期：** 連接 → initialize／協商 → 操作 → 乾淨關閉（不要洩漏子行程）。
- **組合：** 一個主機、多台伺服器（文件＋issue 追蹤器＋資料庫），各自待在自己的用戶端後面。
- **通知：** 若伺服器宣告 list-changed 能力，它可以通知用戶端刷新 `tools/list`（以及類似清單）——主機應更新模型可用的工具。
- **錯誤浮現：** 工具失敗應變成模型看得到的結構化錯誤，而不是主機默默當掉。

### 12. 用戶端功能（指標——進階）

入門只要有意識（深度在 Advanced Topics）：

- **取樣（Sampling）：** 伺服器請主機／用戶端跑一次 LLM 補全（不綁定特定模型的伺服器）。
- **詢問請求（Elicitation）：** 伺服器請主機蒐集使用者輸入／確認。
- **日誌／進度：** 伺服器為長時間工作發出日誌或進度。

入門小考不要對這些過度宣稱——知道它們存在，並知道是哪一邊暴露它們。

### 13. 安全考量（入門必過）

1. **使用者同意：** 主機應核准敏感的工具呼叫，尤其是第一次使用。
2. **最小權限原則：** 檔案系統伺服器拿到的是目錄根，不是整個 `$HOME` 磁碟，能這樣就這樣。
3. **密鑰處理：** 伺服器應使用作業系統鑰匙圈／環境變數／密鑰管理器——不要把 token 寫死在工具回應裡。
4. **混淆代理人：** 一份惡意文件可能試圖脅迫模型去呼叫 `delete_repo`——仍然需要政策閘口。
5. **供應鏈：** 把第三方 MCP 伺服器當成安裝軟體；審查權限。
6. **傳輸層驗證：** 遠端伺服器需要真正的身分驗證；STDIO 繼承使用者的作業系統權限——預設仍然不安全。
7. **稽核：** 記錄工具名稱、遮蔽後的引數、操作者、時間戳記。

### 14. 端到端文件管理心智實驗

呼應課程的公開專案主題，但不抄實驗原文：

1. 伺服器暴露 `list_docs`、`read_document`、`update_section` 工具。
2. 伺服器暴露 `docs://{doc_id}` 模板資源與 `docs://index` 直接資源。
3. 伺服器暴露一個 `format_document` 提示。
4. 在接入 Claude 之前，先用 Inspector 呼叫 `read_document`。
5. 主機列出提示做成「格式化」選單；選定後展開提示，可選擇注入資源。
6. 當使用者要求編輯時，模型仍然可以把 `update_section` 當工具呼叫。

這一個領域就操練了**全部三種原語**。

### 15. MCP 對上普通的 Messages 工具定義

| 關注點 | Messages 裡普通的工具 JSON | MCP |
|---------|------------------------------|-----|
| 探索 | 寫死在應用程式裡 | 來自伺服器的 `*/list` |
| 重用 | 複製 schema | 跨主機共享伺服器 |
| 資源／提示 | 自己做 | 一等原語 |
| 維運 | 行程內函式 | 本機行程或遠端服務 |
| 何時最好 | 一個應用程式、少數工具 | 生態系／許多主機 |

橋接洞察：主機常常在底層把 MCP 工具 schema **翻譯**成模型供應商的工具格式。MCP 沒有拿掉 Claude 的工具迴圈——它標準化的是外層整合。

### 16. JSON-RPC 心智模型（輕量）

入門考試知道這些就夠：

- **請求：** 有 `id`、`method`、`params` → 期待同 `id` 的**結果**或**錯誤**。
- **通知：** 有 `method`（或許有 params）但**沒有 `id`** → 沒有回應。
- 方法長得像 `initialize`、`tools/list`、`tools/call`、`resources/read`、`prompts/get`。
- 未知方法／壞 params → 結構化 JSON-RPC 錯誤，不是 HTTP HTML 頁面（即使在 HTTP 傳輸層上，酬載仍然是 RPC 形狀）。

### 17. 常見失敗模式與除錯

| 症狀 | 可能原因 | 修復方法方向 |
|---------|--------------|---------------|
| 主機顯示沒有工具 | 初始化失敗／能力缺失／沒呼叫 list | 在 Inspector 檢查 initialize ＋ `tools/list` |
| 工具呼叫類似 404／未知工具 | 伺服器變更後清單過期 | 處理 list_changed；刷新 |
| MIME 解析錯誤 | 把文字資源當 JSON | 依 MIME 分支 |
| STDIO 伺服器卡住 | 握手未完成／stdout 被日誌污染 | 協定走 stdout；日誌走 stderr |
| 遠端 401 | 缺 bearer／OAuth | 修好傳輸層驗證 |
| 模型從不呼叫你的工具 | 描述太弱／重疊工具太多 | 改寫描述；精簡集合 |
| 子行程殭屍 | 主機沒有收尾生命週期 | 退出時拆除用戶端 |

### 18. 主機實作檢查清單（「好」長什麼樣子）

當你打造或審查一台講 MCP 的主機，評分者（以及正式環境審查者）要看的不只是「連過一次」。

1. **設定面：** 使用者可以新增／移除伺服器（STDIO 用 command＋args；HTTP 用 URL＋驗證）。
2. **同意使用體驗：** 第一次使用工具時提示；區分唯讀與會改動狀態的工具。
3. **統一登錄表：** 合併所有用戶端的工具，並用命名空間處理碰撞（`docs.read` 對上 `db.read`）。
4. **模型翻譯：** 把 MCP 工具 schema 對應成你的 LLM API 所期待的供應商工具格式。
5. **結果衛生：** 截斷巨大的工具輸出；保留足夠細節讓模型能繼續。
6. **取消：** 使用者可以中止長時間的工具呼叫；在支援時，用戶端取消進行中的 RPC。
7. **可觀測性：** 每台伺服器的延遲、錯誤率，以及注入了哪些提示／資源。
8. **優雅降級：** 一台伺服器掛了，其他伺服器繼續運作。

### 19. 伺服器設計模式（文件領域與之外）

**模式 A — 薄轉接層**
MCP 伺服器包住既有 REST API。工具 ≈ 端點。資源 ≈ 可以安全注入的 GET。

**模式 B — 領域門面**
較少、較聰明的工具（`search_and_summarize_locally`）把後端混亂藏起來。對模型較容易；較難讓描述保持誠實。

**模式 C — 讀寫分離**
把讀取暴露成資源；寫入暴露成需要確認的工具。乾淨對上控制平面三原語。

**模式 D — 提示包**
伺服器主要運送提示＋少數資源（風格指南）。適合團隊標準化工作流程，又不把寫入權交給模型。

**反模式 — 大雜燴**
一台伺服器任意 shell 出去、讀所有檔案、還能寄信。違反最小權限原則，也嚇到主機的權限 UI。

### 20. 對應 Claude Academy 模組 → 今晚的練習動作

| 公開模組 | 今晚練習什麼 |
|---------------|--------------------------|
| 導論 | 畫架構；背三原語 |
| 動手做伺服器 | 做 2–3 個工具；打開 Inspector |
| 連接用戶端 | 讀資源＋MIME 分支；列出提示；注入上下文 |

呼應 Building with the Claude API：MCP 回傳工具輸出之後，你仍然要做 Messages 的 `tool_result` 續接——MCP 沒有抹掉那個迴圈。

### 21. 走完的故事：自動完成＋上下文注入

**自動完成：** 主機在閒置時呼叫 `prompts/list` 與 `tools/list`。UI 顯示「格式化成 ADR」、「搜尋文件」、「建立 issue」。使用者挑「格式化成 ADR」→ 主機帶引數呼叫 `prompts/get` → 把展開的文字放進編輯器。

**上下文注入：** 使用者用 @ 提及一份文件。主機解析 `docs://{id}` 資源、檢查 MIME、把截斷後的本文注入下一則使用者訊息（放在標了標籤的 `<doc>` 分隔符裡），並且*另外*在使用者要求編輯時，繼續提供寫入工具。

考試洞察：自動完成是**探索 UX**；注入是**上下文組裝**。兩者都是主機職責，即使資料來自伺服器。

### 22. 版本與相容性心態

- 協定版本出現在 initialize；不相容的版本應快速失敗。
- 伺服器與主機獨立升級——能力旗標的存在，是為了讓可選功能不要硬性破壞。
- 考試時：優先回答「協商能力並優雅降級」，不要發明一個永遠不變的版本號。

8. 先 initialize，再 list／call。
9. 通知 ≠ 請求（沒有回應 id）。
10. MCP 補足 Messages 的工具使用；它沒有刪掉 tool_result 迴圈。

## 自我檢核問答

**Q1. MCP 的三個角色是什麼？**
**A：** 主機（LLM 應用程式）、用戶端（一對一連接器）、伺服器（暴露原語）。

**Q2. 誰通常決定呼叫一個工具？**
**A：** 模型（加上主機的政策閘口）；工具是模型控制的動作。

**Q3. 誰通常選取提示模板？**
**A：** 使用者（使用者控制的原語），通常透過 UI。

**Q4. 直接資源對上模板資源？**
**A：** 直接 = 固定 URI；模板 = 帶參數的 URI 模式，由用戶端填入。

**Q5. 為什麼用 Python SDK 裝飾器？**
**A：** 從型別／Field 描述推導工具 schema，而不是親手維護原始 JSON schema。

**Q6. MCP Inspector 是做什麼的？**
**A：** 瀏覽器測試／除錯伺服器工具／資源，再接到完整主機整合。

**Q7. 說出兩種傳輸層，並各給一個使用情境。**
**A：** STDIO 給本機子行程伺服器；Streamable HTTP（或 HTTP／SSE 家族）給遠端伺服器。

**Q8. 這門入門課之後下一步去哪裡？**
**A：** [MCP Advanced Topics](https://academy.claude.com/courses/model-context-protocol-advanced-topics)，學取樣、進度／roots，以及正式環境傳輸層／擴展細節。

**Q9. MCP 在數學上減少了什麼問題？**
**A：** 把 M×N 客製整合，收成 M 個主機＋N 台專門伺服器。

**Q10. MCP 的兩層是什麼？**
**A：** 資料層（JSON-RPC 語意／原語）與傳輸層（STDIO／HTTP）。

**Q11. 一般的 tools/list 呼叫之前必須發生什麼？**
**A：** 傳輸層連接＋initialize 能力協商（＋ initialized 訊號）。

**Q12. GitHub MCP 伺服器的後端 API 金鑰由誰擁有？**
**A：** 通常是伺服器（或其密鑰儲存）——不是每個主機都把 token 寫死。

**Q13. 用戶端該如何回應 tools/list_changed？**
**A：** 刷新工具清單，並更新模型可以呼叫的東西。

**Q14. 資源還是工具：「為上下文擷取 schema」？**
**A：** 資源（以讀取為導向、應用程式控制的注入）。

**Q15. 資源還是工具：「插入一列」？**
**A：** 工具（副作用／動作）。

**Q16. 為什麼 STDIO 伺服器要保持 stdout 乾淨？**
**A：** 協定訊息走 stdio——日誌噪音會破壞訊框處理；日誌改走 stderr。

**Q17. 什麼是上下文注入？**
**A：** 主機讀取資源（或其他資料），並刻意把它們附到模型請求裡。

**Q18. MCP UI 裡的自動完成／探索是什麼？**
**A：** 列出工具／資源／提示，讓使用者／主機不必寫死就能挑選能力。

**Q19. MCP 有取代 Claude 的 tool_result 迴圈嗎？**
**A：** 沒有。主機仍然要把工具結果餵回模型對話。

**Q20. 說出一個用戶端暴露的進階原語。**
**A：** 取樣、詢問請求，或日誌（入門：只要有意識）。

**Q21. 好的工具粒度規則是什麼？**
**A：** 窄而可組合、schema 清楚的工具，勝過一個巨型工具。

**Q22. 為什麼 Field 描述重要？**
**A：** 它們變成模型面對引數的指引——工具的提示工程。

**Q23. 「本機 = 安全」的安全錯誤是什麼？**
**A：** STDIO 伺服器以使用者權限執行，仍然可以外洩或刪除資料。

**Q24. 提示如何幫助團隊？**
**A：** 跨主機共享審過的指示模板，而不是每個使用者自己重發明措辭。

**Q25. 經典的 MIME 相關錯誤是什麼？**
**A：** 把 text/plain 資源當 JSON 解析（或完全忽略內容類型）。

**Q26. 憑記憶畫：4 台伺服器要幾個用戶端？**
**A：** 四個用戶端（一對一），由一個主機管理。

**Q27. 這裡的「與傳輸層無關」是什麼意思？**
**A：** 同一套資料層方法可以跑在不同傳輸層上。

**Q28. 通知缺少請求所具備的什麼？**
**A：** 一個 `id`／預期的回應。

**Q29. 什麼時候普通內嵌工具比 MCP 更好？**
**A：** 單一應用程式原型、少數穩定函式、沒有重用需求。

**Q30. 新伺服器行為異常時，你第一個用的工具是什麼？**
**A：** MCP Inspector（列出／呼叫／檢查酬載），再接到完整主機整合。

## 練習操練（原創練習構想）

1. **憑記憶草圖：** 主機／用戶端／伺服器，接上兩台伺服器；標出哪一跳是一對一。
2. **原語分類：** 給一份清單，如「載入 README」、「建立 issue」、「套用 ADR 模板」，把每一項標成資源、工具或提示。
3. **假文件伺服器：** 兩個工具（`list_docs`、`get_doc`）＋一個模板資源；用 Inspector 式心態操練它們（即使你只印 JSON）。
4. **MIME 處理：** 回傳 JSON 與純文字資源；寫依 MIME 類型分支的用戶端程式碼。
5. **失敗路徑：** 工具丟出例外；確保主機浮現一個模型能從中恢復的錯誤 `tool_result`，而不是當掉工作階段。
6. **傳輸層選擇備忘：** 一段話主張桌面檔案系統伺服器用 STDIO，共享的公司知識伺服器用 HTTP。
7. **生命週期閃卡：** 排出 connect／initialize／initialized／list／call／shutdown 的順序。
8. **安全審查：** 對一個提議的 `shell_exec` 工具，寫下你會要求主機具備的三道政策閘口。
9. **描述改寫：** 拿一句含糊的工具簡介（「管理文件」），改寫成何時用／何時不用／副作用。
10. **橋接操練：** 用四句話解釋 MCP 的 `tools/call` 如何在主機內部變成 Claude 的 `tool_use`／`tool_result` 來回。

保持操練精短；取樣、roots 與 Streamable HTTP 的深度，屬於上方連結的 Advanced Topics 課程。

## S1. MCP 工具的結構化錯誤回應（任務 2.2）

**`isError` 旗標**是 MCP 把工具失敗傳達回 agent 的機制，而且是*包在一次成功的協定回應裡*：`tools/call` 結果帶著 `isError: true`，錯誤細節放在 `content`，這樣**模型**才能讀到失敗並推論如何恢復。（協定層的 JSON-RPC 錯誤是給格式錯誤的呼叫；*工具領域*的失敗則以一般結果加上 `isError: true` 傳送。）

**為什麼泛用錯誤會失敗：** 一律回 `"Operation failed"`，agent 就沒有依據在重試、替代作法、上報，或問使用者之間做選擇。對永久錯誤浪費重試、對可恢復錯誤卻放棄，都源自非結構化錯誤。

**考試使用的錯誤分類法（背這四類）：**

| 類別 | 例子 | 可重試？ | Agent 的正確動作 |
| --- | --- | --- | --- |
| **暫時性（Transient）** | 逾時、服務不可用 | 是 | 重試（帶退避） |
| **驗證（Validation）** | 輸入格式錯誤、壞的 ID 格式 | 否（原樣） | 先修正輸入，再重試 |
| **業務（Business）** | 政策違反（退款上限） | **否** | 向使用者解釋／替代工作流程 |
| **權限（Permission）** | 呼叫者缺少存取權 | 否 | 上報／改走不同憑證路徑 |

**結構化錯誤中繼資料模式：** 回傳 `errorCategory`（`transient`／`validation`／`permission`／business）、一個 **`isRetryable` 布林值**，以及一份**人類可讀的描述**。對業務規則違反，把可重試設成 **false**，並附上 agent 可以轉述的**對客戶友善說明**（「超過 500 美元的退款需要主管核准」）——agent 接著溝通，而不是猛打重試。

**多 agent 連結（領域 5.3）：** 子代理在本地恢復**暫時性**失敗；只有無法解決的錯誤才傳到協調者，並帶上嘗試過什麼與部分結果。而且要保持**存取失敗 ≠ 有效的空結果**：空結果集是*成功的*查詢、零筆符合，永遠不要 `isError: true`。

## S2. Claude Code 裡的 MCP 伺服器：範圍與設定（任務 2.4）

**兩個範圍，一個考試區分：**

| 檔案 | 範圍 | 共享？ | 用於 |
| --- | --- | --- | --- |
| **`.mcp.json`**（專案根目錄） | 專案 | 是——提交進版本控制；每個隊友 clone／pull 就拿到 | 共享的團隊工具（團隊的 Jira／GitHub／資料庫伺服器） |
| **`~/.claude.json`** | 使用者 | 否——只在個人機器上 | 你在試用的個人／實驗伺服器 |

**`.mcp.json` 裡的環境變數展開**——例如 env／標頭值裡的 `${GITHUB_TOKEN}`——讓團隊可以提交伺服器*設定*，同時每位成員從自己的**環境提供憑證**。考試框架：如何共享設定**又不提交密鑰**？→ 專案範圍 `.mcp.json` 裡的環境變數展開。

**探索模型：** 來自**所有已設定 MCP 伺服器的工具，在連線當下被發現，並同時對 agent 可用**——專案伺服器與個人伺服器共存於同一個工作階段（官方準備練習 2 就是要你核實這一點）。

**MCP 資源作為內容目錄：** 把 issue 摘要、文件階層或資料庫 schema 暴露成**資源**，讓 agent *看見有哪些資料存在*，而不必把輪次燒在探索性工具呼叫上。目錄 = 資源；動作 = 工具（與上方第 7–9 節的三原語一致）。

**另外兩項 2.4 技能：**

- **與內建工具的描述競爭：** 若你的 MCP 工具描述很薄，agent 可能偏好內建工具（如 Grep）而不是你那個更有能力的伺服器工具。修復方法是**豐富 MCP 工具描述**，寫出它的能力與輸出——描述品質驅動採用，不只是在相似工具之間做選擇。
- **社群對上自訂伺服器：** 標準整合（例如 Jira）優先用既有的社群 MCP 伺服器；把自訂伺服器留給團隊專屬工作流程。（部署／託管 MCP 伺服器基礎設施對考試**明確超出範圍**。）

## S3. 內建工具：選擇標準（任務 2.5）

考試點名的 agent 端工具箱——知道每個工具的*選擇標準*：

| 工具 | 何時選用…… | 典型例子 |
| --- | --- | --- |
| **Grep** | 在檔案**內容**裡搜尋模式 | 找出函式的所有呼叫者；定位錯誤訊息；找 import 陳述 |
| **Glob** | 依模式比對檔案**路徑／名稱** | `**/*.test.tsx`——依命名慣例找所有測試檔 |
| **Read** | 載入檔案全文 | 跟著 Grep 找到的 import 走 |
| **Write** | 寫入完整檔案 | 當 Edit 無法錨定時，與 Read 搭配 |
| **Edit** | **透過唯一文字比對做針對性修改** | 替換一個函式本體 |
| **Bash** | 執行命令（測試、建置、git） | 執行測試套件 |

**Edit 失敗模式（會考）：** Edit 要求錨點文字**唯一**符合。當它因非唯一符合而失敗時，後援是**Read 全文，再 Write 修改後的版本**——不是用更長的錨點反覆嘗試 Edit。

**漸進式探索模式（會考）：** **漸進地**建立對程式碼庫的理解——先 Grep 進入點，再 Read 跟著 import 走並追蹤流程——而不是一開始就把所有檔案讀完（上下文膨脹；見領域 5.4）。跨包裝模組追蹤用法：先找出所有匯出名稱，再在程式碼庫裡搜尋每個名稱。

## S4. 補充問答

**SQ1.** MCP 工具如何告訴 agent 它失敗了？
**A.** 工具結果上的 `isError: true`，細節放在 content——領域失敗以可讀結果傳送，不是協定錯誤，這樣模型才能推論如何恢復。

**SQ2.** 說出四種錯誤類別，以及哪一種可重試。
**A.** 暫時性（可重試）、驗證（先修正輸入）、業務（不可重試——向使用者解釋）、權限（不可重試——上報／憑證）。

**SQ3.** 哪三個欄位讓錯誤回應成為「結構化」？
**A.** `errorCategory`、`isRetryable` 布林值、人類可讀描述（業務違反再加對客戶友善的說明）。

**SQ4.** 為什麼一律 `"Operation failed"` 的回應會傷害 agent？
**A.** 它們拿掉恢復決策的依據——導致對永久錯誤浪費重試、對可恢復錯誤卻放棄。

**SQ5.** 共享的團隊 MCP 伺服器放哪裡？個人實驗呢？
**A.** 專案範圍 `.mcp.json`（納入版本控制）；使用者範圍 `~/.claude.json`。

**SQ6.** 如何提交 MCP 設定而不提交 token？
**A.** `.mcp.json` 裡的環境變數展開（例如 `${GITHUB_TOKEN}`）——每位成員經由自己的環境提供憑證。

**SQ7.** 來自多台伺服器的 MCP 工具何時可用？
**A.** 在連線當下被發現；所有已設定伺服器的工具同時可用。

**SQ8.** Agent 一直做探索性呼叫，想知道有哪些資料。MCP 修復方法？
**A.** 把內容目錄（issue 摘要、文件階層、schema）暴露成**資源**。

**SQ9.** Agent 偏好內建 Grep，而不是你那個更有能力的 MCP 搜尋工具。修復方法？
**A.** 豐富 MCP 工具的描述，寫出能力與輸出——描述驅動採用。

**SQ10.** Grep 對上 Glob，一句話？
**A.** Grep 在檔案*內容*裡搜尋模式；Glob 比對檔案*路徑／名稱*。

**SQ11.** Edit 一直因非唯一符合而失敗。後援？
**A.** Read 全文，再 Write 修改後的版本。

**SQ12.** 建立對大型程式碼庫理解的正確方式？
**A.** 漸進地：Grep 進入點 → Read 跟著 import／追蹤流程——不是一開始全讀。

**SQ13.** 子代理的搜尋逾時一次，重試後成功。協調者收到什麼？
**A.** 什麼都沒有——暫時性失敗在本地恢復；只有無法解決的錯誤才往上傳（帶嘗試與部分結果）。

**SQ14.** 空搜尋結果：`isError: true` 還是不要？
**A.** 不要——有效的空結果是成功查詢、零筆符合；把它標成錯誤會腐化重試邏輯。
