## 概覽

考試的領域 1 測試你能否設計並推理 **agentic（自主代理式）迴圈**（任務 1.1）、**協調者–子代理（subagent）編排**（1.2）、**子代理生成與脈絡傳遞**（1.3）、**工作流程強制執行與交接**（1.4）、**Agent SDK hooks**（勾子機制）（1.5）、**任務拆解**（1.6），以及 **工作階段狀態、恢復與分叉**（1.7）。題目是情境形的：生產環境日誌呈現一個失敗模式，你要挑出架構上相稱的修復方法。

**總體心智模型：** 一個 agent = 模型 + 工具 + 迴圈。*模型* 根據脈絡決定下一個要呼叫的工具（模型驅動的決策）；*迴圈* 是笨拙的管線接駁，負責執行工具並把結果餵回去；*hooks*（勾子機制）是包在這層管線接駁外面的確定性政策層；*子代理*（subagent）是協調者為聚焦工作而生成的額外隔離迴圈。

## 深入筆記

### 1. Agentic 迴圈（任務 1.1）

每個迴圈都實作的生命週期：

1. 把請求（messages + tools）送給 Claude。
2. 檢查 **`stop_reason`**：`"tool_use"` → Claude 想要執行工具；`"end_turn"` → Claude 完成了。
3. 執行被請求的工具。
4. 把助理訊息 **以及** `tool_result` 區塊附加到對話歷史。
5. 把更新後的歷史送回去；重複直到 `end_turn`。

```text
loop:
 response = call_claude(history, tools)
 history.append(response)
 if response.stop_reason == "tool_use":
 results = execute(response.tool_calls)
 history.append(user_message(tool_results=results))
 continue
 if response.stop_reason == "end_turn":
 break # final answer is in response content
```

**為什麼附加工具結果很重要：** 模型在請求之間是無狀態的。只有當某個工具的輸出出現在它*下一次收到的對話*中，它才能對那個輸出進行推理。丟棄或截斷一個 `tool_result`，會靜默改變模型「知道」的東西。

**模型驅動對預先設定：** 考試區分 agent（Claude 根據累積脈絡推理下一個要呼叫的工具）與由你寫死的決策樹或固定工具序列。Agent 在高度模糊的輸入上表現出色（退貨、帳務爭議），這類路徑無法事先列舉；固定管線在路徑已知時表現出色（見任務 1.6）。

**迴圈終止反模式（考試指南點名這些——要背起來）：**

| 反模式 | 為什麼失敗 | 正確訊號 |
| --- | --- | --- |
| 解析自然語言訊號（「我完成了！」）來決定終止 | 脆弱的字串比對；模型表達完成的方式千變萬化 | `stop_reason == "end_turn"` |
| 把任意的迭代次數上限當成**主要**停止機制 | 切斷合理的長任務；掩蓋真正的 bug | stop_reason；上限只保留為*安全後備閘* |
| 檢查助理訊息是否包含文字，作為完成指標 | 助理回合可以同時包含文字*與* tool_use 區塊 | stop_reason，絕不是內容形狀 |

### 2. 協調者–子代理編排（任務 1.2）

**中樞輻射式：** 一個協調者 agent 掌管任務拆解、委派、結果彙總與錯誤處理。子代理之間絕不直接對話——**所有子代理間的通訊都經由協調者路由**。為什麼：可觀測性（只有一個地方記錄日誌）、一致的錯誤處理（只有一套復原政策）、受控的資訊流（沒有未經審查的交叉通話）。

**上下文隔離（考試重點）：** 子代理**不會**自動繼承協調者的對話歷史，多次呼叫之間也不共享記憶。每個被生成的子代理都以全新的上下文開始，只包含它自己的系統提示詞，加上協調者傳入的提示詞字串。如果綜合子代理需要網頁搜尋的發現，協調者必須**把那些發現放進綜合子代理的提示詞裡**——沒有任何東西會隱性流動。

**協調者的工作清單：**

- 分析查詢並**動態選擇**要呼叫哪些子代理——不是總是跑完整管線。一個簡單的查詢不該驚動四個專家。
- **跨子代理劃分範圍**，把重複降到最低（為每個 agent 指派不同的子主題或來源類型）。
- **彙總**結果，並評估綜合輸出有沒有缺口。
- **迭代式精煉迴圈：** 若綜合輸出有覆蓋缺口，就用*有針對性的*查詢重新委派給搜尋／分析子代理，然後重新呼叫綜合；重複直到覆蓋範圍足夠。

**領域 1 的招牌失敗——過窄的拆解**（官方範例題 Q7）：關於「創意產業」的研究報告只涵蓋視覺藝術，因為協調者把主題拆解成數位藝術／平面設計／攝影。每個子代理都正確執行了它的任務；**根本原因是它們被指派的內容**。考試反射：當子代理日誌看起來乾淨、但覆蓋範圍很差時，怪協調者的拆解，不要怪下游的 agent。

**協調者提示詞設計：** 指定**研究目標和品質標準**（「涵蓋每一個主要的創意產業部門；每個主張都附引用來源」），而不是一步一步的程序指令。目標形的提示詞讓子代理能夠適應；程序形的提示詞在第一個意料之外的情況就崩壞。

### 3. 生成、AgentDefinition 與脈絡傳遞（任務 1.3）

**Task 工具**是協調者用來生成子代理的機制，而且協調者的 **`allowedTools` 必須包含 `"Task"`**，否則它根本無法委派——經典的考試干擾選項，就是委派失敗的根本原因是少了 Task 條目。*（現行文件註記：Claude Code 在 v2.1.63 把此工具改名為 `Agent`；考試指南與附錄仍使用 `Task`——用指南的術語作答，並知道這次改名存在。）*

**AgentDefinition** 設定每種子代理類型（已對照現行 SDK 文件查證——`query()` 的 `agents` 選項把名稱對應到定義）：

| 欄位 | 用途 |
| --- | --- |
| `description` | 協調者什麼時候該用這個子代理——Claude 靠這個把任務配對到 agent |
| `prompt` | 子代理的**系統提示詞**：角色、專長、限制 |
| `tools` | 工具限制清單——綜合 agent 拿不到網頁工具；審查者只拿唯讀的 `["Read", "Grep", "Glob"]` |
| `model` | 選用的逐子代理模型覆寫（例如用較便宜的模型做大量閱讀） |

**考試指南列出的明確脈絡傳遞技巧：**

- 把**先前 agent 的完整發現直接放進子代理的提示詞**（例如把搜尋結果和文件分析傳進綜合提示詞）。
- 使用**把內容與詮釋資料分開的結構化資料格式**（主張文字對來源 URL／文件名稱／頁碼），做出處歸屬能在交接之後存活——這個概念在領域 5.6 會再次出現。
- **平行生成：** 在**協調者的單一回應中發出多個 Task 工具呼叫**，而不是每回合一個。每回合一個會把本可同時進行的工作序列化；單一回應模式是文件記載的平行化方式（官方備考練習 4 測量的就是延遲收益）。

**基於分叉的探索**在概念上屬於這裡（細節見第 7 節）：分叉一個工作階段，從共享的分析基線出發，探索分歧的做法。

### 4. 多步驟工作流程：強制執行與交接（任務 1.4）

**程式化強制執行對提示詞引導——領域 1 被考得最多的區別**（官方範例題 Q1）：

> 12% 的案例在執行 `process_refund` 之前跳過了 `get_customer`。修復方法？**一個程式化前置條件，在前置條件完成之前擋住下游的呼叫。** 提示詞措辭和 few-shot（少樣本）範例是機率性的——它們降低失敗率，但永遠降不到零。當錯誤有財務或合規後果時（「金融操作前的身分驗證」），只有確定性的閘口可以接受。

強制執行階梯（最弱 → 最強）：系統提示詞指令 → few-shot 範例 → **程式碼中的 hook／前置條件閘口**。考試獎勵的是選擇*相稱*的那一階：審查提示詞的精準度問題，給標準和 few-shot（領域 4）；合規關鍵的順序，給程式碼。

**多重事項的請求：** 把一則包含幾個不同事項的訊息拆解成項目，逐一調查（彼此獨立的就平行進行，並共享共同脈絡，例如已驗證的客戶 ID），然後綜合成**一個統一的解決方案**——不要回答了事項 1，卻靜默丟掉事項 3。

**上呈用的結構化交接協定：** 接收上呈案件的真人客服，通常**看不到對話逐字稿**。一份合規的交接摘要要攜帶：客戶 ID、關注的事項、**到目前為止的根因分析**、涉及的金額／訂單編號、已經嘗試過什麼，以及**建議的行動**。什麼結構化酬載都沒有就「上呈給真人」，會逼那個人從零開始重新調查——這是反模式，情境題幹會懲罰它。

### 5. Agent SDK hooks（任務 1.5）

Hooks 是 SDK 在固定生命週期點觸發的回呼；它們是**確定性保證層**，相較於提示詞指令的**機率性遵從**——與檔案 `05` 的 Claude Code 一節同一條建議式對強制式軸線，現在搬進了 SDK。

考試點名的兩種 hook 模式：

1. **PostToolUse——在模型看到結果之前做轉換。** 不同的模型上下文協定（MCP）後端回傳異質格式：一個工具輸出 Unix epoch 時間戳，另一個輸出 ISO 8601，第三個輸出數字狀態碼。PostToolUse hook **在 agent 處理工具結果之前，把它們正規化成單一標準格式**，模型就不必在推理途中同時應付三種日期格式。*（現行 SDK 機制，已查證：hooks 透過 `hooks` 選項註冊，以事件名稱為鍵，附帶匹配器；PostToolUse 回呼可以替換工具輸出——`updatedToolOutput`——或附加 `additionalContext`。）*
2. **工具呼叫攔截——對外發呼叫強制執行合規規則。** 在*執行之前*攔截呼叫；若它違反政策（退款 > 500 美元），**擋住它並改導到替代工作流程**（真人上呈）。*（現行 SDK 機制，已查證：PreToolUse 回呼回傳 `permissionDecision: "deny"`，並附上模型看得到的 `permissionDecisionReason`；或用 `updatedInput` 改寫參數；當多個 hooks 觸發時，deny 永遠勝出。）*

**何時用 hooks、何時用提示詞：** 需要**保證**遵從的業務規則 → hooks。風格、語氣、軟性偏好 → 提示詞。若題目說「永遠不准」、「合規」、「監管」，或點名一個美元門檻——答案就是 hook 或閘口，不是在系統提示詞裡寫一句更好的話。

### 6. 任務拆解策略（任務 1.6）

兩個家族：

| 策略 | 形狀 | 何時使用 |
| --- | --- | --- |
| **提示鏈**（固定的順序管線） | 預先定義的步驟 1 → 步驟 2 → 步驟 3 | 可預測的多面向工作：步驟事先已知 |
| **動態自適應拆解** | 計畫從中間發現中浮現 | 開放式調查：下一步要做什麼，取決於你發現了什麼 |

**提示鏈範例（同時是官方範例題 Q12／領域 4.6）：** 一份涵蓋 14 個檔案的 pull request（PR）用單一回合審查，產出深度不一致、結論互相矛盾——**注意力稀釋**。修復方法：**逐檔的局部分析遍次**，加上**獨立的跨檔整合遍次**。拆分是拆解類的答案，不是加大上下文視窗類的答案（Q12 的選項 C 之所以錯，正是因為更大的視窗修不好注意力稀釋）。

**自適應範例：** 「為一個遺留程式碼庫加上全面的測試」——你無法事先列舉步驟。先**繪製結構圖**，識別**高影響區域**，建立一份**會隨著依賴被發現而調整的優先順序計畫**。這份計畫是活的工件，隨著發現到來而重新產生。

**怎麼選：** 問「我能不能在開始之前寫出完整的步驟清單？」能 → 用提示鏈。不能 → 用自適應。混合式很常見：外層是自適應計畫，內層是串鏈的遍次。

### 7. 工作階段狀態、恢復與分叉（任務 1.7）

- **`--resume <session-name-or-id>`** 延續一個特定的先前對話，連同完整上下文（讀過的檔案、做過的分析、下過的決策）。已查證的現行 CLI：`--resume` 接受工作階段 **ID 或名稱**（或顯示一個選擇器）；`--continue` 抓取目前目錄中最近的工作階段。在 SDK 中，於 query 選項傳入 `resume=<session_id>`（Python）／`resume: sessionId`（TypeScript）。
- **`fork_session`** 從共享的分析基線建立一個**獨立分支**：分叉會複製原工作階段的歷史，並得到自己的工作階段 ID；**原工作階段保持不變**。用它探索分歧的做法——例如從一次昂貴的程式碼庫分析出發，比較兩種測試策略或兩種重構設計，每種做法一個分叉。已查證的 SDK 拼法：`fork_session=True`（Python）／`forkSession: true`（TypeScript），*與* `resume` 一起傳入。
- **程式碼變動之後的恢復：** 被恢復的工作階段，其工具結果描述的是檔案*當時*的樣子。**告訴 agent 哪些檔案變了**，讓它專門重新分析那些檔案，而不是信任過期的讀取——有針對性的重新分析，勝過全面重新探索。
- **恢復對上帶摘要重開：** 若先前脈絡*大致仍有效* → 恢復（便宜，而且保留細微差異）。若先前工具結果*大幅過期* → **開新工作階段，並注入一份仍然有效結論的結構化摘要**。一個帶著乾淨、當前事實的新工作階段，比一個拖著已被推翻的檔案讀取、而模型仍可能信任的恢復工作階段，更可靠。

## 決策樹

**「agent 沒做 X」的分流排查：**

```text
它是否跳過了必要步驟（合規／順序）？
 → 程式化前置條件，或 PreToolUse 式攔截 hook（1.4／1.5）
它是否在相似工具之間選錯了工具？
 → 先修工具描述（領域 2.1），再補 few-shot
它是否產出不完整的覆蓋，而子代理日誌很乾淨？
 → 協調者的拆解太窄（1.2）
它是否完全沒有委派？
 → 協調者的 allowedTools 裡有沒有 "Task"？（1.3）
它是否過早終止或無限迴圈？
 → 檢查 stop_reason 處理；移除自然語言解析／文字存在檢查（1.1）
```

**工作階段延續：**

```text
先前脈絡仍然有效？
 是 → --resume（加一則列出任何變動檔案的說明）
 大致有效，想試兩個方向 → 恢復 + 每個方向一個 fork_session
 否（工具結果過期） → 新工作階段 + 注入的結構化摘要
```

## 考試陷阱

| 陷阱 | 修復方法 |
| --- | --- |
| 對合規關鍵的順序 bug「加強系統提示詞」 | 程式化前置條件／hook——提示詞是機率性的 |
| 以為子代理看得到協調者的對話 | 它們只看到自己的系統提示詞 + 生成時傳入的提示詞 |
| 把覆蓋缺口怪到下游 agent 頭上 | 先查協調者的拆解（範例題 Q7） |
| 把平行子代理分散在多個回合生成 | 在單一回應中發出多個 Task 呼叫 |
| 把迭代次數上限當主要迴圈終止器 | stop_reason `end_turn`；上限只當後備閘 |
| 只帶一個「需要真人」旗標就上呈 | 結構化交接：ID、根因、金額、建議行動 |
| 在大量程式碼變動之後恢復工作階段，卻不說明 | 點名變動的檔案，或帶著摘要重開 |
| 以為分叉會改變原工作階段 | 不會——分叉把歷史複製到一個新的工作階段 ID |
| 用 hooks 處理語氣／風格偏好 | Hooks 給保證；提示詞給偏好 |
| 因為上下文視窗裝得下，就做一個巨大的審查回合 | 注意力稀釋——拆成逐檔遍次 + 整合遍次 |

## 自我檢查問答

**Q1.** 當 `stop_reason` 是 ___ 時迴圈應繼續，是 ___ 時應終止。
**A.** `"tool_use"`；`"end_turn"`。

**Q2.** 為什麼工具結果必須在下一個請求之前附加到歷史？
**A.** 模型在每個請求上是無狀態的——它只能納入出現在所收到對話中的結果。

**Q3.** 說出考試指南列出的三個迴圈終止反模式。
**A.** 解析自然語言完成訊號；把任意迭代次數上限當主要停止機制；檢查助理文字內容作為完成指標。

**Q4.** Agent 對預先設定管線——決定性差異是什麼？
**A.** 模型驅動的決策：agent 根據脈絡推理下一個工具；管線遵循寫死的序列。

**Q5.** 中樞輻射式裡，誰跟誰說話？
**A.** 所有子代理通訊都經由協調者路由——為了可觀測性、一致的錯誤處理，以及受控的資訊流。

**Q6.** 研究報告只涵蓋主題的一小塊；每個子代理的日誌看起來都正確。根本原因？
**A.** 協調者的任務拆解太窄——子代理的指派沒有涵蓋主題（範例題 Q7 模式）。

**Q7.** 協調者要生成子代理，`allowedTools` 必須滿足什麼條件？
**A.** 必須包含 `"Task"`（生成子代理的工具；目前 Claude Code 已改名為 `Agent`——考試使用 Task）。

**Q8.** 剛生成的子代理以什麼脈絡開始？
**A.** 它自己的系統提示詞（AgentDefinition `prompt`）加上協調者傳入的提示詞字串——沒有父代歷史，也沒有共享記憶。

**Q9.** 綜合 agent 需要搜尋 agent 的發現。它怎麼拿到？
**A.** 協調者把完整發現直接放進綜合 agent 的提示詞，最好是把內容與來源詮釋資料分開的結構化資料。

**Q10.** 如何平行執行三個子代理？
**A.** 協調者在單一回應中發出三個 Task 工具呼叫。

**Q11.** AgentDefinition：說出兩個必填欄位，以及各自做什麼。
**A.** `description`（告訴協調者什麼時候用這種 agent 類型）和 `prompt`（子代理的系統提示詞）；`tools` 和 `model` 是選用的限制／覆寫。

**Q12.** 12% 的退款跳過身分驗證。最好的修復方法？
**A.** 一個程式化前置條件，在 `get_customer` 回傳已驗證 ID 之前擋住 `process_refund`——確定性的，不像提示詞／few-shot 修復方法（範例題 Q1）。

**Q13.** 結構化上呈交接該包含什麼？
**A.** 客戶 ID、關注的事項、根因分析、金額／訂單編號、已嘗試的事項、建議行動——真人沒有逐字稿存取權。

**Q14.** 三個 MCP 工具分別以 epoch、ISO 8601 和字串回傳日期。在哪裡正規化？
**A.** 一個 PostToolUse hook，在模型處理之前把工具結果轉換成單一標準格式。

**Q15.** 超過 500 美元的退款永遠不准自動執行。用什麼機制？
**A.** 工具呼叫攔截（PreToolUse 式）hook，擋住呼叫並改導到真人上呈——hooks 給確定性保證；提示詞是機率性的。

**Q16.** 提示鏈對自適應拆解——一句話規則？
**A.** 步驟能事先列舉 → 用提示鏈；計畫取決於發現 → 用自適應。

**Q17.** 大型多檔案審查產出互相矛盾、不一致的結論。怎麼重組？
**A.** 逐檔的局部分析遍次，加上獨立的跨檔整合遍次（注意力稀釋修復方法；範例題 Q12）。

**Q18.** 「為遺留程式碼庫加上全面的測試」——前三個動作？
**A.** 繪製結構圖、識別高影響區域、建立一份隨依賴浮現而調整的優先順序計畫。

**Q19.** fork_session——分叉與原工作階段共享什麼、改變什麼？
**A.** 它以原工作階段歷史的複本開始，使用新的工作階段 ID；原工作階段不受影響。

**Q20.** 什麼時候新工作階段加摘要勝過 `--resume`？
**A.** 當先前工具結果過期時（程式碼大幅變動）——注入有效結論的摘要，勝過含有已被推翻讀取的恢復上下文。

**Q21.** 你在編輯兩個檔案之後恢復一個調查工作階段。你的第一則訊息該包含什麼？
**A.** 哪些檔案變了，讓 agent 專門重新分析那些檔案，而不是信任過期讀取或重新探索一切。

**Q22.** 協調者提示詞該指定 ___，而不是 ___。
**A.** 研究目標和品質標準；一步一步的程序指令（適應力）。

**Q23.** 迭代次數上限什麼時候可以合理地存在於迴圈中？
**A.** 作為防止失控的安全後備閘——絕不作為主要終止機制。

**Q24.** 協調者把每個查詢都路由到全部四個子代理，連瑣碎的也一樣。評論？
**A.** 協調者應該按查詢複雜度動態選擇子代理——全管線路由浪費延遲／成本，還增加失敗面。

**Q25.** 迭代式精煉迴圈——描述它。
**A.** 協調者評估綜合輸出的缺口 → 把有針對性的查詢重新委派給搜尋／分析 agent → 重新呼叫綜合 → 重複直到覆蓋範圍足夠。

## 詞彙表

| 術語 | 含義 |
| --- | --- |
| Agentic 迴圈 | 送出請求 → 檢查 stop_reason → 執行工具 → 附加結果 → 重複 |
| stop_reason | 驅動迴圈控制的 API 欄位：`tool_use` 繼續，`end_turn` 停止 |
| 協調者 | 掌管拆解、委派、彙總與錯誤處理的中樞 agent |
| 中樞輻射式 | 所有子代理通訊都經過協調者的拓撲 |
| Task 工具 | 生成子代理的工具（目前 Claude Code 已改名為 Agent） |
| allowedTools | 自動核准所列工具的 SDK 選項；要委派就必須包含 Task |
| AgentDefinition | 逐子代理的設定：description、prompt、tools、model |
| 上下文隔離 | 子代理從全新狀態開始；只有生成提示詞把脈絡帶進去 |
| 程式化前置條件 | 一個程式碼閘口，在前置條件完成之前擋住下游工具 |
| PostToolUse hook | 在模型看到工具結果之前，將其轉換／正規化的回呼 |
| 工具呼叫攔截 | 執行前的 hook，擋住或改寫違反政策的呼叫 |
| 提示鏈 | 由聚焦遍次組成的固定順序管線 |
| 自適應拆解 | 從中間發現產生並修訂的計畫 |
| 注意力稀釋 | 一個遍次涵蓋太多檔案／面向時發生的品質劣化 |
| --resume | 以完整上下文延續具名或有 ID 的工作階段，CLI／SDK 皆有的選項 |
| fork_session | 把工作階段歷史分叉到一個新的、獨立的工作階段 ID |
| 結構化交接 | 上呈酬載：ID、根因、金額、嘗試過的事項、建議 |
