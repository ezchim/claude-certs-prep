## 深入筆記

### 1. 工作的三種形態

- **逐輪對話** — 每一步由你掌舵。最適合迭代、快速取得答案、帶著回饋起草。
- **交辦式 agentic** — 你下指示，Claude 連續完成多步驟（Research；長時間 agentic 任務）。消耗較多用量；需要更好的簡述與引用查核。
- **可重複使用的系統** — Projects、Skills、Artifacts、Connectors 把脈絡與程序一次性編碼，整個團隊就不用再反覆解釋。

考試裡大多數功能題幹其實在問：這份工作屬於哪一種形態？

### 2. 功能目錄（什麼時候該用哪一個）

**Chat。** 在單一對話串上快速迭代。不適合承載反覆出現的共享脈絡 — 那是 Project。對話會留在你的歷史紀錄（開啟 Memory 後，可以影響後續對話 — 見 §5）；它們不是團隊知識庫。

**Projects。** 自足工作區，帶有 **指示**（常態行為）＋ **知識**（參考檔案），以及獨立的對話歷史。**所有方案都有；Free 帳號上限為五個 projects**（已於 2026 年 8 月對照 support.claude.com 查證）。**透過檢索增強生成（RAG）的增強知識僅付費方案提供，知識容量最多擴大約 10 倍**，當專案知識接近上下文上限時啟動（已於 2026 年 8 月查證）。分享是 Team／Enterprise 能力：「可檢視」對「可編輯」，可逐一、批次或全組織分享。你在共享 Project 裡的對話仍是你的 — 分享散佈的是知識與指示，不是你的對話逐字稿。

**Artifacts。** 獨立、可編輯的交付物（文件、程式碼、HTML／SVG、互動式應用程式），顯示在對話旁邊。可以發布／分享；AI 驅動的 artifacts 消耗的是 **觀看者** 的用量上限，不是建立者的。並非預先驗證過的 — 領域 03 的規則照樣適用。

**Skills。** 打包好的任務程序，在相關時載入。對比：專案知識是隨時可用的參考資料；Skill 是 *可重複執行的程序*；Connector 是 *即時資料*。

**Connectors（模型上下文協定，MCP）。** 接入即時系統（Drive、Gmail、Slack、自訂遠端 MCP 伺服器）。Team／Enterprise 上的常見模式是管理員啟用，加上每位使用者各自驗證。**自訂 connectors 每種方案都有，但 Free 帳號限一個自訂 connector**（已於 2026 年 8 月查證）。治理見領域 06。

**Research。** 附引用來源的 agentic 多角度調查；需要開啟網頁搜尋；可以使用 connectors；需付費方案；比聊天燒用量更快。對於單一已上傳的 PDF，直接引用該檔案即可。

**Enterprise Search。** 組織內部搜尋，附帶指回已連接來源的引用（Team／Enterprise）。「我們當初決定了什麼？」→ Enterprise Search。「公開的整體局面是什麼？」→ Research。

**程式碼執行與檔案產生。** Claude 在 claude.ai 上有 **沙箱運算環境**：它撰寫並執行程式碼來分析資料、製作圖表，以及產生可下載檔案 — Excel、PowerPoint、Word、PDF、逗號分隔值（CSV）。**所有方案（Free–Enterprise）在網頁、Desktop 與 Mobile 上都有**（已於 2026 年 8 月查證）；它取代了舊的「分析工具」。當題幹涉及 *對資料做運算*（總計、樞紐分析、從試算表看趨勢）或 *檔案交付物* 時用它 — 純聊天裡的模式比對，對大規模算術不可靠。與 Artifacts 有別：Artifact 是互動／可編輯的交付物；程式碼執行是能產生檔案與已驗證數字的運算。

### 3. 模型階梯與任務對齊

考試指南點名三個層級 — 要能乾淨地區分：

| 層級 | 性格 | 何時用 |
|---|---|---|
| **Haiku** | 最快、最輕、最便宜 | 萃取、分類、短摘要、大量簡單任務 |
| **Sonnet** | 均衡的每日預設 | 大多數起草、分析、日常知識工作 |
| **Opus** | 最深的推論 | 多重限制的困難策略、細膩分析 — *在* 較輕模型或更好的簡述失敗之後 |

*註：* 目前產品在 Opus 之上還提供一個層級（Fable 等級），用於時間跨度最長、最複雜的工作。指南的目標措辭是 Haiku／Sonnet／Opus — 用這三個詞作答；「升級超過 Opus」出現在題幹裡時，只是威望偏見的干擾選項。

決定考試答案的規則：

- **最輕可交付模型勝出。** 從較輕模型往上評估；停在你真的願意交付的最便宜輸出。官方範例題獎勵「為直接、大量任務挑更快、成本更低的模型」。
- **因為實際失敗而升級，不是因為威望。** 「用最大的模型把品質最大化」是教科書級的錯誤選項 — 它浪費成本與延遲預算。
- **effort／延伸思考在模型內部調整深度。** 快速查詢用較低 effort；真正困難的問題用較高。有時正確修復方法是把 Sonnet 的 effort 調高，而不是跳去 Opus。
- **把失敗對上對的解方。** Haiku 漏掉細微差異 → 往上移。Sonnet 在對抗性策略上太淺 → Opus 或更好的拆解。Opus「敗」在成本／延遲／額度 → 往 *下* 移或重組。簡報不好 → 先修好描述（領域 02），再碰模型選擇器。
- **兩模型試驗法。** 同一個已知任務先跑 Haiku 再跑 Sonnet；比較內容，不是比較長度。若 Haiku 已經挖出你在意的主張，就留在輕的這邊。

### 4. 上下文限制（重開／摘要／持久保存）

上下文視窗是有限的；長對話會劣化 — 漂移、矛盾、被遺忘的限制。

- **重開** 當矛盾累積、角色漂移或品質崩壞。帶著精簡的簡述開新對話，勝過硬撐一條被污染的對話。
- **摘要** 當你需要決策延續性、不要草稿雜訊：要求一份交接簡述（決策、未決問題、限制），再用它開啟新對話。
- **持久保存** 當重複使用可預見：把常態規則放進專案指示，把參考檔案放進專案知識 — 不要每個星期一都寫一封英勇的第一則訊息。

指示會與任務 token 競爭：指示要短、要穩定；把厚重政策放進名稱清楚的知識檔，並按檔名點名。

### 5. Memory（產品內建的持久層）

claude.ai 現在有一等公民 **Memory** 功能（已於 2026 年 8 月對照 support.claude.com 查證 — 細節會演變；考試前重新查證）：

- Claude 從你的對話建立 **記憶條目**（專業脈絡、偏好、進行中的工作），並在後續對話套用。記憶產生在 **Free、Pro 與 Max**（較新體驗）以及 **Enterprise**（舊版綜合體驗）提供；**對話搜尋**（找回過去的對話）為 Pro 以上。
- **以專案為範圍：** 每個 Project 有自己獨立的記憶，所以客戶 A 的脈絡不會滲進客戶 B — 這直接回答考試的「記憶考量」目標。
- **由你控制：** 可檢視、編輯、刪除個別條目，或在 Settings 全部重置；搜尋與記憶各自獨立開關。
- **無痕對話**（幽靈圖示，所有方案，存在於 Projects 之外）被排除在歷史紀錄、記憶與搜尋之外 — 一次性敏感查詢用它。

**考試框架：** 「重開、摘要、持久保存」仍是那個技能。Memory 減少跨對話的重複解釋，但它 *不是* 團隊知識庫（以個人為單位），*不能* 取代專案知識（對政策問題來說，整理過的檔案勝過推測出來的記憶），也 *不保證* 完整 — 承重的脈絡仍然屬於 Projects。Memory 的設定與治理見領域 05（見 `05-configuration-knowledge-management.md` 的 Memory 小節）。

### 6. 方案與隱藏限制

考試題幹把方案限制藏在附屬子句裡。解出題幹裡那個有限制的世界，不是你腦中的理想世界：

- Free：五個 project 上限；一個自訂 connector；沒有 Research。
- Research 需要付費方案 **並且** 開啟網頁搜尋。
- Enterprise Search 需要 Team／Enterprise，且由管理員連接資料來源。
- 團隊成員 ≠ 管理員：啟用是管理員的工作；驗證通常是每位使用者各自進行。
- Artifact 觀看者燒的是自己的額度；被關掉的能力開關會擋住 artifact／程式碼功能。

### 7. 流暢度之橋（4D）

**委派（Delegation）** 就是整個這個領域：在自動化、增強、自主代理之間做選擇，並選擇由哪個功能／模型承載。**描述（Description）** 包括選擇 Research 還是 chat，不只是措辭。**明辨（Discernment）** 在重型模型上最吃緊 — 冗長流暢的 Opus 輸出仍需要領域 03 的評測。**盡責（Diligence）** 把發布 Artifact 或啟用 connector 視為一次部署行動。

選錯功能會偽裝成提示詞失敗；選錯模型會偽裝成「Claude 很笨」。領域 07 會問是哪一層壞了 — 為每個反覆出現的工作流程留一頁摘要：功能 | 模型 | 上下文策略。

### 8. 迷你案例（功能＋模型一次到位）

**專案管理辦公室（PMO）星期五進度：** 帶範本指示＋ Drive connector 的 Project；預設 Sonnet。**董事會策略質詢：** Opus（領域 03 評測仍是必須的）。**客服退款問題：** 從 Project 政策或 Enterprise Search 回答 — 絕不要靠模型的一般知識。**工作坊破冰題：** chat＋ Haiku／Sonnet；跳過 Research。**建議邀請書（RFP）比較：** 評分量規放進 Project，用 Research 取得公開局面，用程式碼執行計算評分，交付物以表格／Artifact 呈現。**季末投影片：** 上傳資料 → 程式碼執行算數字 → Sonnet 起草評論 → 由人驗證。

反模式：一個巨型 Project 混合法務＋人資＋行銷；對單一已上傳 PDF 跑 Research；把可寫入的 connectors 交給唯讀分析；把頂級層級當創意旋鈕；以為 Artifact 觀看者用的是建立者的憑證或額度；依賴 Memory 承載團隊的政策真相。

### 9. 複選題模式庫

這裡的選兩項／三項題幹，會把一個正確的功能／模型動作配上干擾選項。演練排除：「所有重要的事都用 Opus」（威望偏見）；「Projects 會分享你的對話逐字稿」（錯誤機制）；「Research 在 Free 可用」／「Research 不用開網頁搜尋」（方案／能力誤判）；「Memory 取代專案知識」（持久層混淆）；「叫 chat 去算 10,000 列表格總計」（錯的工具 — 該用程式碼執行）。正確組合通常是一個 **符合功能** 的選擇（Project／Research／程式碼執行／Artifact）搭配一個 **尊重限制** 的選擇（方案上限、驗證步驟、最輕可交付模型）。

## 決策樹

**功能：** 可重複／反覆出現的脈絡 → Project。附引用的多來源公開調查 → Research。組織內部「我們當初決定了什麼」→ Enterprise Search。獨立互動式交付物 → Artifact。可重複執行的程序 → Skill。即時正式紀錄系統 → Connector。對資料做運算／檔案交付物 → 程式碼執行。一次性問題 → chat。

**模型：** 即時萃取／分類 → Haiku。預設知識工作 → Sonnet。較輕嘗試失敗後的深度推論 → Opus。跳層級之前先調 effort。

**上下文：** 漂移的對話 → 重開。需要延續性、不要雜訊 → 摘要成交接。可預見的重複使用 → 持久保存在 Project。跨對話的個人脈絡 → Memory（查證條目；一次性敏感 → 無痕對話）。

## 考試陷阱

1. 為了「保險」用最大模型（威望偏見 — 官方範例題會罰它）
2. 以為 Project 分享會分享你的對話逐字稿（它分享的是知識＋指示）
3. 沒開網頁搜尋就跑 Research，或對單一已上傳 PDF 跑 Research
4. 「已啟用＝已存取」：忘記每位使用者的 connector 驗證
5. 「Free 沒有 Projects」（錯 — 上限五個）／忽略 Free 一個自訂 connector 的上限
6. 因為 Artifacts 看起來像成品，就當成已預先驗證
7. Enterprise Search ≠ Research（內部附引用查找 vs 公開 agentic 調查）
8. 叫 chat「計算」大型表格算術，而不是用程式碼執行
9. 把 Memory 當成共享的團隊大腦或政策真相來源
10. 簡述、知識或功能選擇才是壞掉的那層，卻去升級模型

## 練習問答（18）— 情境題幹附答案與理由

**Q1.** 一位行銷主管每個星期一都把風格指南貼進新對話，重建同一份品牌語氣簡述。他們該怎麼設置？
**A：** 建立一個 Project，把風格指南放進知識，把常態規則放進指示。反覆出現的脈絡屬於持久工作區，不是每週英勇貼上。

**Q2.** 營運團隊必須從一份 40,000 列的 CSV 抽出總計與依區域的樞紐分析，並交付一份 Excel 檔。最佳做法？
**A：** 上傳檔案，讓 Claude 用程式碼執行計算並產生試算表。只用 chat「讀」大型表格有算術錯誤風險；程式碼執行跑的是真正程式碼，並產出可下載檔案。

**Q3.** 一位 Free 方案使用者想為新客戶開第六個 project。現實是什麼？
**A：** Free 帳號上限五個 projects — 封存或合併一個，或升級。（方案上限會變；請在 support.claude.com 查證。）

**Q4.** 一位助理跑 Research 卻得不到有用結果；網頁搜尋是關掉的。第一步修復方法？
**A：** 開啟網頁搜尋 — Research 是 agentic 的網頁調查，依賴它。先診斷能力開關，再怪模型。

**Q5.** 顧問希望 Claude 跨對話記住他們的報告格式，但兩個客戶之間絕不能帶過客戶機密細節。什麼產品行為有幫助？
**A：** Memory 以專案為範圍 — 每個 Project 有獨立記憶。每個客戶放在自己的 Project；一般偏好可以放在帳號層級記憶，條目可在 Settings 檢視／編輯／刪除。

**Q6.** 同事問一個一次性的敏感人資問題，不想留在歷史紀錄或記憶裡。你建議什麼？
**A：** 無痕對話（幽靈圖示）— 排除在歷史紀錄、記憶與搜尋之外；所有方案都有，存在於 Projects 之外。

**Q7.** 選兩項適合 Haiku 的任務。
**A：** 依類型分類進線工單；從發票萃取欄位。大量、規格清楚、低細微差異的工作，是輕模型的甜蜜點。

**Q8.** 兩輪紮實迭代之後，Sonnet 的競爭分析在真正多重限制的策略題上仍顯得淺。下一步？
**A：** 升級到 Opus（或提高 effort）— 深度推論上的實際失敗才是升級觸發條件，不是面子。

**Q9.** 法務需要從 Slack 與 Drive 回答「我們在 Q2 對資料保留做了什麼決定？」。用哪個功能？
**A：** Enterprise Search — 跨已連接來源的組織內部附引用查找。Research 用於公開局面。

**Q10.** 一條 300 則訊息的對話現在與自己的限制互相矛盾。最佳上下文動作？
**A：** 要求一份交接摘要（決策、限制、未決問題），再用它重開新對話。先摘要再重開，勝過硬撐一條已漂移的對話。

**Q11.** 高階主管想要一個業務團隊能用的互動式投資報酬率（ROI）計算機。用哪個功能？
**A：** Artifact（互動式應用程式）。注意觀看者消耗自己的用量上限，計算機的公式仍需領域 03 驗證。

**Q12.** 一位 Team 方案使用者把 Project 全組織分享，擔心同事會讀到他們的草稿對話。事實是什麼？
**A：** 分享以檢視／編輯權限散佈知識與指示；他們在 Project 裡自己的對話，不會當成逐字稿交給每一位成員。（請在 support.claude.com 查證現行分享行為。）

**Q13.** 選兩項「永遠用最能幹的模型」政策失敗的理由。
**A：** 它在輕模型就能交付的任務上浪費成本／延遲；它用面子取代由輕到重往上評估的方法。（簡單任務的品質提升，不足以正當化這項政策。）

**Q14.** 團隊每月重複一套 12 步驟的季度業務回顧（QBR）準備程序，一直在 chat 裡重新教一遍。用哪個功能？
**A：** Skill — 打包、可重複使用的程序。專案知識放參考材料；Skill 放 *怎麼做*。

**Q15.** 一個付費方案 Project 的知識已接近上下文上限。什麼能讓它繼續可用？
**A：** 搭配 RAG 的增強知識（付費方案）— 檢索把容量擴大最多約 10 倍；檔名清楚、問得精準，會更有幫助。

**Q16.** 使用者在 Pro 方案的全新對話裡說「Claude 把昨天的事全忘了」。診斷？
**A：** 檢查 Memory／對話搜尋是否開啟，以及昨天的對話是否為無痕、或在另一個 Project 的範圍裡。然後決定：把常態脈絡持久保存在 Project，而不是依賴回想。

**Q17.** 一位主管問，若「買 Opus」，Claude 能否起草董事會資料包文字且「幻覺風險為零」。正確框架？
**A：** 沒有任何層級能消除幻覺 — 模型選擇是成本／速度／品質的取捨，準確性由驗證（領域 03）管理。Opus＋跳過審核，比 Sonnet＋主張對照表更糟。

**Q18.** 選兩項正確的需求 → 介面對組。
**A：** 答案裡要有即時 Drive 資料 → Connector；從已分析資料產出可下載的 PowerPoint → 程式碼執行／檔案產生。（Research 不是給單一已上傳檔案用的；Memory 不是團隊知識庫。）

## 詞彙表

| 詞 | 意義 |
|---|---|
| **Project** | 帶有指示＋知識＋自己對話的工作區 |
| **RAG（在 Projects 中）** | 付費方案的檢索，在接近上下文上限時擴大知識容量（約 10 倍） |
| **Artifact** | 顯示在對話旁邊的獨立可編輯／互動式交付物 |
| **Skill** | 打包好的可重複任務程序 |
| **Connector（MCP）** | 接入外部系統的即時整合；管理員啟用、使用者驗證 |
| **Research** | 付費的 agentic 多來源調查，附引用來源 |
| **Enterprise Search** | 組織內部附引用搜尋（Team／Enterprise） |
| **程式碼執行／檔案產生** | Claude 執行程式碼並產生檔案的沙箱環境（所有方案） |
| **Memory** | 以個人為單位、以專案為範圍的被記住脈絡；在 Settings 檢視／編輯／刪除 |
| **無痕對話** | 幽靈圖示對話，排除在歷史紀錄、記憶與搜尋之外 |
| **effort** | 模型層級內部的深度控制 |
| **上下文視窗** | 一段對話有限的工作記憶 |
