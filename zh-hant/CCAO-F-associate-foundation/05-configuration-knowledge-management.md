## 深入筆記

### 1. 經得起團隊考驗的 Project 設定

清單：用途；負責人；敏感度標籤；指示；知識集；分享權限；模型預設指引；評測筆記。已查證的方案事實（support.claude.com，2026 年 8 月）：Projects 存在於 **所有方案；Free 上限為五個 Project**；**透過檢索增強生成（RAG）的增強知識僅付費方案提供，並將容量擴大至約 10 倍**，於知識接近上下文上限時啟動；**分享屬 Team/Enterprise**，分「可檢視」（唯讀）與「可編輯」（可修改知識／指示），可逐一、批次或全組織授予。

### 2. 指示工程

好的指示會指明：角色；預設受眾；輸出 schema；引用規則；升級規則（「若不在知識中，回答 **Not found**」）；衝突優先順序（法務 > 品牌）；以檔名指向檔案。壞的指示會把公司故事從頭講一遍、自相矛盾，或把關鍵規則埋起來。保持 **簡短、穩定、有優先順序**——指示會與任務 token 競爭；厚重的政策應放在知識檔案中。

用三個黃金任務與三個對抗性任務測試指示（要求知識以外的答案，看「Not found」是否觸發）。當失敗成群出現時再更新。**Styles／偏好設定 vs 專案指示：** 全域個人口味 vs 工作區規則——Style 無法承載 Project 的法務限制。**Skills vs 指示：** 程序 vs 常態規則；不要把整份 Skill 貼進指示。

### 3. 知識衛生 playbook

- **命名：** `Policy-Refunds-v4-2026-06.pdf` 勝過 `finalFINAL.pdf`。把版本日期放進檔名；用檔名指名要檔案。
- **策劃：** 新版本落地當天即移除被取代的文件——過期檔案是無聲的線上缺陷（對檔案為真、對世界為假）。不要保留重複或衝突的版本；檢索混淆是自找的。
- **結構：** 把不相關領域（法務／人資／行銷）拆到不同 Projects；保留一份清單備註，列出每份文件及其用途。
- **品質：** 優先使用可萃取文字的檔案；光學字元辨識（OCR）亂碼掃描檔會污染檢索。
- **RAG 行為：** 知識量大時，預期為搜尋式檢索——提問要收窄並指名檔案。

### 4. Connectors：上傳對比連接，以及最小權限原則

上傳＝你必須自行刷新的凍結快照；連接器＝帶驗證與權限複雜性的即時資料。要有意識地選擇：每週變動的活文件 → 連接器；穩定的正式政策 → 有版本紀律的策劃上傳。

治理基礎（深入內容屬領域 06）：最小權限原則——分析用途優先 **唯讀**；寫入權限範圍是治理決策，需搭配人工關卡。Team/Enterprise 模式：**管理員啟用，每位使用者各自驗證**。把 Project 預期使用的連接器寫成文件，這樣「Claude 看不到 Drive」才會被診斷為驗證問題，而非模型故障。**自訂連接器（遠端模型上下文協定，簡稱 MCP）各方案皆有；Free 限一個自訂連接器**（2026 年 8 月查證）。

### 5. Memory — 設定 Claude 記得什麼（本節為新增；考試指南點名此主題）

事實已對照 support.claude.com 查證（2026 年 8 月——此功能會演變；考試前請重新查證）：

- **是什麼：** Claude 從你的對話建立 **Memory 條目**——專業背景、角色、偏好、進行中的工作——組織成分類，並套用到後續對話。這取代了「對話是短暫的；對話串之間沒有任何東西留存」的舊心智模型。
- **可用性：** 記憶產生在 **Free、Pro、Max**（較新體驗）以及 **Enterprise**（舊版 24 小時綜合體驗）；**對話搜尋**（Claude 檢索你過去的對話）為 **Pro 以上**。Team 方案 **沒有組織層級的記憶控制**——成員各自管理。
- **Project 範圍：** 每個 Project 有 **自己獨立的記憶** 與摘要，讓客戶工作、機密對話串與一般對話彼此分開。這就是「防止脈絡滲漏」的設定答案。
- **控制項（本領域核心）：** Settings → Memory：**檢視**條目、**編輯**、**刪除個別條目**，或 **全部重置**；Memory 與搜尋 **各自獨立開關**；引用來源會顯示被記住的事實來自哪一段對話。
- **無痕對話：** 幽靈圖示，所有方案皆有，位於 Projects 之外；排除於歷史紀錄、記憶與搜尋之外。（Enterprise 會因安全理由將無痕對話保留最短期間，並納入資料匯出——治理細節。）
- **可攜性：** Memory 包含在資料匯出中；實驗性匯入／匯出可在助理之間搬移記憶。

**管理心法：** Memory 是 *個人脈絡層*，不是知識庫。像對待知識一樣策劃它：定期檢視條目；刪除錯誤或過期者（一條壞的 Memory 條目，是你帶進每一段對話的設定漂移）；敏感事項請關閉記憶或使用無痕對話；承重的團隊真相放在 **專案知識**——有負責人的策劃檔案，勝過按使用者推測出來的記憶。當 Claude「記錯了」，修復方法是編輯／刪除該條目，不是換更大的模型（通往領域 07 的橋）。

### 6. 維護、生命週期與所有權

每個共享 Project 都需要一位指名負責人，對更新課責；沒有負責人，設定漂移必然發生。節奏：每月檢視指示；政策變動時刷新知識（替換檔案＋公告＋在指示中更新版本註記）；共享 Project 在知識中保留變更紀錄；封存死去的 Projects——在 Free 上，五個 Project 的上限會逼你這麼做。帶隊友上手：分享 Project、解釋指示、展示評測清單、確認連接器驗證、監督第一個任務。

### 7. 看起來像模型缺陷的失敗模式

Claude「無視政策」→ 知識中仍躺著已被取代的 PDF。「混用品牌」→ 兩份風格指南沒有優先規則。「忘了我們的專案脈絡」→ 使用者依賴個人 Memory 而非專案知識，或 Memory 條目被刪除／範圍屬於另一個 Project。「看不到 Drive」→ 連接器未驗證。「記錯了關於我的事」→ 過期 Memory 條目；編輯或刪除它。先修設定，再升級模型。

### 8. 迷你案例（設定稽核）

**案例 1 — 神秘的品牌語氣。** 行銷的共享 Project 在正式文案與活潑文案之間搖擺。稽核發現 `Brand-Voice-2025.pdf` 與 `Voice-Refresh-2026.docx` 同時躺在知識裡，沒有優先規則，也沒有負責人。修復方法：刪掉 2025 年的檔案，在指示中加上「語氣依 `Voice-Refresh-2026.docx`」，指定一位負責人，並開始一份變更紀錄。一次稽核，每位使用者都修好了。

**案例 2 — 顧問的滲漏風險。** 一位獨立顧問從一般對話服務兩家互相競爭的客戶，擔心脈絡會洩漏。修復方法：每個客戶一個 Project（記憶以專案為範圍；知識分開），一般 Memory 只放個人偏好，定期檢視 Memory 條目，探索性、利益衝突敏感的問題用無痕對話。

**案例 3 — 腐爛的星期五報告 Project。** 3 月建好，4 月被稱讚，到 8 月就錯了：政策第 5 版已發布，但第 3 版還在知識裡；建造者離職了；沒有人擁有它。經典的漂移。修復方法：指定負責人、替換檔案、在指示中加版本註記，並把每月檢視排進行事曆。預防比那份揭露問題的壞報告便宜。

**案例 4 — 上手出了差錯。** 一位新分析師拿到 Project 存取權，但他第一批輸出完全沒有引用 Drive 的東西。稽核：連接器已由管理員啟用，但分析師從未驗證；而且他用的是個人帳號，不是工作區。修復方法：一個工作區席位、一次逐人驗證的導引，以及對照評測清單監督第一個任務。

### 9. 複選題模式庫

學會刪去這些反覆出現的錯誤選項：「把整份政策貼進指示」（膨脹——那是知識的工作）；「保留舊檔案以供參考」（被取代＝刪除或清楚封存）；「Memory 會讓團隊對齊」（按使用者，不是共享的）；「給每個人編輯權，這樣就沒有人被擋住」（權限失敗）；文件是活的卻「每週重新上傳而不連接」（或其鏡像：「什麼都連接」，包括穩定的政策）。正確組合是把一個 **存放位置** 選擇（指示 vs 知識 vs Skill vs 連接器 vs Memory）配上一個 **生命週期** 選擇（負責人、版本註記、節奏、封存）。

## 決策樹

| 情境 | 行動 |
|---|---|
| 反覆出現的團隊脈絡 | Project（指示＋知識＋負責人） |
| 厚重的參考資料 | 知識檔案，命名並標版本——不放指示 |
| 即時、頻繁變動的文件 | 連接器（唯讀，除非寫入受到治理） |
| 政策已更新 | 替換檔案＋公告＋版本註記 |
| 跨對話的個人偏好 | Memory——在 Settings 中檢視／編輯條目 |
| 機密的一次性對話 | 無痕對話（排除於記憶／歷史／搜尋之外） |
| 脈絡絕不能互相滲漏 | 分開的 Projects（記憶以專案為範圍） |
| Free 接近五個 Project 上限 | 封存或合併 |
| 記錯的事實 | 編輯／刪除該 Memory 條目 |
| 共享 Project 行為異常 | 先檢查負責人、重複檔案、過期，再怪模型 |

## 考試陷阱

1. 把所有東西塞進指示（小說長度，還自相矛盾）
2. 從不更新知識；把被取代的 PDF 留在原地
3. 把個人 Memory 當團隊的知識庫
4. 以為記憶跨越 Project 邊界（它是以專案為範圍的）
5. 給純分析工作的連接器預設寫入權限範圍
6. 忽略分享權限（對受限制的知識開全組織編輯）
7. 重複衝突的檔案造成檢索混淆
8. 共享 Project 沒有負責人（漂移必然發生）
9. 期待 Styles 承擔 Project 的法務合規工作
10. 忘記無痕對話是為敏感的一次性對話而存在的

## 練習問答（18）— 情境題幹附答案與理由

**Q1.** 一個團隊需要常態的語氣規則，加上一份 40 頁的政策 PDF，套用到每週的工作。設定是什麼？
**A：** 一個 Project：簡短的語氣規則放進指示；PDF 放進知識，以版本與日期命名；指示用檔名指向它。

**Q2.** 一位 Free 方案顧問在接第 6 個客戶時撞上專案上限。選項是什麼？
**A：** 封存或合併一個不活躍的 Project，或升級——Free 上限為五個（2026 年 8 月查證；請在 support.claude.com 重新查證目前上限）。

**Q3.** 選出兩項知識衛生做法。
**A：** 檔名放版本日期；立即移除被取代的文件。（重複檔案與 `finalFINAL` 命名是反模式。）

**Q4.** Claude 引用的是上一季的退款窗口。第 4 版政策昨天發布了。根本原因與修復方法？
**A：** 過期知識——用第 4 版替換第 3 版，公告變更，並在指示中更新版本註記。對檔案為真、對世界為假，是維護失敗。

**Q5.** Project 的 RAG 什麼時候重要，誰有？
**A：** 付費方案，當知識接近上下文上限時——檢索將容量擴大至約 10 倍；用清楚的命名與收窄的提問幫它一把。

**Q6.** 一位使用者預期新對話自動知道昨天的專案決策。正確的設定答案是什麼？
**A：** 把決策放進專案知識（團隊真相）——Memory 也許會回想起一些脈絡（按使用者、依方案而定、以專案為範圍），但它不是承重事實的可靠或共享儲存。

**Q7.** 純分析的 Drive 工作流程：哪種連接器範圍？
**A：** 唯讀／最小權限原則。寫入權限範圍需要治理核准與人工關卡。

**Q8.** Claude 一直把一位經理關聯到他幾個月前離開的專案。修復方法？
**A：** Settings → Memory：編輯或刪除該過期條目。Memory 是使用者策劃的設定，不是命運。

**Q9.** 共享 Project 上「可檢視」與「可編輯」差在哪？
**A：** 檢視＝以唯讀方式使用 Project；編輯＝可修改知識與指示。編輯權要窄授；分享是一種治理控制。

**Q10.** 豐富的多步驟程序該放哪裡：指示還是 Skill？
**A：** Skill——程序在相關時才載入；指示承載簡短的常態規則。在指示裡複製一份 Skill 會讓上下文膨脹。

**Q11.** 兩份衝突的風格指南住在同一個 Project 的知識裡。症狀與修復方法？
**A：** 檢索混淆造成的品牌輸出不一致——移除其中一份，或在指示中加一條明確的優先規則。

**Q12.** 一位高階主管要做敏感的董事會準備，要求在記憶或歷史中零痕跡。建議？
**A：** 無痕對話（所有方案皆有，位於 Projects 之外）——排除於歷史紀錄、記憶與搜尋之外。若是反覆出現的董事會工作，一個分享收緊的專用 Project，勝過反覆用無痕對話。

**Q13.** Enterprise Search 對一個團隊信誓旦旦說已連接的來源，什麼都沒回傳。檢查什麼？
**A：** 管理員是否真的啟用了連接器；提問的使用者是否已驗證；來源是否在範圍內。先查設定，再怪模型。

**Q14.** 誰維護共享 Project，什麼產物能證明？
**A：** 一位指名負責人；知識裡的一份變更紀錄備註，記錄檔案替換與指示版本。

**Q15.** 一位 Free 方案使用者想要三個自訂 MCP 連接器。現實是什麼？
**A：** 自訂連接器在 Free 上存在，但限一個；多個自訂連接器需要付費方案（2026 年 8 月查證）。

**Q16.** 個人 Styles vs 專案指示——什麼時候 Styles 是錯的答案？
**A：** 只要規則是工作區真相（法務限制、團隊 schema）：Styles 是個人口味，不管轄共享 Project。

**Q17.** 選出兩個「記憶以專案為範圍對設定很重要」的理由。
**A：** 客戶脈絡無法在 Projects 之間滲漏；敏感的專案討論留在一般對話記憶之外。（這也是為什麼「每個客戶待在自己的 Project」是常態設計規則。）

**Q18.** 在帶隊友上手一個已設定的 Project 時，哪兩個步驟能防止第一週的混亂？
**A：** 確認他們的連接器驗證，以及對照評測清單監督第一個任務。

## 快速複習檢查清單（考前）

- [ ] Project 設定：用途、負責人、敏感度、指示、知識、分享
- [ ] 指示：簡短、有優先順序、衝突規則、「Not found」升級規則、檔案指引
- [ ] 知識：有版本的命名、沒有重複、替換被取代的檔案、清單備註
- [ ] 上傳 vs 連接器；最小權限原則；管理員啟用＋使用者驗證

## 詞彙表

| 術語 | 含義 |
|---|---|
| **專案指示** | 範圍限定在工作區的常態行為規則 |
| **專案知識** | 策劃過的參考檔案；團隊的真相來源 |
| **RAG（Projects）** | 付費檢索，在接近上下文上限時擴大知識容量 |
| **連接器（Connector）** | 即時整合（例如 Drive、Gmail）；管理員啟用、使用者驗證 |
| **最小權限原則** | 完成工作所需的最小範圍；預設唯讀 |
| **Memory** | 按使用者、以專案為範圍的被記住脈絡；在 Settings 中策劃 |
| **Memory 條目** | 一則可編輯、可刪除的被記住事實，附對話引用 |
| **無痕對話** | 排除於歷史、記憶與搜尋之外的對話 |
| **知識衛生** | 命名、版本、去重與修剪的紀律 |
| **設定漂移** | 指示／知識／記憶慢慢偏離現實 |
