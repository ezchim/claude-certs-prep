## 深入筆記

### 1. 需求與使用案例分析優先

碰工具之前先引導挖掘：觸發事件、輸入、輸出、使用者、頻率、延遲需求、敏感度等級、下游系統、完成的定義、錯誤預算。若利害關係人答不出來，Claude 可以幫忙訪談與勾勒 — 但由人類確認。過早碰工具是經典失敗。

把使用案例分類：**generate、transform、retrieve、decide、act。** decide／act 需要更強關卡（決策通常留在人類手上）。generate／transform 仍需要與風險相稱的明辨。盤點目前工作流程的步驟，標出 Claude 在哪裡起草、檢索、轉換、運算，或者（很少見地）做決定。

### 2. 解決方案模式目錄

- **模式 A — 知識中樞（Knowledge Hub）：** 存放政策／範例／指示的 Project；團隊編輯權限；預設 Sonnet；評估檢查清單放在指示裡。
- **模式 B — 從局面到決策（Landscape to Decision）：** 附引用來源的 Research → 領域 03 主張對照表 → 決策備忘錄 Artifact。
- **模式 C — 收件台（Intake Desk）：** Connector 讀取信箱／表單 → Claude 起草工單欄位 → 人類確認 → 系統更新。寫入前的人工關卡就是重點。
- **模式 D — playbook 型 Skill（Playbook Skill）：** Skill 把程序編碼下來（例如事故通報更新）；Project 存放嚴重程度定義。
- **模式 E — 組織大腦（Org Brain）：** Enterprise Search 回答「我們當初決定了什麼」，並附帶指回 Slack／Drive 的引用。
- **模式 F — 資料到交付物（Data-to-Deliverable）：** 上傳資料 → 程式碼執行計算（總計、趨勢、圖表）→ 產生 Excel／PDF／投影片交付物 → 人類對照來源核對數字。當工作流程的核心是 *運算或檔案產出*、不是文字時用它。（程式碼執行與檔案產生所有方案都有 — 已於 2026 年 8 月對照 support.claude.com 查證。）

組合模式；很少有單一功能就是完整解決方案。考試答案裡，經過思考的組合勝過單一功能萬靈丹。

### 3. 增強 vs 重新設計

**增強：** 保留流程，把 Claude 安插到起草／檢索／運算步驟。變革管理成本低；受監管或高風險流程的預設（外加稽核軌跡）。
**重新設計：** 移除那些 AI＋ connectors 讓它們變得多餘的步驟。報酬更高，但需要變革管理、訓練與明確所有權。

決策邏輯：高度人工浪費＋低風險＋有意願的負責人 → 重新設計候選。受監管、對外或不可逆的流程 → 先增強並加人工關卡；用試點證據去贏得重新設計。永遠不要為面向客戶的發送設計「全自動駕駛」— 起草＋人類發送才是考試正確的形狀。

### 4. 研究、規劃與流程最佳化

規劃期間用 Research 做外部局面（依領域 03 驗證後才讓它影響決策）；用 Projects 持久保存計畫脈絡；用程式碼執行量化（「哪個步驟吃掉工時？」）。最佳化目標跟著衡量走，不是感覺：先裝上起草耗時、修改輪次、錯誤類型，再用最便宜的槓桿重新設計最差的步驟。

### 5. 利害關係人溝通（價值以及限制 — 藍圖講得很明白）

一頁摘要：問題、提議的工作流程圖、人工關卡、資料流、指標、風險、請求。展示時用真實混亂的輸入，不是打磨過的玩具；展示一次 *被抓到的* 幻覺，比一次完美運行更能建立信任。永遠包含：幻覺風險與審核標準作業程序（SOP）；資料邊界（什麼可以／不可以進入哪個方案／功能 — 領域 06）；Claude 不該擁有什麼（最終決策、受監管判斷）；成功指標與回滾。

異議處理：「它會取代我們」→ 增強指標與工時重新配置到更高價值工作。「它會產生幻覺」→ 展示評估 SOP 與審核後的錯誤率。「資料會離開我們的系統」→ 方案控管、connector 授權範圍、組織政策。沒有限制的吹捧在這個領域不及格；沒有試點計畫的末日論也一樣。

### 6. 衡量與迭代

追蹤：節省的時間、到交付為止的修改輪次、錯誤類型（事實性、完整性、語氣、政策）、採用度、用量上限消耗。用錯誤分類法更新指示／知識／Skills — 不要用來責怪使用者。試點一個團隊；指標過關後再擴大。解決方案是產品：幫它們編版本、記變更紀錄、指定負責人。

整合失敗模式：知識過時、負責人不清楚、死線壓力下關卡被繞過、採用被忽略（「我們蓋好了，沒人來」）。為真實組織設計，不是為投影片上的組織設計。

### 7. 迷你案例（套用完整迴圈）

**案例 1 — 每週高層摘要。** 對內溝通每個星期五花四小時，從 Slack、Drive 文件與兩個儀表板彙編摘要。設計：connectors 讀取來源；一個 Project 存放摘要範本、語氣範例與收錄標準；Claude 在星期五早上起草；對內溝通主管驗證主張（領域 03）後送出。指標：準備時間、送出後更正。連續四週乾淨之後成為重新設計候選：拿掉手動儀表板截圖步驟，改成匯出資料給程式碼執行畫圖。

**案例 2 — RFP 工廠。** 業務每季從一個沒人更新的 wiki 回答 20 份建議邀請書（RFP）。解決方案：放在專案知識裡、經過整理的答案庫（由業務營運擁有、編版本）；一個 Skill 把答案組裝程序編碼下來；RFP 問題的萃取 schema；提交前的人工審核關卡，因為答案是合約承諾。被拒絕的反模式：「自動填寫並提交」— 對外承諾保留人工關卡。

**案例 3 — 客服分流。** 目標：縮短首次回應時間。Connector 讀取佇列；Claude 分類嚴重程度，並引用政策 Project 起草回應；人員審核後送出；Sev-1 直接路由給人類，附一份 Claude 起草的脈絡簡報。高影響工單的嚴重程度 *判定* 留在人類手上；起草與脈絡彙整，才是 Claude 安全加速的地方。

**案例 4 — 董事會資料包分析。** 財務長（CFO）想從每月匯出得到趨勢評論。資料到交付物：程式碼執行計算趨勢並做出圖表＋ PDF 附錄；主計長對照來源核驗算出來的數字；Opus／Sonnet *只根據算出來的數字* 起草評論；人類擁有敘事。組合：程式碼執行（數學）＋ Project（語氣、定義）＋人工關卡（受監管受眾）。

每個案例演練同一個迴圈：需求 → 使用案例類別 → 模式組合 → 關卡 → 指標 → 迭代。

### 8. 複選題模式庫

常見應排除的錯誤配對：「為省時間自動化發送」＋「永遠全部手動」（關卡失敗＋反委派）；「向利害關係人承諾零錯誤」＋「開頭就講所有可能出錯的事」（吹捧＋末日 — 兩者都漏掉 SOP 加指標這個中間地帶）；「立即全組織推行」＋「無限期試點、沒有擴大標準」（沒有證據＋沒有決策規則）；「設計自訂 API 微服務」（走錯軌道）。正確組合把一個 **組合** 選擇（Project＋ connector＋關卡；Research＋驗證；程式碼執行＋審核）配上一個 **溝通或衡量** 選擇（揭露限制、定義指標、指定負責人）。

## 決策樹

| 情境 | 動作 |
|---|---|
| 流程裡有不可逆的對外動作 | 執行前設人工關卡 — 不容商量 |
| 帶共享脈絡的反覆工作 | Project（程序豐富則加 Skill） |
| 多來源公開探索 | Research（經驗證）— 內部：Enterprise Search |
| 工作流程核心是運算／檔案輸出 | 程式碼執行模式 F |
| 利害關係人需要互動工具 | Artifact |
| 需求不清楚 | 先做探索訪談＋流程盤點 |
| 受監管／高風險流程 | 用關卡＋稽核軌跡增強；有證據才重新設計 |
| 成功未定義 | 動手之前先定義指標 |
| 試點成功 | 逐步擴大；持續衡量；指定負責人 |

## 考試陷阱

1. 面向客戶發送採全自動駕駛（沒有人工關卡）
2. 利害關係人溝通漏掉限制那一半
3. 把 Claude 賣成零錯誤；或因恐懼而拒絕試點
4. 重新設計時忽略變革管理與訓練
5. 在產品路線考試上給 API／微服務架構答案
6. 沒有成功指標或回滾計畫
7. 需要組合時卻端出單一功能萬靈丹
8. 沒有需求或流程盤點就工具優先設計
9. 最佳化沒人衡量過的步驟
10. 忘記採用：沒有負責人的解決方案會腐爛

## 練習問答（18）— 情境題幹附答案與理由

**Q1.** 一位主管說「把 Claude 放進我們的開立發票流程」，沒有進一步細節。第一步？
**A：** 需求與使用案例分析 — 在選功能之前先盤點流程、輸入／輸出、敏感度與完成的定義。需求之前就碰工具是陷阱。

**Q2.** 設計一個搭配 Claude 的客戶支援郵件工作流程。考試正確的形狀？
**A：** Claude 從 Project 政策知識起草 → 人類審核後送出。面向客戶的發送保留人工關卡。

**Q3.** 選兩項每週競爭簡報解決方案的元件。
**A：** 一個存放簡報範本／指示的 Project；Research（附引用驗證）做局面掃描。

**Q4.** 你的推行投影片只列好處。要通過這個領域的門檻，必須加上什麼？
**A：** 限制：幻覺風險＋審核 SOP、資料邊界、什麼留在人類手上、指標與回滾。溝通限制是藍圖明白寫出的。

**Q5.** 財務想從匯出的逗號分隔值（CSV）做每月差異分析，以 Excel 交付。哪個模式？
**A：** 資料到交付物：程式碼執行計算差異並產生活頁簿；流通前由人類對照來源核對數字。

**Q6.** 什麼時候重新設計勝過增強？
**A：** 高度人工浪費、低風險、有意願的負責人，以及試點證據 — 移除 AI 讓它們變得多餘的步驟。受監管流程從帶稽核軌跡的增強開始。

**Q7.** 哪一對指標最能證明工作流程價值？
**A：** 交付草稿耗時加上審核後錯誤率。沒有品質的速度（或反過來）只是半個論據。

**Q8.** 營運想要一個同事能點選走完的共享互動 SOP 檢查器。用哪個功能？
**A：** Artifact — 獨立互動式交付物；觀看者消耗自己的額度；內容仍須先驗證。

**Q9.** 試點輸出反覆出現語氣失誤，以及兩處可追溯到過期政策 PDF 的事實錯誤。迭代？
**A：** 更新知識檔（過時）並把語氣範例加進指示／Skill — 修造成每種失誤類型的系統。

**Q10.** 高階主管問「這會取代團隊嗎？」最佳回應框架？
**A：** 重新框成增強：展示 Claude 吸收哪些步驟、保留哪些人類判斷、指標，以及釋出的工時去哪裡。

**Q11.** 選兩項解決方案提案中必須向利害關係人揭露的風險。
**A：** 幻覺／錯誤風險及其緩解；資料敏感度邊界與處理規則。

**Q12.** 團隊想跳過試點、全組織推行「才能走得快」。為什麼這是錯誤選項？
**A：** 沒有錯誤分類法、沒有採用證據、沒有回滾；試點在指示／知識仍生疏時把失敗局部化。

**Q13.** 進線郵件應該變成客戶關係管理（CRM）工單。關卡在哪裡？
**A：** Claude 從 connector 讀取的郵件起草工單欄位；寫入 CRM 之前由人類確認。讀可以寬；寫要設關卡。

**Q14.** 「上季我們與供應商 X 談成什麼？」一直在 chat 裡走進死胡同。解決方案？
**A：** 在已連接的 Slack／Drive 上用 Enterprise Search — 組織內部附引用查找，不是 Research，也不是更大模型。

**Q15.** 一套反覆出現的 RFP 回應程序（12 步驟、嚴格順序）每週都被重新解釋。解決方案元件？
**A：** 一個把程序編碼下來的 Skill，制式／來源材料放在專案知識。

**Q16.** 你如何做一場能建立耐久信任的展示？
**A：** 真實混亂的輸入，展示評測步驟，並展示一次被抓到的錯誤及其修復方法 — 證明的是安全網，不只是魔術。

**Q17.** 推行後，用量很高但修改輪次加倍。診斷路徑？
**A：** 切分錯誤分類法：哪些失誤類型增加、哪些工作流程步驟產出它們；針對那些步驟收緊指示／知識。衡量 → 鎖定目標 → 最便宜的槓桿。

**Q18.** 選兩項提議解決方案相對於其風險程度過度自動化的跡象。
**A：** 不可逆的對外動作在沒有人類確認下執行；受監管判斷（人資／法務／財務）被直接委派給 Claude 的輸出。
